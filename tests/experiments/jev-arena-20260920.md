not proof of progress or tactical optimality. Having inspected the independent
set, future tuning requires new unseen cases rather than repeatedly calling this
same set “held out.”

## Allocator cache and latency

Same six-case input sequence (three state shapes repeated), two local services:

| Run | FP32 mean / range ms | 4-bit mean / range ms | Max reported cache, FP32 / 4-bit GiB |
| --- | ---: | ---: | ---: |
| Previous MLX default, concurrent | 4,513 / 905–8,574 | 4,720 / 1,088–9,111 | 21.221 / 23.299 |
| Previous MLX default, serial | 685 / 559–995 | 707 / 589–849 | 21.221 / 23.299 |
| Restarted, 512 MiB cache, concurrent | 1,853 / 1,650–2,132 | 1,815 / 1,710–2,013 | 0.499 / 0.500 |
| Restarted, 2,048 MiB cache, concurrent | 1,140 / 885–1,603 | 1,098 / 851–1,583 | 1.992 / 2.000 |

Evidence: `latency-default-concurrent`, `latency-default-serial`,
`latency-cache512-ready`, `latency-cache2048-ready`.
The failed startup transport run is `latency-cache512-concurrent`.

The prior-default runtimes had already processed many different input shapes,
while capped runs started fresh; serial ran after concurrent. These are **not
randomized, isolated or equal-coldness trials**. Cache growth, warm state, shared
GPU contention and unrelated machine activity are confounders. A system snapshot
showed 64 GiB physical memory and about 43 GiB swap in use, but accumulated swap
usage alone does not prove these requests caused paging or the latency spikes.

What is established in this sample:

- Previous free allocator caches retained a combined **44.520 GiB** after the
  varied-shape experiments; this is not live model-weight or KV memory.
- An explicit 2 GiB per-process allocator-cache setting held reported cache to
  <=2 GiB in this sequence. Total active/model/system memory is **not** capped.
- Across the 12 matched calls, capped versus prior-default probabilities had
  maximum absolute difference **0**, with **0 choice flips out of 24 choices**.
  This checks these inputs only, not a new full-weight numerical parity suite.
- 512 MiB was slower than 2 GiB in the observed paired runs, so 2 GiB was selected
  as the service default. It remains configurable (0..8192 MiB).

The setting uses `mx.set_cache_limit`, without extra evaluation/synchronization or
per-request `clear_cache`. Reclamation follows MLX allocation semantics. Native
metadata now includes the configured limit and pre-call active/cache memory.
Do not claim that all slow calls are fixed or that 4-bit is generally faster.

## Scheduling and real browser verification

The scheduler previously requested on the pulse **after** an action-completion
frame. It now requests immediately after observing that completed attempt in the
same pulse, eliminating the extra 200 ms gap per replan. Sync barriers and the
single-attempt action contract are unchanged; no speculative action is executed.

The final user-visible browser match used the original task protocol, same
`tank-2026` seed, step realtime, FP32 Blue / 4-bit Red, and six calls per side:

- ID: `607fdf29-10d8-4f7e-bbbe-250bb8ecd621`.
- Completed in **10,452 ms** at decision-budget exhaustion; no errors.
- Mean call times: **1,154.5 / 1,111 ms** (FP32 / 4-bit).
- Cadence bucket: about **205 ms per side**, versus about **1,206 ms** in the
  supplied baseline. The remaining initial pulse is expected.
- Each side still moved six times and attempted six invalid shots: **the model
  behavior problem is not solved**. Runtime optimization is not quality gain.
- Backend `archive_status: saved`; the read-only capture CLI retrieved the match
  without knowing its UUID and without any additional inference.

The final four protected-probe verification calls were serial, 463–491 ms, with
unchanged original-profile choices. They validate the new transport, not a new
speed claim. All previous browser tabs were retained.
