数据策略：与既有 CRM 共存的三种方式

客户要求后台 CRM 与前端 App 尽可能接近实时，同时不能让跨网络调用的不确定时延直接决定页面响应。下列集成图只显示数据调用、持久化、同步和校验链路，不把同步技术提前锁定。推荐方案 C 只有三条主路径：普通读取走 Dataverse 投影，关键数据走 CRM 实时校验，确认后的变更由同步适配器写回。适配器由既有 CRM 的事件、Webhook、CDC、增量查询和写入接口能力决定。

方案 A

全量复制 / 迁移过渡

Dataverse 保存完整业务副本，App 主要在本地读写；同步服务把变化与既有 CRM 对齐。适合已有明确迁移终点的项目，不适合作为长期无边界双写。迁移期必须逐实体或字段限定单一写入方。

方案 B

实时接口调用（REST API / MCP）

Dataverse 不参与 CRM 业务数据链路。App 和 Agent 的每次业务读写都经 Custom Connector、API Management 与 CRM API 同步完成；未提交草稿只保留在 App 本地或会话状态，遥测进入 Application Insights。这里的“直连”指不经过业务副本，不是绕过 APIM 治理直接访问数据库。数据最接近 CRM 当前值，但页面响应与可用性直接继承网络和 CRM 波动。

方案 C（推荐）

近实时投影 + 按需实时校验

“近实时”不是固定秒数承诺。试点期应根据 CRM 变更能力和地区网络实测，确定投影延迟 SLO、新鲜度阈值、实时校验超时预算与允许进入 Pending 的动作范围。
