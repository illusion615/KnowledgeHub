语音架构设计 · 连接器方案

让移动端语音不再看设备的能力

移动优先、语音优先是本项目改善销售体验的核心价值。当前的听写与朗读都建在浏览器自带的 Web Speech API 上，而这套能力在 Android——尤其是 Power Apps 的 WebView 与无谷歌服务的设备上——不可用。本文给出已落地的方案：以 Azure AI Speech 为引擎、语音在服务端完成、经自定义连接器由应用调用（Code App 沙箱下唯一可行的通道），把语音从依赖设备能力变成跨设备一致、安全、可降级的能力——朗读近实时，听写为点按录音转写。

看方案总览 从需求讲起
一句话方案

应用经连接器调服务端 Function，Azure 语音在服务端完成，密钥不进前端。

沙箱禁止应用直接对外发请求，所以语音经 Power Apps SDK 的自定义连接器由宿主代发到服务端 Function，Function 用密钥调 Azure Speech 返回结果。播放器编排逻辑不动，只把最底层「产生 / 识别音频」换成连接器调用。默认 Azure 保证跨设备一致，可用本地能力的设备按设置降级省流量。

01 / Business Need and Architectural Requirements

移动优先语音优先对语音方案提出四条属性要求

销售在拜访之间用口语与系统交互：口述一段活动纪要、听系统朗读客户简报、点按说话快速提问。要让这套语音在一线的真实设备上都成立，方案必须同时满足四条属性。这四条属性是本文其余章节的验收标准，每一章都在兑现其中一条。

01

跨设备一致

同一套语音体验必须在 iOS、Android、桌面浏览器与 Power Apps 移动播放器里表现一致。当前 Web Speech 的听写接口在浏览器兼容数据中直到 Chromium 139 才进入 Android WebView，而一线在用的华为 WebView 12.1.2.326 内核远早于此，接口根本不存在；朗读又依赖设备自带的语音引擎，无谷歌服务的设备常常没有可用音色。能力随设备而变，就是招牌功能在部分设备上直接消失。

02

实时响应

响应时效是语音体验的关键：朗读要按下即出声，听写要尽快出字。朗读可做到近实时——按下到首字一到两秒、段与段之间无明显停顿。听写受平台约束（应用不能开实时音频流，见第 3 章），退为「点按录音、再点转写」，停止后约一到两秒出字。目标是把这两处延迟压到最低，而非追求边说边出字。

03

密钥零暴露

语音服务的订阅密钥绝不能进入前端包或浏览器可见的任何位置。代码库已有一次教训：一段直接在浏览器里换 Azure AD 令牌的实现被证明会被 CORS 拦截，注释里写明「浏览器无法直连、需后端代理」。因此所有对外调用都走服务端——密钥只在 Function 的应用设置里，前端从不持有密钥或令牌，语音经连接器由宿主代发（见第 3 章）。

04

成本可控可降级

云语音按量计费，不能让每一次朗读、每一次听写都无条件产生费用。方案要允许具备本地语音能力的设备按用户选择走免费的本地引擎，也要在离线时明确禁用而非静默失败。默认云端保证可用，本地作为省流量的选项。

现状证据：当前听写调用 webkitSpeechRecognition 并将 continuous 固定为 true，而浏览器兼容数据显示 Android 的 Chrome 与 WebView 均不支持该连续模式；朗读经 speechSynthesis，在无本地音色时 getVoices() 返回空数组、静默无声。四条属性正是从这些真实缺口反推出来的验收线。

02 / Solution Overview and Engine Policy

应用经连接器调服务端，Azure 语音在服务端完成

Code App 跑在 connect-src 'none' 的 iframe 沙箱里，应用代码不能直接对外发任何网络请求。因此语音不走前端直连 Azure，而是：应用经 Power Apps SDK 调一个自定义连接器，由 Power Apps 宿主代为请求服务端的语音代理 Function，Function 用密钥调 Azure Speech 并把结果返回。密钥只在服务端，前端从不持有。本章先给整体架构，后续各章展开每个子系统。

改动面收敛的前提：朗读早已收口到单一的 useSpeechPlayer；听写只存在于 copilot 面板一处。因此换引擎只触及这两个接缝，上层 UI、手势、分段与队列逻辑保持不变。

03 / The Sandbox Constraint and the Connector

沙箱禁止直连，所以语音经连接器走服务端

这一节是全篇的枢纽：一个平台约束决定了整套架构。Code App 的 iframe 被赋予 connect-src 'none' 的内容安全策略，应用代码发起的任何 fetch / WebSocket 都被浏览器拒绝。因此不存在「前端直连 Azure」这条路——语音必须经 Power Apps SDK 的连接器通道，由宿主代为出网。下面按需求、机制、取舍、代价四层展开。

需求

应用要到达 Azure，但不能直接出网

实测证据：在已部署的应用帧内执行 fetch 触发控制台报错「Refused to connect … violates the following Content Security Policy directive: connect-src 'none'」；同一请求从顶层 apps.powerapps.com 页面则返回 200。结论是应用帧被网络隔离，密钥又必须留在服务端——两条约束共同排除了客户端直连与客户端持密钥。

机制

自定义连接器 + Function，经 executeAsync 调用

一个 Node 22 的 Azure Function（语音代理）把订阅密钥存在应用设置里，对外暴露 /tts 等操作。围绕它建一个自定义连接器，用 add-data-source 接进 Code App，生成 SalesCopilotSpeechService。应用调 executeAsync 的 connectorOperation，由 Power Apps 宿主在沙箱外向连接器发请求——绕过 connect-src。这条通道与应用现有调 Dataverse、调大模型是同一条。

取舍

连接器而非 Flow 或 Dataverse 插件

备选一是 Power Automate Flow，但仓库已记录 shared_logicflows 连接引用会导致应用启动 500，所以大模型才改走 Dataverse 自定义 API；备选二是 Dataverse 自定义 API 加 C# 插件，通道最稳但要写、编译、装插件。选自定义连接器的判据：它复用应用已在用的连接器机制（Copilot Studio 连接器已证明能正常启动、不触发 500），无需插件开发，且直接包住已有 Function。已实测应用带该连接器数据源仍正常启动。

代价与边界

连接器是请求/响应，不能实时流式

连接器只支持请求/响应，没有应用可消费的实时双向流。这直接决定了听写只能做整段录音、停止后转写的批处理，而非豆包那种边说边出字（详见第 5 章）。朗读是请求/响应天然契合，不受影响。另有两处工程代价：NoAuth 连接实例需在 maker 门户手工创建一次（无法脚本化）；端点当前匿名 + CORS 全开，仅供 dev，上线前须收紧。

04 / The Read-Aloud Engine Seam

在合成这一步换引擎，编排全不动

兑现属性①跨设备一致的朗读一半。现有 useSpeechPlayer 已经处理好分段、分轨、暂停恢复、移动端手势解锁与朗读进度；要做的是把它内部「念一段」的动作抽象成一个引擎接口，让本地与 Azure 两种实现可替换。

引擎只承担「产生并播放这一段音频」的机械动作；runId 守卫、分段推进、分轨切换、状态机全部留在 hook 内不变。接口方法如下：

方法 职责 本地实现 Azure 实现
speakSegment 念一段文本，完成后回调 SpeechSynthesisUtterance 连接器合成 → 播放元素
pause / resume 暂停与恢复当前朗读 speechSynthesis 暂停/恢复 播放元素原生暂停/恢复
cancel 立即停止并清队列 speechSynthesis.cancel 停止播放并释放
primeGesture 在用户手势内解锁音频自动播放 静音占位 utterance 静音播放元素触发一次
机制

经连接器请求服务端合成，播放元素输出

AzureTtsEngine 调 SalesCopilotSpeechService.Synthesize（经连接器 → 宿主 → Function），Function 用选定的 Neural 音色合成并返回 base64 MP3；引擎将其解码进一个复用的播放元素播放，完全绕开设备自带的语音引擎。音色映射复用 LOCALE_META 的五个区域：中文 zh-CN-XiaoxiaoNeural、英文 en-US-AvaNeural、德文 de-DE-KatjaNeural、法文 fr-FR-DeniseNeural、西文 es-ES-ElviraNeural，可在设置中更换。

取舍

先按段合成加预取，暂缓段内逐块流式

更彻底的做法是段内逐块流式播放，首字延迟最低，但实现更复杂。判据：应用早已把长文本按句子切成短段，单段合成本就很快，配合「本段在念、下段已在合成」的预取，首字延迟已经足够低。因此第一版取按段合成加预取，段内逐块流式列为后续优化。附带收益：经播放元素的暂停恢复是原生可靠的，避免了 Web Speech 在部分移动端暂停后卡住的老问题。

代价与边界

迁移两处裸调用，统一到 hook

要让换引擎覆盖全部朗读，必须先把绕过 hook 的两处裸 speechSynthesis 调用迁进来：简报页与首页各有一处独立实现。一个具体边界：若某段 Azure 合成失败（网络抖动），引擎应回调错误让 hook 按既有 onError 逻辑停止本轮，而非静默跳过——保持朗读进度对用户可见。

05 / Tap to Record and Transcribe

点按录音，再点转写，填入输入框

听写落到「点按录音、再点转写」这一批处理形态，因为第 3 章的约束在此收口：连接器是请求/响应，应用无法向 Azure 开一条实时音频流，所以做不到边说边出字。麦克风采集在本地进行（getUserMedia 可用），前端把整段录音编码成 16kHz 单声道 WAV、经连接器送服务端转写，再把文字填入输入框。交互从「按住说话」改为「点按切换」——因为 Android 的 Power Apps WebView 在长按松手时不派发任何抬起事件，只有一次独立点击才可靠。

机制

Web Audio 录 WAV，经连接器送服务端转写

点按用 getUserMedia 开录，Web Audio（ScriptProcessorNode）把采样降到 16kHz 单声道并编码成 WAV，再点按停止后转 base64，经 SalesCopilotSpeechService（连接器）调 Function 的 /stt，服务端用密钥调 Azure STT 返回文本。copilot 面板只把「送识别」这一步从 Web Speech 换成连接器调用，其余编排不动。

取舍

批处理是沙箱下的天花板，非选择

实时流式听写（边说边出字）需要应用直接持有一条到 Azure 的实时通道，而 connect-src 'none' 与请求/响应式的连接器都禁止这点，所以批处理不是取舍而是天花板。可做的半实时改进：录音时每约 1.5 秒切一段增量送转写、拼接呈现，逼近边说边出——但切词边界会掉准确率、且每段都付一次连接器往返，故列为后续可选，基线仍是整段录完再转。

代价与边界

格式已定，中文转写走 base64，停止后 1 到 2 秒出字

不走浏览器 MediaRecorder（其 WebM/Opus 不被 Azure 短音频 REST 接受），而用 Web Audio 直接编码 16kHz 单声道 PCM WAV——正是 Azure 短音频 REST 接受的格式，无需服务端转码。连接器响应层会破坏多字节 UTF-8，故转写文本在 Function 侧 base64 编码、前端解码，规避中文与带重音字符的乱码。延迟来自录音时长 + 上传 + 转写，停止后约 1 到 2 秒出字。麦克风权限被拒时回落到明确的「麦克风未授权」提示并给开启指引。

06 / The Real-Time Optimization Pipeline

用预热与预取把首字延迟压到最低

属性②实时被提为第一原则，本章把它落成可核对的具体动作与目标值。响应时效由两处决定：按下到出字（识别）、按下到出声（朗读）。两处都靠「把能提前做的事提前做」来压延迟。

Function 预热 — 打开面板发一次轻量请求

消费计划 Function 会缩容到零、首次调用有冷启动。打开 copilot 面板时发一次轻量连接器请求把它唤醒，避免首次朗读被冷启动拖慢。

短段与短录音 — 压低单次往返负载

朗读按句子切短段，听写录音尽量短，使每次连接器往返携带的音频与文本都小，转写与合成都快、首响更早。

手势解锁 — 按下同步解锁音频

在按下的同步阶段触发一次静音播放解锁自动播放策略，保证随后朗读能立即出声，沿用现有的手势解锁经验。

分段预取 — 本段在念下段在合成

朗读时当前段落播放的同时预先合成下一段，使段与段之间无明显停顿，朗读首字发声目标控制在一秒内。

目标值汇总（验收口径）：朗读首字发声（含一次连接器往返与服务端合成）目标一到两秒内、段与段之间无明显停顿；听写停止后约一到两秒出字。这些数字是真机自测时的核对项。

07 / Progressive Degradation and Offline

每一级失效都有下一级，最差也说得清

兑现属性④可降级。语音能力沿一条明确的降级链退让：云端优先，本地兜底，采麦被封则录音上传，离线则明确禁用。关键是任何一级都不静默失败——现在的「按钮凭空消失」正是要被替换的反例。

听写降级链

Azure 转写（点按录音）→ 本地 → 明确禁用

在线且采麦放行：点按录音、再点经连接器送 Azure 转写；设置为本地优先且设备本地识别可用则走本地；离线则禁用麦克风按钮并给出「离线不可用」而非隐藏它。

朗读降级链

Azure Neural → 本地音色 → 明确禁用

在线优先 Azure Neural 音色；设置为本地优先且设备有对应语言的本地音色走本地；两者皆不可得（离线且无本地音色）则禁用朗读入口并说明原因，不留一个点了没反应的按钮。

离线一致性：应用已有统一的离线判定与门禁，Copilot 在离线时本就禁用。语音挂在同一判定上——离线即禁用语音输入与朗读，联网恢复后自动可用，无需单独的离线逻辑。

08 / Delivery Plan

先探明麦克风闸门，再复活朗读与听写

按依赖与风险排序分六个阶段，每个阶段独立可测、独立可发，完成判据都以真机自测为准（含华为设备）。第一阶段是权限探针，用最小成本回答最大未知数。

P0 · 权限探针（已完成）

设置里加隐藏探针，报告采麦是否放行、识别接口是否存在、本地音色数量。华为实测：采麦成功、本地朗读引擎缺失。结论：麦克风闸门可用，缺的是服务端语音。

P1 · 语音代理 + 连接器（已完成，读已通）

建 Speech 资源与语音代理 Function（/tts），建自定义连接器 + 连接，用 add-data-source 接进应用生成 SalesCopilotSpeechService。华为实测：经连接器合成的中文语音成功播放——绕过沙箱的通道打通。

P2 · 朗读全面接入（已完成）

已把连接器合成接到 useSpeechPlayer 引擎层，覆盖 Copilot 回复、洞察简报、Brief 页等所有朗读入口；两处裸 speechSynthesis 已迁移；分段预取压首字延迟；并加了完成看门狗，规避 Android WebView 丢失段落结束事件导致朗读卡在首段。华为实测各处朗读复活，暂停恢复停止全过。

P3 · 听写（点按录音转写，已完成）

已给 Function 加 /stt；前端用 Web Audio 编码 16kHz 单声道 WAV，点按开始、再点停止录音，经连接器送转写、base64 解码后填入输入框；中文转写走 base64 规避连接器对多字节 UTF-8 的截断；麦克风权限被拒有明确提示。华为实测中文听写可用，停止后一到两秒出字。

P4 · 降级与离线一致

落地降级链（Azure 连接器 → 本地引擎 → 明确禁用），把现在的静默禁用箭头换成可解释状态，语音挂到应用既有离线门禁。判据：最差设备也有可用路径或清晰说明。

P5 · 收尾发布

服务端安全收紧（CORS 收窄、加鉴权、限流），补五语言文案与埋点（所用引擎、失败率、延迟），加用量护栏，写变更日志，同步本文档，构建推送并真机自测。判据：全绿、真机通过、文档同步。

构建纪律：本方案不在应用里引入客户端语音 SDK——语音在服务端 Function 完成，前端只多一个生成的连接器服务，增量构建即可、不触发冷编译。Function 侧改代码用 run-from-package 重新部署（见第 10 章）。

09 / Cost, Risk and Privacy

按量计费的语音，量级在个位数美元每人每月

云语音按使用量计费，规模可估、量级可控，本章给出估算口径与主要风险的缓解。所有金额均为按公开单价与假定用量推算的量级参考，非承诺值。

用途 单价量级 假定用量 估算
语音识别（批处理） 约 1 美元 / 音频小时 每人每天约 5 分钟听写 约 2 美元 / 人 / 月
Neural 朗读 约 15 美元 / 百万字符 每人每天约 1.5 万字符朗读 约 5 美元 / 人 / 月
Function 计算（消费计划） 前 100 万次执行 / 月免费，超出约 0.2 美元 / 百万次 每次语音调用一次执行，全队远低于免费额度 约 0 美元 / 团队 / 月（免费额度内）
Storage（Standard_LRS） 约 0.02 美元 / GB / 月，另加少量事务费 Function 依赖包与运行元数据，不足 1 GB 低于 1 美元 / 团队 / 月

量级结论：每人每月成本由语音主导（约个位数美元）；Function 与 Storage 属全队共享的固定基础设施，在消费计划与免费额度下几乎可忽略。若为消除冷启动改用常驻计划（见下方风险表），则新增一笔与人数无关的固定月度计算费，需单列预算。省钱开关（本地优先档）与用量埋点护栏进一步压低默认云端支出。

风险 影响 缓解
个别设备封采麦 该设备听写不可用 P0 已验证华为采麦可用；封则系统录音文件上传兜底
Function 冷启动 首次语音偏慢 打开面板时预热；必要时改常驻计划
Flow 启动 500 包袱 应用调用路径不稳 改用自定义连接器（复用现有连接器机制）
默认每次语音都计费 费用随用量上升 本地优先档加用量护栏

隐私：Azure 路径把音频送往本租户区域内的语音服务，可控且便于合规声明。相比之下，当前 Web Speech 的听写本就把音频发往浏览器厂商的云端服务——改用 Azure 反而缩小了数据出境面。

10 / Resource Requirements and Deployment

从零部署：五种资源、一个脚本、两处手工

本节给后来者一份可照做的部署清单：需要哪些资源、按什么顺序建、哪两处必须手工、以及两个不避开就会被卡住的坑。下方「端到端命令序列」是可整段复制、逐条执行的完整命令（把参考名称换成自己的即可）；仓库另带一个 provision.sh 把可脚本化的步骤 1–6 一键做完，剩下两处（建连接、接进应用）因平台限制需手工。密钥全程只在服务端。

资源 用途 档位（dev）
Azure AI Speech（kind SpeechServices） 语音转文字与 Neural 文字转语音 F0 免费（生产 S0）
Function App（Linux 消费计划） 服务端语音代理，持有密钥 消费计划 · Node 22
Storage account（Standard_LRS） Function App 运行依赖 Standard_LRS
自定义连接器 让 Code App 经 SDK 调 Function（绕过沙箱） pac connector create
连接（NoAuth） 应用绑定的连接器实例 maker 门户手建
1 · 建 Speech 资源（F0 免费）

先确认订阅已注册 Microsoft.CognitiveServices 提供程序，再用 az cognitiveservices account create 建一个 kind 为 SpeechServices、sku 为 F0 的资源。

2 · 建 storage 与 Function App（Node 22）

先建 Standard_LRS 存储账户，再用 az functionapp create 建 Linux 消费计划、运行时选 Node 22、Functions v4。

3 · 密钥写入应用设置（只在服务端）

从 Speech 资源取 key，用 az functionapp config appsettings set 写入 SPEECH_KEY 与 SPEECH_REGION；密钥永不进前端。

4 · run-from-package 部署

本地 npm install 打包，上传到 blob 并生成 SAS，把 WEBSITE_RUN_FROM_PACKAGE 指向该 URL 后重启。完整命令见 README。

5 · 开 CORS 并验证 Function

用 az functionapp cors add 放开来源，再 curl POST /api/tts，应返回 200 与一段 base64 MP3。

6 · 建自定义连接器

用 pac connector create 从 azure/speech-connector 的 swagger 与 apiProperties（NoAuth）建连接器，让 Code App 能经 SDK 调 Function。

7 · 建连接（门户手工）

NoAuth 连接无法脚本化：在 maker 门户 Connections → 新建 → 选该连接器 → Create（秒建）。再 pac connection list 取连接 id 与 apiId。

8 · 接进 Code App

用 npm 版 power-apps CLI 的 add-data-source（带 --api-id 与 --connection-id）接入，生成 SalesCopilotSpeechService；再 pnpm build 与 pac code push。

自助部署包：仓库的 azure/speech-token-broker/provision.sh 把步骤 1–6 一键做完（资源组、区域、名称可用环境变量覆盖），跑完打印步骤 7、8 的手工指引。未来若打成部署包交给客户，客户只需 az login + pac auth，跑 provision.sh，再照打印的两步在自己环境里建连接、接进应用即可。

坑一 · Node 版本：CLI 会推你用 Node 24（称 20 已 EOL），但 Node 24 目前在 Linux 消费计划上起不来（持续 503，function list 报 Bad Request）。用 Node 22 LTS；若已建在 24 上，把 linux-fx-version 改成 Node 22 再重启。

坑二 · 部署方式：新建的 Linux 消费计划 App 上，config-zip 与 OneDeploy 都会因 Kudu/SCM 未就绪返回 Bad Request / 503。改用 run-from-package（应用启动时从 blob SAS 拉包）绕开 Kudu。

安全：端点默认匿名；一旦在 Function 应用设置里配置 SPEECH_API_KEY，就启用共享密钥鉴权——连接器经 x-api-key 头在每次调用时发送该密钥，未带或不匹配即 401，挡住匿名滥用。provision.sh 会为新部署自动生成并配好这把密钥。上线前仍建议把 CORS 收紧到具体来源并加限流。订阅密钥只在服务端应用设置里、从不进前端；端点返回的是合成音频或转写文本、不含数据访问权。

下面把步骤 1–8 串成一份可复制的命令序列。参考名称用的是本项目的部署（资源组 WellsRG、区域 eastus、Function sales-copilot-token）；换环境时替换这些名称与 <尖括号> 占位符即可。前置条件：az login、pac auth、Node/npm、zip。

# ===== Sales Copilot voice backend: deploy from scratch ===== # ---- 1. Speech resource (F0 free) ---- az cognitiveservices account create -n sales-copilot-speech -g WellsRG \ --kind SpeechServices --sku F0 -l eastus --yes # ---- 2. Storage + Function App (Node 22, NOT 24; see Trap 1) ---- az storage account create -n scspeechtok279487 -g WellsRG -l eastus \ --sku Standard_LRS --allow-blob-public-access false --min-tls-version TLS1_2 az functionapp create -n sales-copilot-token -g WellsRG \ --storage-account scspeechtok279487 --consumption-plan-location eastus \ --runtime node --runtime-version 22 --functions-version 4 \ --os-type Linux --disable-app-insights true # ---- 3. Keys into Function app settings (Speech key + anti-abuse API key) ---- KEY=$(az cognitiveservices account keys list -n sales-copilot-speech -g WellsRG --query key1 -o tsv) APIKEY=$(openssl rand -hex 32) # anti-abuse shared secret; the connector sends it as x-api-key az functionapp config appsettings set -n sales-copilot-token -g WellsRG \ --settings SPEECH_KEY="$KEY" SPEECH_REGION=eastus SPEECH_API_KEY="$APIKEY" # ---- 4. Deploy function code via run-from-package (NOT config-zip; see Trap 2) ---- cd azure/speech-token-broker && npm install --omit=dev zip -r -X /tmp/speech-broker.zip host.json package.json src node_modules CONN=$(az storage account show-connection-string -n scspeechtok279487 -g WellsRG --query connectionString -o tsv) az storage container create -n deploy --connection-string "$CONN" az storage blob upload -c deploy -n speech-broker.zip -f /tmp/speech-broker.zip --overwrite --connection-string "$CONN" EXPIRY=$(date -u -v+2y '+%Y-%m-%dT%H:%MZ') # Linux: date -u -d '+2 years' '+%Y-%m-%dT%H:%MZ' SAS=$(az storage blob generate-sas -c deploy -n speech-broker.zip --permissions r --expiry "$EXPIRY" --connection-string "$CONN" --full-uri -o tsv) az functionapp config appsettings set -n sales-copilot-token -g WellsRG --settings WEBSITE_RUN_FROM_PACKAGE="$SAS" az functionapp restart -n sales-copilot-token -g WellsRG # Redeploy after any Function code change: re-run this block's zip + blob upload. # ---- 5. CORS + verify both operations ---- az functionapp cors add -n sales-copilot-token -g WellsRG --allowed-origins "*" curl -s -X POST https://sales-copilot-token.azurewebsites.net/api/tts \ -H "Content-Type: application/json" -H "x-api-key: $APIKEY" \ -d '{"text":"hello","locale":"en-US"}' | head -c 60 # expect: {"audio":"<base64 mp3>", ...} (without x-api-key you get 401) curl -s -X POST https://sales-copilot-token.azurewebsites.net/api/stt \ -H "Content-Type: application/json" -d '{}' | head -c 80 # expect: {"error":"audio_required", ...} (route is live) # ---- 6. Custom connector (both Synthesize + Transcribe ops) ---- cd ../speech-connector pac connector create \ --api-definition-file apiDefinition.swagger.json \ --api-properties-file apiProperties.json # ---- 7. Connection: maker portal, MANUAL (NoAuth is not scriptable) ---- # Maker portal: Connections, "+ New connection", pick "Sales Copilot Speech", Create pac connection list # copy the Connection Id and the shared_... apiId # ---- 8. Wire the connector into the Code App ---- cd ../../apps/sales-copilot BIN=$(find node_modules/.pnpm -path "*@microsoft/power-apps-cli/dist/Bin.js" | head -1) node "$BIN" add-data-source \ --api-id shared_<apiId> --connection-id <connectionId> \ --org-url https://<your-org>.crm.dynamics.com/ --non-interactive pnpm build && npx power-apps push
