01 / Business Challenge

现状与挑战：桌面 CRM 在拜访现场失效

客户业务依赖一套高度定制的既有 CRM，承载从客户活动、商机、订单、安装到售后的完整业务流程。系统在桌面端覆盖了完整的功能集，但其访问形态与现代销售的实际工作场景之间存在明显错位——销售真正需要它的时刻，恰恰是它最难以使用的时刻。

Pain 01 · 形态错配

移动访问 = 浏览器套桌面，并非真正的移动应用

当前所谓的"移动端"实质是桌面 Web 在手机浏览器内的简单包装：仅做了 Responsive 布局适配，未按移动操作特性重新设计交互；首屏与列表加载时间长，触控热区与导航层级仍是桌面思维，销售在拜访现场仍倾向退回 Excel/微信记录。

Pain 02 · 性能瓶颈

跨境访问慢，等待消耗耐心

既有 CRM 后端部署集中，跨区域访问需经多段网络，单页加载与列表查询常需数秒至十余秒，使一线销售更倾向用 Excel/微信记笔记，绕过系统。

Pain 03 · 录入摩擦

表单字段繁多，移动端难以完成

"记录拜访"需填写 10+ 字段（主题、纪要、起止时间、目的、联系人、状态、跟进动作、关联客户/商机），即便上线移动表单也只是把痛苦从大屏迁移到小屏。

Pain 04 · 智能缺位

从"信息记录"到"商机识别"全靠人脑

销售完成拜访后需要自己判断"是否要建商机"、"产品线是什么"、"信心度多少"，再手动到另一个模块创建——这恰恰是 AI 最擅长辅助、却尚未介入的环节。

核心判断 AI 已经可以理解口语、识别意图、自动调用业务 API。销售在路上仍被迫低头填表，跟“CRM 该不该上移动端”无关，原因是现有 CRM 把桌面表单原样搬到了 6 寸屏上。本方案的目标：表单退出主界面，由对话与 AI 草稿承接录入。

02 / Design Philosophy

设计哲学：Conversational CRM

下面四条原则规定了销售与 CRM 的交互方式：一句话说清原则，一条硬规则约束实现。这些原则直接决定后续的架构选型与产品配置。

原则 01

Mobile-First，不只是 Mobile-Compatible

设计起点是"单手 · 户外光线 · 30 秒内完成"，而非桌面缩小版。

Design Rule单一焦点 · 一拇指可达 · 离线可写；超过 3 屏的表单必须由对话承接。
原则 02

Voice-First，键盘是 fallback

语音是拜访间隙最自然的输入；键盘只在语音失败时出现。

Design Rule主页面常驻语音按钮 · Azure AI Speech (STT) 流式转写为主、iOS 系统输入法听写为 fallback · AI Builder 抽取字段。
原则 03

Confirm，Don't Configure

AI 主动给草稿，用户只做"确认 / 微调 / 拒绝"三选一，配置型交互压成判断型。

Design Rule每条 AI 输出附"来源 + 置信度 + 一键编辑"；拒绝/编辑沉淀为提示词优化语料。
原则 04

Agent 编排，不是菜单导航

用户表达意图，Generative Orchestration 调度 Agent，无需知道既有 CRM 菜单。

Design Rule移动端只有"对话 · 看板 · 任务"三入口；新增能力靠注册 Agent 而非重构 UI。

05 / System Architecture

系统架构：智能业务伙伴的分层协同

架构分五个功能区：体验层（用户入口）、认知层（AI 推理带 OCR / 实体抽取）、编排层（Agent 调度，与认知层并行协作）、数据层（与既有 CRM 按职责划分、分别持有不同数据）、治理层（身份、合规、可观测，横切所有区域）。下方架构图按上→下的调用方向排列：体验层调用认知 / 编排层，编排层读写数据层，治理层从侧边接入每一区。

Experience · 体验层

主战场 + 两侧入口

销售用代码型 Power Apps（写 React / TS，复用平台身份与治理）作为主端，能调相机、语音、离线缓存等原生能力；Teams 给会议中的临时查询，Model Driven App 给后台运维。

Power Apps Code App (React) Copilot in Teams Model Driven App（管理后台）
Cognitive · 认知层

设备原生语音 + AI Builder 文本智能

语音走 Azure AI Speech、文本走 AI Builder。这些预构建能力由前端与编排层共用，不需要自己训模型。

Azure AI Speech (STT) · iOS 输入法听写 fallback AI Builder Prompt (GPT) AI Builder Form Processing Entity Extraction / Classification

Generative Orchestration 按用户意图自动选择并串联 Agent，无需手写路由；Agent Flow 处理多步事务（可理解为嵌了 Agent 的 Power Automate）；每个 Domain Agent 自带知识与工具集，详见第 07 节。

Data · 数据层

Dataverse 作为 AI 操作面 · 既有 CRM 仍是 System of Record

按数据所有权分域共生：销售自有数据落 Dataverse、既有 CRM 权威数据实时调用，写入统一走"草稿 → 确认 → 异步回写既有 CRM"。详细方案见第 09 节。

Microsoft Dataverse（销售自有 + AI 元数据） Custom Connector → 既有 CRM（实时读 / 写） Power Automate（增量同步） Azure API Management（统一接入） Azure Service Bus（异步回写） Azure Blob Storage（拜访照片 / 设备铭牌）
System of Record

既有 CRM（保留 · 不动其底座）

权威记录、合同、价格、订单履约仍在此处；本方案所有写入最终回流既有 CRM，保持其唯一真相源地位。

Governance · 治理层（横切）

横切全栈的身份 · 安全 · 合规

身份沿用现有 Entra ID + 既有 CRM 角色；连接器边界、环境隔离、AI 输出审核、凭据托管与端到端可观测都用平台原生组件，不再自建。

06 / Data Strategy

数据策略：与既有 CRM 共存的三种方式

移动端与既有 CRM 的数据关系有三条主流路径：全量复制到 Dataverse、通过接口实时调用、按数据所有权分域共生。三者在查询时延、数据冗余、同步复杂度与对既有系统的侵入度上各有取舍。本方案采用分域共生路径。

方案 A

整迁 / 双写

把既有 CRM 的数据全量同步到 Dataverse，两侧维护一致性。优势是 AI 侧查询最快、可离线；代价是同步基础设施沉重、双向冲突、合规审计复杂、既有系统端定制功能可能丧失。

方案 B

实时接口调用（REST API / MCP）

不复制任何数据，Agent 通过既有 CRM 暴露的 REST API 或 MCP Server 实时读写。优势是零数据冗余、既有 CRM 始终是唯一真相源、上线最快；代价是每次交互都要回既有系统链路（受跨境延迟影响）、复杂查询难以编排、需要既有系统侧补齐 API/MCP 覆盖面。

方案 C（本方案采用）

分域共生：Dataverse 持有销售自有数据 + Custom Connector 实时调既有 CRM

按数据所有权划分两路：客户 / 商机 / 活动 / AI 元数据这类销售自有数据落 Dataverse 物理表，由 Power Automate 与既有 CRM 做增量双向同步；报价 / 库存 / 订单状态这类既有 CRM 权威数据仍由 Custom Connector 经 APIM 实时调用，前端加短期客户端缓存。写入统一走"草稿 → 确认 → Service Bus 幂等回写既有 CRM"，提供草稿态 → 待同步 → 已同步三段式可视化。优势是销售高频路径走 Dataverse（快、可离线）、既有 CRM 权威路径保持唯一真相源；代价是需要明确划分每个实体的主权与同步双向。

08 / Agent Architecture

多 Agent 协同：30+ Agent 如何共同回答一句话

Agent 全景图回答了"有哪些 Agent"，本节回答"它们怎么协同"。我们采用 Microsoft Copilot Studio 的 Generative Orchestration 作为调度核心，把 Agent 分成三层职责，规定四种协作模式，并以一条统一的消息契约串起所有 Agent，使任何业务域的新 Agent 加入时，无需修改现有 Agent。

Tier 1 · 调度

Orchestrator Agent —— 一个，全局唯一

由 Copilot Studio 的 Generative Orchestration 充当。它不执行业务逻辑，只做三件事：理解用户意图、选择业务 Agent、把多 Agent 的回答合成一段连贯回复。所有界面（HomeDashboard / BriefMe / CopilotChat / ActivityCapture）的 mic 按钮最终都打到这一个 Orchestrator。

Generative Orchestration（内置）
▼
Tier 2 · 业务

Domain Agents —— 与业务概念一一对应

即第 06 节列出的 30+ Agent。每个 Agent 拥有自己的 system prompt、知识源（Dataverse 表 / 既有 CRM 虚拟表 / 知识库）与可调用工具集。Domain Agent 之间默认不直接互调，统一由 Orchestrator 串联，避免硬编码依赖。

客户画像 / 商机评估 / 活动创建 … 订单查询 / 物流查询 / 现场服务 … 见 §06 全景图
▼
Tier 3 · 工具

Skill / Tool Layer —— 可被多个 Agent 复用

原子能力，单一职责。包括既有 CRM Connector、Dataverse CRUD、AI Builder Prompt(GPT)、Form Processing、Azure AI Search、Power Automate Flow 等。同一工具可被任意 Domain Agent 调用，治理与权限由 Power Platform 集中管控。

既有 CRM Connector Dataverse CRUD AI Builder Prompt(GPT) Form Processing Azure AI Search（Phase 3） Power Automate Flow

设计原则：上层只调下层，跨层不可越级；任何新 Agent 加入只需在 Tier 2 注册并声明所需 Tier 3 工具，Orchestrator 通过描述自动学会调度。

09 / Worked Example

实战演练：一句话拜访录入

把第 07 节的三层架构落到一次真实交互上：销售说一句话，Orchestrator + 5 个业务 Agent 并行/串行协作，最终回送一张可一键 Confirm 的 draft 卡片。

刚拜访完上海仁济医院张主任，他对监护仪 N17 感兴趣，要 12 台，下周三再约一次定标书细节。
Orchestrator 识别意图为「活动录入 + 商机线索」，决定走「顺序流水 + 审阅闭环」组合模式。 工具：Generative Orchestration · 路由耗时 ≈ 200 ms
实体抽取 抽出客户=上海仁济医院、联系人=张主任、产品=监护仪 N17、数量=12、下次跟进=下周三。 工具：AI Builder Prompt(GPT) + 自定义 schema
客户画像 Agent 并行查询：仁济医院在既有 CRM/Dataverse 中已存在，最近 30 天 4 次拜访 · 信用 A 级 · 已签 MSA。 工具：Dataverse 物理表 · Custom Connector → 既有 CRM
活动创建 Agent 生成 Activity draft（type=Visit, date=今天, 摘要 = 三句话, 下次 follow-up=下周三日历占位）。 工具：Dataverse CRUD · Outlook Calendar
商机创建 Agent 检索到对该客户已存在监护仪 N17 商机（Identify 阶段）→ 不创建新商机，建议追加为既有商机的活动证据。 工具：既有 CRM Opportunity 表 · 重复检测规则
商机督导 Agent 校验：12 台 N17 + Identify 阶段 + 客户级 A → 触发"阶段建议升级到 Qualify"提示，附建议下一步：发送报价。 工具：业务规则引擎（Power Fx）
Orchestrator 把 5 段 agent 输出合成一段连贯回复 + 一张可一键 Confirm 的 draft 卡片回送 UI；用户 Confirm 后才落库。 端到端分段：语音转写完成 ≤ 1秒 · UI 堆出初始 draft ≤ 4秒 · 6 Agent 全部推理完成 ≤ 12秒 (P50)。UI 以边到边流式渲染掩盖总时长。

单次录入耗时 · 试点期测真实分布

每日"被表单消耗"的时间

显著下降

系统使用意愿（NPS）

商机识别覆盖率

是否现场获得答案 + First-Time-Fix 率

让方案在多区域、多语言、低耦合下持续扩展

新功能交付节奏

14 / Delivery Method

交付方式：Plan-First · Vibe Build · ALM Promote

不是瀑布交付，也不是纯 vibe coding。本方案采用 Microsoft 官方 Power Platform ALM + 新发布的 Plan Designer，组成三段式交付：Plan-First 起手、Vibe Build 出原型、ALM Pipeline 推到生产。详细六阶段路线图见《开发者设计文档》。

阶段 1 · Plan-First

一句话 → v0 Plan

进 Power Apps Plan Designer，三个官方 Agent（Requirement / Data / Solution）接力生成用户角色、Dataverse 表与推荐技术栈。后续三轮人审使 v0 收敛到既有 CRM 共生边界，输出锁定的 Data Model + Phase 1 技术清单。

阶段 2 · Vibe Build

Bootstrap + 一屏一 Prompt

一个 Bootstrap 提示词拉起脚手架，四屏提示词逐屏生成原型；既有 CRM API、性能敏感视图、安全审计交给 pro-code（PCF / Plug-in / Custom Connector）。Vibe 与 Pro-Code 边界明确，不靠默契。

阶段 3 · ALM Promote

Solution 化 + Pipeline 推送

unmanaged Solution 导出后用 SolutionPackager 解包进 Git，prompt 与代码同仓；CI 打出 managed 包，In-product Pipeline 依次推 Test / UAT / Prod，Patch 走 hotfix、Upgrade 走 minor；App Insights 监控拜访完成率、Agent 成功率、既有 CRM 写入时延。

  • 试点扩展到 3 个区域 · 100 名销售
  • 建立 AI 质量基线：意图识别准确率、商机草稿采纳率、平均节省时间
Phase 3 · M5

售后与知识 Agent 拓展1 个月 · 关键里程碑：覆盖售后场景闭环

  • 维修知识检索 Agent + 现场服务 Agent + 备件推荐 Agent
  • 智能知识库：以 SharePoint + Dataverse 知识源做 RAG 索引
  • Microsoft Teams 内置 Copilot 入口，覆盖会议中临时查询
  • 区域级运营看板基于 Power Apps 自定义页面 + Dataverse 视图实现，由考核管理 Agent 推送关键洞察
Phase 4 · M6 及以后

全球推广 + 持续演进持续 · 关键里程碑：覆盖全部销售人员

  • 全球推广：分批接入欧洲、亚太、北美、中东等区域
  • 建立 Agent 运营机制：每月一次 prompt/工具优化、新 Agent 评审
  • 引入预测性维护、销售预测等高阶 Agent
  • 形成内部 Citizen Developer 培训体系，让区域业务专家参与新 Agent 设计
风险控制三原则 ① 任何 AI 写入操作均经过"草稿确认"，不直接覆盖既有 CRM；② 每个 Agent 都可独立下线/灰度，不影响其他流程；③ 每阶段结束做"销售真实满意度"测量（NPS + 关键流程节省时间），未达标禁止进入下一阶段。
