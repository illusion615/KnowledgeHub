00 / 开通前交接

先明确费用归属，再分配操作职责

适用对象是客户侧业务申请人、平台管理员、Azure 订阅管理员和财务负责人。以下是 Global 商业云指南，不代替租户审批，也不覆盖中国云或政府云。

  • 1
    计费关系

    按量付费（Pay-as-you-go，PAYG）把用量计入 Azure 订阅。计费计划（billing plan，部分文档仍称 billing policy）把一个或多个 Power Platform 环境与一个 Azure 订阅关联；每个环境同时只能关联一个计划。[1][2]

  • 2
    Azure 账单载体

    创建计划会在所选资源组中生成同名 Power Platform account 资源，用来归集计量费用。资源组是管理相关 Azure 资源的容器；它不是 Power Platform 环境。[1][2][9]

  • 1
    业务申请人（协作建议）

    产品、环境 ID、用途、批准的费用承担部门和停用联系人。

  • 2
    平台管理员（协作建议）

    环境类型与区域、现有计费关联、应用／流程负责人、执行人的平台管理权限。

  • 1
    Azure 订阅管理员（协作建议）

    租户／订阅 ID、订阅状态和合约类型、资源组、资源创建和提供程序注册权限。

  • 2
    财务负责人（协作建议）

    批准的费用范围、成本查看人、预算维护人、告警收件人和后续复核安排。

01 / 步骤 1 · 适用性

确认租户、订阅和环境符合条件

先核对身份和目标环境，再申请权限。Microsoft Entra 租户是组织的身份目录；Azure 订阅关联一个这样的目录，当前开通向导只列出本租户内执行人有足够权限的订阅。[1][8]

  • 1
    前提

    准备已批准的产品范围、目标环境 ID、环境类型／区域、Azure 订阅 ID 及其目录 ID。使用组织账号；同一个人能登录两个目录不代表订阅和环境属于同一租户。[1][8]

  • 2
    执行人与权限范围

    平台管理员核对其可管理的环境；Azure 订阅管理员提供订阅状态和目录信息。Azure Reader 可在获授的订阅范围查看资源；这不是创建计划的权限。业务申请人只整理交接资料，无需因此获得管理员角色。[1][8]

  • 1
    操作与位置

    由管理员在 Azure portal 的 Subscriptions 中核对目录和 Status；在 Power Platform admin center（PPAC）核对环境 ID、类型和区域。标准开通只支持 Production 与 Sandbox；FAQ 明确 Norway 和 Korea (South) 的按量计费与报表不可用。[1][3][10]

  • 2
    成功判据

    交接表中的目录一致，订阅为 Active/Enabled，目标是可选区域内的 Production 或 Sandbox。区域下拉框用于筛选环境；不能据此推定所有区域或所有环境类型都受支持。[1][3][10]

  • 1
    缺失或不可见

    订阅不显示：先查目录与执行人权限，不要先新建订阅。Disabled、Expired 或 Warned 会限制创建／更新；Past Due 仍可能可用，但应先交财务处理。当前开通文档没有列出完整的订阅优惠类型白名单，不能承诺任意试用、赠金或学生订阅均可用。[1][10]

  • 2
    区域与资源组

    资源组必须属于选定的 Azure 订阅。Azure 文档允许资源与资源组处于不同区域；资源组区域用于存储元数据，不能擅自增加「必须等于环境区域」的规则。按向导实际可选范围和组织区域政策确认；不要把费用合约类型与成本可见性条件混为产品资格。[1][9][12]

02 / 步骤 2 · 权限交接

分别确认平台权限、Azure 资源权限和授权权限

平台管理角色、Azure 基于角色的访问控制（Azure RBAC）和 Azure 计费／成本权限属于不同授权体系。Global Administrator 默认没有 Azure 资源访问权；持有 Azure Owner 也不能代替环境管理权限。[1][8]

  • 1
    前提

    先选定计划创建人和备用维护人，并取得步骤 1 的订阅、环境与资源组信息。环境创建者或 Environment Maker 不等于开通文档要求的管理员；有 Dataverse 的环境使用 System Administrator 管理数据库权限。[1][16]

  • 2
    执行人与权限范围

    创建人须符合官方平台矩阵：Environment admin 的编辑／关联范围受本人创建的计划及本人管理的环境限制；Power Platform admin、Global admin、Dynamics 365 admin 的计费矩阵范围为租户。还必须具备 Azure 侧权限，或与持有人协作；不能只验证其中一侧。[1]

  • 1
    操作与位置

    Azure 管理员在目标订阅的 Access control (IAM) 核对创建人权限。开通文档要求能在订阅中创建新资源、注册资源提供程序，或与有这些权限的人协作；订阅范围的 Contributor 或 Owner 通常覆盖这些能力，Owner 不是统一必选角色。[1][6]

  • 2
    注册权限与范围

    资源提供程序是提供某类 Azure 资源的服务。需要注册时，由有目标订阅 /register/action 权限的人在 Subscriptions > Resource providers 处理；Contributor 与 Owner 包含该权限。只注册本次需要的提供程序，不批量注册所有服务。[5]

  • 1
    资源组准备

    已有资源组就复用经批准的目标。没有时，由具备订阅资源创建权限的 Azure 管理员在 Resource groups > Create 填订阅、名称和区域，Review + Create > Create；刷新后交接资源组名称。这里是客户后续操作说明，本文未执行创建。[1][6][9]

  • 2
    成功与缺权排障

    记录创建资源与注册能力的持有人及范围。资源组 Contributor 不自动具备订阅注册权限，也不保证订阅下拉框可见；请订阅管理员核对。Contributor 不能分配 Azure RBAC 角色；Add role assignment 灰显时，需要在所授范围有 Microsoft.Authorization/roleAssignments/write 的授权人处理。[1][5][6][7]

  • 3
    不要扩大权限代替排查

    先核对账号、范围、已有角色和组织审批；不要为了看见订阅直接给所有人 Global Administrator 或 Owner。本文列的是官方所需能力与内置角色示例，不提供自造的最小权限自定义策略。[1][6][7][8]

矩阵中的「可创建」不免除 Azure 权限条件；Environment admin 的计划归属限制也适用于 Power Apps 入口。[1]

  • 1
    Environment admin

    可创建；仅编辑本人创建的计划，只关联本人管理的环境与本人创建的计划。[1]

  • 1
    Power Platform admin

    可创建；可编辑租户内所有计划，关联租户内所有环境。[1]

  • 1
    Global admin

    开通文档列为可创建、编辑全部计划、关联全部环境；不因此自动获得 Azure 资源权限。[1][8]

  • 1
    Dynamics 365 admin

    开通矩阵也列为租户级权限；另核对已有环境安全组的成员要求。[1][18]

需要补平台服务管理员角色时，官方路径由 Privileged Role Administrator 在 Microsoft 365 admin center > Users > Active users > Account > Roles 处理；服务管理角色应直接授予用户。使用组织既有审批和按需激活流程，不在开通向导中尝试自行提权。[18]

03 / 步骤 3 · 填写计划

从当前 PPAC 入口填写计费计划

本流程使用官方当前文档中的 Licensing > Pay-as-you-go plans。文档还保留 Billing policies 等旧称；不要把不同入口的按钮名称拼成一条未经证实的操作路径。[1]

  • 1
    前提

    准备计划名称、已批准的订阅／已有资源组、产品清单和费用审批。Save 或 Connect subscription 前须完成下方可见的预检；这些操作会创建 Azure 资源并关联计费，不是保存草稿。[1][2]

  • 2
    执行人与权限范围

    由步骤 2 确认的计划创建人操作：官方平台矩阵中的创建权限，加目标订阅所需的新资源创建／提供程序注册能力，或已安排有权限者协作。范围是目标租户、目标订阅及所选资源组，不是任意 Azure 订阅。[1]

  • 1
    产品与许可预检

    无需已保存计划。平台管理员与产品负责人先按适用产品分支的许可条件核对所选产品、现有用户许可／app passes 和容量。Process 许可及 unattended RPA add-on 在 PAYG 环境内不消耗；依赖 Process 的流程须留在非 PAYG 环境。[1][3][4]

  • 2
    容量与存储影响

    财务与平台负责人在关联前核对 Dataverse 数据库、文件和审计日志存储及容量分配。Dataverse 计量默认开启；当前文档允许预分配容量，超分配部分计入 Azure。存储可能在应用使用之前收费；影响获批准前不得保存或连接。[3][4]

  • 1
    操作与位置

    在 PPAC 选择 Licensing > Pay-as-you-go plans > New billing plan > Azure subscription。填写 Name；在 Azure subscription 选订阅，在 Resource group 选已有资源组，在 Power Platform products 选经批准的产品，然后选 Next。[1]

  • 2
    成功判据

    确认表单中的订阅 ID、资源组和产品范围与审批一致，并进入 Select environments。此时只完成表单，不把进入下一屏当作已开通成功。[1]

  • 1
    缺权或不可见

    订阅不显示或出现权限错误，联系订阅所有者或 Azure 管理员核对目录和官方创建／注册条件。资源组为空，先让 Azure 管理员核实组是否存在于该订阅。不要为绕过空列表而选择其他部门订阅或新建未批准资源组。[1]

  • 2
    另一种计划不属于此主流程

    Microsoft 365 Copilot Chat 是 New billing plan 中另一个选项：官方说明保存后会自动预配或重用名为 Microsoft 365 Copilot Chat 的环境，且管理员不能删除该环境。只有目标确为该场景时才用该分支，不把它当作标准环境关联步骤。[1]

这是官方记录的另一个入口，使用相同平台／Azure 权限条件，不是当前 PPAC 菜单的别名。[1]

  • 1
    位置与操作

    在 Power Apps 选对环境，进入 Apps > 应用 > Settings；尚未开通时选 Set up pay-as-you-go，填计划／订阅／资源组。完成上方产品／许可、Process 与 Dataverse 预检后，才选 Connect subscription 启用环境计费。支持 canvas 与 model-driven apps。[1]

  • 2
    成功与边界

    成功后返回应用设置；通过应用入口连接仍会对环境中所有未退出该模式的应用启用按量计费，不是仅对当前应用开通。已开通时，Edit pay-as-you-go billing 会转到 PPAC。不要把本入口的 Connect subscription 写成 PPAC 最后一步。[1]

04 / 步骤 4 · 关联环境

保存前核对每个环境的计费影响

一个计划可以关联多个环境，但一个环境同时只能关联一个计划。已有计划的环境需要走受控变更，不能假设可在多个订阅间重复计费。[2]

  • 1
    前提

    Save 前须确认支持的环境类型／区域、现有计划和业务／财务审批，并完成产品／许可、Process 与 Dataverse 预检。已有工作负载／存储即使不试用也可能收费。[1][3][4]

  • 2
    执行人与权限范围

    Environment admin 只能把本人管理的环境关联到本人创建的计划；官方矩阵中的租户管理员可关联租户内环境。创建与保存仍受目标订阅 Azure 条件约束。若由接替人维护，先核对计划归属，不把环境权限当作所有计划的编辑权限。[1]

  • 1
    操作与位置

    完成产品／许可、Process 与 Dataverse 预检后，在 Select environments 选择目标 Region，核对环境 ID／名称，勾选经批准的环境，才选 Save。只使用向导有效选择，不推断未记录的跨区域组合。[1]

  • 2
    成功判据

    重新打开计划，确认订阅、资源组、产品及环境成员均已保存。到 Azure portal 的相同订阅／资源组打开 View hidden types，应看到与计划同名的 Power Platform account 资源。这是配置核验，不是费用已经上报的证据。[1][11]

  • 1
    缺权或不可见

    环境不在列表：核对当前租户、Region、Production／Sandbox 类型、受支持区域、计划归属和环境管理权限。保存失败：保留错误信息，交平台与 Azure 管理员分别核对各自范围；不要反复新建计划。Azure 资源不见时先检查隐藏类型筛选与选中的订阅／资源组。[1][2][3]

  • 2
    交接记录

    记录计划名称／ID、Azure 资源 ID、环境 ID、所选产品、执行人与生效时间；由平台管理员和财务负责人各保留一份。这是便于后续对账的建议记录，不是官方额外许可条件。

05 / 步骤 5 · 产品确认

保存后核验计费选择和产品使用权限

只有计划中选择的产品启用按量计费；FAQ 另说明 Dataverse 默认开启。计划不授予应用、数据或代理访问权，也不提高请求权益。下列许可条件须先用于保存前预检；保存后的动作只核验配置／访问。[3][4][16][17]

  • 1
    前提

    以下配置／访问核验使用已保存计划、产品负责人及预检记录。产品／许可／容量预检本身无需已保存计划，且必须已在 Save／Connect subscription 前完成。[3][4]

  • 2
    执行人与权限范围

    平台管理员按官方计划编辑范围核对产品；产品负责人只处理其有权编辑／共享的应用或流程。Dataverse 数据权限在具体环境内另授；例如为 canvas app 用户分配 Dataverse 角色需要该数据库的 System Administrator。Azure 角色不代替这些 scope。[1][16][17]

  • 1
    操作与位置

    按预检记录重新打开计划，核验 Power Platform products。只查适用的已保存配置／访问：Power Apps 应用 Settings 计费开关；Power Automate 流程类型／许可与预检清单的一致性；Copilot Studio 作者访问和目标环境。不运行应用、流程或代理试收费。[1][4][14][19]

  • 2
    成功判据与缺权排障

    所选产品、默认 Dataverse 影响和用户访问前提均已由对应负责人确认。能看到计划却打不开应用时，查应用共享、数据角色或作者访问，而不是增加 Azure Owner；找不到产品项时，复核当前产品文档、预览状态和本租户实际入口，不假设每个租户界面一致。[1][3][4][16][17][19]

  • 3
    缺权时联系哪一方

    计费选择交计划维护人；应用编辑／共享交应用所有者；Dataverse 角色交该环境管理员；Copilot Studio 作者设置交下列有权访问 Tenant settings 的管理员。不要因为开通费用而给最终用户管理员权限。[1][16][17][19]

  • 1
    仅在选择 Power Apps 时执行

    前提是环境计费已关联且应用负责人可编辑该应用；canvas app 的 Co-Owner 可编辑／共享。由具备官方计费权限的管理员与应用负责人在 Apps > 应用 > Settings 核对 PAYG 开关；环境开通默认影响所有应用，单个应用可以退出。[1][17]

  • 2
    许可与成功判据

    开关及共享／数据权限符合审批才算完成。退出 PAYG 的应用需要用户许可；环境中的 per-app app passes 不会继续消耗，不能假设同环境混用。已有 per-user 许可，或具备 Microsoft 365 权益且只用标准连接器的用户，按官方条件不计入 Power Apps 计量。[1][3][4][17]

  • 1
    仅在选择 Power Automate 时执行

    官方当前仍把 flow-run meters 标为 preview（预览，功能和条款可能变化）。平台管理员核对计划中的产品选择；流程负责人提供自动／定时／即时、云端／桌面及 attended／unattended 类型。本文不增加官方未说明的逐流程启用按钮。[4]

  • 2
    许可与成功判据

    复核保存前已确认的许可条件：标准连接器流程不计费；独立用户许可仅在权益内豁免。PAYG 环境不消耗 Process 许可及 unattended RPA add-on；依赖 Process 的流程留在非 PAYG 环境。保存后只对照预检结论核验配置，不运行流程试收费。[3][4]

  • 1
    仅在选择 Copilot Studio 时执行

    本分支的作者访问条件依据 standard harness 代理文档；其他运行机制及 Microsoft 365 Copilot Chat 须另核对。当前计量为 Copilot Credits，不是旧 messages。环境须关联含 Copilot Studio 的计划；作者另需适用的访问配置，如 Copilot Studio authors 安全组或作者许可。只有 trial 不能发布代理。[4][14]

  • 2
    执行人、范围与成功判据

    在 PPAC Manage > Tenant settings，官方列出的 Power Platform Administrator 或 Dynamics 365 Administrator 可访问租户设置，核对 Copilot Studio authors 及 Copilot Studio pay-as-you-go users。复用已批准的安全组，确认目标作者与环境；不要把计划创建成功当成作者已获访问权。[14][19]

把存储分配和 API 请求额度分开核对；连接 Azure 不代表请求无限制。[3][4]

  • 1
    Dataverse

    当前文档允许预分配容量；超分配部分计入 Azure。PAYG 环境含首 1 GB 数据库和 1 GB 文件容量；开启审计后产生的日志存储会计费。不要沿用「租户容量绝不能分配到 PAYG 环境」的旧口径。[3][4]

  • 2
    Power Platform requests

    当前请求计量尚未可用，不收费；连接 Azure 不提高用户／流程请求权益。连接器、并发和 Dataverse 服务保护限制仍适用。不要把报表中有请求数量理解成已经收费。[3][4]

产品许可要按实际使用方式核对；预付容量、作者访问和按量计费不能互相代替。[4][14][15]

  • 1
    Power Automate 计量主体

    自动／定时流程按所有者权益判断，即时或 Power Apps 触发流程按运行用户判断；应用上下文内的流程另有官方规则。服务主体、无人值守和 Process 场景不能套用普通用户豁免。只把已核实的场景写入费用审批。[3][4]

  • 2
    Copilot 作者访问

    如选择分配作者许可的路径，由有许可管理权限的租户管理员在 Microsoft 365 admin center > Users > Active users > Manage product licenses 办理；该文档没有在此列出唯一最小管理员角色。PAYG 不一律要求先买预付包；当前 billing-licensing 页已限定 standard harness 代理，其他运行机制和 Microsoft 365 Copilot Chat 要另核对。[14][15]

06 / 步骤 6 · 配置验收

先验收配置，不用未批准的消费证明开通

「计划和关联已保存」与「业务用量已上报」是两个验收阶段。后者需要实际用量且可能收费；本指南没有登录租户、创建资源、调用模型或执行收费测试。[1][4][11]

  • 1
    前提

    计划保存完成，产品分支前提已确认，交接记录含计划／环境／Azure 资源 ID。尚未批准正式使用时，不为核验而打开应用、触发流程或与代理对话。[1][4]

  • 2
    执行人与权限范围

    平台维护人按计划编辑／环境范围核对 PPAC；Azure 核验人可用目标订阅或资源组范围的 Reader 查看资源，无需为查看申请 Owner。若要读 PPAC 用量报表，使用有权管理该计划的管理员；用量页未声明独立的最小只读角色，不能推断 Azure Reader 自动有该权限。[1][6][8][11]

  • 1
    操作与位置

    在 PPAC 重新打开计划核对产品和环境成员；在 Azure 相同资源组启用 View hidden types，核对同名 account 资源及 ID；把它们与审批订阅、环境 ID 对照。避免依赖未记录在官方文档中的特定「已激活」状态文案。[1][2]

  • 2
    成功判据

    计划、环境成员和 Azure 资源三处相互对应，产品范围与默认 Dataverse 影响已确认，财务知道账单应归集到哪个资源。记录为「配置核验完成；用量对账待正式业务发生后复核」，不要写成收费链路已经实测。[1][4][11]

  • 3
    缺权或结果不一致

    PPAC 与 Azure 结果不一致时，先查账号／目录、资源组、隐藏类型和计划归属；把错误交给对应管理员。没有 Azure 费用记录不等于配置失败，也不能证明后续不会收费。[1][11]

07 / 步骤 7 · 成本交接

给财务可见性和告警，不把预算当停机开关

正式业务获批后才核对用量；配置验收不需要制造消费。Azure Cost Management 用于归集成本，PPAC 报表用于下钻到环境、应用／代理和调用方，两者权限不同。[11][12]

  • 1
    前提

    财务收到计划和 Azure 资源 ID、费用批准范围、告警收件人及复核安排。记录订阅合约是 EA、MCA 或 CSP 等，便于排查成本查看政策；这些分类不是本文对 PAYG 产品资格的承诺。[11][12]

  • 2
    执行人与权限范围

    成本查看人可获目标订阅或资源组范围的 Cost Management Reader。本流程以订阅预算并筛选 account 资源为例：预算维护人在该订阅范围使用 Cost Management Contributor 或 Contributor；官方允许创建／修改／删除本人预算，Reader 只可读其有权预算。分配角色仍需独立授权人。[7][12][13]

  • 1
    操作与位置

    在 Azure portal 打开目标订阅的 Cost Management／Cost analysis，按与计划同名的 Power Platform account 资源筛选，再按 meter 查看。到该范围的 Budgets > Add，确认范围和资源筛选、周期、获批金额、阈值及收件人后保存；金额由客户批准，本文不提供样例价格。[11][13]

  • 2
    成功判据

    成本查看人可以打开批准范围；预算维护人能看到已保存的筛选、周期和告警收件人。实际用量发生后，PPAC 管理员再下载计划的用量报表，按计划／环境／资源 ID、时间和 Status 对账；报表中有数量不必然表示已收费。[4][11][13]

  • 1
    缺权或暂未上报

    开通过后没有费用时，先看是否有获批实际用量、筛选是否正确。Power Platform 官方说明 Azure Cost Management 可能延迟最多 24 hours；新订阅的成本功能可能需要最多 48 hours。这些是文档说明，不是每个租户的时效保证；不要用反复收费测试催报表。[11][13]

  • 2
    预算不会停止消费

    预算触发告警，不是硬性消费上限；官方说明消费不会自动停止。成本通常延迟上报，预算每天评估一次，通知也有延迟。达到阈值后由责任人按已批准的停用流程处理，不能把保存预算当作免超支保证。[13]

能管理 Azure 资源不代表合约允许你看费用，预算读取也不代表可以维护预算。[12][13]

  • 1
    EA

    由 Enterprise Administrator 核对 AO view charges；部门范围另有 DA view charges。订阅／资源组仍需相应 Cost Management 角色。[12]

  • 1
    MCA

    由 Billing Profile Owner 在计费配置文件 Policies 核对 Azure charges = Yes；该计费角色与 Azure Owner 不同。[12]

  • 1
    CSP

    由 CSP 合作伙伴确认已为客户启用 Cost Management 可见性；不把合作伙伴价格或费用显示政策推断成计量资格。[12]

  • 1
    可看成本但不能建预算

    核对预算所选范围和维护权限。订阅范围 Reader 不能创建预算；不要为了预算直接授予 Owner。若只获批资源组范围，按官方教程在该资源组建立预算。[12][13]

08 / 后续步骤 · 变更或停用

停用前安排替代许可，并保留已发生费用

本步骤仅在需要变更或退出 PAYG 时执行，不是首次开通的必做动作。删除计划会影响该计划的环境；先核对成员与应用／流程依赖，再执行受控变更。[1][2]

  • 1
    前提

    明确停用单个环境还是整个计划，安排所需替代许可／容量及业务通知，保存用量和成本记录并取得费用负责人批准。不能假设退出 PAYG 后原来依靠它的用户仍可正常访问。[1][2][3]

  • 2
    执行人与权限范围

    平台维护人按官方编辑矩阵操作：Environment admin 只处理本人创建的计划及本人管理的环境；租户级角色按矩阵范围处理。清理残留 Azure account 资源是另一项操作，需要该资源／资源组范围的删除权限，例如 Contributor；不因删除计划自动获得该权限。[1][6]

  • 1
    操作与位置

    在 PPAC 的 Pay-as-you-go plans 中编辑计划并移除目标环境，或在核对全部成员后删除整个计划。官方停用段仍使用 Billing policies 旧称。只迁移归属时，按官方「同一环境一次一个计划」规则变更，不同时挂到两个计划。[1][2]

  • 2
    成功判据

    重新打开计划／环境确认关联已移除，记录生效时间；环境恢复常规计费方式，检查替代许可安排。官方说明停用后的新增用量不再计入该 Azure PAYG 关联，但已发生用量仍会向 Azure 订阅收费，可能延迟显示。[1][2][11]

  • 1
    权限或清理问题

    无权编辑时，联系计划创建人或矩阵中有权的租户管理员。删除 PPAC 计划不会自动删除 Azure Power Platform account；若组织决定清理，由有权的 Azure 管理员另在 Azure portal 操作。不要把直接删 Azure 资源当作官方环境解绑步骤。[1][6]

  • 2
    保留费用责任

    解绑、删计划或清理 Azure 资源，都不能抹去已经发生的费用。继续按计费周期核对最后一批用量与成本；预算仍是告警机制，不会替代停用或自动撤销费用。[1][11][13]
