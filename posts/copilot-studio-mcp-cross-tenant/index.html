Cross-Tenant MCP Decision Guide

Copilot Studio 跨租户 MCP 连接：以 Global 调用 21Vianet Dataverse MCP 为例

Copilot Studio 内置「Dataverse MCP Server」连接器只解析到 maker 自己租户内的 Dataverse 环境，不提供 UI 切换到外部租户。本文以 Global Commercial 租户调用 Microsoft Azure operated by 21Vianet 的 Dataverse MCP 为主线，给出三类跨租户场景（同云 B2B / Global × GCC / Global × 21V）的可行性判定、配置步骤与替代路径。所有结论以 Microsoft Learn 官方文档 + 2026-05 实测可复现路径为准（2026-05-28 核验）。

直达操作 Runbook 先看三类场景判定

本文分两层阅读：§01–§05 是操作层，聚焦机制、场景判定、可执行步骤、边界与替代路径；§06 是治理层，面向管理员与安全合规角色。Maker 想最快配通，直接看 §03。

一句话结论

Global Commercial Copilot Studio 可以连通 21Vianet Dataverse MCP（2026-05 实测）：OAuth 2.0 Manual + 21V 应用注册 + 目标环境 allowedmcpclient 表登记调用方 app ID，全链路即可走通。

01 / Dataverse MCP Mechanism

Dataverse MCP 的工作机制：理解三个边界

跨租户能否成立，取决于三个层面是否对齐：MCP 端点的物理位置、调用方使用哪个 Entra 身份获取 token，以及目标 Dataverse 环境是否把调用方的 client ID 加入了允许清单。本节先固定术语，后续章节据此判断各场景。

Dataverse MCP server 不是租户级服务，而是绑在每个环境上的 endpoint。URL 由环境主域名 + /api/mcp 组成，sovereign 云走对应的根域名。

01

Commercial（Global）

格式：https://{org}.crm.dynamics.com/api/mcp。地域后缀（.crm4、.crm5 等）随环境实际所在 region 变化。

02

21Vianet（China）

格式：https://{org}.crm.dynamics.cn/api/mcp。China 3 区数据中心 2023 年完成切换，环境 ID/URL/URI 未变。

03

GCC / GCC High / DoD

分别走 .crm9、.crm.appsplatform.us、.crm.microsoftdynamics.us 等政府云后缀，规则同上：环境绑定，不跨域。

Copilot Studio 接入 Dataverse MCP 有两种身份模型，二者的跨租户能力截然不同。理解它们的差别，是判断跨租户可行性的关键。

Path A · 内置连接器

Dataverse MCP Server（开箱即用）

  • 身份模型 — 复用 Power Platform connector 框架，使用 maker 当前登录身份对应的 Dataverse connection。
  • 目标环境 — 默认指向 maker 当前选择的 Power Platform environment，UI 中无独立的「目标 org URL」字段。
  • 租户边界 — 在同一租户的不同环境间可切换；不支持指向另一个租户或另一个云的 Dataverse 实例。
  • 许可清单 — Copilot Studio client 默认已被 PPAC 自动允许，无需手工配置。
Path B · OAuth Manual

自带 Entra 应用 + MCP 向导

  • 身份模型 — 在目标租户注册自定义 Entra 应用，授予 Dynamics CRM/mcp.tools 权限，Copilot Studio 在运行时用 OAuth 2.0 拿用户委托 token。
  • 目标环境 — 在 MCP 向导里直接填 https://{org}.crm.dynamics.com/api/mcp，可以是任意租户的环境 URL。
  • 租户边界 — 跨同云租户可行；跨云受到 §04 的数据面限制。
  • 许可清单 — 必须把这个自定义应用的 Application (client) ID 加到目标环境的「Dataverse Model Context Protocol → Advanced Settings」白名单。

无论走 Path A 还是 Path B，调用方的 Entra app ID 必须在目标 Dataverse 环境的 MCP allow-list 中显式启用，否则 Dataverse 直接拒绝 /api/mcp 调用。

  • 位置 — Power Platform admin center → Environments → 选择环境 → Settings → Product → Features → Dataverse Model Context Protocol → Advanced Settings。
  • 默认条目 — Microsoft Copilot Studio client、Microsoft GitHub Copilot client、Dataverse CLI client（app ID 0c412cc3-0dd6-449b-987f-05b053db9457）。Copilot Studio 默认启用，其他默认关闭。
  • 前置条件 — 环境必须是 Managed Environment；操作者必须有 Power Platform administrator 角色。
  • 作用范围 — 只对 /api/mcp 入口生效，不影响 MCP 命名的 Custom API（后者按普通 Dataverse API 走原有权限）。

02 / Scenario Matrix

三类跨租户场景的能力边界

把「Copilot Studio 在租户 A，要调 Dataverse MCP 在租户 B」按云分布拆为三类。下表给出各层是否成立的判定，后续章节展开同云跨租户（§03）和跨云（§04）。

判定按四层展开：Entra 身份联邦是否可建立、Dataverse 端点是否可被 Commercial Copilot Studio 直接拨号、PPAC allow-list 是否提供管控位、整链是否走得通。

场景 Entra B2B 身份层 MCP 端点可达性 PPAC Allow-List 整链结论
Global 租户 A → Global 租户 B 支持 同云内可达 在 B 环境配置 可配置（§03）
Global → GCC / GCC High B2B 可建立 跨云隔离 允许配置但不可达 不支持（§04）
Global → 21Vianet（China） 需启用 Microsoft cloud settings sovereign URL 可达 在 21V 环境配置 实测可通（§4.4）

「支持 B2B 身份层」不等于「Copilot Studio 能调通 MCP」。下两章分别给可行场景的步骤和不可行场景的根因。

Microsoft Entra 的「Microsoft cloud settings」明文允许 Commercial × 21Vianet、Commercial × Government 两对跨云 B2B；但 Power Platform 服务部署是按云独立的，Copilot Studio Commercial 的连接器栈不会主动尝试解析 .crm.dynamics.cn 这类 sovereign 主机。

01

身份联邦支持

Commercial 与 21Vianet 通过 Microsoft cloud settings 互加 tenant ID 后，用户可被作为 guest 邀请到对方租户；但 B2B Direct Connect 在跨云场景明确不支持。

02

数据面物理分离

Power Platform 和 Dynamics 365 apps 在 China 由 21Vianet（Shanghai Blue Cloud Technology）作为本地运营方独立运营，与 Commercial 是「physically separated environment」。

03

连接器栈分云部署

Copilot Studio 通过 Power Platform connectors 接 Dataverse MCP；连接器运行在云本地的 Power Platform 实例中，没有官方的跨云路由把 Commercial 调用转译到 China cloud。

03 / In-Cloud Cross-Tenant Runbook

操作 Runbook：同云跨租户配通步骤

当两个租户位于同一 Microsoft 云（两个 Commercial、两个 21V、或两个 GCC 租户），按以下 5 个阶段顺序执行。Phase 0 是不可跳过的前置；Phase 1–2 双方各做一半；Phase 3 做验收；Phase 4 做回滚排错。§3.6 给出 OAuth Manual 6 项字段速查表。

先对完这 6 项，再进入配置动作。缺一项，后面都会卡在注册、授权、allow-list 或连接阶段。

01

同一云域

双方租户必须同处 Commercial、21V 或 GCC 的同一云。跨云场景直接跳到 §04，不要进 §03。

02

Managed Environment

目标 Dataverse 环境必须是 Managed Environment，否则 PPAC 中不会出现 Dataverse Model Context Protocol 开关。

03

管理员权限

目标方至少具备 Entra Application Admin 与目标环境 System Administrator；来源方至少是 Copilot Studio Maker。

04

跨租户身份

来源方实际操作者必须已在目标租户中作为 B2B guest 或原生用户存在，并且可登录目标租户。

05

许可与容量

来源方有 Copilot Studio 可用容量；目标方用户在 Dataverse 环境中有对应安全角色，不是“能登录就够了”。

06

基础信息互换

目标方知道来源方使用者 UPN；来源方知道目标 Org URL 与目标租户 tenant ID，后续 callback 回填有对接人。

Step 1A / Registration

注册页先把 Multitenant App 建出来

目标方先在自己的租户里创建一个 multitenant Entra app。这个 app 后面既是 OAuth Manual 的 client ID，也是 Dataverse MCP allow-list 要放行的主体。

  • 入口 — Entra 管理中心 → Identity → Applications → App registrations → New registration。
  • 关键参数 — Name = Dataverse MCP Bridge for {SourceTenantName}；Supported account types = Multiple Entra ID tenants。
  • 注意事项 — 二级单选优先选 Allow all tenants；先把应用注册成功，再用环境 allow-list 和安全角色做边界控制。
  • 完成判据 — 点击 Register 后成功进入应用详情页，没有被 Preview 的 allowed tenants 面板卡住。
Step 1B / Overview

注册完成后马上回看 Overview

应用一旦建好，第一时间在 Overview 里记录两项最关键的 ID。后面 Phase 1 的 allow-list 和 Phase 2 的 OAuth Manual 都要用到。

  • 入口 — 应用注册完成后落在 Overview；如不在该页，手动点左侧 Overview。
  • 必须记录 — Application (client) ID 与 Directory (tenant) ID。
  • 交付对象 — 这两个值后面都要发给来源租户的 Copilot Studio 配置人。
  • 注意事项 — 对外发布截图时要遮挡具体 ID，公开版不应暴露真实值。
Step 2A / API Permissions

从默认权限页进入 Dataverse 授权流程

应用刚创建出来通常只有 Microsoft Graph / User.Read。这不是问题，真正需要补的是 Dataverse MCP 所需的 delegated permission。

  • 入口 — 左侧 API permissions → 左上角 Add a permission。
  • 当前状态 — 页面只显示 User.Read 很正常，说明还没加 Dataverse 权限。
  • 下一步目标 — 进入 Microsoft APIs，继续寻找 Dynamics CRM。
  • 完成判据 — 成功打开右侧的 Request API permissions 侧栏。
Step 2B / Dynamics CRM

在侧栏里继续向下找 Dynamics CRM

21V 门户这里最容易误判：第一屏并不会把 Dynamics CRM 直接露出来，所以很多人以为该 API 不存在。

  • 关键动作 — 保持在 Microsoft APIs tab 内，向下滚动找到 Dynamics CRM。
  • 权限选择 — 进入后选 Delegated permissions → 勾选 mcp.tools → Add permissions。
  • 管理员动作 — 回到权限主页后点 Grant admin consent for {tenant}。
  • 注意事项 — 不要先切到 APIs my organization uses，这次实操里那一页是空的。
  • 21V 差异（实测） — Azure China 门户下对应服务名为 Common Data Service（well-known appId 00000007-0000-0000-c000-000000000000），Delegated permissions 仅暴露 user_impersonation。21V Dataverse /api/mcp 入口不要求 mcp.tools claim，user_impersonation 即可通过；完整 Global → 21V 路径见 §4.4。
Step 3 / Client Secret

创建 Client Secret，并且当场保存 Value

OAuth Manual 最终要吃的是 secret value，不是 secret ID。这个值在 Azure 门户只显示一次，所以这一页不是“回头再看”的步骤。

  • 入口 — 左侧 Certificates & secrets → Client secrets → New client secret。
  • 建议写法 — Description 写清来源租户或用途，避免后面多个 secret 混在一起。
  • 注意事项 — 页面生成后必须立即复制 Value，不要只记 Secret ID。
  • 完成判据 — 已把 secret value 安全保存，并能与 client ID 一起交付给来源方。
Step 4 / Allow-List

在目标环境 allow-list 里显式放行这个 App ID

应用注册成功并不等于 Dataverse MCP 能放行。真正控制 /api/mcp 是否接受调用的，是环境级 allow-list。

  • 入口 — PPAC → Environments → 目标 Environment → Settings → Product → Features → Dataverse Model Context Protocol → Advanced Settings，跳转到模型驱动表 allowedmcpclient（URL {org}/main.aspx?...&etn=allowedmcpclient）。
  • 填写字段 — Name（自由文本，便于识别，如 Wells Dev 21V Dataverse MCP Test）；Unique Name（必须带 publisher prefix，如 crf5c_21vdataversemcptest，否则保存报 must start with a valid customization prefix）；Application Id = Step 1B 的 client ID；Is Enabled = Yes。
  • 注意事项 — 目标环境必须已是 Managed Environment；Unique Name 的 prefix 取自该环境默认 publisher 或 maker 自定义 publisher。
  • 完成判据 — 新条目保存成功并出现在 Active Allowed MCP Clients 视图，Application ID 与 Entra 应用完全一致。
Step 5 / Guest Authorization

把来源方使用者绑到最小权限安全角色

OAuth 拿到的是用户委托 token，但最终这个用户能读什么、写什么，还是由目标 Dataverse 环境里的安全角色决定。

  • 入口 — 目标环境 → Settings → Users + permissions → Users。
  • 关键动作 — 找到来源方 UPN 对应的 guest 用户 → Manage security roles → 绑定最小权限 role。
  • 注意事项 — 不要图省事直接给 System Customizer 之类高权限角色。
  • 完成判据 — guest 用户能看到目标环境需要暴露的表，但没有多余写权限。
Step 6 / Handoff

把来源方真正需要的 4 项交付物一次发全

如果目标方交付不完整，来源方在 Copilot Studio 里会不断来回补字段。最省事的做法是这里一次性交齐。

  • 必须交付 — Application (client) ID、Client secret Value、Directory (tenant) ID、目标 Dataverse Org URL。
  • URL 格式 — 必须是 https://{org}.crm.dynamics.com 这一层 org host，不是 PPAC 地址。
  • 交付对象 — 直接交给来源租户中负责 Copilot Studio MCP 向导的人。
  • 完成判据 — 来源方不需要再回头追问“还缺哪一个字段”。
Deliverables

来自 Step 1B 的 Application (client) ID。
Tenant ID
来自 Step 1B 的 Directory (tenant) ID。
Secret + Org URL

Step 1 / Open MCP Wizard

从 Agent 的 Tools 面板进入 MCP 向导

来源方所有动作都从 Agent 的 Tools 面板开始。这里决定你走的是“自带 Entra 应用的通用 MCP”路径，而不是内置 Dataverse MCP Server。

  • 入口 — Copilot Studio → 选 Agent → Tools → Add a tool → New tool → Model Context Protocol。
  • 关键判断 — 当前目标是“连到外部租户的 Dataverse MCP endpoint”，不是“连到自己租户的 Dataverse”。
  • 注意事项 — 不要点 catalog 里的「Dataverse MCP Server」；那条路径只能指向本租户环境。
  • 完成判据 — 进入新建 MCP server 的向导页，而不是 Dataverse 内置连接器详情页。
Step 2 / Server Basics

先把 MCP Server URL 填对

这一页的重点只有一个：连接必须打到目标 org 的 /api/mcp。最多人犯的错，是把 PPAC 地址、租户首页，甚至环境列表页 URL 填进去。

  • Server name — 自定义即可（CS 后台会以正则校验生成 connector 唯一名，仅接受字母数字 / - / _ 且首字符为字母数字，空格/括号/中文会触发 HTTP 400），例如 21V Dataverse MCP。
  • Server URL — Commercial 目标填 https://{target-org}.crm.dynamics.com/api/mcp；21V 目标填 https://{target-org}.crm.dynamics.cn/api/mcp（本次实测：https://coe.crm.dynamics.cn/api/mcp）。
  • 注意事项 — URL 必须落在目标 org host，末尾必须显式带 /api/mcp；不要填 PPAC / make.powerapps 入口。
  • 完成判据 — 基础信息页能顺利继续，不是因为 URL 基础格式错误而被拦住。
Step 3 / OAuth Manual

按 3.6 速查表填写 6 个 OAuth 字段

这一步不需要猜，也不应该猜。所有输入都来自目标方交付物，尤其是 tenant ID、secret、scope 格式，只要有一个写错就会出现 token 或 refresh 异常。

  • 必填来源 — Client ID、Client secret、Directory (tenant) ID、Org URL 全都来自目标方。
  • 最容易漏 — Scopes 必须包含 offline_access，否则 60–90 分钟后会强制重新登录。
  • 不要自己拼 — Authorization / Token URL 直接按 §3.6 模板替换 tenant ID，不要写成通用 login URL。
  • 完成判据 — 6 个字段填完后能进入 Create 阶段，不出现明显的字段级格式报错。
Step 4 / Callback URL

Create 后立刻把 callback URL 回填给目标方

Copilot Studio 只有在创建连接动作发生后，才会吐出 callback URL。目标方必须把这条 URL 加进应用 Redirect URI，否则授权完成后一定会 404 或 redirect_uri_mismatch。

  • 动作顺序 — 点 Create → 复制 callback URL（形如 https://global.consent.azure-apim.net/redirect/{connector-hash}，跨云时同样在 Commercial APIM 域）→ 发给目标方。
  • 目标方动作 — 目标方在 Entra 应用的 Authentication → Web → Redirect URIs 中保存这条 URL。必须先回填再点 Create connection，否则 OAuth 弹窗会以 redirect_uri_mismatch 拒绝。
  • 浏览器 — Create connection 会以 window.open 弹子窗，浏览器需放行 copilotstudio.preview.microsoft.com 的弹窗；自动化场景无法完成同意握手。
  • 完成判据 — 两侧都完成保存后，再继续下一步建连接。
Step 5 / Connection + Agent

建立连接，并把 MCP 工具真正挂进 Agent

到这一步，来源方才会以 guest 身份跳到目标租户完成 consent。授权成功后，还要把连接挂进 Agent，最后确认 Agent 的编排模式。

  • 连接动作 — Next → Create new connection → 浏览器跳目标租户登录页 → 用准备好的 B2B 身份登录并同意。
  • 加入 Agent — 授权成功后点 Add to agent。
  • 最后检查 — Agent → Overview 确认 Generative orchestration 已开启。
  • 完成判据 — Agent 测试面板里能看到 MCP 工具被正常调度，而不是一直留在连接状态未挂载。
Validation 1 / Connectivity

先验证 MCP 调用是否真的打到目标环境

第一项不要做复杂动作，先确认最基本的连通性。只要这里不通，后面所有权限和写入验证都没有意义。

  • 测试动作 — 在 Copilot Studio 的 Test your agent 面板输入「list tables in Dataverse」。
  • 期望结果 — 返回的是 目标环境 的表列表，而不是来源租户本地环境的表。
  • 注意事项 — 如果返回空或返回错环境，先回查 Server URL 与 allow-list。

确认写操作确实归到目标租户里的 guest 身份

  • 测试动作 — 用 MCP 工具创建一条测试记录。
  • 核对位置 — 到目标环境 Auditing 查看 Modified By。
  • 期望结果 — Modified By 等于准备好的 B2B guest UPN。

Validation 3 / Boundary

故意降权限，确认边界真的生效

最可靠的安全验证，不是“它能写”，而是“我收回写权限后它立刻不能写”。这一步验证的是角色边界是否真实生效。

  • 测试动作 — 临时把 guest 安全角色降为只读，再调 create_record。
  • 期望结果 — 应返回 403 / Insufficient privileges。
  • 注意事项 — 验证完要恢复原角色，避免影响正式使用。
Pass Signal

“能失败”才说明边界有效

Pass
降权后立刻收到权限不足错误。
Fail
降权后依旧能写，说明角色配置过宽。
Validation 4 / Refresh

等待一轮 token 周期，确认 refresh 正常

很多连接第一次能通，但 1 小时后就掉。第四项验证的是 refresh token 路径，核心看点是你有没有把 offline_access 配对。

  • 测试动作 — 等待 60–90 分钟后再次发起 MCP 请求。
  • 期望结果 — 能自动续期，不弹登录页。
  • 注意事项 — 如果重新要求登录，优先回查 scope 是否缺少 offline_access。
Pass Signal

自动续期才算真的可用

Pass
二次调用直接成功，不要求再次登录。
Fail
强制回到登录流程，通常是 scope 配置不完整。
Error 1 / 401

401 或 Insufficient privileges

这类问题通常不是 OAuth 字段本身错了，而是目标环境还没有真正放行这个应用，或者 guest 用户没有对应表权限。

  • 先查 allow-list — 回到 §3.2 Step 4，确认启用的是正确的 Application ID。
  • 再查安全角色 — 回到 §3.2 Step 5，确认 guest 用户确实被绑定了需要的 role。
  • 判断顺序 — 401 更偏 allow-list / token；403 更偏 role / privilege。

优先回查目标租户两道门

Error 2 / Register Disabled

Register 按钮灰掉，提示缺少 allowed tenant

这不是账号权限问题，而是你选了 Allow only certain tenants (Preview) 但没有把来源租户加进 allowed list。

  • 症状 — 提示 At least one allowed tenant is required。
  • 两种处理 — 要么点 Manage allowed tenants 输入来源 Tenant ID 后 Apply；要么改选 Allow all tenants 先注册。
  • 推荐处理 — 首次配通优先用 Allow all tenants，边界靠 allow-list + role 兜底。
Fast Fix

别在注册页提前做过度收紧

Fastest Path

Strict Path
只有在你已经掌握来源 tenant ID 时，再用 Preview 选项。
Error 3 / No Consent

外租户用户看不到同意页

最常见原因是应用仍然是 single-tenant。这样外租户用户即使拿到了 URL，也不会被允许进入授权流程。

  • 回查位置 — §3.2 Step 1A 的 Supported account types。
  • 正确值 — 必须是 Multiple Entra ID tenants。
  • 错误值 — Single tenant only 会直接拒绝外租户用户。
Root Cause

这是 app registration 级别的路由问题

Fix
回到注册配置，把应用改成 multitenant。
Why
single-tenant app 根本不会接受外租户用户授权。
Error 4 / Callback

Callback 404 或 redirect_uri_mismatch

这种错误不要怀疑 token endpoint，先看 Redirect URI 是否原样回填。这里最怕人为修改大小写、删尾部路径、或者加错 slash。

  • 回查位置 — §3.3 Step 4 拿到的 callback URL 原文。
  • 正确做法 — 整条复制到目标方应用的 Redirect URI，不做手改。
  • 注意事项 — 含末尾路径、斜杠、大小写都必须完全一致。
Root Cause

这是字符串精确匹配，不是“差不多就行”

Fix
重新复制 callback URL，整条覆盖 Redirect URI。
Typical Mistake
省略尾部路径、手动改 slash、复制错环境 URL。
Error 5 / No Tool Call

这类问题通常不在连接本身，而在 Agent 的编排模式。连接存在不等于 Agent 一定会自动调用 MCP 工具。

  • 回查位置 — Agent → Overview。
  • 正确状态 — Generative orchestration 已开启。
  • 常见误区 — Classic 模式下连接和工具都在，但编排器不会自动调度。
Root Cause

这不是权限错，是编排模式错

Fix

Signal

04 / Cross-Cloud Boundary

跨云跨租户：Global → 21V 实测可通与三项差异

Global Commercial × 21Vianet 在 §3 同云路径之外有三项差异：Authority 在 partner 云、Common Data Service 只暴露 user_impersonation、allow-list 在 Dataverse allowedmcpclient 表里手建。本节给出可复现的完整路径与 2026-05 实测证据。

跨云不只是「换个域名」，三个层面均与同云不同，但每一层都有对应的可执行动作。

01

Authority 不同

21Vianet 的 Entra 授权端点是 login.partner.microsoftonline.cn，与 Commercial 的 login.microsoftonline.com 是两套独立目录。实测动作：在 21V 租户独立注册 Entra 应用，OAuth Manual 填 sovereign authority。

02

资源端点不同

21Vianet Dataverse 走 *.crm.dynamics.cn，只接受由 partner authority 颁发、audience 为该 China org 的 token。实测动作：Scopes 填 https://{org}.crm.dynamics.cn/.default offline_access。

03

Allow-list 入口不同

PPAC Features 上的「Advanced Settings」跳转到模型驱动表 allowedmcpclient，需手建记录并填调用方 client ID，Unique Name 必须带 publisher prefix（如 crf5c_）。

上面三个差异叠加后，实际走通需严格按以下顺序。任一项错位都会表现为「连接看起来建好了但 /api/mcp 报 401/403」。

  1. 21V 侧先完成身份与允许

    在 21V 租户注册多租户 Entra 应用 + Common Data Service / user_impersonation + client secret；以 publisher prefix 在 21V Dataverse allowedmcpclient 表里建一条 Is Enabled = Yes 的记录，填上该 app ID。

  2. Commercial CS 填 sovereign OAuth Manual

    Authority 填 login.partner.microsoftonline.cn/{21V-tenant-id}，Scopes 填 https://{org}.crm.dynamics.cn/.default offline_access，Client ID/secret 用 21V 侧发过来的值。名称需符合后台正则（仅字母数字 / - / _，首字符为字母数字）。

  3. Redirect 回填后再点 Create connection

    CS Create connector 后生成 https://global.consent.azure-apim.net/redirect/{hash}，必须先作为 Web Redirect URI 保存到 21V 应用注册，再点 Create connection。浏览器弹窗需放行 copilotstudio.preview.microsoft.com。

记在案的风险：跨云 OAuth 回跳跳出 sovereign 云，打到 Commercial APIM 域，Conditional Access 严格或企业出口网关拦截 sovereign authority 回跳时仍会失败；调用以用户委托身份发生，跨云数据交互需自行评估 PIPL / 数据出境、跨境传输合规。

本文仅实测了 Commercial → 21Vianet 路径。类推到 GCC / GCC High / DoD 需同时满足三个条件：目标云提供对应的 sovereign authority（如 login.microsoftonline.us）、目标 Dataverse 环境启用 Dataverse MCP 且 allowedmcpclient 表可写入、企业 CA 及出口网关放行 Commercial APIM 回跳。未实验证之前不作成败断言。

2026-05 实测：Commercial Copilot Studio Preview（环境 Wells Dev）调用 21Vianet 租户 illusion615.com 下 https://coe.crm.dynamics.cn/api/mcp，全链路走通、Agent Tools 列表出现 Model Context Protocol (1)。同云路径以外需额外完成三件事：(a) 在 21V 侧采用 Common Data Service / user_impersonation + .default scope；(b) 在 21V Dataverse allowedmcpclient 表里手建一条带 publisher prefix 的允许记录；(c) 把 CS 生成的 Commercial APIM 回跳 URL 回填到 21V 应用注册。

7 项与同云路径不同的实测发现：

  1. F1 · CS 向导不校验 sovereign host

    Commercial Copilot Studio「Add MCP」向导对 Server URL 主机不做云校验，https://*.crm.dynamics.cn 直接通过，Create 按钮可点。

  2. F2 · OAuth 现暴露 3 个子类型

    OAuth 2.0 下拉新增 Dynamic discovery / Dynamic / Manual。前两者要求 server 公开 metadata 端点；跨租户/跨云只有 Manual 能填全 sovereign 端点。

  3. F3 · 21V SP 名称不同

    Azure China 门户里对应服务名是 Common Data Service（well-known appId 00000007-0000-0000-c000-000000000000），不是 Commercial 的 Dynamics CRM。在 21V 找不到 Dynamics CRM 时去搜 Common Data Service。

  4. F4 · 21V 不发布 mcp.tools，但端点不要求

    21V Common Data Service 的 Delegated permissions 列表里只有 user_impersonation，没有 mcp.tools（见 step-05）。实测表明 21V /api/mcp 不要求 token 携带 mcp.tools claim：Scopes 填 https://{org}.crm.dynamics.cn/.default offline_access 后即可放行（.default 涵盖 user_impersonation）。这是 21V Dataverse 侧的实现差异，与同云 Commercial 路径需要 mcp.tools 不同。

  5. F5 · CS 连接器命名正则

    CS Manual OAuth Create 后台对 connector 名做正则校验：alphanumeric / - / _，必须以字母数字开头。空格、括号、中文都会触发 HTTP 400。本次名称填 21V Dataverse MCP，后台生成的 connector 唯一名为 crf5c-5f21v-20dataverse-20mcp-5f...（空格被转义）。

  6. F6 · Redirect URL 在 Commercial APIM 域

    CS Create 后自动生成的 Redirect URL 形如 https://global.consent.azure-apim.net/redirect/{connector-hash}，是 Commercial APIM 同意域。需在点 Create connection 之前回填到 21V 应用注册的「Authentication → Web → Redirect URIs」（step-12），否则 OAuth 弹窗以 redirect_uri_mismatch 拒绝。

  7. F7 · 浏览器同意弹窗易被拦

    CS Create connection 触发的是 window.open 子窗口；浏览器需放行 copilotstudio.preview.microsoft.com 的弹窗才能完成握手，自动化/身份托管场景无法代走这一步。

F8 · 环境级 Allow-List 需手建带 publisher prefix 的记录：21V Dataverse allowedmcpclient 表里默认只有 Microsoft first-party 三条；要让自定义 multitenant app 调用 /api/mcp，必须在该表 + New 一条记录，填 Name、Unique Name（必须带 publisher prefix 如 crf5c_，否则保存报 must start with a valid customization prefix）、Application Id、Is Enabled = Yes。本次实测记录 crf5c_21vdataversemcptest / app 5581c024-... / Yes 保存成功后，/api/mcp 立即接受调用。

Evidence 05 · Scope Inventory

21V Common Data Service 的 Delegated 权限列表只暴露 user_impersonation

这是 21V 与 Commercial 同云路径的关键差异。Commercial 同云租户里 Dynamics CRM 的 Delegated 权限有 user_impersonation 与 mcp.tools 两项；21V 这边筛选框输入 mcp 后无任何匹配，目录里彻底没有 mcp.tools。

  • 资源服务 — Common Data Service（appId 00000007-0000-0000-c000-000000000000）。
  • 暴露范围 — 仅 user_impersonation（Access Dynamics 365 as organization users）。
  • 应对 — Copilot Studio Scopes 填 https://{org}.crm.dynamics.cn/.default offline_access；.default 已涵盖 user_impersonation，不需也无法补 mcp.tools。实测表明 21V /api/mcp 不要求 mcp.tools claim。
Evidence 06–07 · Configured + Consent

把唯一可选的 user_impersonation 加上、并完成 admin consent

21V 侧在创建应用后把 Common Data Service / user_impersonation 加进配置权限，并由租户管理员 Grant admin consent for {tenant}，状态列全绿勾。这是 OAuth 能颁发 token 的前提。

Evidence 08–09 · Client Secret

给 21V 应用建一个 Client Secret，并当场记录 Value

OAuth Manual 在 Commercial CS 端要填 client_secret value。21V 端的 Certificates & secrets → New client secret 流程与 Commercial 一致；生成后 Value 列只显示一次。本次实测以 Description cs-to-21v-dataverse-mcp 创建，过期日按企业最短可接受周期设置。

Evidence 10–11 · CS Wizard

CS 向导接受 sovereign URL，向导后台对名称做正则校验

Server URL 填 https://coe.crm.dynamics.cn/api/mcp、Authority 填 https://login.partner.microsoftonline.cn/{21V-tenant-id}、Scope 填 https://coe.crm.dynamics.cn/.default offline_access，向导 Create 直通。名称填中文或含空格会被 HTTP 400 拒绝（F5）；本次填 21V Dataverse MCP 后后台生成的 connector 唯一名为 crf5c-5f21v-20dataverse-20mcp-5f...，对应的 Redirect URL 在 global.consent.azure-apim.net 域。

Evidence 12 · Redirect URI

跨云 callback 域要在 sovereign 租户里登记

把 CS 自动生成的 https://global.consent.azure-apim.net/redirect/{hash} 回填到 21V 应用 Authentication → Add a platform → Web → Redirect URIs。这一步是为了让 21V 授权服务在用户同意后允许把 code 跳回 Commercial APIM。必须在 CS Create connection 之前完成保存，否则同意弹窗会以 redirect_uri_mismatch 拒绝。

  • 记录顺序 — CS 侧 Create connector → 复制 Redirect URL → 21V 侧应用保存 Web Redirect URI → CS 侧点 Create connection 跳 OAuth 同意。
  • 风险 — 跨云 DNS / TLS 回跳不在文档 SLA 范围内，严格 CA 或企业出口网关可能拦截 Commercial APIM 域的回跳。

综合判定：Global → 21V 在 Copilot Studio Preview 中可复现走通。需同时满足：(1) 21V 应用注册走 Common Data Service / user_impersonation + admin consent + client secret；(2) 21V Dataverse allowedmcpclient 表里存在带 publisher prefix、填入调用方 client ID 且 Is Enabled = Yes 的记录；(3) CS 生成的 Commercial APIM Redirect URL 在 Create connection 之前已写入 21V 应用 Authentication；(4) 浏览器与企业 CA 放行 copilotstudio.preview.microsoft.com 弹窗与 global.consent.azure-apim.net 回跳。Scope 使用 .default offline_access 即可被 21V /api/mcp 接受，无需 mcp.tools。跨境数据交互的 PIPL / 数据出境合规需自行评估，详见 §06 治理层。

05 / Alternative Paths

跨云场景的替代路径

§04 的实测路径技术上可走通，但跨境数据交互、CA 放行 sovereign 回跳、弹窗策略都不属于文档 SLA。生产承诺前可考虑以下三条替代路径，按「合规优先 → 工程量低 → 用户体验」依次列出，选哪条取决于谁是主使用者、数据是否允许离开 sovereign 云。

把 Copilot Studio Agent 直接在 21Vianet 或 GCC 的 Power Platform 实例里构建，使用本云内置 Dataverse MCP 连接器，再通过本云原生的发布渠道触达用户。这是合规与稳定性的默认解。

  • 身份 — 用户必须在目标云租户内有原生或 B2B guest 身份。
  • 许可 — 需要在目标云分别采购 Copilot Studio 许可（China 价目独立、由 21Vianet 销售）。
  • 渠道 — Teams、Web 渠道在 China 云独立提供；跨云分享 Agent 链接需要再走 cross-cloud B2B。
  • 合规收益 — 数据始终留在 sovereign 云，符合「Customer data is stored at rest within the geography」承诺。

在客户自己的网络部署一个标准 MCP server（如基于 Microsoft 官方 SDK），由它在后台以 21Vianet 租户的服务主体身份调 Dataverse Web API，再通过公网把 MCP 协议暴露给 Commercial Copilot Studio。

  1. 身份

    在 21Vianet 注册 daemon 应用 + Application user，由代理用 client credentials 直接拉 Dataverse。注意此时所有调用以服务身份发生，丢失 per-user 审计。

  2. 协议

    代理对外发布 Streamable HTTP transport（Copilot Studio 2025-08 起仅支持 Streamable），URL 公网可达且具备 TLS 证书。

  3. 认证

    对 Commercial Copilot Studio 暴露 OAuth 2.0 或 API key 鉴权，由代理决定谁能进。这一层与 21V 内部身份完全脱钩，等于绕过了 Dataverse MCP allow-list 的天然管控。

  4. 风险

    需要专门评估：跨境数据传输合规、服务身份的权限最小化、代理本身的审计与告警、TOS 是否允许这种二次分发。中国法律层面对跨境数据出境（PIPL / 数据出境安全评估）有硬约束，必须先合规再实施。

对「集中分析」类需求，可以把跨云数据先按合规要求 ETL 到 Commercial 侧的 Dataverse / Fabric / SQL，由 Commercial Copilot Studio 走本租户内置 MCP 访问。这条路径不解决「实时跨云调用」，但解决「跨云洞察」。

  • 定位 — 用于报表、跨地区合并分析、Agent 问答历史快照；不适合写操作或需要实时一致性的场景。
  • 合规 — 出境数据范围需提前过合规、签 SCC、做数据出境安全评估；Sensitive 字段需脱敏。
  • 工程 — 用 Dataverse 长轮询、Synapse Link、Fabric Mirroring 等已成熟的同步路径，不要自己造轮子。
Layer 2 · 治理层 · 管理员 / 安全合规关注

06 / Governance Layer

治理层：管理员发布前对齐清单

本节面向 Power Platform 管理员、安全与合规角色。Maker 配通（§03）后，发布到生产前必须由管理员把以下三个治理位逐条对齐，避免 PoC 通过后被合规审核拦截。如果只是开发测试，可以先跳过本节回到 §03。

MCP server 通过 Power Platform connectors 接入，意味着 DLP（数据丢失防护）策略对 MCP 工具同样生效。规划时必须把 MCP 的 connector 单独放入策略组评估。

  • 分组 — 自定义连接器（包含 §03 注册的 OAuth Manual MCP 连接器）默认为 non-business；明确归入 business 或 blocked 之前不要发布。
  • 跨组流 — DLP 默认禁止 business 与 non-business 数据在同一 Agent 中流转；MCP 工具与其他 connector（如 Mail Send、SharePoint）混用时会被拦截。
  • 环境作用域 — DLP 策略可按环境授予，跨租户场景下两侧管理员都要确认自家策略不会拒绝该 connector。

跨租户场景下，「外部应用 + 委托权限」叠加「目标环境安全角色」共同决定可见数据范围，任何一层失控都会放大风险。

  • 应用权限范围 — 仅授予 Dynamics CRM/mcp.tools delegated 权限；不要顺手开启 user_impersonation 等高权限 scope。
  • Admin consent — 由目标租户管理员显式 Grant admin consent，避免每个用户都跳出同意页。
  • 安全角色 — 在目标 Dataverse 环境内单独建一个最小权限的 Security Role 绑给跨租户用户，不要复用 System Customizer 之类的高权限角色。
  • Secret 轮换 — Client secret 必须按企业策略轮换；建议改用 Certificate credential，统一通过 Entra 应用 manifest 管理。

跨租户调用要能在事后被追溯到某次具体的用户会话、某个 MCP 工具调用、某条 Dataverse 修改记录。

  • Copilot Studio 侧 — Agent 的 Analytics + Conversation transcripts 能看到 MCP 工具调用次数与参数，留存期取决于环境配置。
  • Dataverse 侧 — 启用 Auditing on entities；对 create_record/update_record/delete_record 工具，目标环境的 audit log 会记录 Modified By（guest 用户）和具体字段变更。
  • Entra 侧 — Sign-in logs 显示自定义应用的 OAuth 授权与 token 颁发，可用于异常 token 使用追溯。
  • 跨云路径 B 额外 — 自托管代理要自带 request/response 日志、调用方身份映射，并按法律保存期归档。
