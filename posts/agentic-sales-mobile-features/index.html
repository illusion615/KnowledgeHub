功能设计 · 业务视角

数据为基，目标为向：一套 Purpose-Driven 的销售 CRM

这是本应用的功能设计文档。第一章先定义所有功能必须遵循的设计哲学，后续章节再从业务视角说明应用提供哪些功能域、每个域的触发场景、输入与产出、以及必须遵守的业务规则。它与「架构设计文档」从技术视角讲 Frame + Orchestrator 如何实现，构成业务 / 技术一对。

先看设计哲学 看跨切底座
核心观点

在数据驱动的 CRM 里，录入成本落在一线销售，而分析价值多半需要额外查询、且偏于事后复盘；Purpose-Driven 让 AI 从两头缩短这段距离——录入端把一句话变成结构化记录、省掉填表，产出端在数据之上即时给出对目标的判断。销售因此成为数据的即时受益人。

这一转变不取代数据，而是给数据装上方向：输入侧把录入成本压到一句话、一段语音，输出侧让每条记录当下回流成离成交更近的下一步。

  • 1数据退回手段，目标成为主线：CRM 不再以攒数据为目的。
  • 2两头都让销售获益：录入端一句话代替填表省力，产出端录入即回报。
  • 3AI 只说增量、且可信赖：给销售没注意到的信号，并且有据可查。

01 / Design Philosophy

Beyond Data-Driven，迈向 Purpose-Driven CRM：数据为基，目标为向

数据驱动是 CRM 的地基，它让客户关系第一次变得可存、可查、可分析——这一步不可或缺，也从未过时。只是在实践中存在一个不对等：录入发生在拜访现场、成本由一线销售承担，而数据的分析价值多半需要额外查询才能取出、且往往偏于事后复盘。AI 不是取代数据驱动，而是让它进化——在这块地基上，把数据在录入的当下就翻译成对目标的判断：谁该被关注、为什么、下一步做什么。以下原则分两组：输入侧让数据更轻松地沉淀，输出侧让数据回流成离成交更近的一步；它们是后续所有功能域的共同约束。

过去 · Data-Driven

CRM 以数据为中心：销售把客户关系拆成字段填进系统，是主要的数据贡献者；而数据变成判断需要额外查询与汇总，价值兑现偏晚、多服务于管理复盘。

进化 · Purpose-Driven

CRM 以目标为向：数据退回手段的位置，AI 在数据之上即时产出对目标的判断与下一步建议。销售录入的每一条，都在当下回流成对自己有用的行动——他从数据的贡献者，同时成为数据的即时受益人。

01

Mobile-First，不是桌面缩小版

设计起点是单手、户外光线、30 秒内完成。长表单不能成为主路径，超过三屏的录入必须由对话、草稿或分步确认承接。

02

Voice-First，键盘是 fallback

拜访间隙最自然的输入是语音。功能必须允许用户用一句话表达意图；键盘用于修正、补充与语音失败后的兜底，而不是第一入口。

03

Confirm，Don't Configure

AI 负责把自然语言塑成草稿，用户负责确认、微调或拒绝。所有写入型功能必须先展示可核对草稿，不能把配置项和字段选择推回给销售。

04

意图编排，不是菜单导航

用户说业务意图，系统决定落到哪个功能域；新增能力应通过注册新的意图/技能扩展，而不是不断增加菜单层级。

05

即时闭环：录入即回报

数据与行动必须接成闭环，且足够及时。销售刚录入，下一步建议就要在当下回到眼前，而不是隔天报表。反馈越快，销售越认这个系统的价值；慢一拍，价值就流失。

06

增量价值：说他不知道的

输出必须是销售自己没注意到的信息——久未联系、信心下滑、被忽略的机会——而不是把他刚说的话复述一遍。只有产出增量判断，AI 才不会沦为可有可无的参考。

07

可信赖：有据可查，宁缺毋编

每条 AI 输出都应基于真实字段事实、可追溯来源、可被销售核对推翻；低置信时显式降级，而不是硬编一个看似确定的答案。这是把「参考」变成「可依赖」的唯一办法。

02 / Functional Overview

六个功能域 + 一个跨切底座

应用的全部能力归为六个功能域：四个「写」域负责把销售口述变成 CRM 记录（记录活动、客户联系人、商机、规划推荐里的排程），两个「读 / 呈现」域负责把数据变成判断（查询报表、主动呈现）。所有域共用一套跨切底座。下图先给出全貌，后续逐域展开，每域统一按「场景 → 输入 → 产物 → 业务规则」四要素说明。

03 / Write · Log Sales Activity

说一句话，代替填一张活动表

拜访、电话、会议、邮件——销售一天里最高频的动作就是记录这些触点。本域把一句口述变成一条正确归类、正确归档、（对未来活动）正确排程的活动记录，用户不必手选类型与状态。

要素说明
① 场景销售描述一次客户触点：「我拜访了……」「给张主任打了电话」「下周三约……」。
② 输入类型（拜访/会议→appointment，电话→phonecall，邮件→email）、具体标题（客户+主题+产品）、日期（解析「昨天/下周三」）、备注、关联的客户或商机。
③ 产物写入对应活动表，通过 regarding 绑定客户或商机；未来活动额外创建一条 Work IQ 日历事件。
④ 规则标题必须具体、绝不用通用名；客户名解析歧义则追问、无则问是否新建；所有权默认当前用户。

日期锚点是命门。模型必须知道「今天」才能把「下周三」换成具体日期。早期缺锚点时，标为「今天」的活动被臆造成错误年份、在当周视图里消失。当前在意图识别的提示词里显式注入今天的 ISO 日期与星期，并给出换算规则。

过去活动（statecode 1）

只写 Dataverse 记录，绝不创建日历事件——已经发生的事不该出现在未来日程里。

未来活动（statecode 0）

先用 Work IQ 日历查用户（及与会者）可用性：有时间则确认，冲突则提示并给最近空档；没给具体时间则推荐 2–3 个最佳时段让用户选。确认后同时写 Dataverse 记录与日历事件。

04 / Write · Accounts and Contacts

建客户、加联系人、挂到正确的客户名下

CRM 的根是客户主数据与人脉。本域处理客户组织与联系人的新建与更新，并保证每个联系人都挂到正确的父客户下——这是后续商机、活动能正确归集的前提。

要素说明
① 场景「新增一个客户：上海瑞金医院」「张主任是新来的心内科主任，挂到 Royal London 下」「更新某客户电话」。
② 输入先判断是「客户（组织）」还是「联系人（个人）」、是新建还是更新；客户取名称/电话/邮箱/行业/地址/备注，联系人取姓名/职务/电话/邮箱+父客户。
③ 产物客户写标准表 account；联系人写 contact 并用 parentcustomerid 绑定到父客户。
④ 规则联系人必先解析父客户：歧义则追问、不存在则先建客户；更新只发改动字段、先按名匹配现有记录；所有权默认当前用户。

05 / Write · Opportunity Management

开单、推进阶段、调整金额与信心

商机是销售管线的核心对象。本域负责开新单、推进阶段、改金额/信心、记阻塞点，并把口语里的金额与日期换算成结构化字段，关联到正确客户。

要素说明
① 场景「开一个 25 万的单，7 月底关」「把协和的单子推进到谈判阶段，信心降到 60」。
② 输入deal 名称（客户+产品）、金额（25万→500000、250k→250000）、阶段（prospecting/qualification/proposal/negotiation/won/lost 六选一）、信心 0–100、预计关单日期（ISO）、最近动作、阻塞点。
③ 产物写自定义表 crf5c_opportunity1，用 biz_Account 绑定到关联客户。
④ 规则命名已有单则更新、否则新建；更新只发改动字段；紧接活动而来的单复用该活动的客户、不再追问；「at risk」=信心 0–49，「active/pipeline」=阶段非 won/lost。

一句话两意图：当用户「新增客户 + 同一句里开单」时，按两个独立意图处理——先建客户，再把商机交给本域；这正是架构文档里 Frame 阶段拆意图的业务来源。

06 / Read · Query, Report and Plan

把数据变成判断：先报数字，再给清单或计划

光能写还不够，销售要随时问数、要被告知该做什么。本域覆盖两类「读」：查询报表回答「现在怎么样」，规划推荐回答「接下来做什么」——后者还能把建议直接转成排好期的活动。

要素说明
① 场景「这个月要关的单」「哪些单有风险」「今天的拜访」「我的管线怎么样」。
② 输入从问题里识别目标实体与过滤条件（关单日期区间、信心<50、阶段、本周日期、completed=statecode 1）。
③ 产物先给标题数字（条数/总额），再给紧凑列表或简短分析；活动查询合并 appointment+phonecall+email 按时间倒序。
④ 规则一律按当前用户过滤；多段报表是一个意图、合并作答；同会话可复用上次查询结果；绝不臆造记录或总额，只报工具返回的真实数据。
按信号排优先级

读当前用户的开放商机与近期活动，按「将到期、金额高、信心低/下滑、久无联系、有阻塞点」排序，产出当天/本周的少数高影响事项，每项=做谁、为何现在、建议动作。

建议可一键转排程

用户接受某条建议时，用 Work IQ 日历读取空闲、推荐 2–3 个最佳时段，再交给「记录活动」域写入 Dataverse 记录与日历事件。

规划只建议，不改单

规划推荐自身从不修改或关闭商机字段——那属于商机管理域；规划过程不写任何记录，只有用户确认某事项时才落库。

07 / Surface · Insights and Voice Briefing

不等用户问，应用主动把要点送上门

前面的查询规划要用户开口。本域是「呈现层」：把每日要点主动推到眼前，并在不便看屏幕时用语音读出来——让判断与提醒无需用户发起。

按现象→原因→行动结构生成

洞察由 LLM 生成，输入汇集高风险客户（附「上次联系天数」等事实）与管线数据，用资深销售教练的系统提示词，要求输出遵循「现象 → 原因 → 行动建议」三段结构，让每条洞察都可执行。

重新生成 = 先删本人旧、再批量建新

点「重新生成」时，先删除当前用户自己的旧洞察（所有者范围限定，不碰他人），再批量建新。删除按本人范围是数据保护，不是安全边界——安全由平台裁剪保证（见第 08 节）。

未读铃铛：浏览即标记

已读集合持久化在本地存储，未读数驱动铃铛角标。洞察被实际查看时触发回调写入已读，角标随之递减——已读状态是纯客户端 UI 偏好，不占数据库。

贯穿全部六域的三条共同规则

前六域各管一件事，但它们共享同一套底座：任何写入前先出草稿等用户确认、每个人只动自己的数据与偏好、安全交给平台而非客户端。这三条不属于某一个功能，而是所有功能成立的前提。

无论建客户、开单还是记活动，应用都先给一行草稿（写什么、关联谁），等用户确认后才落库。这让 AI 的解析结果在写入前可核对，是「可核对的销售动作」这一架构主张在每个功能里的落点。

不是所有设置都该跨设备同步。应用按作用范围把设置分两层：纯界面偏好留在本地，需要持久化或跨设备的应用级配置写进 Dataverse。

层 存储 用途
本地偏好 localStorage 纯客户端 UI 偏好，无需跨设备（如列表默认视图、Top-N 截断）。写入即派发事件，订阅组件即时刷新。
共享配置 crf5c_settings 需持久化/跨设备的应用级配置（如 Power Automate Flow URL、Copilot Studio Agent 名称），以键值 upsert 写入 Dataverse 设置表。

已移除的设置：失效的「卡片化组织数据」开关，以及与平台安全模型冲突的 adminMode 开关——后者是可被绕过的客户端标志，不构成真实安全，已整体删除。

代表看自己的、经理看团队的——这种差异不是靠界面开关实现的，而是平台按安全角色裁剪的结果。应用以直连绑定 + 委派用户身份运行，每个用户用自己的凭据访问数据，隔离归属一目了然。

操作 谁负责隔离 客户端动作
读取列表平台（安全角色裁剪）不加任何 owner 过滤
创建客户端落章写入所有者，保证归属正确
删除 / 重生成客户端仅删本人行（范围保护，非安全边界）

一条硬规则：严禁在客户端加「ownerid 等于当前用户」之类的过滤当作安全。数据已在浏览器里，客户端过滤不是安全；它还会在经理（团队/组织级可见）场景下错误隐藏本应可见的数据。差异化可见性靠 Dataverse 安全角色的访问级别（用户级 / 业务部门级 / 组织级）实现。
