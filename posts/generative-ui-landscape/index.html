Generative UI 全景

生成式 UI 全景：从设计时生成到运行时界面

生成式 UI（Generative UI）指由 AI 模型生成用户界面，而非由人手写固定界面。它包含两个层次：设计时生成（模型产出设计稿或前端代码，由人审校后部署）与运行时生成（模型在对话或请求中即时生成可交互界面）。2024 年 6 月 Claude Artifacts 把生成的界面带进对话窗口，2025 年 11 月 Google Gemini 3 的 Generative UI 把整张界面交给模型即时生成[1][4]。本文用三层范式梳理当前事实、代表产品与开放协议，并给出一张定位象限图。

核心观点

生成式 UI 的重心正从「设计时生成代码」向「运行时生成界面」迁移，可控性与一致性是落地的主要约束。

  • 1设计时层：v0、bolt.new、Lovable 把自然语言变成可部署的前端工程，人仍是发布前的审校者。
  • 2运行时组件层：Vercel AI SDK、Claude Artifacts、thesys C1 在对话中流式渲染组件，把文本回答升级为可交互控件。
  • 3运行时界面层：Gemini 3 Generative UI 与开源 A2UI 让模型对每个 prompt 即时生成整张界面，是当前最前沿的方向。
  • 4协议层：MCP、A2A、AG-UI、A2UI 四个开放标准正在把 Agent 与界面之间的连接标准化。

01 / 什么是生成式 UI

1. 定义：界面由谁生成，在什么时候生成

传统 UI 的形态在发布前就被人固定下来；生成式 UI 把「生成界面」这件事的一部分交给模型。区分两者的关键有两个：界面由谁产出（人 vs 模型），以及界面在什么时候被确定（设计时 vs 运行时）。读完本节，你能用这两个坐标给后文每个产品定位。

基线 · 传统 UI

人在设计时写死界面

设计师与工程师在发布前确定每一个屏幕、状态和分支。界面是静态资产：同一段代码对所有用户呈现相同结构，个性化靠预先写好的条件分支实现，模型（如果有）只填充数据，不改变结构。

新范式 · 生成式 UI

模型参与生成界面结构

模型根据 prompt、上下文或数据决定界面里出现哪些组件、如何排布。它可以发生在设计时（产出代码交人审校），也可以发生在运行时（对话中即时渲染，甚至整张界面按需生成）。结构本身成为模型的输出。

02 / 市场与动能

2. 市场与动能：为什么是现在

第三方测算显示，企业生成式 AI 工具支出在 2025 年约达 370 亿美元，其中应用层占比过半[8]；面向 UI 设计的生成式 AI 细分市场被估算从 2023 年的 1.38 亿美元增长到 2033 年约 17 亿美元，复合年增长率约 29.4%[9]。这些是机构预测而非实际收入，但方向一致：界面生成正从研究走向产品。下面三股力量解释了动能来源。

驱动 1

模型能力跨过可用线

前沿模型在代码生成与结构化输出上的准确率显著提升，使「让模型直接产出可运行界面」从演示变成可交付。模型还能读图表、按系统指令稳定输出固定格式，这是运行时生成的前提[1]。

驱动 2

组件化前端成为天然靶子

React 与设计系统（shadcn/ui、Material、Chakra 等）把界面拆成可组合的组件单元。模型不必逐像素绘制，只需选择并组装既有组件，输出空间受控、可验证，生成质量因此更稳定。

驱动 3

Agent 与协议标准化

Agent 需要把结果还给用户，纯文本不够。2025 年 MCP、A2A、AG-UI、A2UI 等开放协议补齐了 Agent 与界面之间的连接层，使「Agent 驱动界面」有了跨平台的标准接口[5][2]。

03 / 三大范式

3. 三大范式：界面在生命周期的哪一刻被生成

承接上一节的两个坐标，把市面方案按「生成发生的时机」分成三层。越往后，模型对界面的掌控越多，人审校的环节越少，可控性挑战也越大。展开每一层可见代表产品。

一句话：模型在开发阶段把自然语言变成设计稿或可部署的前端工程，人在发布前审校。这是当前商业化最成熟、收入最集中的一层，代表产品如下。

v0

v0（Vercel）

从 prompt 生成可运行的 React / Next.js 应用，可连接 GitHub 直接推代码、一键部署到 Vercel。定位是「prompt、build、publish」的全流程[10]。

bolt.new

bolt.new（StackBlitz）

基于 WebContainer 在浏览器里跑全栈工程，支持导入企业设计系统（Porsche、Material、Shadcn 等），主打自动测试与迭代降低错误率[10]。

Lovable

Lovable

面向非工程读者的「prompt 到全栈应用」工具，提供模板与托管，官网称已构建数百万个项目。把后端、数据库、鉴权打包进对话式构建流程[10]。

Figma / Uizard

Figma Make 与 Uizard

偏设计稿一端：Figma 的 AI 能力与 Uizard 把文字、草图变成线框与高保真界面，产出物是设计而非生产代码，连接设计与开发的交接。

一句话：在对话或请求处理过程中，模型即时返回可交互组件（图表、表单、卡片），而不是纯文本。界面是运行时生成的，但范围限定在组件级，宿主应用框架仍由人写好。

AI SDK

Vercel AI SDK（streamUI）

开发框架。streamUI 让模型调用服务端函数并以 React 组件作答；通过 AI State 与 UI State 分离，把可序列化的状态喂给模型、把不可序列化的组件留在客户端[3]。

Artifacts

Claude Artifacts

2024 年 6 月随 Claude 3.5 Sonnet 发布。当用户请求代码、文档或网页时，生成物出现在对话旁的专用窗口里，可实时查看、编辑、迭代，把对话式 AI 变成协作工作台[4]。

Canvas

ChatGPT Canvas

OpenAI 的并排编辑界面，把写作与编码从线性对话中拆出来，放进可定点修改的画布。同属「在对话中生成可操作界面」一类，强调局部编辑而非整页重写。

C1

Thesys C1

把生成式 UI 作为 API 提供：传入数据或意图，返回仪表盘、表单、图表、报告等可渲染界面，目标是让「超越文本」的 AI 应用有现成的界面生成基座[7]。

一句话：模型对每个 prompt 即时生成一整张定制界面，而不只是一个组件。这是 2025 年底出现的最前沿方向，目前以实验性功能与开源规范为主。

Gemini 3

Gemini 3 Generative UI

2025 年 11 月 18 日随 Gemini 3 发布，通过 Dynamic View 与 Visual Layout 两种体验，对每个 prompt 即时生成完整的可交互界面（如行程规划器、教学工具）。技术上结合内容与布局生成、agentic 编码与后处理[1]。

A2UI

A2UI（开源规范）

Google 开源的 agent 驱动、跨平台生成式 UI 规范，定义 Agent 如何投递可渲染的 UI 控件，邀请社区协作以推动动态界面跨生态落地[2]。

AG-UI

AG-UI + CopilotKit

AG-UI 是开放、事件型的 Agent↔用户交互协议；CopilotKit 是兼容 AG-UI 的前端栈，提供聊天、生成式 UI、共享状态与 human-in-the-loop，把 Agent 后端接到任意前端[5][6]。

06 / 协议基础设施

6. 协议基础设施：让运行时生成可互操作

运行时生成式 UI 要跨产品落地，需要标准化的连接层。2025 年成型的四个开放协议各管一段：工具调用、Agent 间协调、Agent 与用户交互、以及界面控件投递。它们互补而非竞争[5]。

MCP

Agent ↔ 工具与数据

Model Context Protocol，由 Anthropic 提出。让 Agent 安全发现并调用外部工具、工作流与数据源，是生成界面所需数据的来源层[5]。

A2A

Agent ↔ Agent

Agent-to-Agent，由 Google 提出。定义分布式系统中 Agent 如何协调与分工，使复杂任务可由多个 Agent 协作完成后再交付界面[5]。

AG-UI

Agent ↔ 用户交互

开放、轻量、事件型协议，标准化 Agent 状态、UI 意图与用户交互在前后端之间的流动，让 Agent 后端接到任意用户界面[5]。

A2UI

界面控件投递规范

生成式 UI 规范，定义 Agent 如何投递可渲染的 UI 控件。与 AG-UI 配合：AG-UI 管交互通道，A2UI 管界面内容本身，二者协同支撑跨平台动态界面[2][5]。

07 / 现实约束

7. 现实约束：为什么运行时生成尚未默认开启

生成式 UI 的难点不在「能不能生成」，而在「生成的界面能不能信」。把界面交给模型即时产出，会触碰四类工程与产品约束，越靠近运行时层越突出。

约束 1

一致性与品牌约束

同一个 prompt 两次生成可能给出不同布局。企业需要界面符合设计系统与品牌规范，因此现实方案多采用「受约束生成」：模型只能从既有组件库中选择并组装，而非自由绘制。

约束 2

可控性与确定性

关键流程（支付、合同、医疗）不能容忍界面随机变化。这类场景要么停留在设计时生成（人审校后固定），要么对运行时生成施加严格的 schema 与结构化输出约束，把不确定性限制在可枚举范围内。

约束 3

可访问性与合规

即时生成的界面要满足无障碍标准、键盘可达、对屏幕阅读器友好，并通过合规审计。结构由模型动态决定时，这些保证更难给出，需要在生成后引入自动校验环节。

约束 4

性能、成本与信任

每次交互都调用模型生成界面会带来延迟与推理成本，并产生新的信任问题：用户如何形成对「界面为何长这样」的认知。多数产品因此采用缓存、模板兜底与渐进生成来平衡体验。

08 / 未来趋势

8. 未来趋势：界面会越来越晚被确定

把前文事实外推，可见一条清晰的轨迹：界面被确定的时刻持续后移，模型生成的范围持续扩大。以下四步既是过去两年的回放，也是未来的方向。

  1. 1
    从设计时到运行时

    界面确定的时刻从「发布前」后移到「请求处理时」。设计时工具不会消失，但越来越多界面会在用户提出请求的那一刻才被组装。

  2. 2
    从组件到完整界面

    生成范围从单个组件扩展到整张界面。Gemini 3 Generative UI 与 A2UI 已在演示「按 prompt 生成完整体验」，这一范围会随模型可靠性提升而扩大[1]。

  3. 3
    个性化与自适应界面

    界面按用户、上下文与行为实时调整，而非对所有人呈现同一结构。个性化从「填不同数据」升级为「给不同结构」，这是运行时生成最直接的产品价值。

  4. 4
    受约束生成成为主流工程实践

    为同时满足灵活性与可控性，主流做法会是「设计系统 + schema 约束 + 生成后校验」：模型在受限组件空间内自由组装，工程层保证一致性、可访问性与合规。

一句话总结：生成式 UI 的竞争不在「谁能生成更炫的界面」，而在「谁能在保证一致性、可控性与合规的前提下，把界面确定的时刻安全地推到运行时」。
