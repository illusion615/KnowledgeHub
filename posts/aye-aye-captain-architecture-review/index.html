02 / 结构与边界

按职责收敛单体，不按文件长度重写系统

同步 SQLite 和单进程服务符合当前本地单人目标。多服务、消息中间件或前端框架迁移不能自动修复入口门禁；本轮也没有负载数据支持容量判断。

1
Dashboard → Fastify API → services → SQLite

浏览器经 HTTP 读写；API 持有 SQLite 单例，开启 WAL 与外键。UI 不承担持久化门禁。

2
Delegation Engine → jobs → CLI → MCP → API

引擎组装 Playbook 与约束，jobs 管进程和日志。MCP 经 HTTP 回写，没有直接打开数据库。

3
产品意图 → 设计 → 任务 → 证据 → 人工验收

Blueprint、Solution、Scenario、Requirement 表达产品意图；批准 L2 后原子生成任务和 implements 关系。复杂任务增加 L3；架构变化通过 reconcile_runs 与 ADR 审批。

[1] [2] ADR 是架构决策记录；L2/L3 在此指功能设计和任务详细设计，不是审查框架的判据层。

app.js 的 4,538 行和 routes/index.ts 的 1,885 行是定位线索，不是预设超标；重复职责才是拆分依据。

收敛对象建议
导航提交与 Job 观察先统一生命周期，再分离实体渲染模块；保留原生 JS。
路由中的业务编排按产品意图、设计、执行和证据拆注册；可复用用例进入现有 services。
共享架构数据功能/集成投影继续复用构件和关系；保留子集批准、ADR 和事务回滚。

[2] [3] 不恢复直接需求执行，不增加第二个数据库写入者，也不为减少行数而改接口。

03 / 持久状态门禁

创建入口和验收证据存在已复现缺口

同一工作项不能因使用 POST 或 PATCH 而获得不同的质量保证。以下两项在临时 SQLite 与 Fastify inject 中复现，没有启动真实 Agent，也未读写实际项目数据。

操作结果
POST tasks/bugs，直接指定 done201；无验证命令或根因也能成为 done
PATCH task→done，无通过记录422；更新路径门禁确实生效
先 POST pass-only run，再 PATCH done201 + 200；无证据也能完成

[4] [5]

普通创建直接调用 repo.create；质量门禁集中在更新服务，形成可复现的入口差异。

机制与影响POST 接受 task/bug 的 done；fixture 中任务无 validation_command、Bug 无 root_cause，仍保存成功。完成率不再可靠。
方案取舍建议普通创建固定 triage；历史状态重建使用独立、可验证来源的导入契约。只补 PATCH 无效；通用 POST 不应成为导入捷径。
关闭判据普通创建不能直达 ready/in_progress/review/done/blocked；合法初态、明确批准的导入例外和设计任务原子生成都有回归。维护者需确认历史导入例外范围。

[4]

当前契约接受执行者声明；它没有保证执行证据与本次修改关联。这不等于已证明实现错误，也不否认 requirement 已实现状态的特例。

机制与影响done 查询任意历史 pass；run 与 evidence 分开写。仅提交项目、任务和 test_result=pass，随后 done 即获批准。
方案取舍run 绑定工作项版本或重开轮次、命令、退出码和输出来源；区分可信执行器记录与人工申报。只要求非空摘要仍允许自证。
关闭判据与边界无证据 pass、其他工作项 run、重开前旧 pass 均不满足新的验收；有效结果和批准的人工例外可追踪。API 能校验记录契约，不能证明任意外部文件真实无伪造。

[5]

04 / 执行生命周期

权限、取消和结构化交付需要独立的运行契约

现有消息交付门禁值得保留，但消息、工作记录与进程终态不是同一件事。以下为静态源码确认，未运行真实 CLI 权限或取消实验。

F03

P1 建议 · 只读边界

禁用 write 不等于禁止 shell 写入；默认权限仍广于分析任务用途。

[6]
F04

P1 · 取消顺序

模型回退先于 canceled 检查；数据库终态不证明进程树已停止。

[7]
F05

P2 · 结果契约

消息门禁未覆盖所有声明的 work_run、变更单及目标话题。

[8]

buildCommand 默认传入 allow-all-tools 和 allow-all-paths；allowWrite=false 只拒绝 write，不建立文件系统只读边界。

优先级依据只读分析不应修改工作区。P1 是基于该边界重要性的建议；安装版本的 CLI 实际权限行为仍需夹具确认，不作漏洞利用声明。
方案取舍按 Playbook 授予工具和目录范围；必须运行任意命令时提供只读工作区。拒绝更多命令不能穷尽 shell 写入，系统级隔离则增加兼容和维护成本。
关闭判据代表性只读任务无法通过文件工具或 shell 写入，但读取代码和允许的结构化提交仍可成功。

[6]

取消先保存 canceled 并对直接子进程发 SIGTERM；close 回调先检查模型回退，满足条件时可能重启已取消任务。

建议机制取消请求先禁止重试并撤销写入授权；canceling 表示停机中。确认进程树退出后才 canceled 和回滚，并增加可配置截止时间及有界升级终止。
取舍与边界移动 canceled 判断可修回退复活，但不能解决后代进程存活。仅发 SIGTERM 也不能证明已停止；本轮未运行残留进程实验。
关闭判据回退诊断后取消、忽略 SIGTERM、生成后代三种夹具均不重启、不遗留写入者；写入者未停不得回滚；截止时间行为可观察。

[7]

outcome 声明尚未成为完整 postflight 门禁；消息存在性也未确认目标话题。现有缺消息失败处理应保留，而不是重新实现一套。

机制engine 向 jobs 传递是否必须发消息，未按 outcome 强制核对 work_run 或提案；消息查询只使用 job_id 和 Agent 角色。
方案取舍持久化带类型的 expected_outputs，验证 Job、工作项、话题和来源。失败、部分完成、阻塞分别记录，不要求失败执行制造 pass。增加提示词不能替代检查。
关闭判据仅发消息却无所需 run、未交提案、发错话题均不能算交付完成；符合该 Playbook 声明的有效结果才通过。

[8]

05 / 重启恢复

持久化 Job 不等于持久化编排

F06 / P2 包含初始化后续任务和架构提取恢复互斥两个子项。两者需要批次身份和恢复状态，而不只是保存进程记录；以下为静态确认。

F06-A

初始化 continuation 在内存中

Set 和定时器保存后续一致性阶段；重启后缺少批次恢复。等待一小时后只要已有成功任务便可继续，即使其他任务仍运行。

F06-B

恢复失败未重建项目互斥

提取回滚失败会保留快照，却没有重建项目锁；新提取可能与尚未完成的恢复冲突。

[9]

先明确取消和结果终态，再把编排存入现有数据库；否则只是持久化错误状态。

建议结构保存初始化批次、前置 Job、唯一后续任务声明及项目恢复租约。恢复失败保留阻塞；超时显式处理，不提前合并。
取舍无批次身份的启动扫描可能混合多次初始化；外部工作流平台则超出当前体量需要。复用同一 API 写入边界。
关闭判据前置完成与后续启动之间重启，后续恰好启动一次；前置未结束不合并；恢复失败禁新提取，恢复成功释放租约。依赖 F04/F05。

[9]

06 / 页面生命周期

异步结果必须归属于当前导航

F07 / P1 合并两个页面生命周期子项，但分别记录证据与验收。修复共享时序比迁移前端框架更直接；两个子项都关闭才计主项完成。

F07-A

旧请求覆盖新页面

tasks 请求先启动，随后导航到 bugs；tasks 最后返回，重新查询全局 listArea 后写入。内存 mock 复现 Bugs 标题配 tasks 内容；不是源应用浏览器 E2E。

F07-B

修订观察器调用不存在

方案/场景重新进入修订状态调用未定义的 startEntityRevisionPoll，异常被空 catch 吞掉。另有两个已有轮询器承担近似职责，属于静态确认的接线缺陷。

[10]

复用 dock 已有的请求序号思路；实体只定义刷新回调，不再各自管理完整轮询生命周期。

方案与取舍提交前校验 project/view/entity/generation；统一 Job 订阅、终态和退出清理。AbortController 可减少无效请求，但不能替代提交身份校验。
A 关闭判据乱序响应、快速下钻、返回及跨项目切换后，只能呈现当前导航结果与上下文。
B 关闭判据三类产品实体修订后离开再返回，恢复进度并在终态刷新；同一 Job 不重复轮询，失败可见。
