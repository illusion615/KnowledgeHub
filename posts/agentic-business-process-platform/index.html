01 / 业务现状与挑战

四类断裂让审批人把时间花在找入口、补信息和追状态上

传统企业通常按财务、采购、销售、HR 和项目管理分别建设业务系统。提交端与专业流程已经稳定，但审批任务、材料结构、催办方式和历史记录散落在各系统。立项前应至少采集四项同口径基线：每名审批人每周访问的系统数、单笔主动处理分钟、等待时长中位数、因材料不全造成的退回率；没有基线就不能承诺提速幅度。

01

入口分散

审批人需要在邮件通知、ERP、采购、费用和 CRM 等入口之间切换，移动场景下更容易把等待任务误当成已处理任务。

02

上下文不完整

表单只呈现本系统字段，审批人还要查合同、预算、供应商历史、邮件和政策，主动处理时间因此高于点击同意或拒绝本身。

03

集成改造昂贵

重做每个系统的表单和工作流会触发回归测试、培训、发布窗口与供应商定制费用；把提交端一并迁移会扩大首期范围。

04

记录无法统一复核

待办、已办、转派、补件和回写失败分布在不同数据库，管理者难以按流程、部门、金额、时长和异常原因统一分析。

基线按同一流程、同一风险等级和同一月份采集，避免把业务季节性误判为平台收益。

02 / 设计理念与期望获益

保留来源系统，把审批体验、证据和治理标准化

平台以一次审批旅程为主线：来源系统创建事项，中台生成标准工作项和 AI 简报，审批人在 Outlook、Teams 或 Power Pages 统一工作台决策，结果回写来源系统，Power Pages 保留面向内部与外部参与者的统一入口。收益必须落在四个可测结果上：减少系统切换、降低单笔处理时间、减少材料退回、提高跨系统追溯覆盖率。

原则 1

来源系统保持权威

平台保存审批副本、事件和引用，不复制全部业务主数据。正式订单、费用、合同和人员记录仍由原系统负责。

原则 2

先统一工作项，再统一界面

所有流程先映射到同一 ApprovalCase 数据契约，再投递到 Outlook、Teams 和工作台，避免每接一个系统就开发一套审批页面。

原则 3

AI 输出证据简报

简报分为已确认事实、规则异常、缺失信息和建议关注点，并保留来源链接。AI 不改变金额、审批链或最终决定。

原则 4

一次决定形成完整事件链

接收、补件、委派、提醒、决定、回写和失败重试都写成不可混淆的事件，支持复核、分析和责任追踪。

03 / 解决方案架构

Copilot Studio Agent 负责理解与分派，Agent Flow 负责确定性执行

生产基线采用 Copilot Studio autonomous agent + Agent flows：事件触发器唤醒流程 Agent，Agent 根据已授权上下文选择版本化 workflow；Agent flow 按固定分支执行连接器、AI 节点与 human-in-the-loop action；Dataverse 保存跨等待时段的 ApprovalCase。新 Workflows 画布目前仍是 public preview，适合沙盒验证，不作为生产基线。[1][4]

理解与分派

Copilot Studio 流程 Agent

接收事件，读取有权限的上下文，识别流程类型、风险和缺失信息，只从已注册的 Agent flow、prompt 与 connector tool 中选择下一步。

确定性执行

Copilot Studio Agent Flow

按规则完成校验、分支、循环、连接器调用、AI 节点、Approval、Request information 和幂等回写；相同输入走相同规则路径。

持久状态

Dataverse ApprovalCase

保存来源引用、Agent/Workflow 运行 ID、人工任务、决定、回写结果和 Credits 遥测；等待人员数小时或数天时不依赖对话会话存活。

  1. 1 · 来源事件唤醒流程 Agent

    ERP、CRM、HR 或专业系统保留原表单；Copilot Studio event trigger 把经过筛选的 payload 发送给 Agent。事件触发器目前使用 maker credentials，生产环境必须使用专用低权限 maker 身份。[2]

  2. 2 · Agent 识别流程、风险与下一工具

    Agent 读取来源引用和允许的企业上下文，识别流程类型、风险级别与缺失信息，只选择发布清单中的 Agent flow；金额计算、审批矩阵和权限不交给生成式判断。[5]

  1. 3 · Agent Flow 执行规则、连接器与 AI 节点

    workflow 用 sourceSystem + sourceRecordId + version 做幂等校验，通过 Copilot Studio connector tool 读取业务数据，并用原生 prompt / content processing 节点生成带来源的证据简报。[6][7]

  1. 4 · 缺信息时 Request information

    Request information action 暂停 Agent flow，通过 Outlook 向指定人员收集字段，收到响应后把答案作为动态参数恢复执行。当前限制是仅支持 Outlook、采用首个响应且不能发送给租户外用户；外部补件改由 Power Pages Human Task 收集。[8][17][18]

  2. 5 · 人员决定进入 ApprovalCase

    Agent flow 为租户内审批人生成 Approval；参与人数较多或包含外部人员时，workflow 同时生成 Dataverse Human Task，由 Power Pages 统一工作台展示证据并收集决定。Outlook、Teams 与 Power Pages 的人员响应都写回 ApprovalCase；Agent 只能解释、提醒和升级。[1][9][10][17][18]

  1. 6 · Workflow 回写，Agent 监督异常

    Agent flow 先写入决定与运行遥测，再调用来源 connector 幂等回写。原生 connector 不满足要求时才封装 custom connector 或调用既有 Power Automate adapter；失败进入 Dataverse 异常队列，由 Agent 催办和解释。[11]

统一数据契约只保存完成审批所需的最小字段和来源引用，避免把中台扩张为第二套 ERP。

六个状态把 Agent 规划、workflow 执行、人员等待和来源系统落账分开；长时间等待保存在 Dataverse，不依赖一个持续对话。

  1. Triggered → Planned

    事件完成真实性校验，Agent 记录分类、风险、所选 workflow 与输入版本；无法匹配发布清单时进入 Exception。

  2. Running → WaitingHuman → Resumed

    Agent flow 执行到补件或审批 gate 后持久化 human task；人员响应触发恢复，原输入、响应与 workflow 版本保持关联。

  3. Writeback → Closed / Exception

    来源系统确认幂等回写后进入 Closed；权限拒绝、版本冲突、容量阻断或重试耗尽进入 Exception。

三类执行者各自拥有明确决定权；Agent 的生成式规划不能覆盖 workflow 规则，也不能覆盖人员审批。

Agent

理解、解释与选择受控工具

可分类事项、整合证据、识别缺失、选择已发布 workflow、解释状态与发起催办；不能自创工具、金额或审批规则。[5]

Workflow

计算、校验、授权与回写

拥有金额公式、审批矩阵、SLA、连接器输入、幂等键、重试和补偿逻辑；生成式输出只能作为显式字段进入规则判断。

Human

补充事实并承担最终责任

信息提供者确认缺失字段；审批人完成批准、拒绝、退回或委派。每次操作保存身份、时间、意见和所见证据版本。

失败样例：合同读取失败时，Agent 标记「合同内容未知」，workflow 转入 Request information 或人工审阅；禁止 Agent 根据供应商历史补写本合同条款。

Approval 完成与来源系统落账是两个状态；Agent 负责解释和催办，Agent flow 负责重试与补偿，任何一方都不能把回写失败标成完成。

  1. 决定入账

    平台保存 Approve、审批人、时间、意见和输入版本，状态进入 WritebackPending。

  2. Agent Flow 按幂等键重试

    workflow 按指数退避重试 3 次；来源接口必须接受 idempotencyKey，避免网络恢复后重复过账。

  3. 进入异常队列

    三次失败后进入 Exception，通知流程负责人；Power Pages 统一工作台显示「已批准，待回写」，而不是「已完成」。

  4. 对账后关闭

    人工修复权限或版本冲突后再次回写；只有 ERP 返回业务凭证号并完成对账，状态才进入 Closed。

Agentic 运行时增加了触发身份、工具权限、Credits 容量和 preview 边界；四项必须分别设定生产门槛。

  • 1触发身份：event trigger 当前只使用 agent maker credentials；生产使用专用低权限 maker 账号，并把 payload 缩到最小字段。[2]
  • 2工具与数据：DLP 控制 connector 组合，Dataverse 角色限制表、列与记录；Agent 只获得完成当前流程所需工具。[12][14]
  • 3容量：每 100 个 Agent flow actions 消耗 13 Copilot Credits；预付容量耗尽会阻止新 flow run，生产环境启用告警、月度上限和 PAYG 连续性方案。[3]
  • 4发布与风险：Agent、Agent flow、prompt、connector 与 Dataverse 表进入 Solution，经 Dev → Test → Prod；preview action 不进入关键生产路径，AI 风险按持续治理、测量和处置执行。[13][15]

新流程首先在 Copilot Studio 内完成；只有连接能力或既有资产无法直接迁移时，才保留 Power Automate 适配层。

首选

Copilot Studio 原生 Connector / Agent Flow

预置 connector、custom connector、规则、AI 与 human action 全部留在同一 workflow，统一版本、测试、观察与 Credits 计量。

兼容

已在 Solution 中的 Power Automate cloud flow 可把 plan 改为 Copilot Studio，转成 Agent flow 并改用 Copilot Studio capacity；转换不可逆。[1]

    复用 Agent instructions、Agent flow、Prompt、Connector、Human Gate、ApprovalCase、DLP 和 ALM 模板；一次只增加一个流程或组织范围。

05 / ROI 评估计算器

用时间、返工、延误损失和避免重构成本计算回报

计算器把年化运营收益与一次性、年度成本分开：时间收益来自有效审批量 × 单笔节省分钟 × 综合人力成本 × 收益兑现率；返工收益来自退回率差值；延误损失按可避免暴露额折减。年度平台成本直接读取上方 SKU 表的月度 USD 合计，按可调规划汇率折算为 CNY，再加 APIM、外部 IdP 等另计成本；不再重复手填 Copilot Credits 与 Power Pages 预算。默认值是组合示例假设，不代表客户实测或 Microsoft 收益承诺。

审批量、采用与时间价值

所有效率输入都应由同流程试点替换；采用率按实际通过新入口完成决定的审批量计算。

返工与延误损失

返工收益只使用材料缺失或冲突造成的退回率差值；延误收益只计入能够稳定归因的暴露额。

实施、汇率与年度预算

已计价 SKU 由配置器自动带入；汇率只用于规划折算，APIM、外部 IdP、税费和折扣等通过「另计成本」补充。

收益与投资判断

回收期按净前期投入 ÷（年化运营收益 − 年度运行成本）计算；避免重构成本只抵减前期投入一次。

组合采购案例说明如何设置生产试点门槛

以下是基于常见制造业采购审批特征构造的组合示例，不对应任何单一真实客户，也不宣称已经实现结果。它用于展示如何把业务问题、产品配置、基线、目标和扩展条件放进同一份试点章程。所有数字都必须由客户日志、财务口径和安全评审替换。

01

现状假设

3 个来源系统，180 名审批人，月均 20,000 笔；单笔主动处理 7 分钟，材料退回率 10%，审批人需要分别登录采购、ERP 和合同系统。

02

试点范围

选择一个工厂、一个间接采购流程和 30 名审批人；保留原提交表单，接入预算、供应商状态和合同附件，Outlook/Teams 处理内部审批。

03

产品配置

Copilot Studio 流程 Agent + Agent Flow + Dataverse + Power Pages 统一工作台 + Teams Approvals；原生 Prompt 与 Content processing 生成简报并提取附件；Custom Connector 回写 ERP；Power BI 分析流程。

维度组合示例基线8 周试点通过条件停止扩展条件
采用0% 使用统一入口至少 70% 试点审批通过 Outlook/Teams 完成连续 2 周低于 50%
效率单笔主动处理 7 分钟同风险等级中位数降至 4 分钟或以下处理时间下降但错误决定率上升
材料质量材料退回率 10%降至 6% 或以下，且政策标准不变AI 简报出现 1 次未标注来源的关键事实
可靠性跨系统追踪缺失99% 事项具备完整事件链，回写成功率至少 99.5%出现重复过账或未授权数据访问
财务无同口径收益基线用实测参数重算后，三年收益/成本比至少 1.2x只靠未报价的避免重构成本才能达到 1.0x

扩展依据是试点门槛，不是演示反馈；每轮只增加一个流程或组织范围。

通过

复用模板，增加第二个采购流程

复用状态机、异常队列、连接引用、DLP、简报 schema 和指标定义，只新增字段映射、审批规则与来源 API。

未通过

保持原入口，修复单一失败原因

按采用、数据质量、AI 简报、集成可靠性或经济性定位失败；修复后重跑同范围 4 周，不同时更换流程和组织。
