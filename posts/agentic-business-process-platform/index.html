01 / 业务现状与挑战

四类断点让审批人把时间花在找入口、补信息和追状态上

传统企业通常按财务、采购、销售、HR 和项目管理分别建设业务系统。提交端与专业流程已经稳定，但审批任务、材料结构、催办方式和历史记录散落在各系统。立项前应至少采集四项同口径基线：每名审批人每周访问的系统数、单笔主动处理分钟、等待时长中位数、因材料不全造成的退回率；没有基线就不能承诺提速幅度。

01

入口分散

审批人需要在邮件通知、ERP、采购、费用和 CRM 等入口之间切换，移动场景下更容易把等待任务误当成已处理任务。

02

上下文不完整

表单只呈现本系统字段，审批人还要查合同、预算、供应商历史、邮件和政策，主动处理时间因此高于点击同意或拒绝本身。

03

集成改造昂贵

重做每个系统的表单和工作流会触发回归测试、培训、发布窗口与供应商定制费用；把提交端一并迁移会扩大首期范围。

04

记录无法统一复核

待办、已办、转派、补件和回写失败分布在不同数据库，管理者难以按流程、部门、金额、时长和异常原因统一分析。

基线按同一流程、同一风险等级和同一月份采集，避免把业务季节性误判为平台收益。

02 / 设计理念与期望获益

保留来源系统，把审批体验、证据和治理标准化

平台以一次审批旅程为主线：来源系统创建事项，中台生成标准工作项和 AI 简报，审批人在 Outlook、Teams 或 Power Pages 统一工作台决策，结果回写来源系统，Power Pages 保留面向内部与外部参与者的统一入口。收益必须落在四个可测结果上：减少系统切换、降低单笔处理时间、减少材料退回、提高跨系统追溯覆盖率。

原则 1

来源系统保持权威

平台保存审批副本、事件和引用，不复制全部业务主数据。正式订单、费用、合同和人员记录仍由原系统负责。

原则 2

先统一工作项，再统一界面

所有流程先映射到同一 ApprovalCase 数据契约，再投递到 Outlook、Teams 和工作台，避免每接一个系统就开发一套审批页面。

原则 3

AI 输出证据简报

简报分为已确认事实、规则异常、缺失信息和建议关注点，并保留来源链接。AI 不改变金额、审批链或最终决定。

原则 4

一次决定形成完整事件链

接收、补件、委派、提醒、决定、回写和失败重试都写成不可混淆的事件，支持复核、分析和责任追踪。

03 / 逻辑架构与职责

Source Adapter 隔离系统差异，Agent 与 Workflow 分开理解和执行

生产基线由四个职责层组成：Source Adapter 统一来源系统事件与读写契约，Copilot Studio 流程 Agent 理解上下文并选择已发布的 Copilot Studio Workflow，Copilot Studio Workflow 执行确定性规则与人员 gate，Dataverse 保存 IntegrationEvent 和 ApprovalCase。每层只拥有自己的决定，来源系统仍是业务权威；新 Workflows 画布目前仍是 public preview，不作为生产基线。[1][4][5][11]

来源接入

Source Adapter

实现 ReceiveEvent、ReadContext、ApplyDecision、GetWritebackStatus 与 GetSourceDeepLink；隐藏 Connector、Gateway、批量和 RPA 差异，但不拥有审批矩阵。

理解与分派

Copilot Studio 流程 Agent

接收 IntegrationEvent 引用，通过 Source Adapter 读取有权限的上下文，识别流程类型、风险和缺失信息，只从已注册的 Copilot Studio Workflow、prompt 与 connector tool 中选择下一步。

确定性执行

Copilot Studio Workflow

按规则完成校验、分支、循环、连接器调用、AI 节点、Approval、Request information 和幂等回写；相同输入走相同规则路径。

持久状态

Dataverse IntegrationEvent + ApprovalCase

保存来源事件、重放状态、Agent/Workflow 运行 ID、人工任务、决定和回写凭证；等待人员数小时或数天时不依赖对话会话存活。

04 / 来源系统接入

前端改造能力决定任务入口，后端接口能力决定接入可靠性

每个来源系统先按事件、读取、回写和网络能力分类，再选择 Connector、Webhook、轮询、批量或 RPA。前端可改造时可在原系统呈现结构化任务面板；前端不可改造时使用 Outlook、Teams 或 Power Pages Sidecar。两类体验都调用同一 Source Adapter 契约，且只有来源系统返回业务凭证后事项才能关闭。[6][11][23][24][25][28][29][30]

首选 · 原生事件

标准 Connector

适用于已有标准连接器和业务事件的系统。事件实时进入 Source Adapter，读取与回写由受支持接口完成，延迟和维护成本最低。

API 优先

Custom API + Webhook

适用于没有标准 Connector、但具备 API 的系统。用 Webhook 推送可信事件，通过 OpenAPI 契约读取上下文并返回可核验的业务凭证。

异步接入

轮询、网关或批量

适用于只有查询、数据库、文件或队列接口的系统。按水位发现变化，明确展示数据截止时间，并对批量回写结果逐笔对账。

兜底路径

受控 UI 自动化

仅用于完全没有机器接口的 Web、桌面或终端系统。写入后必须重新读取关键字段，失败日志与录像进入异常队列，不能把界面点击视为落账成功。

前端可改造：在原系统内呈现任务，业务事实仍由服务端确认

前端能否改造只决定任务入口放在原系统还是统一工作台；事件真实性、数据读取和结果回写仍由后端接口能力决定。原系统可以增加审批状态、补件入口和 Agent 解释面板，但浏览器事件只能作为交互信号；可信事件必须来自服务端提交钩子、事务性事件表或后续查询。

系统接口事件与读取原系统体验回写与边界
事件 + 读写 API服务端 Outbox 或 Webhook → Source Adapter；按记录 ID 和版本读取内嵌结构化任务面板；Agent 通过安全 Direct Line token 提供解释按钮调用确定性 Workflow；API 返回凭证号与新版本
只有查询或更新 API优先补服务端提交钩子；否则按时间戳或递增编号轮询仍可内嵌任务面板，但明确展示轮询延迟按可用 API 或批量接口回写；异步结果进入对账
无后端机器接口前端只能传递来源引用；受支持的服务端插件优先，做不到才用 RPA可显示平台状态，不能把浏览器提交当成来源系统已落账RPA 或人工回写；没有可核验结果时保持 WritebackPending

前端不可改造：后台 Sidecar 接入，审批人使用统一入口

来源界面保持不变，平台通过后台接口发现事项；Outlook、Teams 或 Power Pages 展示任务，并用来源深链接帮助审批人返回原记录。

系统接口事件与读取审批入口回写与边界
事件 + 读写 APIWebhook 或 Connector → Source Adapter → IntegrationEvent统一入口 + 来源深链接；来源系统零改造API 幂等回写并返回业务凭证
查询、数据库或批量接口Custom Connector 轮询；内网资源经本地网关；文件按批次水位读取统一入口展示数据截止时间和来源深链接API 或结果文件回写；导入结果单独对账
无机器接口专用受控运行环境读取 Web、桌面或终端界面统一入口；不向来源页面注入未经厂商支持的脚本写入后重新读取关键字段；失败录像和运行日志进入异常队列

五个操作隔离系统差异，Copilot Studio Workflow 不包含来源系统分支

每个来源系统实现同一组窄接口；Connector、Gateway、批量处理或 UI 自动化都封装在适配器内部，Workflow 只处理标准输入与输出。

可改造 CRM：服务端发事件，原页面呈现任务

销售人员继续在 CRM 保存折扣申请；新增页面区域只承载状态、结构化操作和 Agent 解释，不改变 CRM 仍为业务权威。

  1. 1 · CRM 事务与 Outbox 同时提交

    申请记录和来源事件在同一服务端事务中提交；浏览器回调失败或重复发送不会制造第二个 ApprovalCase。

  2. 2 · Source Adapter 写入 IntegrationEvent

    适配器验签、按事件 ID 去重，只把记录 ID、版本、事件类型和来源深链接发送给 Agent。

  3. 3 · 页面任务面板读取 ApprovalCase

    结构化按钮调用 Human Task API；Agent 对话使用服务端换取的单会话 Direct Line token，不能在浏览器暴露 secret。[26][27]

  4. 4 · Workflow 回写并核对新版本

    批准按钮直接进入确定性 Workflow；CRM 返回折扣审批凭证和新记录版本后，页面与统一工作台才显示 Closed。

不可改造 ERP：后台发现事项，统一入口决策

ERP 界面和原提交表单完全不变；接入方式按 Webhook、轮询、批量、RPA 的顺序降级，审批任务始终在平台统一呈现。

  1. 1 · 按最强可用接口发现待审记录

    有 API 时使用 Webhook 或水位轮询；只有内网数据库或文件时经本地网关；全部缺失时才采用受控 UI 自动化。

  2. 2 · 统一入口显示来源与数据截止时间

    Outlook、Teams 或 Power Pages 展示证据、来源记录号、最后读取时间和可用深链接，避免把缓存内容误认为实时数据。

  3. 3 · Workflow 选择 API、批量或 RPA 回写

    适配器隐藏来源差异；Copilot Studio Workflow 始终调用 ApplyDecision，不包含 ERP 产品名、页面选择器或文件目录分支。

  4. 4 · 无凭证不关闭，失败进入 Exception

    RPA 写入后重新搜索业务单号并读取状态；找不到预期值、机器会话冲突或 UI 元素变化时保留 WritebackPending，并提交运行日志和失败录像。

05 / 运行时与持久状态

IntegrationEvent 与 ApprovalCase 把事件、人员等待和来源落账分成可恢复状态

一笔事项依次经过事件登记、Agent 分派、确定性执行、人员等待和来源回写六步。IntegrationEvent 保存可去重、可重放的来源变化，ApprovalCase 保存 workflow 版本、Human Task、决定和回写凭证；任何长时间等待都落在 Dataverse，而不是依赖持续对话或单次 Flow 运行。[1][2][6][8][11]

  1. 1 · Source Adapter 接收并登记来源事件

    ERP、CRM、HR 或专业系统保留原表单。适配器按系统能力使用 Connector、Webhook、轮询、批量或 RPA，验签并按 sourceSystem + sourceEventId 去重，再把最小事件引用写入 IntegrationEvent。Copilot Studio event trigger 当前使用 maker credentials，生产只发送事件引用，并使用专用低权限 maker 身份。[2][23][24][28][29]

  2. 2 · Agent 读取受控上下文并选择 Workflow

    Agent 用 IntegrationEvent 引用调用 ReadContext，读取允许字段、附件引用和数据截止时间，识别流程类型、风险级别与缺失信息，只选择发布清单中的 Copilot Studio Workflow；金额计算、审批矩阵和权限不交给生成式判断。[5]

  1. 3 · Copilot Studio Workflow 执行规则、适配器与 AI 节点

    Copilot Studio Workflow 用 sourceSystem + sourceRecordId + sourceVersion 阻止同一业务版本重复审批，通过 ReadContext 获取标准数据，再用原生 prompt / content processing 节点生成带来源和截止时间的证据简报。[6][7]

  1. 4 · 缺信息时 Request information

    Request information action 暂停 Copilot Studio Workflow，通过 Outlook 向指定人员收集字段，收到响应后把答案作为动态参数恢复执行。当前限制是仅支持 Outlook、采用首个响应且不能发送给租户外用户；外部补件改由 Power Pages Human Task 收集。[8][17][18]

  2. 5 · 人员决定进入 ApprovalCase

    Copilot Studio Workflow 为租户内审批人生成 Approval；参与人数较多或包含外部人员时，Workflow 同时生成 Dataverse Human Task，由 Power Pages 统一工作台展示证据并收集决定。Outlook、Teams 与 Power Pages 的人员响应都写回 ApprovalCase；Agent 只能解释、提醒和升级。[1][9][10][17][18]

  1. 6 · Copilot Studio Workflow 调用 ApplyDecision，Agent 监督异常

    Copilot Studio Workflow 先写入决定与运行遥测，再调用 Source Adapter 的 ApplyDecision。API、批量或 RPA 差异留在适配器内；只有返回业务凭证号和来源新版本，事项才进入 Closed。失败或结果未知时进入 Dataverse 异常队列，由 Agent 催办和解释。[11][29][30]

IntegrationEvent 保存可重放的最小事件引用，ApprovalCase 保存完成审批所需字段；业务明细仍按来源引用读取，避免把平台扩张为第二套 ERP。

六个状态把 Agent 规划、workflow 执行、人员等待和来源系统落账分开；长时间等待保存在 Dataverse，不依赖一个持续对话。

  1. Received → Triggered → Planned

    Source Adapter 先把事件写入 IntegrationEvent；Agent 只在验签、去重和顺序检查通过后记录分类、风险、所选 workflow 与来源版本。

  2. Running → WaitingHuman → Resumed

    Copilot Studio Workflow 执行到补件或审批 gate 后持久化 human task；人员响应触发恢复，原输入、响应与 workflow 版本保持关联。

  3. Writeback → Closed / Exception

    来源系统确认幂等回写后进入 Closed；权限拒绝、版本冲突、容量阻断或重试耗尽进入 Exception。

闭环

回写凭证决定是否完成

人员批准后先进入 WritebackPending；只有来源系统返回业务凭证和新版本才进入 Closed。失败或结果未知进入异常队列。

数据

IntegrationEvent + ApprovalCase

IntegrationEvent 保存可重放的最小来源引用；ApprovalCase 保存 workflow 版本、人工任务、决定、遥测和回写凭证，业务明细仍留在来源系统。

状态

长时间等待持久化

Received、Planned、Running、WaitingHuman、Writeback 与 Closed/Exception 分开管理；人员等待不依赖持续对话或单次运行存活。

决定权

Agent、Workflow 与人各自负责

Agent 理解、解释并选择受控工具；Workflow 负责计算、校验、授权与回写；人员补充事实并承担最终审批责任。

06 / 可靠性与治理

决定权、失败恢复和发布控制必须独立于生成式判断

生产环境用三组横切控制约束全部组件：Agent、Workflow 与人员分别拥有明确决定权；回写失败保持 WritebackPending 或进入 Exception，不能伪装成完成；身份、DLP、Dataverse 权限、Credits 容量和 Dev → Test → Prod 发布门分别设定生产阈值。任何未授权访问或重复过账都直接触发试点停止条件。[2][3][5][12][13][14][15]

三类执行者各自拥有明确决定权；Agent 的生成式规划不能覆盖 workflow 规则，也不能覆盖人员审批。

Agent

理解、解释与选择受控工具

可分类事项、整合证据、识别缺失、选择已发布 workflow、解释状态与发起催办；不能自创工具、金额或审批规则。[5]

Workflow

计算、校验、授权与回写

拥有金额公式、审批矩阵、SLA、连接器输入、幂等键、重试和补偿逻辑；生成式输出只能作为显式字段进入规则判断。

Human

补充事实并承担最终责任

信息提供者确认缺失字段；审批人完成批准、拒绝、退回或委派。每次操作保存身份、时间、意见和所见证据版本。

失败样例：合同读取失败时，Agent 标记「合同内容未知」，workflow 转入 Request information 或人工审阅；禁止 Agent 根据供应商历史补写本合同条款。

Approval 完成与来源系统落账是两个状态；Agent 负责解释和催办，Copilot Studio Workflow 负责重试与补偿，任何一方都不能把回写失败标成完成。

  1. 决定入账

    平台保存 Approve、审批人、时间、意见和输入版本，状态进入 WritebackPending。

  2. Source Adapter 先查状态，再按接入方式重试

    API 临时错误可按幂等键指数退避重试 3 次；批量或 RPA 在任何重试前先按业务单号查询来源状态，已经生成凭证时禁止再次提交。

  3. 进入异常队列

    三次失败后进入 Exception，通知流程负责人；Power Pages 统一工作台显示「已批准，待回写」，而不是「已完成」。

  4. 对账后关闭

    人工修复权限或版本冲突后再次回写；只有 ERP 返回业务凭证号并完成对账，状态才进入 Closed。

Agentic 运行时增加了触发身份、工具权限、Credits 容量和 preview 边界；四项必须分别设定生产门槛。

  • 1触发身份：event trigger 当前只使用 agent maker credentials；生产使用专用低权限 maker 账号，并把 payload 缩到最小字段。[2]
  • 2工具与数据：DLP 控制 connector 组合，Dataverse 角色限制表、列与记录；Agent 只获得完成当前流程所需工具。[12][14]
  • 3容量：每 100 个 Copilot Studio Workflow action 消耗 13 Copilot Credits；预付容量耗尽会阻止新 Workflow run，生产环境启用告警、月度上限和 PAYG 连续性方案。[3]
  • 4发布与风险：Agent、Copilot Studio Workflow、prompt、connector 与 Dataverse 表进入 Solution，经 Dev → Test → Prod；preview action 不进入关键生产路径，AI 风险按持续治理、测量和处置执行。[13][15]

07 / 产品配置工具

先识别来源系统接入能力，再估算运行容量与产品组合

基础组合固定为 Source Adapter、Copilot Studio 流程 Agent、Copilot Studio Workflow、Dataverse、Power Pages 统一工作台与 Microsoft 365 内部审批入口。配置向导依次采集接入能力、流程规模、Credits 用量和可选能力，下方实时生成容量摘要与完整产品清单。Copilot Studio PAYG、Power Pages、Power BI Pro 与 Power Automate Process 进入已计价合计；APIM 区域 SKU、RPA 运行机器、外部身份提供商、税费和合同折扣另行核算。[3][16][19][20][21][22][25][27][29][30]

前端、接口、网络与回写能力

四项能力分别决定任务入口、事件接入、网络路径和结果确认；前端可改造不代表浏览器可以替代可信的服务端事件或来源回写。

流程与用户规模

流程数、审批人数、管理员人数和设计节点用于说明实施规模，不直接计费；月事件量与每笔实际执行 action 数决定 Copilot Credits。Power Pages 仅按每个网站每个自然月的唯一认证用户计费。[16]

Copilot Credits 用量参数

按每笔业务事件填写 Agent action、Copilot Studio Workflow action、AI tool 调用与文档页数；AI tool 根据模型层级和 token 用量计费。上线后用 Activity Map 与实际 token 用量替换估算值。[3]

可选能力与边界

勾选会改变推荐产品栈、身份路径、治理要求或 Credits 组成，不改变来源系统仍为业务权威的架构原则。

推荐 Agentic 运行基线与双容量下限

Credits 按 Agent action、Copilot Studio Workflow action 和文档页估算；Power Pages 按每个网站每月唯一认证用户数估算，每 100 人需要 1 个订阅容量包。[3][16]

首期只选一个流程、一个责任部门和一组明确指标；每阶段有退出条件，未达标时不扩范围。

  1. 阶段 1 · 2 周发现与基线

    选定一个月审批量足够、风险可控的流程；完成 4 项基线、ApprovalCase 字段映射、身份边界和回写接口评审。

  2. 阶段 2 · 4–6 周 Agent + Workflow PoC

    用 PAYG 建立流程 Agent、一个 Copilot Studio Workflow、Prompt、Approval、Request information 与模拟回写；验证 Outlook-only、首个响应和租户边界。

  3. 阶段 3 · 6–8 周生产试点

    限制到一个部门和明确金额阈值，保留原审批入口回退；连续 4 周对照业务指标，并记录每笔 Agent actions、Copilot Studio Workflow actions、Prompt tokens 与文档页数。

  4. 阶段 4 · 按模板逐流程扩展

    复用 Agent instructions、Copilot Studio Workflow、Prompt、Connector、Human Gate、ApprovalCase、DLP 和 ALM 模板；一次只增加一个流程或组织范围。

08 / ROI 评估计算器

用时间、返工、延误损失和避免重构成本计算回报

计算器把年化运营收益与一次性、年度成本分开：时间收益来自有效审批量 × 单笔节省分钟 × 综合人力成本 × 收益兑现率；返工收益来自退回率差值；延误损失按可避免暴露额折减。年度平台成本直接读取上方 SKU 表的月度 USD 合计，按可调规划汇率折算为 CNY，再加 APIM、外部 IdP 等另计成本；不再重复手填 Copilot Credits 与 Power Pages 预算。默认值是组合示例假设，不代表客户实测或 Microsoft 收益承诺。

审批量、采用与时间价值

所有效率输入都应由同流程试点替换；采用率按实际通过新入口完成决定的审批量计算。

返工与延误损失

返工收益只使用材料缺失或冲突造成的退回率差值；延误收益只计入能够稳定归因的暴露额。

实施、汇率与年度预算

已计价 SKU 由配置器自动带入；汇率只用于规划折算，APIM、外部 IdP、税费和折扣等通过「另计成本」补充。

收益与投资判断

回收期按净前期投入 ÷（年化运营收益 − 年度运行成本）计算；避免重构成本只抵减前期投入一次。

09 / 客户案例

组合采购案例说明如何设置生产试点门槛

以下是基于常见制造业采购审批特征构造的组合示例，不对应任何单一真实客户，也不宣称已经实现结果。它用于展示如何把业务问题、产品配置、基线、目标和扩展条件放进同一份试点章程。所有数字都必须由客户日志、财务口径和安全评审替换。

01

现状假设

3 个来源系统，180 名审批人，月均 20,000 笔；单笔主动处理 7 分钟，材料退回率 10%，审批人需要分别登录采购、ERP 和合同系统。

02

试点范围

选择一个工厂、一个间接采购流程和 30 名审批人；保留原提交表单，接入预算、供应商状态和合同附件，Outlook/Teams 处理内部审批。

03

产品配置

Copilot Studio 流程 Agent + Copilot Studio Workflow + Dataverse + Power Pages 统一工作台 + Teams Approvals；原生 Prompt 与 Content processing 生成简报并提取附件；Custom Connector 回写 ERP；Power BI 分析流程。

维度组合示例基线8 周试点通过条件停止扩展条件
采用0% 使用统一入口至少 70% 试点审批通过 Outlook/Teams 完成连续 2 周低于 50%
效率单笔主动处理 7 分钟同风险等级中位数降至 4 分钟或以下处理时间下降但错误决定率上升
材料质量材料退回率 10%降至 6% 或以下，且政策标准不变AI 简报出现 1 次未标注来源的关键事实
可靠性跨系统追踪缺失99% 事项具备完整事件链，回写成功率至少 99.5%出现重复过账或未授权数据访问
财务无同口径收益基线用实测参数重算后，三年收益/成本比至少 1.2x只靠未报价的避免重构成本才能达到 1.0x

扩展依据是试点门槛，不是演示反馈；每轮只增加一个流程或组织范围。

通过

复用模板，增加第二个采购流程

复用状态机、异常队列、连接引用、DLP、简报 schema 和指标定义，只新增字段映射、审批规则与来源 API。

未通过

保持原入口，修复单一失败原因

按采用、数据质量、AI 简报、集成可靠性或经济性定位失败；修复后重跑同范围 4 周，不同时更换流程和组织。
