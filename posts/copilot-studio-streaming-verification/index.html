01 / Problem

为什么要验证「流式」

大语言模型回答较长时，一次性等待整段返回的体验很差。逐字渐进显示（livestreaming）是 LLM 聊天的标准体验。

MCSChat 是一个对接 Copilot Studio 的自定义 Web 聊天前端，通过 Direct Line 3.0（WebSocket）与 agent 通信。它已实现一套「模拟流式」——把收到的完整消息按字符切片播放。但这只是视觉障眼法，无法降低真实的首字延迟（TTFT）：用户依然要等服务端把整段答案生成完，才看到第一个字。

真正的 livestreaming 要求服务端在生成过程中就把片段推送过来。问题随之而来：Copilot Studio 到底支不支持把回答一段段推给 Direct Line 客户端？如果支持，片段长什么样？

验证开始前，必须先厘清两个常被混淆的命题：

  • 「能力是否支持」——这是平台层面的声明。微软官方文档明确 Copilot Studio 可以做 livestreaming。
  • 「能力是否下发」——这是某个具体租户 / 区域 / 部署环（ring）的运行时是否实际产生流式片段。

「支持」不等于「下发」。本文的验证目标，正是用原始数据把这两件事分开，而不是停留在文档措辞上。

02 / Protocol

WebChat Livestreaming 协议拆解

判断「有没有流式」之前，必须先知道流式片段在协议里长什么样。依据是 BotFramework-WebChat 官方文档与源码。

下列词分别指 transport、runtime、identity 与 measurement；混用会直接导致 endpoint 或 reducer 选错。

术语本文定义
D2EDirect-to-Engine：客户端直接调用 Copilot Studio runtime 的 SSE 集成方式
SSEServer-Sent Events：服务器通过一个 HTTP response 持续发送 event frames
recognizerAgent shape 判据；GenerativeAIRecognizer 对应 Classic，CLIAgentRecognizer 或 CLICopilotRecognizer 对应 New Agent
published-botClassic Agent 的 D2E runtime family
/3pNew Agent agentic runtime 的第三方 D2E endpoint family
TTFTTime to first token：发送用户消息到收到首个非空答案文本的时间

Direct Line livestreaming 复用既有的 typing 活动携带渐进正文，通常由终止 message 收口。同一条流式回答用 streamId 标识；conversation 由独立的 conversation ID 管理。streamSequence 递增用于丢弃乱序片段。

informative
typing · "正在搜索…"
→
streaming
typing · 累积正文片段
→
final
message · 完整封口

片段的文本编码不能一概而论：可能是 delta，也可能是 snapshot / full-text-so-far。客户端应先读取 chunkType，再按运行时选择 append 或 replace；New Agent /3p 在未明确标记 delta 时按 authoritative snapshot 处理。

这是最容易被误传的一点。「informative」「streaming」「final」不是 activity 的 type，而是流式元数据对象里 streamType 字段的取值。底层 activity 的 type 仍然是 typing（中间态）或 message（最终态）。

元数据可放在 channelData，也可放在 entities 数组里类型为 streaminfo 的对象中，两者等价。一个 streaming 片段的真实形态：

{ "type": "typing", "text": "A quick brown fox", "channelData": { "streamType": "streaming", "streamId": "a-00001", "streamSequence": 2 } }

或者元数据放在 entities：

{ "type": "typing", "text": "A quick brown fox", "entities": [ { "type": "streaminfo", "streamType": "streaming", "streamSequence": 2 } ] }

官方明确 livestreaming 的通道要求，这决定了客户端这边能不能收到：

通道是否支持原因
Direct Line（WebSocket）支持支持 typing 活动且返回 activity ID
Direct Line（REST）不支持忽略 typing 活动
Direct Line Speech / ASE不支持不返回 activity ID
Teams支持原生支持

MCSChat 已使用 webSocket: true 的 Direct Line，满足客户端前提——所以「收不到流式」不能归因于通道选错。

03 / Roadmap

可行路径总览：先对比，再钻进验证

进入具体测试前，先把「在 Web Chat 上拿到逐字体验」的可行路径摆出来对比，随后交代本次验证采用的方法。

术语：官方把「服务端边生成边推送、客户端渐进渲染」这一能力称为 livestreaming（亦称 streaming response），见 BotFramework-WebChat 文档 [1]。它不是新协议，而是一套约定：复用 typing 活动承载增量、用 streamType / streaminfo 元数据标记（§2）。下面四条路共用 Web Chat 作渲染层，但数据来源 / 协议各不相同——并非「同一个 streaming 协议」；其中 Direct Engine 是与 livestreaming 无关的另一套传输协议（SSE）。
路径数据来源 / 协议真实降 TTFT需要登录改造量
① 原生 livestreamingDirect Line（WebSocket）· typing + streaminfo是 · 须服务端下发取决于通道无
② Classic Agent D2E/dataverse-backed/... · SSE是是 · .Invoke中
③ New Agent D2E/agenticruntime/3p/... · SSE是 · 实验性路径是 · .Invoke中
④ 客户端模拟（打字机）无协议 · 本地动画否 · 纯视觉否小

① 原生 livestreaming — 用 agent 的 Direct Line token 端点 createDirectLine({ domain, token }) 接 WebSocket，再 renderWebChat；Web Chat 按 streamType 自动渲染。优：零改造、官方原生。劣：完全取决于服务端是否下发——本环境实测见 §4。

② Classic Agent D2E — published-bot runtime 使用 /copilotstudio/dataverse-backed/authenticated/bots/{schema} 与 api-version=2022-03-01-preview。这是公开 SDK 默认构造的地址。

③ New Agent D2E — CLIAgentRecognizer / CLICopilotRecognizer 必须改走 /copilotstudio/agenticruntime/3p/dataverse-backed/authenticated/bots/{schema} 与 api-version=1。微软官方插件 PR #26 已端到端验证每轮约 25 个 progressive typing 片段；Microsoft Learn 仍标注 New Experience 尚未被 Client Library 正式支持，因此生产采用需要把技术可用与正式支持分开评估。

④ 客户端模拟（打字机） — 在 Web Chat 的 activity middleware 拦截最终 message，按字符切片逐步更新气泡。优：不依赖服务端下发、不需登录、改动最小。劣：不降低真实 TTFT，纯视觉效果。

选型：先从 Agent 的 recognizer / template 判断代际。Classic Agent 走 published-bot D2E；New Agent 走 agentic runtime /3p；只有在不需要真实降低 TTFT 时才使用客户端模拟。

为避免「是不是客户端解析错了」的争议，验证直接订阅 Direct Line 的原始活动流，绕过应用自身的所有解析逻辑——在浏览器中直接订阅 SDK 暴露的原始 observable，把每条 bot 活动的完整 JSON（含 channelData 与 entities）原样记录下来：

directLineService._directLine.activity$.subscribe(activity => { if (activity.from?.id === 'user') return; rawActivities.push(JSON.parse(JSON.stringify(activity))); });

随后发送一条会触发长回答的问题，等最终 message 到达后，对全部活动做递归扫描，检查是否存在 streamType / streamId / streamSequence 字段或 streaminfo 实体。

04 / Direct Line 实测

三类 agent，零流式片段

为排除「agent 类型」这个变量，在同一环境用三种不同编排方式的 agent 各测一遍。

Agent编排方式观测结果
IVATopic 驱动1 条完整 message；typing 无元数据
Storyteller纯 instructions 生成式501 字一次性返回；typing 无元数据
UniversalStudio Campus生成式回答 + 知识库（RAG）~34s 后 1335 字一次性返回；9 条 typing 均无正文和流式元数据

三种最该出现流式的场景全部覆盖，原始活动流中从未出现流式标记。

对该次 RAG 长回答，Direct Line 共返回 10 条活动：9 条 typing + 1 条 message。9 条 typing 全部无正文、无流式元数据；最终 message 文本长度为 1335。

// 典型 typing（keep-alive，无任何流式字段） { "type": "typing", "id": "1zYR...|3eYh8Lrcsbk", "entities": [], "IsKeepAliveSignal": true, "TypingIndicatorActivationTime": "2026-06-15T13:21:13Z" // 无 channelData，无 streamType / streamId / streamSequence } // 最终 message（一次性完整正文） { "type": "message", "textLength": 1335, "textFormat": "markdown", "channelData": { "feedbackLoop": { "type": "default" } }, "entities": [] // entities 里没有 type === "streaminfo" }

逐项检查了本文目标 agent 的「生成式 AI」设置页：编排、深度推理、模型、回复格式、内容审核、用户反馈、允许无依据回答、Web 搜索、文件上传、代码解释器、增强搜索与租户图谱。在这些页面中没有发现 per-agent streaming 开关。是否下发片段仍需按 runtime、channel、environment 与 rollout 分别验证，不能从设置页反推出平台的完整支持范围。

05 / 转机

Direct Engine：SDK 提供 SSE 流式 API，运行时仍需实测

对接 Copilot Studio 不止 Direct Line 一条路。Microsoft 365 Agents SDK 的 Copilot Studio Client 提供 SSE AsyncGenerator API；API 存在证明客户端具备消费能力，不等同于每个 Agent、环境和 runtime 都会下发 progressive 片段。

方式协议 / 传输原生流式
Direct Line 3.0（当前）WebSocket / 轮询取决于服务端下发
iframe 嵌入（demo / live 站点）内部仍是 Direct Line + WebChat同上
Direct Line REST（C# SDK）HTTP 轮询否
Agents SDK — Copilot Studio ClientDirect Engine（SSE）API 已提供 · 是否下发需实测

@microsoft/agents-copilotstudio-client 通过 text/event-stream（SSE）逐条 yield 活动。stream metadata 决定答案生命周期；thought entity 承载 reasoning 文本；toolCall entity 承载工具 started / completed 生命周期。三者必须独立归一化，不能混成一组进度行。stream metadata 可位于 entities 或 channelData：

const streamingEntity = activity.entities?.find( e => e.type === 'streaminfo' && e.streamType === 'streaming' ) case ActivityTypes.Typing: if (streamingEntity || activity.channelData?.streamType === 'streaming') { const id = streamingEntity?.streamId ?? activity.channelData?.streamId const sequence = streamingEntity?.streamSequence ?? activity.channelData?.streamSequence // 按 streamId + sequence 累积片段，排序后拼接 }

它还提供一组 AsyncGenerator 流式 API：startConversationStreaming()、sendActivityStreaming()、executeStreaming()、subscribeAsync()——正是为渐进输出设计的接口形态。

Agent 的 schema name 只标识目标，不能决定运行时。先读取 Dataverse bot.template 或 recognizer，再选择 endpoint family：

Agent shape识别字段Direct-to-Engine base URL
Classic / published botdefault-2.1.0 / GenerativeAIRecognizer/copilotstudio/dataverse-backed/authenticated/bots/{schema}?api-version=2022-03-01-preview
New Agent / agentic loopcliagent-1.0.0 / CLICopilotRecognizer/copilotstudio/agenticruntime/3p/dataverse-backed/authenticated/bots/{schema}?api-version=1
错误特征：把 New Agent 发往旧 published-bot endpoint 时，HTTP 与会话创建可能成功，但 agent 返回 This new-generation agent isn't supported in this experience.。这表示 runtime family 选错，不表示 New Agent 不具备 D2E streaming。

07 / Runbook

Direct Engine 配置实操：从 App 注册到流式调用

§6 已证明端点可达；其捷径测试触发的 403 揭示了正规路径需 CopilotStudio.Copilots.Invoke 委托权限。以下步骤先在 Azure / Entra 完成应用注册与委托授权，再在前端取 token、选择运行时 endpoint 并发起 SSE 调用。截图均来自 Entra 管理中心，账户与具体 ID 已打码。

项要求
注册应用权限目标租户的 Application Developer 或更高，可创建 App Registration
授予同意权限Privileged Role Administrator / Global Administrator，用于 Grant admin consent
目标 agent 信息Copilot Studio agent 所在 Power Platform 环境的 Environment ID 与 agent 的 schema name
前端依赖@microsoft/agents-copilotstudio-client、@azure/msal-browser（浏览器 PKCE 取 token）
一句话定位：整套配置的目的，是让前端能拿到一个 audience 为 api.powerplatform.com、且携带 CopilotStudio.Copilots.Invoke 委托权限的 token——这正是 §6 捷径测试触发 403 所揭示的那一项。

在目标租户创建一个用于 Direct Engine 调用的应用注册。同租户内调用自己的 agent，账户类型选单租户即可。

  • 入口 — Entra 管理中心 → Identity → Applications → App registrations → New registration。
  • Name — 取可识别的名字，如 Copilot Studio Direct Engine Client。
  • 账户类型 — Accounts in this organizational directory only（Single tenant）。
  • Redirect URI — 此处先留空，重定向在步骤四按调用形态单独配置。
  • 完成判据 — 点击 Register 后落到应用详情页（Overview）。

应用一建好就在 Overview 里记录两个 ID，后面取 token 的 clientId 与 authority 都要用。

  • 入口 — 应用注册完成后默认落在 Overview。
  • 必须记录 — Application (client) ID 与 Directory (tenant) ID。
  • 注意 — 对外发布截图时遮挡真实 ID，公开版不暴露具体值。

这是整条链路的关键一步——补上 §6 里缺失的 CopilotStudio.Copilots.Invoke。

  • 入口 — 左侧 API permissions → Add a permission。
  • 选 API — 切到 APIs my organization uses tab，搜索 Power Platform API。
  • API 不在列表？ — 该租户尚未注册其服务主体，先执行 az ad sp create --id 8578e004-a5c6-46e7-913e-12f58912df43 后再搜。
  • 权限类型 — Delegated permissions → 展开 CopilotStudio → 勾选 CopilotStudio.Copilots.Invoke → Add permissions。
  • 管理员同意 — 回到权限主页点 Grant admin consent for {tenant}，Status 列变绿勾。
  • 完成判据 — Configured permissions 中出现 CopilotStudio.Copilots.Invoke（Delegated）且 Status = Granted。
对照 §6.2：当时 az CLI token 的 scope 只是 .Test，服务器返回 InsufficientDelegatedPermissions: [CopilotStudio.Copilots.Invoke]。本步骤补的正是这一项；漏掉 Grant admin consent 同样会复现该 403。

按调用形态二选一配置重定向。MCSChat 这类浏览器前端走 SPA + PKCE；命令行或桌面工具走 public client。

  • 浏览器（SPA + PKCE） — Authentication → Add a platform（新版为 Add Redirect URI）→ Single-page application → Redirect URI 填前端 origin，如 http://localhost:5173。
  • 命令行 / 桌面 — Authentication → 勾选 Allow public client flows = Yes，并按需添加 http://localhost 重定向。
  • 注意 — SPA 平台默认启用 PKCE，无需 client secret；Direct Engine 浏览器直连场景不应下发机密。
  • 完成判据 — 重定向 URI 与前端实际回调地址逐字一致（含端口、是否带尾斜杠）。

走通后记录 SSE 流中的有效 typing chunk 数、streamSequence、TTFT 与 final activity；这能区分服务端真实渐进下发与前端模拟动画。

本文验证的是 delegated user-token 调用链路：浏览器 SPA 通过 MSAL 获取携带 CopilotStudio.Copilots.Invoke 的 token，再调用 D2E SSE endpoint。本文没有验证 application-permission、匿名调用或服务账号代理路径，因此不对这些路径作可用性结论。

不要从 /authenticated/ 字面推导完整支持矩阵。生产架构应以 Microsoft Learn、目标租户的权限清单和一次真实 token exchange 为准。

08 / 消息处理

New Agent 活动必须先按 turn 归一化，再进入 UI

/agenticruntime/3p 返回的内容比 Classic livestreaming 更丰富：一轮中可能交错出现 thought、informative、toolCall、answer snapshot 与 final。activity 到一条就追加一个 DOM 节点会产生断句、重复正文、空气泡和进度后置。正确边界是先维护 TurnState，再分别更新 Work panel 与主答案气泡。

先按语义分类，再决定显示位置；transport 字段本身不应直接决定 DOM 数量。

Raw activity归一化事件更新位置关键规则
entities[type=thought]reasoningUpdateWork panel 的一个 reasoning 段落合并快照与片段，不创建 checklist item
streamType=informativestageUpdateWork panel 的 stage 列表同一阶段原位更新，晚到状态仍留在答案前
entities[type=toolCall]toolUpdateWork panel 的工具行按 tool_call_id 合并 started / completed

空 streaming / 空 finalnoContent / cancel不创建或移除未完成气泡无正文、附件或 action 时不显示 metadata；Work panel 可折叠保留为 trace

所有到达顺序差异都收敛到一个 turn-level state；UI 只订阅 state 变化，不直接订阅 raw activity。

TurnState { phase: 'working' | 'streaming' | 'completed' | 'cancelled' startedAt: number reasoningText: string stages: Map<stageId, { label, status, durationMs? }> answerText: string answerState?: { streamAliases, lastSequence, chunkCount } finalText?: string }
  1. 1 · Working

    首个 thought、informative 或 toolCall 创建 Work panel；reasoning 更新同一段落，stage 按 ID 原位更新。

  2. 2 · Answer Streaming

    首个非空 answer snapshot 只负责延迟创建唯一答案气泡。可以折叠 Work panel 减少视觉干扰，但不能据此把 active tool 或 stage 伪造为 done。临时 stream key 与后续真实 streamId 绑定到同一 answer state。

  3. 3 · Completed / Cancelled

    终止 message 或显式 final 写入权威正文并关闭 answer state。只有收到 tool/stage completed 或 turn final 后，相关 stage 才能标记 done；此时面板改为 Worked for Ns 并自动折叠。contentless final 在没有可渲染正文时取消未完成答案；晚到 answer chunk 直接丢弃。

thought entity 没有稳定 ID 或 sequence，不能把每次返回当成独立步骤。reducer 必须同时处理累计快照、修订快照、重叠片段与新片段。

文本关系处理目的
完全相同忽略去除重发

Stage reducer：toolCall 与 informative 共用一个 stages 容器。有 tool_call_id 时用该 ID；没有 ID 的 informative 先转小写、去掉首尾空白、末尾省略号和 Calling / Running / Loading、completed / finished 等状态词，再把规范化 label 作为 key。started 显示 spinner，completed 在同一行改为勾选，并可附 duration_ms。

Work panel 不是 raw log，也不是主消息列表。它是可折叠的 turn trace：工作时展开；答案开始时可折叠但保留真实 pending/done 状态；收到 turn final 后显示 Worked for Ns 并保持可展开。

验收项通过条件
Reasoning任意数量 thought chunks 最终只对应一个连续 paragraph
Stages同一 tool ID 的 started / completed 只有一行，最终状态为 done
Answer一轮只有一个非空答案气泡；final text 与气泡正文完全一致
OrderingWork panel 在 DOM 和视觉上均位于 answer 前；晚到状态不能移动答案

MCSChat 的验证页在 ?debug=1 时暴露 query-gated replay hook，可确定性回放累计 thought、碎片 thought、修订 thought、tool started/completed、空 chunk、临时 stream key、重复 final 与晚到事件。回放应逐项满足上表，而不是只看页面是否出现文字。

09 / Conclusion

结论与后续路径

把「支持」与「下发」分开后，事实链条清晰了。

  • 协议层成立：livestreaming 协议真实存在，微软自家 SDK 就在用 streaminfo / streamType，与 WebChat 文档一致。
  • 本文实测的 Direct Line 环境未下发：当前环境三类 agent 实测均无流式片段，原始 payload 本身不含协议字段——不是客户端解析问题，也不能外推为所有 Direct Line 环境都不下发。
  • Web Chat 是渲染层：Direct Line livestreaming 与 Direct-to-Engine SSE 是两套传输机制，客户端可把两者规范化到同一个消息渲染状态机。
  • Direct Engine 有两个 runtime family：Classic Agent 使用 published-bot endpoint；New Agent 使用 agentic runtime /3p endpoint。只替换 schema name 不足以切换 Agent 代际。
  • 外部证据验证 New Agent /3p progressive streaming：微软官方插件于 2026-07-22 合并 `/3p` 实现并记录每轮约 25 个 progressive typing 片段；微软员工独立 playground 于 2026-08-05 记录过 150+ progressive 片段。
  • MCSChat 本地证据边界：MCSChat 已在 GitHub Pages 验证 /3p 选路、SPA 登录、目标 New Agent 会话建立，以及 thought / toolCall / answer fixture 的归一化行为；本文没有展示 MCSChat 自身的完整生产 activity dump。
  • 正式支持边界仍存在：Microsoft Learn 于 2026-07-27 仍写明 New Experience 尚未被 Copilot Studio Client Library 正式支持；渠道矩阵也把 Native app / Direct Line 标为不可用。/3p 应视为可用的实验性集成路径，而不是 GA 承诺。
  • 未发现 per-agent streaming 开关：在本文检查的 agent 设置页中没有独立 streaming 开关；实际下发仍可能受 runtime、channel、environment 与 rollout 控制。
  1. Support gate：明确接受 /3p 尚未进入 Microsoft Learn 正式 Client Library 支持矩阵；生产 SLA 不能只依赖实验性实现。
  2. Identity gate：在目标租户完成 delegated permission、admin consent、SPA redirect URI 与真实 token exchange；仅看到登录页不算通过。
  3. Wire gate：保存一轮完整 ordered activity dump，确认至少包含 conversation ID、首个非空 answer、终止 message/final，以及预期的 thought/toolCall/informative 字段。
  4. UI gate：确定性 replay 必须满足 §8.4：一个 reasoning transcript、一个答案气泡、tool lifecycle 原位更新、零空气泡、零重复 final、零 pending spinner。
  • 平台支持声明：只由 Microsoft Learn、正式 release note 或产品支持矩阵支撑；GitHub PR 和公开样例只能证明实现存在。
  • 环境下发事实：只由目标环境的 raw ordered activities 支撑；其他租户的 chunk 数不能代替本地 capture。
  • 客户端行为：由 reducer fixture 和浏览器断言支撑；看到动画不等于服务端 progressive streaming。
  • 错误归因：403、401、404、AADSTS50011 与 runtime mismatch 分别记录 status、response body、token audience 和 endpoint 后再判断，不把所有失败归为“不支持”。
