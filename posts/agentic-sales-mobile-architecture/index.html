运行时架构 · 端到端操作流

让一句话可靠地变成正确的工具调用

本文描述应用的运行时架构：一条把销售口语翻译成工具调用的端到端操作流——理解一句话说了什么、计划该调哪些工具及其顺序、带人工确认与接地地执行、再把每次调用落到其后端（CRM 写操作落 Dataverse，读操作返回记录与答案）。

看端到端操作流 从业务需求讲起
一句话架构

把一句话翻译成经过校验的工具调用——理解、计划、执行、落地四段。

先理解——把一句话拆成多个独立意图；再计划——把每个意图映射到一个技能函数（工具）并建立依赖图。这两次 LLM 调用（代码中称 Frame 与 Orchestrator）都用自由文本输出 + 客户端 Zod 校验。

  • 1理解 — 把一句话拆成多意图
  • 2计划 — 意图映射到工具、定序
  • 3执行 — 带确认与接地地调用
  • 4落地 — 校验并适配到后端

01 / Business Need and Architectural Requirements

把销售口述可靠地变成 CRM 里的记录与判断

现场销售在两次拜访之间用口语与系统交互：一句话既要落成 CRM 记录，也要问出对自己业务盘子的判断。一句自然表达往往裹挟多件有依赖的事，而销售不会按系统的字段边界说话。要把这种输入稳定地变成正确的记录与可信的回答，架构必须同时满足四条属性。

「我刚拜访了协和医院的张主任，他们对新款监护仪很感兴趣，建一个商机，金额大概 150 万，下周三再约他复盘。」——一句代表性的销售口述，下面四条属性都要从它这样的输入里成立。

01

可拆分与定序

上句含三件事：记一次已发生的拜访、建一个新商机、约一个未来的会议——对象、时态、动作各不同，且商机与会议要挂在先解析出的客户与联系人下。架构必须先拆分、再定依赖顺序，才能动手。

02

写前可核对

每一次写库（建商机、记活动、改字段）都要在触及 Dataverse 之前由人确认。销售对着系统说话不等于授权入库，模型输出更不能静默落库——写操作必须先呈现为可核对的草稿。

03

读必接地

销售也要问「这周该盯哪些商机」「这个客户还能不能救」。这类查询与分析的答案必须严格来自真实记录，不允许模型编造名称、金额或趋势——读路径要接地，判断才可信。

04

落库正确

「下周三」要换算成具体日期、「150 万」要落成数字金额、「协和医院」要匹配到 Dataverse 里真实存在的客户记录。任一步错就是脏数据，而底层模型不可信、有不确定性，架构要在其之上保证正确。

02 / End-to-End Operation Flow

从一句话到被执行的工具调用的完整路径

03 / The Understanding Stage

把一句话切成多个独立意图

理解阶段（代码中称 Frame）是流水线的第一段，唯一职责是「拆」。它读入用户原句加页面上下文，输出一个意图数组，每个意图标注销售对象、认知任务、时态，以及它依赖哪些兄弟意图。拆分一旦定下，下游不再重新分类。

每个意图（IntentItem）携带四个判定维度，下游据此选技能、定顺序、解时态：

维度 取值 作用
salesObject Account / Contact / Opportunity / Activity / Product / None 意图操作的业务对象
cognitiveTask Log / Plan / Find / Update / Recommend / Analyze / Knowledge / Report / Chat 意图的动作类型，决定映射到哪类技能
temporal past / future / none 时态，决定活动是已完成还是已计划
relatesTo [0, 2] 等兄弟意图下标 依赖编码，下游据此建 DAG 顺序

时态错点：理解阶段在意图分类的提示词里显式注入今天的日期与星期，模型据此把「下周三」这类相对时间换算成具体日期。

04 / The Planning Stage

把意图排成有依赖的执行计划

计划阶段（代码中称 Orchestrator）是第二段，职责是「排」——不重新分类、不拆并意图，只把上一段给定的每个意图映射到一个技能函数（工具）、填充参数、用 $ref 占位符表达跨步依赖，产出一张 DAG。它是一个受约束的「填空」任务。

↹

一步一函数

每个 DagStep 含 seq 执行序号、function 技能名、arguments 参数；同一 seq 可并行。Orchestrator 只填这些，不碰意图边界。

$

$ref 表达依赖

一步的产出用 outputRef 命名（如 $opp），后续步骤在 arguments 里用 $opp.id 引用；执行时 resolveRefs() 展开占位符。这把「先建客户再挂商机」的顺序固化进结构。

页面绑定实体：当对话发生在某个客户/商机详情页时，Orchestrator 接收页面已解析的实体，无需让 LLM 重新查询或猜测，既省一次解析也避免错挂。

05 / The Intent Queue

多意图如何串成可核对的卡片流

规划出的多意图不会一次性闷头写库，而是进入一条带游标的意图队列，逐个推进。队列把「纯状态」与「纯副作用」分开：意图队列本身是一个纯函数 reducer，所有 I/O 集中在运行时。

draft

草稿类 — 阻塞确认

draftActivity / draftOpportunity 等先把数据整形成预填表单卡片，等用户 Save 才真正 create()。写库前必有人核对。

update

更新类 — 阻塞确认

updateActivity / updateOpportunity 等把现有记录预填进卡片，用户改完 Save 才 update()。与草稿类同样需要核对。

query

查询类 — 直接返回

queryAccounts / queryActivities 等是只读的，立即执行并展示结果列表，不渲染阻塞卡片——读不需要确认。

模糊匹配级联：当意图引用了「协和医院」这类名字，队列先插入一个匹配选择卡片，让用户在候选中确认或跳过；选定的实体 ID 累积进 resolvedContext，供后续兄弟意图自动引用。

06 / The Intelligent Read Path

读路径只在真实记录上作答，并把定量拆解交给可回溯的图表

第 01 节的「读必接地」由本节兑现。标注为 Analyze / Report 的读意图不直接让模型作答，而是先查询、再交给一个接地分析步（analyzeResults）在取回的真实记录上推理。本节分四层展开：如何决策、由谁算数、如何渲染与回到记录、以及文字与图表如何分工与其边界。

分析步返回一个结构化结果 { answer? | followupQuery? , chart? }，运行时按出现了哪个字段分派：

结构字段 运行时动作 终止保证
answer 当前记录足以回答，直接给出接地答案。 终态。
followupQuery 当前记录不足，补一次相关查询（如账户 → 其活动），在合并记录上重分析。 补查上限 MAX_HOPS = 1；末跳被强制只能返回 answer，回路不可能递归。
chart 答案是定量拆解，附一张图表规格（见第二、三层）。 与 answer 并存，非独立分支。

失败样例走查：问「Rush 客户还能不能救」，账户记录里没有商机与近期活动 → 触发一次 followupQuery 补查其活动与商机 → 仍为空 → 末跳强制作答，如实回复「以现有记录无法评估其健康度」，而非编造一个乐观结论。

要让「读必接地」可证，数值的产出权必须离开模型。模型只输出一个图表规格 { type, dimension, metric }——按什么分、用哪种图、看金额还是数量；代码据此对真实记录分组并计算每一个数字。

模型

模型负责选择

判断该不该出图、按哪个维度（阶段 / 客户 / 月份 / 负责人）、用柱 / 环 / 折线、度量取金额还是数量。它只碰「怎么看」，不碰「是多少」，也从不产出 HTML 或 SVG。

代码

代码负责算数

按 dimension 把取回的记录分组，逐组累加 metric，并在每组内保留成员记录的指针。每个柱高、每个占比都能追溯到具体记录，数值可证。

被否掉的替代方案：让模型直接输出聚合后的数字或一张渲染好的表。否决依据——模型会误算或编造，违反「读必接地」，且产出无法与记录对账；只让它出规格，才能把每个数字钉在真实记录上。

选型由数据形状决定

固定渲染器据规格选型：排名比较用柱状，占比且组数 ≤ 6 用环形，时间维度用折线；类别名过长自动转横向柱；类别超过 Top-N（上限 10）时，尾部折叠成一个可展开的「其它」，其内再按子组下钻。

三级兜底保证该出图就出图

有模型规格就用模型的；模型未给时，从用户原话推断维度（「按客户」「按月」）；仍无则回退到阶段管道拆解。因此定量拆解请求即便模型漏给规格，也稳定出图。

下钻闭环回到同一批记录

点一段 → 就地展开它的成员记录 → 点一条 → 按实体类型（商机 / 客户 / 活动 / 联系人四种路由）进入详情页。图表、下钻清单、详情页是同一批取回记录的三个视图：柱上的数字与详情页里的金额是同一个值。

文字

文字只担洞察

有图表时，文字被约束为洞察——集中度、异常、风险、下一步动作；代码会剥掉模型答案里的分组罗列与小标题，使文字不复述图表已呈现的分组明细。

图表

图表只担明细

每组的数值与成员记录由图表及其下钻承担。文字答「为什么重要」，图表答「具体是多少、由哪些记录构成」，两者不重叠。

边界与代价：图表仅在「定量拆解且组数 ≥ 2」时出现，单个数值仍走文字；金额不带统一货币符号，因为同一盘子可能混币种；接地读路径比裸查询多一次模型往返，遇 followupQuery 再多一次——这是用延迟换正确性的取舍。

07 / Contracts and Adaptation

两道防线：注册表契约 与 适配器

LLM 的输出是不可信的，数据库的列名是反直觉的。架构在这两处各设一道防线：函数注册表用 Zod 校验每个技能的输入输出；服务适配器把应用模型翻译成 Dataverse 的真实列名。

第一道：输出必须过契约校验

每个技能在注册表里声明自己的输入输出契约。模型回复必须先过这道校验才能进入业务流程；校验失败就返回一个明确的错误，绝不静默放行、也不允许调用方自行猜测或强转。这是让不可信的 LLM 输出变可用的架构手段。

第二道：适配层隔离数据库细节

每张表一个适配器，把 Dataverse 的物理字段翻译成业务模型、反向再翻译回去，业务代码只面对干净的业务字段，不被平台的选项集、查找字段、创建回读等细节渗透。这些 Dataverse SDK 层面的具体适配机制见 Power Apps Code App 技术文章。

08 / Observability

任何静默降级都必须留下痕迹

LLM 流水线天然有不确定性：某次调用可能畸形需重试，某个字段可能缺失被补默认。架构的硬规则是：任何重试、补值、回退都不能「看起来像一次干净的运行」，必须在控制台告警、在 PipelineResult 里带上布尔与原因、并在 Frame Inspector 里显示一枚标记。

▤

可回放的运行记录

Inspector 保留最近若干次运行的 Frame 结果（意图、推理、置信度）、Orchestrator 延迟，以及发送给 LLM 的精确 prompt 文本与原始响应，可直接复制到 playground 复现。

⟳

重试与补值高亮

当 Frame 或 Orchestrator 因畸形输出重试，运行记录带上 frameRetried / planRetried 与原因，Inspector 用醒目标记呈现；字段补值同样以列表形式标出，绝不静默。
