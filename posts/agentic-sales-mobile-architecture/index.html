Frame + Orchestrator：把一句话拆成可核对、可落库的销售动作

本文描述应用的运行时架构——一条由意图分类（Frame）、计划编排（Orchestrator）、队列执行、数据适配四段构成的对话流水线。

看端到端数据流 从 Frame 讲起
一句话架构

两阶段 LLM 流水线 + 客户端 Zod 契约校验。

Frame 负责「拆」——把一句话切成多个独立意图；Orchestrator 负责「排」——把每个意图映射到技能函数并建立依赖图。两段都用自由文本输出 + 客户端 Zod 校验。

  • 1Frame — 多意图分类（拆）
  • 2Orchestrator — 技能映射与 DAG（排）
  • 3意图队列 — 串联确认与执行
  • 4适配层 — 落库 Dataverse

01 / The Problem

为什么不能用一次 LLM 调用直接落库

销售口述往往一句话裹挟多件事，且彼此有依赖。直接把整句丢给一次 LLM 调用让它「自由发挥」地写数据库，会在三个地方失控：意图边界、执行顺序、数据正确性。

「我刚拜访了协和医院的张主任，他们对新款监护仪很感兴趣，建一个商机，金额大概 150 万，下周三再约他复盘。」

01

意图边界

这句话里有三件事：记一次已发生的拜访、建一个新商机、约一个未来的会议。时态不同、对象不同、动作不同，必须先切开。

02

执行顺序

商机要挂在「协和医院」这个客户下，会议要关联「张主任」这个联系人。客户、联系人必须先解析出来，商机和会议才能引用——这是依赖关系。

03

数据正确性

「下周三」要换算成具体日期，「150 万」要落成数字金额，「协和医院」要匹配到 Dataverse 里真实存在的客户记录——任一步出错就是脏数据。

03 / The Frame Stage

把一句话切成多个独立意图

Frame 是流水线的第一段，唯一职责是「拆」。它读入用户原句加页面上下文，输出一个意图数组，每个意图标注销售对象、认知任务、时态，以及它依赖哪些兄弟意图。Frame 一旦定下拆分，下游不再重新分类。

每个意图（IntentItem）携带四个判定维度，下游据此选技能、定顺序、解时态：

维度 取值 作用
salesObject Account / Contact / Opportunity / Activity / Product / None 意图操作的业务对象
cognitiveTask Log / Plan / Find / Update / Recommend / Analyze / Knowledge / Report / Chat 意图的动作类型，决定映射到哪类技能
temporal past / future / none 时态，决定活动是已完成还是已计划
relatesTo [0, 2] 等兄弟意图下标 依赖编码，下游据此建 DAG 顺序

时态错点：Frame 在意图分类的提示词里显式注入今天的日期与星期，模型据此把「下周三」这类相对时间换算成具体日期。

04 / The Orchestrator Stage

把意图排成有依赖的执行计划

Orchestrator 是第二段，职责是「排」——不重新分类、不拆并意图，只把 Frame 给定的每个意图映射到一个技能函数、填充参数、用 $ref 占位符表达跨步依赖，产出一张 DAG。它是一个受约束的「填空」任务。

↹

一步一函数

每个 DagStep 含 seq 执行序号、function 技能名、arguments 参数；同一 seq 可并行。Orchestrator 只填这些，不碰意图边界。

$

$ref 表达依赖

一步的产出用 outputRef 命名（如 $opp），后续步骤在 arguments 里用 $opp.id 引用；执行时 resolveRefs() 展开占位符。这把「先建客户再挂商机」的顺序固化进结构。

页面绑定实体：当对话发生在某个客户/商机详情页时，Orchestrator 接收页面已解析的实体，无需让 LLM 重新查询或猜测，既省一次解析也避免错挂。

05 / The Intent Queue

多意图如何串成可核对的卡片流

规划出的多意图不会一次性闷头写库，而是进入一条带游标的意图队列，逐个推进。队列把「纯状态」与「纯副作用」分开：意图队列本身是一个纯函数 reducer，所有 I/O 集中在运行时。

draft

草稿类 — 阻塞确认

draftActivity / draftOpportunity 等先把数据整形成预填表单卡片，等用户 Save 才真正 create()。写库前必有人核对。

update

更新类 — 阻塞确认

updateActivity / updateOpportunity 等把现有记录预填进卡片，用户改完 Save 才 update()。与草稿类同样需要核对。

query

查询类 — 直接返回

queryAccounts / queryActivities 等是只读的，立即执行并展示结果列表，不渲染阻塞卡片——读不需要确认。

模糊匹配级联：当意图引用了「协和医院」这类名字，队列先插入一个匹配选择卡片，让用户在候选中确认或跳过；选定的实体 ID 累积进 resolvedContext，供后续兄弟意图自动引用。

06 / Contracts and Adaptation

两道防线：注册表契约 与 适配器

LLM 的输出是不可信的，数据库的列名是反直觉的。架构在这两处各设一道防线：函数注册表用 Zod 校验每个技能的输入输出；服务适配器把应用模型翻译成 Dataverse 的真实列名。

第一道：输出必须过契约校验

每个技能在注册表里声明自己的输入输出契约。模型回复必须先过这道校验才能进入业务流程；校验失败就返回一个明确的错误，绝不静默放行、也不允许调用方自行猜测或强转。这是让不可信的 LLM 输出变可用的架构手段。

第二道：适配层隔离数据库细节

每张表一个适配器，把 Dataverse 的物理字段翻译成业务模型、反向再翻译回去，业务代码只面对干净的业务字段，不被平台的选项集、查找字段、创建回读等细节渗透。这些 Dataverse SDK 层面的具体适配机制见 Power Apps Code App 技术文章。

07 / Observability

任何静默降级都必须留下痕迹

LLM 流水线天然有不确定性：某次调用可能畸形需重试，某个字段可能缺失被补默认。架构的硬规则是：任何重试、补值、回退都不能「看起来像一次干净的运行」，必须在控制台告警、在 PipelineResult 里带上布尔与原因、并在 Frame Inspector 里显示一枚标记。

▤

可回放的运行记录

Inspector 保留最近若干次运行的 Frame 结果（意图、推理、置信度）、Orchestrator 延迟，以及发送给 LLM 的精确 prompt 文本与原始响应，可直接复制到 playground 复现。

⟳

重试与补值高亮

当 Frame 或 Orchestrator 因畸形输出重试，运行记录带上 frameRetried / planRetried 与原因，Inspector 用醒目标记呈现；字段补值同样以列表形式标出，绝不静默。
