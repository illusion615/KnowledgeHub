Model Context Protocol

MCP 原理与开发指南：协议解剖与 TypeScript 落地实操

Model Context Protocol（MCP）是一套开放协议，用统一的 JSON-RPC 通道把 LLM 应用与外部数据、工具、工作流连接起来。本文面向架构师与技术决策者，先解剖协议原理——参与方、原语、生命周期、传输——再用 TypeScript 演示如何从零构建一个可运行的 MCP server，并给出安全加固与选型判据。

核心主张

MCP 用一套 JSON-RPC 协议，把「模型 × 工具」的集成从 M×N 收敛为 M+N，并划定清晰的安全边界。

  • 3能用 TypeScript 从零构建并运行一个 MCP server。
  • 4能判断某场景该用 MCP、还是直接 function calling 或私有 API。

01 / Why It Exists

为什么需要 MCP：把 M×N 集成收敛为 M+N

每个 AI 应用要接每个工具时，若各写各的胶水层，M 个应用 × N 个工具就是 M×N 套私有集成。MCP 借鉴 Language Server Protocol（LSP）的思路，把这层协议标准化：工具只实现一次 server，应用只实现一次 client，集成成本降为 M+N。官方把它类比为「AI 应用的 USB-C 接口」。

MCP 解决的是「重复集成」而非「模型能力」。同一份工具接入代码，过去要为每个宿主重写一遍；有了协议约定，一次实现即可被所有兼容宿主复用。

无协议 · M×N

每个应用为每个工具单独适配

  • 工具方要为不同宿主分别维护接入逻辑与鉴权。
  • 应用方每接一个新工具，都要理解一套新接口。
  • 接口无版本约定，任一端升级都可能打断对方。
有协议 · M+N

工具实现一次 server，应用实现一次 client

  • 任意 MCP 兼容宿主都能发现并调用同一个 server。
  • 能力通过协商声明，双方只使用彼此支持的功能。
  • 版本以日期串标识，向后兼容变更不打断既有会话。

从生态位置看，MCP 对三类角色各有收益，构成它被广泛采纳的动力。

01

开发者

构建或接入 AI 应用时，减少集成的开发时间与复杂度——一次实现，处处可用。

02

AI 应用与智能体

即时接入一整套数据源、工具与工作流生态，扩展模型能力、改善端到端体验。

03

最终用户

获得更有能力的助手：在获得授权时，能访问自己的数据并代为执行操作。

MCP 不是 function calling 的替代品，而是它的传输与发现层：function calling 决定「模型如何表达要调用某个工具」，MCP 决定「工具如何被发现、连接、鉴权与复用」。

  • 互补关系 — 宿主把 MCP server 暴露的 tools 转成模型的 function/tool 声明；模型仍用 function calling 决定调用哪个、传什么参数。
  • MCP 多做的事 — 连接生命周期、能力协商、资源与提示原语、双向请求（sampling）、传输与会话管理，这些都超出裸 function calling 的范畴。
  • 选择判据 — 单一应用内的少量工具，直接 function calling 更轻；要把工具做成可跨宿主复用的产品，MCP 更合适（详见选型一节）。

02 / Architecture

架构总览：Host / Client / Server 三参与方

MCP 采用 client-host-server 架构：一个 host 进程可运行多个 client，每个 client 与一个 server 维持一对一的有状态会话。架构建立在 JSON-RPC 2.0 之上，专注于上下文交换与 sampling 协调，同时用 host 隔离各 server、维护安全边界。

这张全景图把 MCP 的运行拓扑与「开发责任」叠在一起：分三层看谁在跑、谁提供、你要写哪一层。

三者职责边界清晰：host 是容器与协调者，client 是隔离的连接器，server 是聚焦的能力提供者。

01

Host（宿主）

发起连接的 LLM 应用。创建并管理多个 client，控制连接权限与生命周期，执行安全策略与用户授权，协调 LLM 与 sampling，并跨 client 聚合上下文。

02

Client（客户端）

由 host 创建、与单个 server 保持一对一会话的连接器。负责协议协商与能力交换，双向路由消息，管理订阅与通知，并维护各 server 之间的安全隔离。

03

Server（服务器）

提供专门上下文与能力的服务。通过原语暴露 resources、tools、prompts，职责聚焦、独立运行；可发起 sampling 请求；必须遵守安全约束。可以是本地进程或远程服务。

一次典型的工具调用是「用户/模型意图 → client 请求 → server 执行 → 结果回到宿主与模型」的闭环。

  • 1
    宿主发起动作

    用户或模型触发一个需要工具的动作；host 让对应的 client 准备一次请求。

  • 2
    Client 向 Server 请求

    client 用 JSON-RPC 发送 tools/call 等请求；请求只携带该 server 所需的最小上下文。

  • 3
    Server 执行并返回

    server 执行工具逻辑，返回结构化结果（如文本、图片等 content 数组）。

  • 4
    宿主更新模型上下文

    client 把结果回传 host；host 更新 UI 或把结果并入模型上下文，进入下一步推理。

协议的取舍围绕四条设计原则展开，它们直接解释了为什么 server 被设计得如此轻量、隔离。

  • 1Server 极易构建 — 复杂的编排责任由 host 承担，server 只聚焦定义清晰的能力，接口简单，实现负担低。
  • 2Server 高度可组合 — 每个 server 独立提供聚焦功能，多个 server 可无缝组合，共享协议保证互操作。
  • 3Server 受隔离约束 — server 读不到完整对话，也「看不进」其它 server；完整会话历史留在 host，跨 server 交互由 host 管控。
  • 4能力渐进增加 — 核心协议只保留最小功能，额外能力按需协商；client 与 server 各自独立演进，保持向后兼容。

03 / Primitives

协议原语：六个原语与控制权归属

MCP 的功能由原语承载：server 向 client 提供 Tools、Resources、Prompts；client 向 server 提供 Sampling、Roots、Elicitation。理解每个原语「由谁提供、由谁控制」，是判断一次会话能做什么、以及安全边界在哪的关键。

下表给出六个原语的提供方、控制方与作用；控制方决定了谁能触发它、需要谁同意。

原语 提供方 控制方 作用
Tools Server 模型 可被模型调用的函数，用于执行动作或获取数据（需用户授权）。
Resources Server 宿主应用 类文件的只读上下文数据，由宿主决定何时注入模型。
Prompts Server 用户 预置的模板化消息与工作流，由用户显式选择触发。
Sampling Client Server 发起 让 server 借用宿主的 LLM 完成子任务（每次需用户批准）。
Roots Client Server 发起 向 server 声明其可操作的文件系统或 URI 边界。
Elicitation Client Server 发起 运行时向用户请求补充的结构化输入（2025-06-18 修订引入）。

Server 侧的三个原语覆盖「能做什么、能读什么、按什么模板做」，是 MCP 最常用的部分。

01

Tools（工具）

模型可执行的函数，带 JSON Schema 描述的输入。是产生副作用（下单、写库、调用 API）的入口，宿主在调用前应取得用户同意。

02

Resources（资源）

由 URI 标识的只读数据（文件、API 响应、数据库行）。宿主决定何时把哪些资源纳入上下文，可订阅变更通知。

03

Prompts（提示）

服务器预置的参数化提示模板与工作流，通常呈现为用户可选的斜杠命令或菜单项，由用户显式触发。

Client 侧原语让 server 能反向请求宿主的能力，把简单的「工具服务器」升级为可参与推理的协作方。

01

Sampling（借用推理）

server 请求宿主用其 LLM 生成一段补全，实现 server 侧的智能子步骤。协议刻意限制 server 对提示的可见性，每次调用需用户批准。

02

Roots（根边界）

client 向 server 声明一组文件系统或 URI 根，界定 server 允许操作的范围，是本地文件类 server 的作用域约束。

03

Elicitation（信息征询）

server 运行中向用户请求补充信息（如确认参数、填一个字段），由 client 呈现表单并回传，2025-06-18 修订引入。

MCP 用「控制权归属」把三类 server 原语区分开，这直接决定 UI 应把哪种操作交给谁决定。

  • 1模型控制（Tools） — 由模型在推理中决定是否调用；因为可能产生副作用，宿主应在执行前插入用户确认。
  • 2应用控制（Resources） — 由宿主应用决定何时、把哪些资源注入上下文；模型不能自行拉取任意资源。
  • 3用户控制（Prompts） — 由用户显式选择模板化工作流；适合把「组织沉淀的标准流程」暴露为可复用命令。

04 / Lifecycle

会话生命周期：初始化、能力协商与关闭

MCP 会话有严格的三阶段生命周期：初始化（版本与能力协商）、运行（按协商结果交换消息）、关闭（在传输层优雅终止）。理解握手顺序，是排查「连不上、能力缺失、超时」类问题的前提。

初始化必须是第一次交互：client 发 initialize，server 回自身能力，client 再发 initialized 通知，之后才进入正常操作。

  • 1
    Client → Server：initialize

    携带支持的协议版本、client 能力（roots / sampling / elicitation）与客户端信息。

  • 2
    Server → Client：能力响应

    回同一或自身支持的版本，声明 server 能力（prompts / resources / tools / logging 等）与可选 instructions。

  • 3
    Client → Server：initialized 通知

    client 发 notifications/initialized 表示就绪；此前双方除 ping / logging 外不应发其它请求。

  • 4
    进入运行阶段

    双方只使用协商成功的能力，按协商版本交换 tools/list、tools/call、resources/read 等消息。

initialize 请求（JSON-RPC 2.0）

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {},
      "elicitation": {}
    },
    "clientInfo": { "name": "ExampleClient", "version": "1.0.0" }
  }
}

// 就绪后 / after ready:
{ "jsonrpc": "2.0", "method": "notifications/initialized" }

MCP 用 YYYY-MM-DD 日期串标识版本，只在发生不向后兼容变更时才推进；当前修订为 2025-11-25。

  • 协商规则 — client 发它支持的最新版本；server 支持则原样返回，否则返回自身支持的（通常是最新）版本；client 不支持则应断开。
  • HTTP 头 — 走 HTTP 时，后续每个请求必须带 MCP-Protocol-Version 头（例：MCP-Protocol-Version: 2025-11-25）；缺失时 server 按 2025-03-26 处理。
  • 错误形态 — 版本不受支持时返回 JSON-RPC 错误（如 code -32602），data 中列出 supported 与 requested，便于客户端降级。

能力协商决定这次会话有哪些功能可用：某功能未在初始化时声明，整场会话就不能使用它。

  • Server 声明 — prompts、resources、tools、logging、completions 等；子能力如 listChanged（列表变更通知）与 subscribe（仅 resources 支持单项订阅）。
  • Client 声明 — roots、sampling、elicitation，以及 experimental（非标准实验特性）。
  • 使用约束 — 触发 resources 订阅通知要求 server 声明了 subscribe；调用 tools 要求声明了 tools 能力；发起 sampling 要求 client 声明了 sampling。

MCP 不定义专门的关闭消息，而是由传输层发信号；超时与取消则由实现方按请求管理。

  • stdio 关闭 — client 先关闭子进程的输入流，等待退出；超时后发 SIGTERM，仍不退再发 SIGKILL。server 也可关闭自身输出流并退出。
  • HTTP 关闭 — 直接关闭相关 HTTP 连接即视为关闭；带会话时可用 DELETE 显式终止会话。
  • 超时 — 每个请求都应设超时，超时应发取消通知并停止等待；收到进度通知可重置计时，但必须设一个最大上限，防止被拖住。

05 / Transports

传输层选型：stdio 与 Streamable HTTP

MCP 消息一律用 JSON-RPC 编码（UTF-8），协议定义两种标准传输：stdio 与 Streamable HTTP；官方建议客户端尽可能支持 stdio。协议本身与传输无关，也允许自定义传输。选传输，本质是在「本地进程」与「远程多客户端服务」之间做部署决策。

先做取舍再看细节：本地、单宿主用 stdio；远程、多客户端、需托管用 Streamable HTTP。

stdio · 本地首选

以子进程方式在标准输入输出上通信

  • client 把 server 作为子进程启动，双方用换行分隔的 JSON-RPC 消息通信。
  • 适合本地工具、桌面宿主、开发调试；无网络暴露面，延迟低。
  • stdout 只能写合法 MCP 消息，日志走 stderr。
Streamable HTTP · 远程/托管

独立进程，单端点承载 POST 与 GET

  • server 是独立进程，提供单个 MCP 端点，可选用 SSE 流式推送多条服务器消息。
  • 适合远程服务、多客户端并发、需要托管与横向扩展的场景。
  • 取代 2024-11-05 的旧版 HTTP+SSE 传输，向后兼容可并存。

stdio 的可靠性完全建立在「stdout 是协议专线」这条纪律上，违反它是新手最常见的破坏方式。

  • 消息格式 — 每条消息是单个 JSON-RPC 请求/通知/响应，以换行分隔，且不得含内嵌换行。
  • 通道纪律 — server 不得向 stdout 写任何非 MCP 内容；可向 stderr 写 UTF-8 日志，client 可捕获、转发或忽略。
  • 启动方式 — client 通过命令 + 参数启动 server 子进程（见开发一节的 host 配置）。

Streamable HTTP 用一个端点同时承载「客户端 POST 请求」与「服务器经 GET/SSE 主动推送」，并可选带会话与断线续传。

  • 发送 — 每条 JSON-RPC 消息都是一次 HTTP POST；请求头 Accept 须同时列出 application/json 与 text/event-stream。
  • 响应形态 — 对一个请求，server 可返回单个 JSON 对象，或开一条 SSE 流分批推送直至给出该请求的响应。
  • 会话 — server 可在初始化响应里下发 Mcp-Session-Id 头；此后 client 每个请求都要带上，server 可随时终止会话（返回 404 触发重连）。

用三个问题决定传输：server 在哪跑、有几个客户端、要不要托管与扩展。

  • 1本地集成 — server 与宿主同机、单用户（如 IDE 插件、桌面助手接本地文件/Git）→ 选 stdio。
  • 2远程/多租户 — server 作为共享服务被多个客户端调用、需要鉴权与横向扩展 → 选 Streamable HTTP。
  • 3特殊通道 — 需要走非标准信道（进程内、WebSocket 等）时可实现自定义传输，但必须保留 JSON-RPC 消息格式与生命周期契约。

06 / Build a Server

开发实操：用 TypeScript 从零构建一个 MCP Server

下面用官方 TypeScript SDK 走一遍最小可运行路径：初始化项目 → 定义 server 并注册工具 → 连接 stdio 传输 → 构建并接入宿主。工具输入用 zod 声明 schema，SDK 会据此生成工具定义并做参数校验。

装 SDK 与 zod，并把 package.json 设为 ES module、加一条 build 脚本。

mkdir weather-mcp && cd weather-mcp
npm init -y
npm install @modelcontextprotocol/sdk zod@3
npm install -D @types/node typescript
mkdir src

package.json（关键字段）

{
  "type": "module",
  "bin": { "weather": "./build/index.js" },
  "scripts": { "build": "tsc && chmod 755 build/index.js" }
}

创建 McpServer，用 registerTool 声明工具名、描述与 zod 输入 schema；处理函数返回一个 content 数组。

import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "weather", version: "1.0.0" });

server.registerTool(
  "get_forecast",
  {
    description: "Get the weather forecast for a coordinate.",
    inputSchema: {
      latitude: z.number().min(-90).max(90).describe("Latitude"),
      longitude: z.number().min(-180).max(180).describe("Longitude"),
    },
  },
  async ({ latitude, longitude }) => {
    const text = await fetchForecast(latitude, longitude);
    return { content: [{ type: "text", text }] };
  },
);

用 StdioServerTransport 连接 server；日志一律走 stderr（console.error）。构建后即可被宿主以子进程方式启动。

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("weather MCP server running on stdio");
}

main().catch((err) => {
  console.error("fatal:", err);
  process.exit(1);
});
npm run build   # tsc 编译到 build/ 目录 / compiles to build/

在宿主的 MCP 配置里登记一条 server：给一个名字、一个可执行命令与参数（绝对路径）。多数宿主用同构的 mcpServers 结构。

{
  "mcpServers": {
    "weather": {
      "command": "node",
      "args": ["/ABSOLUTE/PATH/weather-mcp/build/index.js"]
    }
  }
}

保存后重启宿主；宿主会以该命令启动 server 子进程，完成 initialize 握手后即可在会话中调用 get_forecast。

stdio server 里最常见的致命错误，是往 stdout 打日志——它会污染 JSON-RPC 消息流，让 server 静默失效。

反例

向 stdout 写日志

// stdio server
console.log("debug");
// 污染协议流，server 失效
// corrupts the stream
正例

向 stderr 写日志

// stdio server
console.error("debug");
// stderr 安全，不干扰协议
// stderr is safe

规则对所有语言一致：Python 用 print(..., file=sys.stderr) 或 logging；HTTP 传输的 server 则不受此限（stdout 不承载协议）。

Python 侧用 FastMCP：用装饰器把带类型标注与 docstring 的函数暴露为工具，SDK 自动生成工具定义。

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
async def get_forecast(latitude: float, longitude: float) -> str:
    """Get the weather forecast for a coordinate."""
    return await fetch_forecast(latitude, longitude)

if __name__ == "__main__":
    mcp.run(transport="stdio")

依赖 mcp[cli]（Python 3.10+，MCP SDK 1.2.0+）；同样遵守「stdout 只给协议」的纪律。

07 / Connect a Client

客户端集成：Host、模型与 Server 的调用回路

从消费侧看，MCP 的运行时是一个回路：宿主列出 server 的工具 → 连同用户问题交给模型 → 模型决定调用哪些工具 → 宿主经 server 执行 → 结果回给模型 → 模型给出自然语言回答。理解这个回路，才能判断把哪些能力交给 MCP、把哪些留在宿主内。

宿主是模型与 server 之间的编排者；模型只表达「要调哪个工具」，真正的执行与鉴权都在宿主与 server。

  • 1
    列出工具

    client 连接 server 后调用 tools/list，把可用工具及其输入 schema 拿到手。

  • 2
    交给模型决策

    宿主把用户问题 + 工具声明发给模型；模型用 function calling 决定调用哪个、传什么参数。

  • 3
    经 Server 执行

    宿主经 client 调用 tools/call 执行工具（必要时先请用户确认），拿到结构化结果。

  • 4
    回填并作答

    结果回给模型，模型据此生成回答；如需多步，重复 2–4 直至完成。

客户端侧同样用官方 SDK：创建 Client、连接传输、listTools 发现工具、callTool 执行。

import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

const client = new Client({ name: "host-app", version: "1.0.0" });
await client.connect(new StdioClientTransport({
  command: "node",
  args: ["build/index.js"],
}));

const { tools } = await client.listTools();

const result = await client.callTool({
  name: "get_forecast",
  arguments: { latitude: 47.6, longitude: -122.3 },
});

MCP 已被广泛的宿主支持，同一个 server 可被多种客户端复用，这正是「一次实现，多处接入」的落地形态。

  • AI 助手 — Claude、ChatGPT 等对话产品可发现并调用 MCP 工具。
  • 开发工具 — Visual Studio Code、Cursor 等 IDE 内置 MCP 客户端，把工具接进编码工作流。
  • 可移植性 — 因为协议一致，为一个宿主写的 server 通常无需改代码即可被其它宿主接入。

08 / Security & Production

安全与生产化：四条信任原则与传输加固

MCP 打开了「任意数据访问 + 任意代码执行」的能力面，因此安全不是可选项。协议本身无法在协议层强制这些原则，落地责任落在实现方：宿主必须建立同意与授权流程、访问控制与隐私保护。下面先给四条信任原则，再落到 Streamable HTTP 的具体加固与生产降级。

官方规范给出四条必须落实的信任与安全原则，覆盖同意、隐私、工具与推理四个面。

01

用户同意与控制

用户必须明确同意并理解所有数据访问与操作，保留对「共享什么、执行什么」的控制；宿主应提供清晰的审阅与授权界面。

02

数据隐私

宿主在把用户数据暴露给 server 前须取得明确同意，未经同意不得外传资源数据，并以适当访问控制保护数据。

03

工具安全

工具等同任意代码执行；除非来自可信 server，工具的行为描述与注解应视为不可信。宿主必须在调用任何工具前取得用户同意。

04

Sampling 控制

用户必须显式批准任何 sampling 请求，并能控制是否发生、发送什么提示、server 能看到什么结果；协议刻意限制 server 对提示的可见性。

把 server 暴露到 HTTP 上会引入 Web 攻击面；官方对 Streamable HTTP 给出三条强制加固。

  • 校验 Origin 头 — 所有入站连接都必须校验 Origin，防止 DNS rebinding 攻击从远程网页控制本地 server。
  • 本地只绑 localhost — 本地运行时应只绑定 127.0.0.1，而非 0.0.0.0，避免暴露到所有网络接口。
  • 为所有连接鉴权 — 为所有连接实现恰当的身份认证；无这些防护，攻击者可用 DNS rebinding 与本地 server 交互。

生产系统里 server 会挂、工具会失败、连接会断；把这些当常态处理，才能得到稳定的 MCP 集成。

  • 1按请求设超时 — 每个请求设超时，超时发取消通知并停止等待；对整条 agentic 回路设最大步数与总时限。
  • 2结构化错误回传 — 工具失败时回传清晰、可操作的错误文本（而非原始堆栈），让模型能修正参数或改走替代路径。
  • 3会话与重连 — HTTP 传输下处理 404（会话失效即重新 initialize）、断线续传（Last-Event-ID）与显式 DELETE 释放会话。
  • 4最小权限 — server 只暴露必要的工具与资源；把敏感操作放在需要显式用户确认的路径后面。

09 / Adoption Decisions

选型判断：何时用 MCP、如何落地

MCP 不是所有集成的默认答案。它的价值集中在「工具要被多个宿主复用、要有连接生命周期与统一鉴权」这类场景；单一应用内的少量固定工具，直接 function calling 往往更省。本节给出可落地的判据与一份落地清单。

三种做法解决的问题不同；按「复用范围、发现机制、生命周期」三维对照，即可选中合适的那一档。

维度 直接 Function Calling MCP 私有 API 集成
复用范围 绑定单一应用 跨宿主复用 按对接双方定制
发现机制 代码里硬编码工具集 运行时 tools/list 动态发现 靠文档与手工约定
连接生命周期 无（单次请求） 初始化/能力协商/会话 各自实现
最省场景 少量固定工具、单应用 工具产品化、多宿主接入 强耦合、深度定制系统

先厉清前提：MCP 与 REST API 不在同一层，也并非二选一。REST 是供代码调用的通用 API 风格，MCP 是供模型发现与调用的协议；且 MCP Server 内部往往正是在调用 REST。

维度 REST API MCP
调用方 确定性代码 LLM / Agent
发现方式 带外文档（OpenAPI），集成写死 运行时 tools/list 自描述
接口形态 每个 API 各异，逐个适配 统一 JSON-RPC，一个客户端对接所有 server
状态 通常无状态 有状态会话 + 能力协商
方向 单向 client→server 双向（sampling / elicitation）
复用成本 每个 AI 宿主各写一遍 = M×N 写一次，处处可用 = M+N

选择判据：调用方是否为 LLM、以及工具是否需要跨多个 AI 宿主复用。二者成立时用 MCP；若只是代码间的确定性集成，REST 更轻、更省。根本原因在于 REST 的契约在开发期固定、面向已知双方，而 MCP 的契约在运行期协商并自描述、面向被模型动态发现。实践中最常见的是两者叠用：底层 REST，外面包一层 MCP 供 Agent 使用。

决定用 MCP 之后，第二个决策是部署形态；它同时影响鉴权、可扩展性与运维复杂度。

本地 stdio

随宿主分发、按用户机器运行

  • 无网络暴露面，鉴权由本机进程与文件权限承担。
  • 适合个人生产力工具、访问本地文件/Git、开发调试。
  • 更新需随宿主或包分发，集中运维弱。
远程 Streamable HTTP

集中托管、多客户端共享

  • 集中更新与监控，一处修复所有客户端受益。
  • 必须做传输加固（Origin 校验、鉴权）与会话管理。
  • 适合企业共享工具、多租户、需横向扩展的场景。

以下判断可证伪：若命中，直接 function calling 或私有集成通常成本更低、控制更强。

  • 工具不跨宿主复用 — 只有一个应用会用这批工具，引入 MCP 只增加进程与协议开销。
  • 工具集小且稳定 — 三五个固定工具，硬编码到 function calling 声明里维护更简单。
  • 需要极致低延迟或强耦合语义 — 进程内直调或专用 API 能省掉一层序列化与传输，控制更细。

确定用 MCP 后，按此清单推进，可覆盖从原型到生产的主要关口。

  • 1划边界 — 明确哪些能力做成 server，粒度按「可独立复用、职责聚焦」切分。
  • 2选传输 — 本地单用户用 stdio，远程多客户端用 Streamable HTTP，并据此规划鉴权。
  • 3设计 schema — 用清晰的工具名、描述与强类型输入 schema，减少模型误调用。
  • 4加同意与审计 — 敏感工具走用户确认，记录每次调用的输入、输出与耗时，便于排障与合规。
