01 / Positioning

Code App 填补了 Canvas App 与纯自研 Web App 之间的空白

理解 Code App 的定位后，你能判断它在你的项目场景中是否是正确选择。

01

什么是 Code App

Code App 是 Power Apps 的第三种应用类型。开发者在本地 IDE（如 VS Code）中用标准 Web 技术（HTML/TypeScript/React/Vue）编写 SPA 应用，通过 Power Apps Client Library（@microsoft/power-apps npm 包）接入 Power Platform 连接器和数据源，最终发布并托管在 Power Platform 环境中。

02

解决什么问题

Canvas App 对复杂 UI 和自定义逻辑的表达能力有限；纯自研 Web App 需要自建认证、API 网关、部署管线。Code App 让专业开发者在保留完整代码控制力的同时，免费获得平台的认证、授权、DLP、连接器和 ALM 能力。

03

适用场景

需要自定义 UI 组件库（如 Fluent UI v9）的 LOB 应用；需要精细控制前端状态管理和路由的复杂表单；现有 React/Vue 项目需要接入 Power Platform 数据生态但不想重写为 Canvas App。

02 / Architecture

三层运行时架构：代码、Client Library、Host

上一节定义了 Code App 的定位，本节拆解其运行时组成，帮你理解开发和运行时各层的职责。

Your Code (React / Vue / Custom SPA)你的前端代码，完全控制 UI 和逻辑
@microsoft/power-apps Client Library暴露连接器 API，生成 TypeScript 模型和服务文件
Power Apps HostEntra 认证、应用加载、错误处理、托管运行

开发阶段涉及三个关键文件/工具的协作。

power.config.json

由 Client Library 生成的元数据文件，记录连接器配置和环境信息。CLI 和 Client Library 均依赖此文件完成数据源绑定和应用发布，应用代码本身不需要直接操作它。

@microsoft/power-apps (npm 包)

Power Apps Client Library，提供与连接器交互的 API。当你通过 CLI 添加数据源时，它自动生成 TypeScript 类型的 Model 和 Service 文件（如 Office365UsersModel.ts 和 Office365UsersService.ts），放在 src/generated/ 目录下（含 models/、services/ 等子目录）。

PAC CLI / npm CLI

pac code push 命令将编译后的应用打包并发布到 Power Platform 环境。从 v1.0.4 起，Client Library 内置了 npm CLI（npx power-apps），可替代 PAC CLI 的 pac code 命令，减少前置依赖。

应用发布后运行时的三层职责分工。

Your Code

你的 SPA 代码在浏览器中运行，通过 Client Library 暴露的 API 发起数据请求。你完全控制 UI 渲染、路由、状态管理。

Client Library

负责将你的 API 调用转换为 Power Platform 连接器请求，管理连接模型和服务的生命周期。连接的增删会自动更新生成的 TypeScript 文件。

Power Apps Host

管理终端用户的 Entra 认证、应用加载流程、连接器权限同意弹窗。如果应用加载失败，Host 向用户展示上下文错误信息。

根据项目特征选择应用类型的三条规则。

选 Code App

团队有前端工程能力；需要自定义组件库（Fluent UI、Ant Design 等）；需要复杂路由和状态管理；希望用标准 Git + CI/CD 管理代码。

选 Canvas App

需求方可以自助开发；UI 可用标准控件满足；快速原型验证；需要 Power Apps 移动 App 体验。

选 Model-driven App

以 Dataverse 数据建模为核心；需要开箱即用的 CRUD 表单/视图/仪表盘；与 Dynamics 365 深度集成。

04 / Development Workflow

从初始化到发布：4 步完成 Code App 开发

上一节帮你做了选型判断，本节带你走完一个 Code App 从脚手架到上线的完整流程。

Step 1: 脚手架初始化

使用官方模板创建项目。推荐 starter 模板（预配置 React + Vite + Tailwind CSS + Tanstack Query + React Router），适合大多数项目；vite 模板更轻量，适合自定义技术栈。

Step 2: 认证与环境绑定

通过 PAC CLI 认证 Power Platform 租户并选择目标环境。所有应用、流和代理都发布到指定环境中。CLI 使用你的 Entra 身份完成认证。

Step 3: 本地开发与调试

运行 npm run dev 启动本地开发服务器。在与 Power Platform 租户相同的浏览器配置文件中打开 Local Play URL，即可在本地调试并实时调用 Power Platform 连接器数据。

Step 4: 构建与发布

先运行 npm run build 编译，再运行 npx power-apps push（或 pac code push）发布。push 不会自动触发 build——跳过 build 直接 push 会上传旧的 dist 目录。命令成功后返回 Power Apps URL，可在 make.powerapps.com 查看、共享和运行应用。

Code App 开发中最常用的 CLI 命令。

npx degit microsoft/PowerAppsCodeApps/templates/starter my-app cd my-app npm install pac auth create pac env select --environment <env-id> pac code init --displayname "My Code App" npm run dev # 本地开发 npm run build && pac code push # 构建并发布（注意用 && 而非 |）

从 @microsoft/power-apps v1.0.4 起，Client Library 内置 npm CLI，减少对 PAC CLI 的依赖。

npx power-apps init --display-name "My App" --environment-id <env-id> npm run dev # 同上 npm run build npx power-apps push # 替代 pac code push

npm CLI 提供完整的命令集，覆盖 PAC CLI 的 pac code 全部功能且更稳定。主要命令：init（初始化）、run（本地开发）、push（发布）、add-data-source（添加数据源）、delete-data-source（删除数据源）、refresh-data-source（刷新数据源）、list-datasets/list-tables/list-connections（发现元数据）、add-flow/remove-flow/list-flows（集成 Power Automate 流）、find-dataverse-api/add-dataverse-api（Dataverse Action/Function）。

实测经验：PAC CLI（dotnet tool）的 pac code add-data-source 命令在 v1.52.1 中对 Dataverse 连接器报 Invalid URI format 错误，list-datasets/list-tables 也报 Cannot read properties of undefined。相同操作在 npm CLI 中正常完成。推荐优先使用 npm CLI。

GitHub 仓库 microsoft/PowerAppsCodeApps 提供模板和示例。

starter 模板

推荐。预配置 React + Vite + Tailwind CSS + Tanstack Query + React Router，适合大多数业务应用。

vite 模板

最小化 Vite + React 配置，适合希望完全自定义技术栈的团队。

HelloWorld 示例

React + Vite + TypeScript。展示 Power Platform SDK 基础集成，推荐作为第一个阅读的示例。

FluentSample 示例

React + Fluent UI v9 + SQL + Office 365。完整示例，含连接器、自定义 API、SQL 后端和 CI/CD 配置。

05 / Data Connection

通过连接器接入 1,500+ 数据源

上一节跑通了开发流程，本节解决核心问题：如何把 Code App 连接到业务数据。

Step 1: 在 Power Apps 中创建连接

在 make.powerapps.com 的 Connections 页面创建或选择已有连接（如 Office 365 Users、SQL Server、SharePoint）。复制连接的 API Name 和 Connection ID。

Step 2: 用 CLI 添加数据源

运行 npx power-apps add-data-source（推荐）或 pac code add-data-source 将连接绑定到代码项目。对于非表格数据源（Office 365 Users 等），指定 --api-id（或 -a）和 --connection-id（或 -c）；对于表格数据源（SQL、SharePoint），还需指定 --resource-name（或 -t）和 --dataset（或 -d）。Dataverse 表的简化用法见 §06。

Step 3: 使用生成的 TypeScript 模型

添加数据源后，CLI 自动在 src/generated/ 目录生成类型安全的 Model 和 Service 文件。直接 import 使用，如 await Office365UsersService.MyProfile()。

Code App 支持 Power Platform 上的绝大部分连接器，但有少量例外。

01

非表格连接器

Office 365 Users、Microsoft Graph、自定义连接器等。通过 --api-id（-a）和 --connection-id（-c）参数添加。生成的 Service 文件提供对应 API 的方法调用。

02

表格连接器

SQL Server、SharePoint Lists 等。生成 CRUD 方法（create / get / getAll / update / delete）。支持 SQL 存储过程。

03

Dataverse

专用集成，既支持表格 CRUD（通过 add-data-source），也支持 Dataverse Action 和 Function（通过 add-dataverse-api）。Dataverse 表的简化用法见 §06。

04

不支持的连接器

Excel Online (Business) 和 Excel Online (OneDrive) 目前不受支持。连接创建目前只能在 make.powerapps.com 完成，CLI 端暂不支持新建连接。

在 Dev / Test / Prod 多环境场景中，应使用连接引用而非直接绑定用户连接。

为什么用连接引用

直接绑定用户连接会导致 Solution 在跨环境部署时失败。连接引用是一个 Solution 组件，指向特定连接器的连接，让 Solution 具备环境感知和可移植性。

如何配置

获取 Solution ID 和连接引用 Logical Name，运行 pac code add-data-source -a <apiName> -cr <refLogicalName> -s <solutionID> 即可。从 PAC CLI v1.51.1（2025.12）起支持。

06 / Dataverse

对接 Dataverse 的标准做法：连接器接入 + Schema 同步闭环

上一节覆盖了通用连接器接入，本节聚焦 Code App 对接 Dataverse 的推荐路径，以及 Dataverse 数据模型（表 / 列 / 关系）的标准变更流程，并说明 schema 变更后如何与生成的 TypeScript 类型保持一致。

记录级 CRUD → 表格数据源

对 Dataverse 表做增删改查，走 Microsoft Dataverse 连接器作为表格数据源（tabular data source）。pac code add-data-source 生成类型安全的 CRUD Service／Model，调用方式与 SQL、SharePoint 表一致。

业务操作 → Action / Function

需要事务性写入、系统消息或自定义业务逻辑时，调用 Dataverse Action（写）和 Function（读）。这是另一条专用通道，详见下一节「集成专题 · Dataverse Action / Function」。

Dataverse 表的接入有两条路径：PAC CLI 需要 4 个参数逐级发现（连接 → 数据集 → 表），npm CLI 则提供了简化语法——只需表的 logical name 和 org URL，无需 Connection ID。实测 PAC CLI v1.52.1 对 Dataverse 连接器存在 bug（Invalid URI format），npm CLI 无此问题，推荐后者。

路径 A：npm CLI（推荐）

Step 1: 直接按表名添加

运行 npx power-apps add-data-source --api-id dataverse --resource-name <logicalName> --org-url <orgUrl>。--resource-name 是 Dataverse 表的 logical name（如 account、contact、appointment），--org-url 是 Dataverse 实例地址。支持 --non-interactive 跳过交互提示。

Step 2: 验证生成的文件

CLI 自动更新三个位置：power.config.json（databaseReferences.default.cds.dataSources）、.power/schemas/dataverse/*.Schema.json（完整列定义）、.power/schemas/appschemas/dataSourcesInfo.ts（primaryKey 映射）。同时在 src/generated/ 生成 Model 和 Service 文件。

Step 3: 在代码中调用 CRUD

import 生成的 Service，直接调用 create / get / getAll / update / delete，全程类型安全，无需手写 HTTP 请求。

# npm CLI：直接按 logical name 添加（推荐） npx power-apps add-data-source --api-id dataverse --resource-name account --org-url https://org1cd97ca4.crm.dynamics.com npx power-apps add-data-source --api-id dataverse --resource-name contact --org-url https://org1cd97ca4.crm.dynamics.com npx power-apps add-data-source --api-id dataverse --resource-name appointment --org-url https://org1cd97ca4.crm.dynamics.com --non-interactive // 生成后在代码中调用（与 SQL/SharePoint 表一致） await ContactsService.getAll(); await ContactsService.get(id); await ContactsService.create(record); await ContactsService.update(id, changedFields); await ContactsService.delete(id);

路径 B：PAC CLI（备选）

Step 1: 创建 Dataverse 连接并取元数据

在 make.powerapps.com 的 Connections 页创建 Microsoft Dataverse 连接。用 pac connection list 取得该连接的 API Name 和 Connection ID（API Name 即后续 -a 参数）。

Step 2: 发现数据集与表

用 pac code list-datasets -a <apiName> -c <connectionId> 列出数据集，再用 pac code list-tables 列出表。从输出中复制精确的 Name 值。

Step 3: 添加表格数据源

运行 pac code add-data-source -a <apiName> -c <connectionId> -t <tableId> -d <datasetName>。

# PAC CLI：需要 Connection ID 和逐级发现 pac connection list pac code list-datasets -a <apiName> -c <connectionId> pac code list-tables -a <apiName> -c <connectionId> -d <datasetName> pac code add-data-source -a <apiName> -c <connectionId> -t <tableId> -d <datasetName>

三文件同步纪律：每次 add-data-source 必须确认三个位置同时更新：(1) power.config.json 的 databaseReferences.default.cds.dataSources、(2) .power/schemas/dataverse/*.Schema.json、(3) dataSourcesInfo.ts 的 primaryKey。三者缺一则运行时 500 错误。.power/schemas/ 目录下的文件由 CLI 自动生成，不应手动编辑——手改 dataSourcesInfo.ts 的 primaryKey 会导致与 Schema.json 不同步并引发 500 错误。npm CLI 自动保证三文件同步；手动操作时务必逐一核对。[4]

更新 Dataverse 数据模型前，先确认权限，再明确 schema 层面有哪些可执行的操作。

前置权限

System Customizer 安全角色

在目标环境中具备 System Customizer 角色，才能创建和编辑表。该角色默认无法访问未共享给它的他人记录。

Entity 表的 Create / Read / Write 权限

系统或自定义安全角色需对 Entity 表具备 CRW 权限，才能落地表结构变更。编辑记录行还需管理员单独授予数据访问权限。

可用 schema 操作（make.powerapps.com → Tables → Schema）

01

Tables 表

建表方式：从空白、从 Copilot 自然语言生成、从 Excel/CSV、从 SharePoint 列表导入、创建虚拟表。类型：Standard / Activity / Virtual / Elastic。所有权：User & Team 或 Organization（Activity 表只能 User/Team 所有）。

02

Columns 列

新增/编辑列，选择数据类型与格式（见下一条手风琴的完整类型清单）。主列（Primary column）在保存后显示名与描述不可改。

03

Relationships 关系

建立 1:N（一对多）和 N:N（多对多）关系。添加 Lookup 列即自动创建一条 N:1 关系。可配置级联行为（cascade behavior）。

04

Keys 备用键

定义 Alternate Keys，用一个或多个列的组合作为唯一引用，支持外部系统按业务键 Upsert 记录。

可视化设计器限制：data workspace 画布暂不支持 Rich text、Customer、Autonumber、Formula 列，也不支持新建 N:N 关系（需在表的 Relationships 区单独创建）。[14]

建列时可选的数据类型（括号内为 API 的 AttributeTypeDisplayName），按用途分组。

分组数据类型说明
文本Text / Text Area / Multiline Text（StringType / MemoType）单行最大 4000 字符；多行最大 1,048,576 字符。含 Email / Phone / URL / Ticker Symbol 等格式。
数字Whole Number / Decimal / Floating Point / Big（IntegerType / DecimalType / DoubleType / BigIntType）需精确计算用 Decimal；需范围比较用 Float；超大整数用 Big。
货币Currency（MoneyType）首次添加会自动附带 Currency 与 Exchange Rate 列，并为每个货币列生成 _Base 基准列。
选择Choice / Choices（PicklistType / MultiSelectPicklistType）单选用 Choice，多选用 Choices；可引用组织级 global choices。
日期Date and Time / Date Only / Duration / Timezone / LanguageDuration、Timezone、Language 底层为 IntegerType。
关系Lookup / Customer / Owner（LookupType / CustomerType / OwnerType）新增 Lookup 即创建 N:1 关系；Customer 可指向 account 或 contact。
二进制File / Image（FileType / ImageType）独立于关系库存储；每表一个主图像列；File 默认上限 32MB，最大可设 131MB。
计算 / AIFormula（Power Fx）/ Autonumber / PromptFormula、Image、File 不支持业务流程流、业务规则、图表、Rollup、计算列。
系统列Status / Status Reason / Owner / Unique Identifier / Time Stamp / Customer系统维护，设计器中不能直接新增（部分可在 solution explorer 添加）。

检索/排序注意：Formula、Image、PartyList 多值 Lookup 不可搜索；Choices、Customer、File、Formula、Image 不可排序。[15]

Dataverse 底层只有两种关系：1:N 和 N:N（N:1 只是 1:N 从子表视角的呈现）。建关系时需配置级联行为以保证数据完整性。

1:N（一对多）

主表一行关联子表多行，通过子表上的 Lookup 列实现。一对父子表通常只能有一条「父子（parental）关系」，决定 Assign/Share/Delete 等动作是否级联。

N:N（多对多）

依赖一张中间表（Intersect/Relationship 表）建立对等关系。需在表的 Relationships 区创建，可视化画布不支持。

级联行为（Behaviors）× 触发动作（Actions）

触发动作可选级联行为
Assign 重新分配Cascade All / Active / User-owned / None
Reparent 改父Cascade All / Active / User-owned / None
Share / Unshare 共享Cascade All / Active / User-owned / None
Delete 删除Cascade All / Remove Link / Restrict
Merge 合并Cascade All / None

限制：自定义表不能作为级联关系中相对系统表的主表；同一相关表不能同时成为多条 Cascade All/Active/User-owned 关系的子表（防止多父）。把级联从 Reparent/Share 改为 Cascade None 时，系统会跑「继承访问权清理」作业回收因继承而获得的权限。[16]

这一步把 Dataverse schema 变更和 Code App 工作流连成闭环——也是最容易被忽略的纪律点。

1. 在 Solution 中改 schema

始终在非托管 Solution 内创建/编辑表、列、关系，使变更可被打包、版本化并跨 Dev / Test / Prod 部署，而非落入 Default Solution。

2. 重新生成类型文件（关键）

连接器 schema（表的列结构）变化后，npm CLI 提供了 npx power-apps refresh-data-source 命令刷新单个或全部数据源。PAC CLI 则没有 refresh 命令，必须 pac code delete-data-source 删除后再 add-data-source 重新添加。

3. 用连接引用保证跨环境可移植

用 -cr <connectionReferenceLogicalName> -s <solutionID> 绑定连接引用而非用户连接（PAC CLI v1.51.1 起支持），让 Solution 在多环境迁移时只需切换连接引用。

4. 重新构建发布

类型文件更新后，npm run dev 本地验证，再 npm run build && npx power-apps push 发布。push 不会自动 build，务必先 build 再 push。

# 方式 1：npm CLI（推荐）— 一键刷新 npx power-apps refresh-data-source # 刷新全部数据源 npx power-apps refresh-data-source --api-id dataverse --resource-name contact # 刷新指定表 # 方式 2：PAC CLI — 删除重建 pac code delete-data-source -a "shared_commondataserviceforapps" -ds "Contact" pac code add-data-source -a "shared_commondataserviceforapps" -c <connectionId> -t <tableId> -d <datasetName> npm run dev # 验证新列已出现在生成的类型中 npm run build && npx power-apps push # 构建并发布

程序化改 schema（超出 Code App 范围）：若需在管线中自动化创建表/列，可走 Dataverse Web API / Organization Service 的 metadata 操作（如 CreateEntityRequest、CreateAttributeRequest）。但 Code App 本身是浏览器端 SPA，不直接执行 metadata 写操作；schema 由 maker portal 或后端管线维护，Code App 侧只负责删除并重新生成类型文件。[14]

07 / Integration Topics

五大集成专题：从 Flow 到 MCP

上一节确立了 Dataverse 的标准对接路径，本节逐一拆解 Code App 与 Power Automate Flow、Copilot Studio Agent、Dataverse Action、外部 Web API 和 MCP 的集成方法。

Code App 可以调用 Power Automate 云端流，但仅支持使用 "When Power Apps calls a flow (V2)"（PowerAppV2 trigger kind）触发器的手动即时流，且流必须在 Solution 中。V1 触发器不受支持。

发现可用 Flow

运行 npx power-apps list-flows 列出当前环境中所有 Solution-aware 的流。支持 --search 按名称过滤。复制目标流的 Flow ID。

添加 Flow 到项目

运行 npx power-apps add-flow --flow-id <id>。CLI 下载流的 OpenAPI 定义，自动生成 TypeScript Service 和 Model 文件（类名格式为 PowerAppsFlow_{FlowDisplayName}Service），并在 power.config.json 的 connectionReferences 中注册 Flow 连接（含 workflowDetails）。

在代码中调用

导入生成的 Service 类，调用静态 Run(input) 方法。参数类型由 CLI 根据 Flow trigger 的输入参数自动生成（如 ManualTriggerInput），字段名来自 Flow 的参数定义。返回 IOperationResult<T>（即 { success, data, error }），其中 data 类型对应 Flow 的 Respond action 输出。

import { PowerAppsFlow_LLMService } from './generated/services/PowerAppsFlow_LLMService'; // 参数类型由 CLI 生成，字段名来自 Flow trigger 的输入参数定义 const result = await PowerAppsFlow_LLMService.Run({ text: 'Summarize recent activities for Contoso', text_1: 'json', // Flow trigger 的第二个参数 }); if (result.success) { console.log('Flow output:', result.data?.output); }

限制：仅支持使用 "When Power Apps calls a flow (V2)"（PowerAppV2）触发器的手动即时流；V1 触发器、计划流、自动流和其他触发器类型的即时流均不受支持。Flow 命令仅在 npm CLI（npx power-apps）中可用，不支持 pac code。终端用户需要 Dataverse 权限（App Opener 安全角色或等效角色）才能调用流。[9]

已确认 Bug：UTF-8 多字节编码截断（Published 环境）。Flow 返回值包含中文或其他非 ASCII 字符时，Published Code App 的 SDK 解码通道（runtimeDataClient.js _decodeArrayBuffer）会截断多字节 UTF-8 序列，导致 JSON.parse 报 Unterminated string。本地开发和浏览器 dev 不会复现——仅 Published 环境必现。Flow 本身返回 200 无错。缓解方案：在 Flow 的 Respond action 中用 concat('B64:', base64(...)) 对响应体做 base64 编码；客户端检测 B64: 前缀后做 atob → Uint8Array → TextDecoder('utf-8') 解码。非 B64: 前缀的响应透传（向后兼容）。此问题已在 microsoft/PowerAppsCodeApps#359 报告。

Code App 通过 Microsoft Copilot Studio 连接器调用已发布的 Agent，使用 ExecuteCopilotAsyncV2 Action 同步获取 Agent 响应。

添加 Copilot Studio 连接器

在 make.powerapps.com 创建 Microsoft Copilot Studio 连接，然后运行 pac code add-data-source -a "shared_microsoftcopilotstudio" -c <connectionId> 添加到项目。CLI 自动生成 MicrosoftCopilotStudioService TypeScript 文件（注意类名含 Microsoft 前缀）。

获取 Agent 名称

在 Copilot Studio 中发布 Agent，进入 Channels > Web app，从连接字符串 URL 中提取 Agent 名称（如 cr3e1_customerSupportAgent）。名称区分大小写。

调用 Agent

使用 ExecuteCopilotAsyncV2 方法发送消息并同步等待响应。返回 { responses, conversationId, lastResponse, completed } 结构。

import { MicrosoftCopilotStudioService } from './generated/services/MicrosoftCopilotStudioService'; // 注意：第一个参数是 Agent schema name（字符串），第二个是 body 对象 const response = await MicrosoftCopilotStudioService.ExecuteCopilotAsyncV2( "cr3e1_customerSupportAgent", // Copilot (agent schema name) { text: "What is the status of my order?" }, // body undefined, // x_ms_conversation_id (可选) undefined // environmentId (可选) ); // response 类型为 IOperationResult<void>，实际响应需从 HTTP body 解析

注意：必须使用 ExecuteCopilotAsyncV2（/proactivecopilot/executeAsyncV2）端点。ExecuteCopilot（/execute）只返回 ConversationId 不返回响应内容；ExecuteCopilotAsync（/executeAsync）可能返回 502 错误。响应属性大小写可能不一致（conversationId / ConversationId），建议使用可选链处理。[10]

Code App 可以直接调用 Dataverse 中的 Action（写操作）和 Function（读操作），包括系统内置的和自定义的。

发现可用操作

运行 npx power-apps find-dataverse-api --search "WhoAmI" 按名称搜索操作。输出包含操作类型（Action/Function）、参数、绑定实体和返回类型。支持 --json 获取原始 JSON。

添加到项目

运行 npx power-apps add-dataverse-api --api-name WhoAmI。CLI 从 Dataverse $metadata 获取定义，生成 Schema JSON、TypeScript Model 和 Service 文件，并更新 power.config.json。

在代码中调用

Unbound 操作直接传参数调用；Bound 操作第一个参数是记录 GUID。支持 string、Record<string, unknown> 等类型映射。

import { WhoAmIService } from './generated/services/WhoAmIService'; const result = await WhoAmIService.WhoAmI(); // result.data: { BusinessUnitId, UserId, OrganizationId } import { AddToQueueService } from './generated/services/AddToQueueService'; const queueResult = await AddToQueueService.AddToQueue( queueId, target, sourceQueue, queueItemProperties );

限制：此功能仅在 npm CLI（npx power-apps）中可用，不支持 pac code。重复运行 add-dataverse-api 是幂等的，可用于同步最新的操作签名变更。[11]

Code App 通过 Custom Connector 接入外部 Web API。典型路径是将 API 发布到 Azure API Management，再创建 Custom Connector 桥接到 Power Platform。

Step 1: 部署 API

将你的 REST API 部署到 Azure Functions、App Service 或任何可公开访问的端点。官方示例使用 Azure Functions + Node.js 创建资产管理 API。

Step 2: 通过 API Management 暴露

在 Azure Portal 创建 API Management 实例，导入 Function App 作为 API 操作。在 Settings 中关闭 Subscription Required（开发阶段）。

Step 3: 创建 Custom Connector

在 API Management 的 Power Platform 页面中选择 Create a connector，指定目标环境和显示名称。Connector 自动出现在 make.powerapps.com 的 Custom connectors 列表中。

Step 4: 添加到 Code App

使用 pac code add-data-source 将 Custom Connector 添加到项目。CLI 自动生成类型安全的 Service 和 Model 文件，像调用内置连接器一样调用你的 API。

替代方案：如果不走 Custom Connector 路径，Code App 也可以使用标准 fetch() 直接调用外部 API，但需要配置 CSP（Content Security Policy）的 connect-src 指令允许目标域名，且不享受 Power Platform 的连接管理、DLP 策略和连接器权限治理。[12]

AI Builder 和 MCP（Model Context Protocol）目前没有 Code App 专用的集成路径，但可以通过间接方式实现。

AI Builder

AI Builder 的 Power Fx 公式和拖拽组件仅适用于 Canvas App。Code App 可通过两种间接路径调用 AI Builder 模型：(1) 将 AI Builder 模型包装在 Power Automate Flow 中，再通过 add-flow 调用；(2) 通过 AI Builder 连接器（shared_aibuilder）使用 add-data-source 添加，但此路径尚无官方文档明确说明 Code App 的适配情况。

MCP Server

Code App 是浏览器端 SPA，无法直接作为 MCP Client 连接 MCP Server（MCP 使用 stdio 或 SSE 传输）。推荐路径：将 MCP Server 包装为 HTTP API（如 Azure Functions + MCP Server SDK 的 Streamable HTTP 传输），通过 Custom Connector 接入 Code App。Power Apps MCP Server 是反向集成（AI Agent 操作 Power Apps），非 Code App 调用 MCP。

外部图片不显示、外部 API 请求被拦，几乎都不是代码问题，而是 Code App 的 Content Security Policy（CSP）拦截。CSP 在环境级强制启用，默认策略偏严。

默认 CSP 关键指令（环境级生效）

img-src 'self' data: <platform> ← 仅本应用、data URI、平台内置来源 connect-src 'none' ← 默认禁止所有 fetch/XHR/WebSocket（实测发现平台可能内部白名单了部分域名） script-src 'self' <platform> ← 禁止外部 JS style-src 'self' 'unsafe-inline' ← 禁止外部 CSS font-src 'self' ← 禁止外部字体（实测 Google Fonts CDN 可能被拦） media-src 'self' data: ← 禁止外部音视频 frame-src 'self' ← 禁止 iframe 外部页面

诊断结论：外链图片不显示的根因通常是 img-src 不包含该域名；外部 API 调用失败的根因通常是 connect-src 默认为 'none'。打开浏览器开发者工具 Console，看到 Refused to load ... violates the following Content Security Policy directive: "img-src ..." 即可确认。[13]

解决方案（按推荐顺序）

方案 1：图片打包进项目（首选）

把 logo、图标、固定素材作为本地资源放到 src/assets/，通过 Vite 打包随应用一起部署。不依赖外部站点可用性，不需要改环境配置。适合所有"非用户上传"的固定素材。

方案 2：图片走数据源（动态内容）

用户头像、产品图等动态内容存到 Dataverse File 列、SharePoint 文档库或 Azure Blob，通过连接器读取后以 base64 或 data URI 渲染。默认 img-src 已允许 data:，无需改 CSP。

方案 3：环境管理员加 CSP 白名单

必须用外链时：Power Platform admin center → 目标环境 → Settings → Privacy + Security → Content security policy → App tab，在 img-src（或 connect-src、frame-src 等）追加目标域名。白名单值会与默认值合并。配置后该环境所有 Code App 都生效。

方案 4：外部 API 走 Custom Connector

外部 Web API 调用优先走 Custom Connector（见上一节），不仅绕开 connect-src 拦截，还获得 DLP 策略、OAuth 管理、连接器权限治理。直接 fetch() 调用需要管理员加 connect-src 白名单，且无法走 Power Platform 治理。

配置 CSP 白名单的两种入口

Admin Center UI（推荐）

有 Dataverse 的环境可直接在 Admin Center 配置：按指令关闭"使用默认值"开关，添加自定义源（如 https://cdn.contoso.com），自定义值会与默认值合并。可单独启用/禁用每个指令。

REST API + PowerShell

无 Dataverse 的环境或需要批量管理时，调用 Environment Management Settings API（PowerApps_CSPConfigCodeApps 字段）。官方提供 Get-CodeAppContentSecurityPolicy / Set-CodeAppContentSecurityPolicy PowerShell 辅助函数。注意：更新指令会替换整个集合，必须先 Get 再 Set。

常见易错点：(1) CSP 是环境级配置，不能在单个 Code App 内通过 <meta> 标签覆盖；(2) 必须由环境管理员操作，开发者权限不够；(3) 加白名单后需刷新页面才生效，无需重新发布应用；(4) 大规模管理多个环境时，使用 environment groups and rules 统一配置。[13]

08 / Limitations

当前限制：Code App 不能做什么

上一节梳理了各类集成方法，本节明确当前 Code App 的已知限制，帮你避免选型后的意外。

01

移动端

不支持 Power Apps 移动 App 和 Power Apps for Windows。用户只能通过浏览器访问 Code App。

02

Git 集成

不支持 Power Platform Git 集成（源码同步到 Dataverse 的 Git 机制）。代码需在外部 Git 仓库管理，通过 pac code push 部署。

03

SAS IP 限制

不支持 Storage Shared Access Signature IP 限制策略。

04

Power BI 集成

不支持 PowerBIIntegration 函数直接嵌入 Power BI 数据，但 Code App 可通过 Power Apps Visual 嵌入到 Power BI 报表中。

05

SharePoint 表单

不支持 SharePoint 表单集成（将 Code App 作为 SharePoint List 的自定义表单）。

06

Service Principal

Service Principal (SPN) 不能创建或成为 Code App 的 Owner。

Code App 在应用生命周期管理方面有两个已知限制。

Solution Packager

不支持使用 Solution Packager 拆解和重组 Solution。Code App 的发布依赖 pac code push，不走传统 Solution 打包流程。

Source Code Integration

不支持 Power Platform 源代码集成功能。代码版本管理完全在外部 Git 仓库完成。

Code App 发布后运行在 Power Apps Host 的深层嵌套跨源 iframe 中。以下是实测验证的浏览器 API 兼容性和自动化测试约束。

浏览器 API 可用性（实测）

localStorage / sessionStorage：可用

在 Published 环境的 iframe 中，localStorage 和 sessionStorage 均可正常读写。可用于持久化用户偏好（主题、语言设置）和会话状态（聊天记录、表单草稿）。

Web Speech API（speechSynthesis）：可用

window.speechSynthesis 在 Published iframe 中可用，可枚举 voices、创建 SpeechSynthesisUtterance 并播放。但部分浏览器可能需要用户交互后才能首次调用。

fetch() 外部 API：受 CSP 约束

直接 fetch() 调用外部 URL 是否成功取决于环境 CSP 的 connect-src 配置。平台可能内部白名单了部分域名（如微软自有服务域名），但第三方域名通常需要管理员配置 CSP 白名单或走 Custom Connector。

Web Speech API（SpeechRecognition 语音识别）：可用（需用户授权）

SpeechRecognition / webkitSpeechRecognition API 在 Published iframe 中可用。Power Apps Host 的 iframe 已声明 allow="microphone" Permissions Policy（同时还包含 geolocation、camera、fullscreen、clipboard-write）。实测中 new SpeechRecognition() 可以创建，但 start() 需要用户手势触发（如按钮点击回调内调用），否则浏览器会因缺少用户交互上下文而返回 error: not-allowed。建议将 recognition.start() 放在 onClick 或 onPointerDown 事件处理器内，并在 onerror 中处理权限拒绝的降级（提示用户使用文本输入）。

自动化测试约束

关键限制：Published Code App 运行在深层嵌套的跨源 iframe 中（apps.powerapps.com → storageproxy → 你的 SPA），Playwright 等浏览器自动化工具无法直接驱动 iframe 内的 input 元素。这意味着：(1) 端到端自动化测试只能在 npm run dev 本地模式下运行；(2) Published 环境只能手动测试或通过 Playwright 操作外层 Power Apps shell（但无法与 Code App 内容交互）；(3) AI 编程助手验证 Published 环境只能截图观察，不能自动化操作。

尽管有上述限制，Code App 已获得以下平台治理能力支持。

01

连接器权限同意

终端用户运行 Code App 时会看到连接器权限同意对话框，与 Canvas App 行为一致。

02

DLP 策略

应用启动时强制执行数据丢失防护策略。管理员可通过 DLP 控制 Code App 能使用哪些连接器。

03

Conditional Access

支持对单个 Code App 设置 Conditional Access 策略（如多因素认证、设备合规检查）。

04

应用隔离与外部访问

支持租户隔离、App Quarantine 和 Azure B2B 外部用户访问。支持管理员同意弹窗抑制。

09 / Best Practices

Code App 开发与部署的最佳实践

上一节划清了限制边界，本节给出经过验证的最佳实践，帮你在这些边界内高效交付。

从项目初始化开始建立良好的工程实践。

优先使用 starter 模板

官方 starter 模板预配置了 React + Vite + Tailwind CSS + Tanstack Query + React Router，覆盖了大多数 LOB 应用需求。避免从零搭建浪费时间。

不要在代码中存储敏感数据

Code App 发布后代码托管在公开端点上。用户/组织的敏感数据应存储在数据源中，通过认证和授权后再获取。

利用生成的 TypeScript 类型

添加数据源后自动生成的 Model 和 Service 文件提供了类型安全的 API 调用。直接 import 使用，不要手写 HTTP 请求。

数据源变更后重新生成

连接器 Schema 变化后，npm CLI 可直接运行 npx power-apps refresh-data-source 刷新类型文件；PAC CLI 则需要 delete-data-source 删除后 add-data-source 重新添加。

确保 Code App 的部署流程可重复、跨环境可移植。

始终发布到 Solution

使用 pac code push --solutionName <name> 或配置 Preferred Solution，避免应用落入 Default Solution。实测中如果 push 时未指定 Solution，也可以在 make.powerapps.com → Solution → Add existing → App → Canvas app 中手动将 Code App 添加到指定 Solution（Code App 在 Solution 中的组件类型与 Canvas App 相同，type 300）。

使用连接引用实现跨环境可移植

在 Solution 中创建连接引用，用 -cr 参数绑定数据源。这样 Solution 在 Dev / Test / Prod 间迁移时，只需更新连接引用指向的连接，无需修改代码。

使用 Pipelines 管理多阶段部署

应用进入 Solution 后，利用 Power Platform Pipelines 在 Dev / Test / Prod 间部署，带有依赖检查、连接引用验证等预检机制。

上线后持续保障应用的可观测性和安全性。

Azure App Insights

为 Code App 配置 Azure Application Insights，获得前端性能指标、错误追踪和用户行为分析。

Health Metrics

Code App 的运行健康指标同时在 Power Platform Admin Center 和 Maker Portal 可用。

Content Security Policy

配置 CSP 头限制外部资源加载，减少 XSS 攻击面。参考官方 CSP 配置指南。

以下经验来自实际项目（React + Vite + Dataverse Code App），涵盖官方文档未提及的关键细节。

Vite 插件配置

必须添加 @microsoft/power-apps-vite 插件

在 vite.config.ts 中 import { powerApps } from '@microsoft/power-apps-vite'，并将 powerApps() 加到 plugins 数组。pac code init 或 npx power-apps init 会自动配置，但手动迁移现有项目时必须手动添加。

power.config.json 结构

理解配置文件的三级结构

Dataverse 表注册在 databaseReferences.default.cds.dataSources 下，每个 key 是 entitySetName（如 accounts、contacts、crf5c_opportunity1s）。非 Dataverse 连接器（Flow、Copilot Studio 等）注册在顶层 connectionReferences 下。没有顶层 dataSources 键。

Dataverse 字段命名约定

生成的 Model 使用 Dataverse 原生列名

字段名不是友好名而是 API 列名：如 emailaddress1（非 Email）、telephone1（非 Phone）、address1_composite（非 Address）。Lookup 字段以 _xxx_value 格式读取（如 _parentcustomerid_value、_ownerid_value）。Choice 字段返回数字值（如 industrycode 返回 1 而非 "Accounting"），需要手动映射标签。

DATA_SOURCE_NAME 匹配规则

Service 中的表名必须与 dataSourcesInfo 的 key 一致

生成的 Service 通过 getClient(dataSourcesInfo) 获取 client，dataSourcesInfo 的 key 就是 power.config.json 中 databaseReferences.default.cds.dataSources 的 key（即 entitySetName）。如果手写代码传入友好名（如 'Account'）而非 entitySetName（如 'accounts'），SDK 查找失败，表现为无数据或运行时错误。

推荐架构：生成 Service + 手写 Adapter

不要让业务代码直接调用生成的 Service

生成的 Service 使用 Dataverse 原生列名（如 emailaddress1），且 Model 包含数百个系统列。推荐在 src/generated/services/ 目录放置手写的 adapter service，负责：(1) 将 Dataverse 列名映射为业务友好名（emailaddress1 → email）；(2) 只暴露业务需要的字段子集；(3) 封装多表聚合逻辑（如 Activity 同时查 appointment + phonecall + email 三张表）。业务代码只调用 adapter，生成的 Service 仅被 adapter 引用。

// adapter 示例：account-service.ts import { AccountsService } from './AccountsService'; // CLI 生成 const FIELD_MAP = { id: 'accountid', email: 'emailaddress1', phone: 'telephone1' }; function fromDv(dv) { return { id: dv.accountid, email: dv.emailaddress1, phone: dv.telephone1 }; } export async function getAll() { const result = await AccountsService.getAll({ select: Object.values(FIELD_MAP) }); return result.data.map(fromDv); }

.power/schemas/ 目录纪律

不要手动编辑 CLI 生成的文件

.power/schemas/dataverse/*.Schema.json 和 .power/schemas/appschemas/dataSourcesInfo.ts 由 CLI 生成和维护。手动修改 dataSourcesInfo.ts 的 primaryKey 会导致与 Schema.json 不同步，引发 App 启动时 500 错误。需要变更时，始终通过 npx power-apps delete-data-source + add-data-source（或 refresh-data-source）重新生成。

利用 AI 编码助手加速 Code App 开发。

GitHub Copilot 集成

添加数据源后，可以使用 VS Code 中的 GitHub Copilot Agent Mode 自动更新代码以调用生成的 Model 和 Service。微软官方文档明确推荐这一工作流。

Power Platform Skills 插件

微软在 microsoft/power-platform-skills 仓库提供了 AI 编码助手插件（支持 Claude 和 GitHub Copilot），专门针对 Code App 开发场景优化。
