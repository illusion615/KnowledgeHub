01 / Foundations

Container Hierarchy & Role Mapping — Who Manages What, Where

Every licensing, environment, DLP, and approval decision later in this article sits on the same three-layer container model. Each layer has its own boundary and admin surface, and the matching roles only take effect at that layer — cross-layer authority neither cascades automatically nor can it be skipped.

1. Tenant — the Microsoft Entra ID identity boundary

The organization's identity perimeter. All Power Platform resources live inside it; every cross-environment governance action (env creation, tenant DLP, capacity quotas, Managed Environments) happens at this layer.

5 Entra Admin Roles ▾
▼

2. Environment — the isolation & governance boundary

A regional container holding apps, flows, connectors, gateways, and optionally Dataverse. Resources never leak across environments; DLP, capacity, and access roles are scoped here.

2 Environment Roles ▾
▼

3. Dataverse — the in-environment data store

An optional in-environment cloud relational database. When present, it layers table / column / record-level security roles on top of environment access — without a Dataverse role, table data is unreadable.

2 ALM + 5 Workload-Admin Roles ▾

Three rules to remember: (1) the three containers are physical boundaries — resources do not cascade; (2) a role at one layer never extends to the next — granting Environment Admin does not unlock Dataverse data; (3) every role is assigned from a specific admin surface — there is no 'direct grant' that bypasses it.

The five Entra built-in roles below are the hard gates for ALM — without any one of them, the end-to-end pipeline (provision environment, register service principal, grant roles, assign licenses, maintain security groups) cannot complete. Group 1 covers platform operations, ALM service principals, and role-grant approval. Group 2 (licensing / users) plus conditional roles is on the next page.

Environments · DLP · capacity

Power Platform Administrator

The day-to-day platform operations role. From PPAC, manages every environment, tenant DLP, capacity allocation (Dataverse / Copilot Credits / AI Builder / Power Pages logins), Managed Environments, Copilot Studio tenant switches, Power Pages site governance, and Power Platform Pipelines. Does not cover Power BI / Fabric tenant settings, nor M365 user or license management.

Admin portals
Power Platform admin center (PPAC) Microsoft 365 admin center › Service health
ALM · cloud service principals

Cloud Application Administrator

Manages Microsoft Entra app registrations and service principals (no on-premises Application Proxy). Creates, rotates, and disables the S2S credentials used by ALM pipelines (Power Platform CLI, GitHub Actions, Azure DevOps, Power Platform Build Tools); also handles bot channel registration when Copilot Studio agents publish to Teams. Preferred least-privilege option for cloud-only ALM — chosen over Application Administrator.

Admin portals
Microsoft Entra admin center › App registrations Entra › Enterprise applications Azure portal › Microsoft Entra ID
Role-grant gatekeeper

Privileged Role Administrator

Required to grant any of the admin roles above (alongside Global Administrator). It does not act on Power Platform resources directly, but every role-assignment approval flow runs through it — the mandatory node for PIM enrolment, audit, and privilege change.

Admin portals
Microsoft Entra admin center › Roles & admins Entra › Privileged Identity Management (PIM)

Group 2 (licensing + users) closes the seat-issuance and account side of the baseline gate; the footnote summarises conditional & break-glass roles that are added only when their trigger applies and are not part of the ALM baseline.

Seat licensing

License Administrator

License-only role: assign, remove, and reassign Power Apps / Power Automate / Power Pages / Copilot Studio / Power BI seats, plus Copilot Credit prepaid pack subscriptions. Cannot create environments, change DLP, or manage capacity allocation.

Admin portals
Microsoft 365 admin center › Billing › Licenses Microsoft Entra admin center › Billing
Users & security groups

User Administrator

Owns users and security groups: create/disable accounts, reset passwords, maintain the security groups used to bind environments and assign Dataverse roles. No license or environment authority, but every Power Platform authorization chain depends on the objects this role maintains.

Admin portals
Microsoft 365 admin center › Users M365 › Teams & groups Microsoft Entra admin center › Users Entra › Groups

Conditional & break-glass roles — assigned only when the trigger applies, not part of the baseline ALM gate.

  • Global Administrator — break-glass only (2–4 named owners + MFA + PIM JIT elevation), never a daily operations role.
  • Dynamics 365 Administrator — legacy alias of Power Platform Administrator, retained for D365-first orgs.
  • Application Administrator — use only if the ALM pipeline still needs on-premises Application Proxy; otherwise Cloud Application Administrator covers the same surface with less privilege.
  • Fabric Administrator — required when solutions ship Power BI / Fabric assets (workspaces, datasets, reports).
  • AI Administrator — required to approve and publish agents to Microsoft 365 Copilot Chat from the M365 admin center (Integrated apps).
  • AI Reader — read-only audit / governance committee access to M365 Copilot & AI service settings.
  • Security Administrator — required when Conditional Access policies gate Power Platform sign-in or block service principal authentication.

Only two core roles inside an environment: Environment Admin manages settings & role assignment, Environment Maker authors apps & flows.

Environment lifecycle · access · env-scoped DLP

Environment Admin

Full control of one environment: manage settings, assign environment roles, author environment-scoped DLP policies, and reclaim resources. In an environment with Dataverse, this role is automatically mapped to the Dataverse System Administrator role (full access to every table); only in Dataverse-less environments does it stay limited to platform settings. Tenant-wide DLP remains owned by Power Platform Administrator in PPAC.

Primary surfaces
PPAC › Environments › Settings PPAC › Users + permissions PPAC › Security PPAC › DLP policies (env scope) PPAC › Capacity PPAC › Resources
App / flow / agent authoring

Environment Maker

Builder role: create apps, flows, custom connectors, and solutions inside the environment. Cannot administer the environment or grant roles; in an environment with Dataverse, it is mapped to the Dataverse Environment Maker security role (can author solutions and custom components but does not bring business-table data access).

Primary surfaces
make.powerapps.com make.powerautomate.com copilotstudio.microsoft.com make.powerpages.microsoft.com

An optional cloud relational database decided at environment creation time. When present, it layers its own security roles (table + column + record level) on top of environment access — without a Dataverse role, table data is unreadable. The roles here split into two groups: (A) Dataverse predefined roles required for ALM — solution import, Pipelines, security-model maintenance; (B) workload-specific admin roles installed with an app — relevant to a project's runtime, but not part of solution deployment. End-user roles such as Basic User / App Opener and custom business roles are out of scope here.

A · ALM roles

Solution import/export, Pipelines, environment variables, connection references, security-role edits — the automation account (service principal) must hold one of the two below (System Administrator in most pipelines).

ALM master gate · all tables · all actions

System Administrator

Top Dataverse privilege inside the environment: every table, every action, organization-level access, plus the ability to create and edit security roles and business units. Power Platform Pipelines, PAC CLI, and Build Tools deployment accounts default to requiring this role. Reserve for platform operations and break-glass — never assign to business users.

Primary surfaces
PPAC › Environment › Settings › Security roles PPAC › Environment › Users + permissions Pipelines / PAC CLI / Build Tools (service principal)
Schema customization · no business data

System Customizer

Schema / solution customization admin: create or change tables, columns, relationships, forms, views, and solutions, but does not grant access to business data. Pair with Environment Maker so customizers can build without unlocking data; also the common starting point when building a least-privilege ALM "Deployment User" role.

Primary surfaces
PPAC › Environment › Settings › Security roles make.powerapps.com › Solutions

B · Workload admin roles

Provisioned in the environment when the matching workload is enabled (Approvals / Dynamics 365 Conversation Intelligence / Power Automate Desktop / Copilot Studio / Fabric & Power BI). They govern that workload's runtime data: approval template config, RPA machine onboarding, agent publishing, BI workspace linkage. Names below come from a real PPAC › Environment › Settings › Security roles list filtered by "admin".

Approvals runtime

Approvals Administrator

Added when Power Automate Approvals is enabled in the environment. Manages approval templates, runtime approval records, reassignments, and orphan cleanup; read/write on the flow_approval / flow_approvalrequest tables. Does not affect solution packaging or environment administration.

Primary surfaces
Power Automate › Action items › Approvals make.powerautomate.com › Admin (Approvals settings)
Conversation / call intelligence

CCI admin

Added when Conversation Intelligence (a.k.a. CCI — Customer / Conversation Intelligence) is enabled in Dynamics 365 Sales or Customer Service. Manages call recordings, transcripts, KPIs, and keyword triggers; exists only in environments that have the matching D365 SKU. Not involved in ALM.

Primary surfaces
D365 Sales Hub › Conversation intelligence Customer Service workspace › Conversation intelligence
RPA machines & groups

Desktop Flow Machine Configuration Admin

Added when Power Automate Desktop (RPA) is enabled. Manages unattended / attended machine registration, machine groups, shared credentials, and assignment policies in this environment; does not grant authoring or run rights on the Desktop flows themselves. Deployment of Desktop flows inside a solution still goes through System Administrator / Customizer.

Primary surfaces
Power Automate › Monitor › Machines Power Automate › Monitor › Machine groups
Agent runtime governance

Microsoft Copilot Administrator

Added when Copilot Studio is enabled (a.k.a. Copilot Studio Administrator). Manages agent publishing, sharing, knowledge sources, analytics, and generative answers in this environment; solution import/export of agents still requires System Administrator / Customizer, and channel publishing to Teams / M365 Copilot Chat still needs tenant-level Cloud Application Admin / AI Administrator.

Primary surfaces
copilotstudio.microsoft.com › Agents PPAC › Environment › Copilot Studio
Power BI workspace linkage

Power BI workspace admin

Added when Fabric / Power BI integrates with this Dataverse environment. Manages the Dataverse-side artifacts created by that linkage (dataset link, report permissions, Dataverse → Power BI export); the Fabric workspace / capacity itself is still governed in the Fabric admin portal by the Fabric Administrator.

Primary surfaces
PPAC › Environment › Power BI app.powerbi.com (workspace owner)

Note: Group B roles are not Dataverse predefined — they are added automatically when the matching workload (Power Automate Approvals, D365 Conversation Intelligence, Power Automate Desktop, Copilot Studio, Fabric & Power BI) is enabled. If the workload is not enabled, the entries will not appear under PPAC › Environment › Settings › Security roles. Power Pages visitor authorization uses Web Roles (Anonymous / Authenticated Users etc.) — a Power Pages in-site concept, not a Dataverse security role, and therefore out of scope here.

Capacity Allocation · Part 1 (Storage / Copilot Credits / AI Builder)

04 / Capacity Allocation · Part 1

Turn Tenant Entitlements Into Per-Environment Operating Budgets — Part 1: Storage, Copilot Credits, AI Builder

Now that you know what you've licensed (§02) and where it lives (§03), capacity is the first resource that needs intentional budgeting. Power Platform has six independent capacity pools, each with its own unit, allocation grain, overage behavior, and admin surface. The three cards below cover Dataverse storage, Copilot Credits, and AI Builder credits; the remaining three pools (Requests / RPA / Pages logins) live in Part 2.

01

Dataverse storage

Unit: GB (split into Database / File / Log pools). Allocation: tenant pool = sign-up default + per-user license accruals + add-ons; preallocated per environment in PPAC. Overage: 15% remaining = first warning, 5% = ops impact warning; once in overage, create/copy/restore in the environment is blocked. Default env has its own 3+3+1 GB quota.

02

Copilot Credits

Unit: Copilot Credits per month (replaces the legacy Copilot Studio Messages; the common currency across Copilot Studio capabilities). Allocation: tenant pool from prepaid pack subscription or pay-as-you-go; allocated per environment in PPAC › Licensing › Copilot Studio, with per-agent monthly caps available. Overage: custom agents are disabled when tenant consumption hits 125%; agent flow enforcement is separate — it blocks new flow runs without disabling the agent. Linking an Azure subscription for pay-as-you-go avoids enforcement.

03

AI Builder credits (legacy)

Unit: AI Builder credits per month. Allocation: same model as Copilot Credits, allocated per environment in PPAC. Overage: within a month, exhausted AI Builder credits fall back to Copilot Credits; if both are out, model runs are blocked. Credits do not roll over. Note: AI Builder add-ons are renewal-only for existing customers; seeded credits are removed in November 2026 — design new workloads around Copilot Credits.

Capacity Allocation · Part 2 (Requests / RPA / Pages logins)

Expand to look up API requests, Power Automate Process / Hosted RPA, or Power Pages login allocation.

04 / Capacity Allocation · Part 2

Turn Tenant Entitlements Into Per-Environment Operating Budgets — Part 2: Requests, RPA, Power Pages Logins

Continuing from Part 1: the remaining three capacity pools — Power Platform Requests, Power Automate Process / Hosted RPA, and Power Pages logins — plus a separate-domain note that Power BI / Fabric capacity is not allocated from PPAC.

04

Power Platform Requests

Unit: requests per 24-hour rolling window (covers Dataverse API calls, connector calls, Power Automate flow actions). Allocation: accrued from user licenses to a tenant pool; not allocated per environment. Overage: throttled rather than blocked — runs slow down but do not hard-stop. Sustained overage requires a Power Platform Requests add-on or higher-tier license.

05

Power Automate · Process / Hosted RPA

Unit: Process plans (billed per workflow) and Hosted RPA bots (billed per concurrency). Allocation: process / hosted bot capacity is bound per environment. Overage: new unattended desktop flow triggers fail; attended desktop flows come from Power Automate Premium user licenses and do not draw on process capacity.

06

Power Pages logins

Unit: authenticated user logins per month and anonymous user logins per month (metered separately). Allocation: set by each site's paid SKU configuration; not allocated from a PPAC capacity pool. Overage: tiered billing on monthly logins — site access is not blocked but extra charges accrue. Governance focus is SKU selection and login forecasting per site.

Separate domain: Power BI / Microsoft Fabric F-SKU capacity (CUs, workspace binding, auto-pause) is owned by the Fabric admin domain, managed by Fabric Administrator in the Fabric admin portal, and is not allocated from PPAC.
Sources: Dataverse capacity-based storage, Copilot Credits billing & overage, AI Builder licensing, Power Platform Requests limits, Process plan & Hosted RPA, Power Pages billing, Fabric capacity.

Environment Strategy · Part 1 (Six Environment Types)

05 / Environment Strategy

Choose the Right Environment Type for Each Workload — Default, Sandbox, or ALM-Ready Production

Capacity (see Capacity reference above) lives inside environments. Environments are the primary governance boundary — each is scoped to a region and optionally contains Dataverse. Pick the right type up front; converting later is painful or impossible (e.g. the "Enable Dynamics 365 apps" switch is set at provisioning time and can't be reversed).

Core

Default

One per tenant, auto-created. All licensed users get Maker role. Limited to 1 TB. Cannot be deleted. Designed for personal productivity — NOT production. Rename it to clarify purpose.

Managed

Production

Full admin control. For permanent, business-critical workloads. Requires 1 GB available capacity. Full backup & restore support.

Dev/Test

Sandbox

Non-production with copy & reset. For development and testing. Full admin control. Convert to/from production.

Temporary

Trial

Expires after 30 days. One per user. Admin-controlled creation. Cannot enable Dynamics 365 apps.

Temporary

Developer

Via Developer Plan. Individual-use only, no sharing. No security group assignment. For learning and prototyping.

Auto

Dataverse for Teams

Auto-created when a Power App is first built in Teams. Limited admin settings. Roles map to Teams membership automatically.

Task 10 Reference

Governance Controls · DLP Policies & Monitoring Toolchain

Expand for the three-tier DLP classification, Managed Environments features, or the CoE monitoring checklist.

07 / Monitoring and Governance Controls

Stop Bad Actions With DLP and Managed Environments — Then Watch the Signals in Power Platform admin center

Permissions (see Task 11 reference) decide who can act. Governance controls decide what those actions are allowed to touch — and how you spot misuse early. Run governance as a closed loop: define policy, enforce, monitor, remediate.

Preventive

Data Policies (DLP)

Classify connectors into Business / Non-Business / Blocked groups. Connectors in different groups cannot coexist in one app or flow. Enforcement latency: typically <1 hour, up to 24h at scale. Violations cause apps/flows to be suspended.

Premium

Managed Environments

Adds sharing limits, usage insights, extended backup, solution checker, IP firewall, Customer Managed Key, and Lockbox. Included with standalone PP/D365 licenses. Not included with Developer Plan.

Monitoring

Admin Center Views

Inventory — all apps/flows/agents. Usage — adoption tracking. Monitor — operational health. Actions — risks & recommendations. Replaces CoE Starter Kit as primary governance tool.

Network

Conditional Access & Intune

Entra ID P1/P2 conditional access policies for Power Apps/Automate based on user, device, or location. Intune mobile app protection on iOS/Android.

Sources: Data policies, Managed Environments, CoE Starter Kit transition.

Org profile: Power Platform is a strategic enterprise platform; governance and release are largely automated; the Maker community has a Champion program; AI / Copilot is live in mainstream scenarios.

●Must
  • All 17 tasks + automated release via Power Platform Build Tools
  • Environments & DLP via IaC (PowerShell / Terraform provider)
  • CoE dashboards wired into business OKRs / finance
◐Should
  • Integrate with Azure DevOps / GitHub repos and CI pipelines
  • Formal Maker Champion program with training pathways
  • SecOps wired into Microsoft Purview & Defender
○Optional
  • Contribute patterns / templates / components back to community
  • ISV / cross-tenant solution sharing
—Defer
  • None — governance & release are fully automated

What's next L500 is a rhythm: revisit adoption, AI pipeline, and ROI quarterly; fold into enterprise architecture governance.
