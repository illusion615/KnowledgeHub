Agent Runtime · Platform Integration Decision

Pi × 自研智能体平台：以 Aye aye Captain 为样本的融合与替代决策

本文以 Aye aye Captain 的真实委派链为样本，审计 28 个 Playbook、48 个 MCP 工具、一次性作业令牌、质量门禁与数据库单写者路径，并与《智能体平台设计理念》逐层对照。结论是 Pi 与自研平台只在执行平面部分重叠：它可以承接模型适配、Agent loop、上下文压缩与结构化事件；任务治理、租户边界、业务状态与审批仍由平台负责。

平台决策

采用 Pi 的合理边界是替换 Agent 执行内核，同时保留平台控制面与领域数据面。

  • 1保留：Playbook、状态机、质量门禁、审批与数据库单写者。
  • 2替换：模型 Provider 适配、Agent loop、上下文压缩与会话事件。
  • 3新增：Pi-MCP bridge、运行时适配器与统一 JobEvent schema。
  • 4暂缓：生产写入、API 进程内嵌 SDK 与 Pi 自主子 Agent。

01 / Product Positioning

Pi 是可扩展的 Agent 宿主，不是预设完整工作流的编码产品

官方把 Pi 定义为 minimal terminal coding harness：核心处理模型调用、工具循环、会话和终端交互；计划、审批、MCP、子代理等工作流能力不进入内核，而由 Extensions、Skills、Packages、外部 CLI、tmux 或容器补齐。[1][2][8][9] 这项边界决定了它的优势与学习成本。

Pi 不是一个不可拆分的 CLI；四个公开包把模型接入、Agent 循环、终端 UI 与成品 CLI 分开，允许只复用需要的层。[1][6]

01

pi-ai

统一 OpenAI、Anthropic、Google 等 Provider API，处理流式输出、推理内容、工具调用、成本与跨 Provider 上下文转换。

02

pi-agent-core

提供 Agent 循环、工具执行、状态管理、附件与消息队列，不绑定某一种用户界面。

03

pi-tui

采用保留终端 scrollback 的差分渲染方式，组件可以缓存并局部更新。

04

pi-coding-agent

把模型、Agent、TUI、会话与资源发现组合为可直接使用的终端编码 Agent。

默认工具集围绕 read、bash、edit、write 展开；grep、find、ls 可组成只读工具集。模型在产生不含工具调用的响应前持续循环，用户可以在运行中插入 steering 或 follow-up 消息。[2][6]

  • 1
    组装上下文

    加载系统提示、AGENTS.md / CLAUDE.md、Skills 描述、有效工具和当前会话分支。

  • 2
    调用模型

    Provider 适配层负责请求格式、流式事件、推理内容、缓存和使用量差异。

  • 3
    执行并记录工具

    工具参数经 schema 验证后执行，结果写回会话；同一批工具可以并行运行。

  • 4
    继续、转向或结束

    有工具结果或 steering 消息时进入下一轮；无工具调用且队列为空时结束。

这些能力不是完全做不到，而是没有成为所有用户都必须承担的默认复杂度；官方 examples 已提供其中多项的扩展实现。[2][3]

01

权限弹窗

可用 tool_call 事件实现规则与确认；默认没有逐次审批。

02

Plan Mode 与 Todo

可用只读工具、文件或官方 plan-mode 扩展示例实现。

03

MCP

内核不加载 MCP 工具清单；需要时可通过 CLI 包装器或扩展接入。

04

子代理

可由扩展或 pi --print 子进程生成，内核不规定编排方式。

05

后台 Shell

官方建议用 tmux 管理 server、watcher、REPL 和调试器。

06

进程内沙箱

真实隔离交给 Docker、OpenShell、Gondolin 微型 VM 或其他 OS 边界。

02 / Capability Map

日常编码能力完整，差异集中在会话、模型与编程接口

Pi 可以读写项目、运行命令、处理图片、压缩上下文并恢复会话。它进一步把会话存为可分支的 JSONL 树，允许在同一对话中回到任意历史节点；同时提供 TUI、一次性输出、JSON 事件流、RPC 和 Node.js SDK。[2][4][6]

从定位文件到修改与验证，Pi 的默认工具足以完成常见代码任务；TUI 还提供文件模糊搜索、路径补全、多行输入、图片粘贴、外部编辑器与 shell 快捷入口。[2]

01

理解与定位

读取文本或图片，通过 @ 选择文件；grep、find、ls 支持受限的只读分析。

02

修改与执行

精确编辑、完整写入和 shell 执行组成实现闭环，工具调用过程与结果直接显示。

03

运行中干预

Enter 发送 steering，在当前工具批次结束后改变方向；Alt+Enter 把补充任务排到整个 Agent 运行之后。

每条会话记录都有 id 与 parentId，当前活跃位置是一个 leaf；因此改变早期提示不会删除后续历史，而是形成新分支。[4]

/tree

在一个会话文件内探索替代方案

  • 跳到任意历史 entry 并从那里继续。
  • 可为离开的分支生成摘要并带入新路径。
  • 标签可标记重要检查点。
/fork · /clone

把选中的历史路径拆成新会话

  • fork 从较早的用户消息开始新文件。
  • clone 复制当前活跃分支。
  • 适合隔离代码审查、替代实现或模型对比。

Pi 支持订阅 OAuth、API key、云平台、本地 llama.cpp 与 OpenAI-compatible endpoint；模型变化时尽力转换不同 Provider 的工具调用和推理内容格式，但这种交接受上游 API 差异限制。[7][10]

接入类型 代表选项 适用判断
订阅登录 ChatGPT、Claude、GitHub Copilot、xAI 已有个人订阅，希望减少密钥配置；具体计费仍按 Provider 规则。
API 与云平台 OpenAI、Anthropic、Google、Azure OpenAI、Bedrock、Vertex AI 需要固定账单、企业云身份或网关治理。
聚合网关 OpenRouter · Cloudflare AI Gateway · Vercel AI Gateway 希望从一个账户试用多家模型或统一转发。
本地与自托管 llama.cpp · Ollama · LM Studio · vLLM 数据位置、离线运行或推理成本比模型上限更重要。

同一运行时既可以被人直接操作，也可以作为子进程或 Node.js 库嵌入产品；选择标准是是否需要类型安全与进程内状态访问。[2][6]

01

TUI / Print

个人交互用默认 TUI；脚本中的单次任务用 pi -p，标准输入可直接并入提示。

02

JSON / RPC

JSON 输出全部事件；RPC 通过 stdin/stdout JSONL 控制会话，适合非 Node.js 客户端与进程隔离。

03

Node.js SDK

直接访问 AgentSession、事件、模型、工具、会话树与资源加载器，适合自定义 UI、评测和自动化产品。

03 / Integration Sample

Aye aye Captain 已把 Agent 限定在可替换的执行边界内

Aye aye Captain 是一个 local-first 项目操作系统。它把任务设计、状态机、质量门禁、人工审批和项目知识保存在本地控制面，只把一次 Playbook 的执行交给 coding agent。当前内置 28 个 Playbook，MCP server 暴露 48 个结构化工具；Agent 无权直接写 SQLite，所有业务写入必须经过 REST API 与同一组门禁。[17] 这条边界让 Pi 可以替换现有 Copilot CLI，而不改变项目治理语义。

控制面先决定任务和权限，再启动 Agent；Agent 的退出码只说明进程结束，不能越过交付门禁。这条链路可以在不改业务层的前提下更换执行器。

  • 1
    Playbook 决定任务语义

    delegate(playbookKey, ...) 解析项目覆盖或全局版本，并执行 repo、设计和验证命令等前置检查。

  • 2
    引擎组合受约束上下文

    项目原则、质量规则、ADR、架构锚点、产品意图和历史踩坑从数据库注入；输出语言与写作风格由中心指令统一追加。

  • 3
    每个作业获得一次性能力令牌

    runJob 创建作业记录，签发 AAC_JOB_TOKEN，并把 job id、Playbook key 与 repo cwd 注入子进程；作业结束后立即撤销令牌。

  • 4
    执行器只获得本次工具白名单

    Playbook 的 mcp_tools 生成临时配置。读架构、修 Bug、回复话题分别获得不同工具，未授权工具不应进入模型上下文。

  • 5
    MCP 只把调用转给 REST API

    48 个工具共享同一个 server.mjs，调用时携带 job id 与令牌。API 验证项目、作业状态、Playbook 和来源，再由服务层写入。

  • 6
    交付由平台事实判定

    需要 post_message 的任务只有在 messages 表出现关联 Agent 消息后才成功；进程即使 exit 0，缺少消息仍会被标为失败并留下系统说明。

现有引擎已经把 Agent 视为临时执行单元，因此接入 Pi 不需要迁移 Playbook 或数据库。替换范围集中在进程命令、模型接入、Agent loop 与事件解析。

当前职责 Pi 对应能力 处置
resolveCopilot + buildCommand CLI JSON、RPC 或 SDK 启动 AgentSession 替换为 provider-neutral AgentRuntime 适配器。
Copilot 模型目录与登录 Pi ModelRuntime、订阅 OAuth、API key 与自定义 Provider 替换模型接入；项目级凭据归属仍由平台控制。
CLI 内部 Agent loop pi-agent-core + AgentSession 替换；不在平台重复实现工具循环、重试和压缩。
parseRun + parseUsage JSON 事件、工具生命周期与 usage / cost 替换文本正则，归一化为统一 JobEvent。
Playbook、上下文注入、状态机与质量门禁 Pi 不提供这些项目治理语义 完整保留，由 Aye aye Captain 继续作为单一事实来源。
MCP server、REST 服务与 SQLite 单写者 Pi 核心没有内置 MCP 保留现有服务，并增加一个薄 Pi-MCP bridge。

现有自动化测试已经覆盖交付缺失与受保护来源两类失败。把 Copilot CLI 换成 Pi 后，这些 API 事实保持不变，因此可以继续作为验收判据。

失败样例 A

进程 exit 0，但没有提交对话消息

enforceJobDeliveryContract 查询 messages 表；若不存在与 job_id 关联的 Agent 消息，作业改为 failed，并写入可见的系统消息。换用 Pi 不会改变这个结果。

失败样例 B

Agent 伪造来源或使用过期令牌

逆向需求导入会核对 job、project、Playbook、running 状态与一次性令牌；payload 里的 origin 不被信任。Pi 扩展只能转发当前令牌，无法绕过 API 的来源校验。

04 / Product Boundary

Pi 与自研平台只在执行平面部分同质

这里用三个稳定层级判断是否同质：控制面决定谁可以运行什么任务，执行平面完成模型与工具循环，领域数据面拥有业务对象与事务。《智能体平台设计理念》覆盖三个层级，Pi 主要覆盖执行平面。[18] 因此二者存在可替换组件，但面向的完整产品职责不同。

只有执行平面的主要职责能够由 Pi 直接承接；另外两层即使能用扩展拼出局部功能，也缺少平台级数据模型、权限边界和治理语义。

层级 自研平台职责 Pi 原生覆盖 同质判断
控制面 项目与租户注册、Playbook 版本、RBAC、配额、质量门禁、审批、评测与演进提案。 提供扩展、工具 allowlist 和会话钩子，但没有多租户控制面或项目状态机。 不属于同质产品；平台完整保留。
执行平面 模型接入、Agent loop、上下文组装、工具调用、重试、压缩、会话事件与运行时取消。 ModelRuntime、AgentSession、自定义工具、JSON / RPC、压缩、重试和生命周期事件覆盖主要职责。[3][6][7] 部分同质；适合替换自研或单一厂商执行内核。
领域数据面 业务工具、事务、ACL、长期记忆、业务数据库与审计事实。 内置文件和 shell 工具以宿主用户权限运行；Pi 不理解业务事务或领域 ACL。[5] 不属于同质产品；继续通过项目 API / MCP 管理。

平台目标不应按功能名称直接映射。每项目标需要判断 Pi 是否提供机制、平台是否仍负责策略，以及采用后应怎样修订原设计。

原设计目标 Pi 可承担部分 平台保留部分 建议修订
Goal 01 · 业务无关 Pi 核心不含项目业务概念。 项目隔离、工具目录与上下文来源。 把 Pi 作为固定版本依赖，禁止项目扩展反向进入平台公共层。
Goal 02 · 多租户硬隔离 无；Project Trust 不是运行隔离。 身份、数据分区、凭据、网络、配额与审计。 每个作业使用隔离进程或容器、最小挂载和短期凭据。
Goal 03 · 可回放 JSON 事件、会话树、工具参数、结果与 usage。 持久化、租户分区、关联业务结果与证据保留。 把目标拆成取证重建与重新执行比较；模型输出不能承诺确定性复现。
Goal 04 · 可替换 多 Provider、CLI / RPC / SDK 与公开工具接口。 统一 AgentRuntime 接口、回退策略与验收基准。 先让 Copilot 与 Pi 双运行，禁止把 Pi 类型泄漏到业务服务。
Goal 05 · 单镜像可启动 Pi 可作为固定二进制或 npm 包进入 worker 镜像。 API、数据库、队列、健康检查与扩缩容。 把单镜像目标限定为 worker 制品，不再把完整平台压成一个进程。
Goal 06 · BYOK 运行时 key、OAuth、环境变量与自定义 CredentialStore。 租户级密钥托管、轮换、审计与成本归属。 由平台按作业注入短期凭据，禁止共享全局 auth.json 作为生产来源。
Goal 07 · MCP 单通道 无内置 MCP；扩展可以注册桥接工具。 业务工具发现、调用鉴权、来源校验与服务门禁。 把目标改为业务副作用只经 MCP / API；模型请求、日志和控制信号不纳入该限制。
Goal 08 · 可演进 扩展、Skills、Prompt Templates 与热加载机制。 提案、评测、shadow / canary、人审与回滚。 Pi 只能执行或起草改动；生产资源仍通过平台提案门禁发布。

开源项目需要按交付层级比较。Pi、LangGraph、OpenCode 和 Dify 都能运行 Agent，但它们分别交付 harness、workflow SDK、编码产品和应用平台，不能放进同一张功能总分榜。

代表项目 主要交付物 与 Pi 的关系 对自研平台的含义
Pi 可编程 coding harness、模型层、AgentSession、TUI、CLI / RPC / SDK。 本次候选执行内核。 以最少重写复用 Agent loop 与多模型接入。
LangGraph / Microsoft Agent Framework Agent 与 workflow SDK，强调显式图、状态和宿主集成。[19][20] 比 Pi 更靠近应用代码，需要自行组合模型、工具、会话与 UI。 强分支、确定性 workflow 优先保留；开放式 coding loop 可由 Pi 承担。
Claude Code / Codex CLI / OpenCode / Aider / Cline / Gemini CLI 面向开发者的完整编码产品，分别强调第一方模型集成、git / IDE 工作流、权限、MCP 或自动化能力。[11]-[16] 与 Pi 同属执行产品层，但默认产品面更完整、内核边界更重。 适合直接提供给开发者；作为平台内部内核时升级耦合与 UI 冗余更高。
Dify / Azure AI Foundry Agent Service 包含应用配置、知识、工作流、部署与运维入口的 Agent 平台。[21][22] 覆盖范围比 Pi 更接近《智能体平台设计理念》。 可以替换更多自研控制面，但会改变数据驻留、租户、部署和供应商边界。

05 / Integration Architecture

首个版本采用 CLI JSON 子进程，保留升级到 RPC 与独立 SDK worker 的路径

当前 Aye aye Captain 以一个作业对应一个子进程，取消通过进程信号完成，日志按作业独立保存。Pi 的 JSON mode 与这套生命周期最接近，并且直接输出消息、工具、重试、压缩和 usage 事件。[24] RPC 适合后续实时 steering；SDK 适合独立 worker，但不应嵌入 API server，否则模型故障、扩展崩溃和内存压力会进入数据库单写者进程。

选择依据不是接口新旧，而是作业是否需要运行中双向控制、进程隔离和类型级状态访问。

方式 机制 收益 代价 / 限制 决策
CLI JSON pi --mode json --no-session 一作业一进程、结构化 stdout、自然继承 cwd 与临时环境变量，最接近现有 Job runner。 运行中追加指令不方便；需要单独的 Pi-MCP bridge 扩展。 首选。用于只读试点和第一版生产适配器。
RPC pi --mode rpc --no-session stdin / stdout JSONL 支持 prompt、steer、follow_up、abort、状态查询和事件流。[23] 需要常驻双向协议客户端、严格 LF framing 与 extension UI 响应处理。 第二阶段。仅在平台支持运行中改令或追问时启用。
Node.js SDK createAgentSession 类型安全，直接设置模型、工具、ResourceLoader、SettingsManager 和 SessionManager。[6] 升级耦合最高；扩展和模型运行时与宿主共享崩溃、内存和依赖边界。 只用于独立 worker。禁止直接进入 API / SQLite 单写者进程。

Delegation Engine 继续输出渲染后的 prompt、cwd、工具白名单、模型偏好和作业环境；AgentRuntime 只负责把这些中立输入翻译为具体执行器命令，并把原始输出归一化为 JobEvent。

稳定接口

AgentRunSpec → JobEvent*

AgentRunSpec 只包含 prompt、cwd、env、model、read / write 能力和 domainTools。JobEvent 至少覆盖 started、text_delta、tool_started、tool_finished、retry、compaction、usage、settled 与 failed。

回退边界

执行器故障可以回退，业务写入不能重放猜测

只有在首次业务副作用前发生的模型不可用、认证或启动失败可以自动改用另一执行器。任一 MCP 写工具成功后，平台必须停止自动回退，避免重复创建或重复状态迁移。

Pi 核心没有 MCP，因此 bridge 是唯一新增的业务工具适配层。它不得复制 REST schema 或调用业务数据库；工具名称、描述和 inputSchema 仍来自现有 MCP server。

  • 1
    引擎生成作业级工具清单

    继续从 Playbook.mcp_tools 计算白名单，并为 Bug 等系统强制合同补入必需工具；白名单作为 bridge 的显式启动参数。

  • 2
    bridge 启动现有 stdio MCP server

    MCP 子进程继承 AAC_API_BASE、AAC_JOB_ID、AAC_JOB_TOKEN 与 AAC_PLAYBOOK_KEY，继续由 API 验证每次调用。

  • 3
    tools/list 与白名单取严格交集

    任何白名单工具缺失、重复或 schema 无法转换都在 agent_start 前终止作业。不能把 extension_error 只写日志后继续运行。

  • 4
    每个 MCP tool 动态注册为 Pi custom tool

    execute 原样转发 name 与 arguments，映射文本内容和 isError；工具审计仍由 MCP server 写入 tool_calls，避免双份业务日志。

  • 5
    会话结束关闭 MCP transport

    无论成功、取消或模型错误，session_shutdown 都关闭 transport；Job runner 随后撤销令牌并执行原有交付门禁。

06 / Platform Improvements

平台应减少自研执行机制，并加强治理接口与隔离边界

原平台设计把模型路由、Agent workflow、工具桥、会话、telemetry 和演进机制都列为平台职责。[18] Pi 证明其中一部分已经有成熟的可编程实现。改进方向是让平台专注于租户、策略、业务状态和证据，把开放式 Agent loop 作为可替换依赖；确定性 workflow 与企业模型网关则按场景保留。

每项改造都缩小一个耦合面，并保留现有质量门禁。完成后，新增执行器只实现 AgentRunSpec 与 JobEvent，不接触 Playbook、路由或数据库。

  • 1
    抽出 AgentRuntime 接口

    把 resolveCopilot、命令参数和供应商特有回退移出 Delegation Engine；引擎只生成中立的 AgentRunSpec。

  • 2
    建立统一 JobEvent schema

    Copilot 文本日志与 Pi JSON 事件都在后端归一化；前端不再识别某个 CLI 的字符格式，成本统计也不再依赖日志尾部正则。

  • 3
    区分平台 Skill 与 Pi Skill

    平台 Skill manifest 继续拥有版本、工具白名单、模型偏好、评测集和发布状态；适配器把其中的运行字段翻译为 Pi prompt、tools 与 model，不能让 .pi 文件成为生产事实来源。

  • 4
    收窄 MCP 单通道目标

    业务副作用必须经 MCP / API；模型请求、worker 控制、日志和指标走各自标准通道。这样仍保护单写者，又避免把基础设施通信强行包装成业务工具。

  • 5
    把执行器移入隔离 worker

    API server 只排队、签发能力和收集事件；Pi / Copilot 进程位于 worker 或容器，按作业挂载 repo 与短期凭据。生产环境不共享用户级 auth 或扩展目录。

  • 6
    固定依赖版本与兼容合同

    Pi 发布频率高，生产 worker 应固定版本与 SHA-256，并用 adapter contract tests 验证事件、工具 schema、取消和退出行为后再升级。当前核查版本 v0.82.1 提供平台二进制与 SHA256SUMS。[25]

Aye aye Captain 是本地单用户样本，可以让 Pi 直接承担更多模型接入职责；多租户企业平台仍需要中央网关、配额与凭据服务。相同组件在两种部署里不能给出同一处置。

能力 Aye aye Captain 多租户平台
模型 Provider 适配 可由 Pi ModelRuntime 取代当前 Copilot 专用模型目录与文本用量解析。 Pi 连接企业 AI gateway；网关继续负责配额、数据策略、成本归集和区域控制。
Agent workflow 开放式 coding、架构分析和会话回复可由 Pi AgentSession 执行。 强分支、可预测步骤和补偿事务继续使用 LangGraph、Microsoft Agent Framework 或普通代码；Pi 只处理开放节点。
会话与 telemetry 作业可先使用 --no-session，平台持久化 JobEvent 和 tool_calls；需要分支研究时再保存 Pi session。 Pi 事件作为 trace 输入；租户分区、保留期、检索和合规导出仍是平台职责。
Skill 与 Supervisor Playbook 继续是权威 SOP；Pi 只消费渲染结果，不自行发布项目扩展。 评测、shadow、canary、人审与回滚留在平台；Pi 可以起草补丁或执行候选版本。

Pi 具有足够多的扩展点，平台很容易把控制面逻辑重新写进扩展。以下三条约束确保平台仍能替换执行器，并让策略接受独立测试。

01

生产事实不写入 .pi

模型、工具、Prompt 和 Skill 的生效版本来自平台数据库或签名制品；项目 .pi 目录只用于本地开发，不决定生产作业。

02

领域服务不导入 Pi 类型

Pi event、message 和 tool 类型只能存在于 adapter 包；进入 jobs、stats、routes 和前端前必须转换为平台 schema。

03

平台门禁只读取持久化事实

退出码、Agent 自述和 Pi session 标签都不能完成工作项；状态迁移只根据 work_run、业务字段、消息和审批记录判定。

07 / Controlled Pilot

试点从无文件写入的真实 Playbook 开始，并以平台事实验收

本研究没有安装 Pi，也没有执行对照任务；以下阈值属于拟议决策标准，不是实测结果。试点应固定 Pi 版本、同一模型、同一仓库快照、同一 Playbook 和验收条件，让 harness 成为主要变量。任何阶段未通过，Copilot 继续作为默认执行器。

每一阶段都必须先通过自动门禁和人工抽检，再增加下一类副作用；不能因为只读任务表现良好就直接开放 repo 写入。

  • 1
    适配器合同测试：不调用模型

    使用 fake Pi JSON 流与 fake MCP server 验证事件解析、工具交集、令牌继承、扩展错误、取消、退出码和 usage 写入。所有 Playbook 的现有命令构建测试继续通过。

  • 2
    conversation.reply · 业务只写消息

    只开放 get_topic、项目上下文读取和 post_message。验证 20 次运行均产生关联 Agent 消息，静默退出必须失败，未授权工具在 Pi active tools 中为 0。

  • 3
    project.init.architecture · repo 只读、数据库结构化写入

    在一次性项目副本上运行 Copilot 与 Pi，同模型、同 prompt。人工抽检架构组件、关系、ADR 与重复率；repo 工作树必须保持不变。

  • 4
    bug.fix · 一次性 repo 写入

    只在前两阶段通过后启用 edit、write、bash。使用已知根因的小型 Bug，要求测试通过、root_cause 与 fix_summary 持久化、work_run 完整，并由人工审查最终 diff。

Harness 价值不能只看最终答案；同一结果可能以更高 token、更多人工纠正或更差的故障恢复换来。每次对照运行都记录以下六项。

指标 记录方式 拟议晋级标准
工具范围完整性 比较 Playbook allowlist、MCP tools/list 与 Pi active tools；记录缺失和越权项。 缺失 = 0；未授权 = 0。
交付与门禁正确率 成功任务核对 message、work_run、状态和必需业务字段；故意遗漏交付验证是否失败。 20 / 20 正常运行符合合同；负向样例 100% 被拒绝。
事实与产物质量 同一评审表抽检架构事实、重复记录、错误关系、Bug 根因与 diff；模型身份对评审者隐藏。 不得低于 Copilot 基线；任何高严重度事实错误阻断晋级。
人工纠正 记录 steering、补充 prompt、手工修复和重跑次数，并标记发生阶段。 中位数不得高于 Copilot；P95 增幅 ≤ 1 次。
时间与成本 记录 wall-clock、input / output / cached tokens、模型费用和 adapter 开销。 质量相当时，P50 完成时间或模型成本至少一项改善 ≥ 15%。
运行时稳定性 记录启动失败、认证失败、extension_error、模型重试、压缩失败、取消延迟和孤儿进程。 孤儿进程 = 0；取消后令牌 100% 失效；适配器错误不得被误报为 succeeded。

晋级条件按优先级依次判断：合同与安全、结果质量、运营收益。前一项不通过时，后一项的成本改善不能抵消风险。

01

合同与安全门槛

工具越权、门禁漏判、令牌未撤销、孤儿进程或扩展错误误报成功任一发生，停止晋级并修复适配层。

02

质量门槛

Pi 在盲评中不低于 Copilot，且没有高严重度事实错误，才可以从回复进入架构分析、再进入 repo 写入。

03

运营收益门槛

质量相当且合同通过后，只有时间、模型成本、人工纠正或多 Provider 可用性中至少一项产生可量化改善，Pi 才成为默认执行器；否则保留为专项后备。

08 / Adoption Verdict

采用结论：把 Pi 作为可替换执行内核，不把它升级为平台控制面

Pi 可以减少自研平台在模型适配、Agent loop、上下文压缩、会话事件和用量解析上的重复投入，并为多 Provider 与本地模型提供统一入口。它不能替代项目与租户治理、业务事务、质量门禁、审批、长期记忆和平台级可观测性。Aye aye Captain 的合理路径是增加 Pi 执行器并保留 Copilot 回退；原《智能体平台设计理念》则应把开放式运行时从自研核心下沉为依赖，同时保留确定性 workflow 与企业治理。

每项职责只有一个权威所有者。Pi 提供执行机制，平台提供策略与事实；bridge 和 adapter 只做协议转换，不拥有业务语义。

处置 范围 判据
保留 Playbook、项目知识、状态机、质量门禁、审批、work_run、租户与业务数据。 这些职责需要平台级持久化、授权或业务语义，Pi 不提供同等所有权。
替换 Copilot 专用进程命令、模型目录、Agent loop、文本日志解析、上下文压缩和 usage 正则。 Pi 已提供公开接口和结构化事件，继续自研只会扩大维护面。
新增 AgentRuntime、AgentRunSpec、JobEvent、Pi adapter 与 Pi-MCP bridge。 这些边界隔离第三方类型和协议，同时允许 Copilot 与 Pi 并存和回退。
暂缓 生产 repo 写入、API server 内嵌 SDK、Pi 自主发布扩展、Pi 子 Agent 与无人工复核的默认切换。 这些动作扩大副作用、升级耦合或治理范围，必须等待分阶段试点证据。

任务的分支确定性和业务副作用决定运行时。能用普通代码清楚表达的流程不应改成开放式 Agent loop；需要探索代码库、动态选工具和多轮修正的任务才适合 Pi。

采用 Pi

开放式分析与编码任务

  • 代码库架构提取、审查、Bug 根因定位与实现。
  • 工具调用序列无法在运行前完整列出。
  • 模型、成本或数据位置需要跨 Provider 选择。
保留 workflow / 代码

强分支、事务与补偿流程

  • 审批、付款、订单状态和跨系统补偿事务。
  • 每个状态与下一步必须事先证明可达。
  • 失败需要确定性重试、幂等或人工接管。

本轮只能批准接入设计与只读试点，不能据此批准生产切换。默认执行器只在合同、安全与质量门槛全部通过，并出现可量化运营收益后改变。

01

试点不通过

保留现有 Copilot 路径，删除或冻结 Pi adapter；平台改进中的 JobEvent 与 AgentRuntime 抽象仍可服务其他执行器。

02

合同通过但收益不足

把 Pi 保留为本地模型、多 Provider 对照或特定架构分析的专项执行器，不承担默认流量。

03

合同、质量与收益全部通过

按 Playbook 分批把 Pi 设为默认，Copilot 保留为启动前故障回退；任何已有业务副作用的作业不自动跨执行器重放。

最终结论 Pi 不是自研智能体平台的同质替代品；它是执行平面的高价值候选依赖。采用它的目标是减少重复自研，同时让控制面、领域数据面与质量门禁保持独立和可验证。
