从发布热度读出共性需求

短期内，托管服务、开放权重、专项训练、量化和独立运行时集中到类似接口：输入上下文与判定标准，输出软件可消费的选择、等级或概率。这些不同路径共同回应了一个通用需求——软件需要理解含义，但往往不需要生成一段话。[1][37][52][55]

  • 需求层：工单分派、证据筛选、动作选择和审核都反复出现“有界语义判断”。
  • 实现层：不同底座、训练与运行时说明有多条工程路径；这不是某一个品牌独有的需求。
  • 行为层：本次 HN 样本显示后续话题扩散，Gateway 数据显示快速试用；二者比只有发布新闻更接近需求，但不是长期留存或付费意愿。[63][64]
  • 历史痛点：一位开发者回顾 2024 年的数据清洗项目，需要反复标注、训练多个分类器；他把 Jev 视为减少这些支线工作的工具。这是需求早于产品的个人案例，不是代表性调查或等质量验收。[65]
  • 当前判断：证据支持“长期存在的语义判断问题，遇到了让开发者迅速尝试的新接口”，尚不能证明“整个市场期盼已久且已被满足”。还需观察免费期后使用、7/30 日留存、真实付费及与现有分类器的净收益。

02 / 类别与价值

结构化决策模型：软件里的语义判断层

先把模型名字拿掉：许多软件只需要“属于哪类、是否成立、哪个更相关”，却面对不能靠字符串匹配解决的含义。结构化决策模型尝试把这种高频、有界的语义判断变成可组合组件，而不是再造一个聊天助手。

抽象契约与选型边界

上下文 → 判定标准 → 结果 → 程序政策

本文把主要输出预定义判断、等级或分布，供软件直接组合使用的模型称为“结构化决策模型”。这是研究口径，不是已统一的行业分类；System One 是其中一套产品命名，不是必须采用的架构。

组成抽象契约
上下文文本、记录、候选片段或已知环境状态
问题与边界判定标准、候选项、有序等级；必要时允许未知/不适用
结果单选、多标签、是非概率或等级分布；不是任意解释文本
后续处理代码检查一致性与权限，再执行、保留或升级复核

本文重点研究不以自由文本逐字解码为主要输出路径的实现。生成式 LLM 也能输出合法 JSON，但输出格式相同，不代表计算路径、训练目标或概率含义相同。

先找最简单的可用方案

方案适合的工作主要代价

监督分类器固定标签、有训练数据标注、训练、漂移监控

分类任务并不新；这里关注把可配置的语义判断嵌入现代软件流程。这些工程选项并非互斥的学术分类：决策实现也可使用分类器。应问任务是否需要动态候选与语义泛化，以及更简单的方案是否已经足够。

定位与潜在收益

程序掌握工作流，模型补足语义

它更像软件中的语义判断层，而不是完整 Agent：程序提供状态与候选，模型补上难以穷举的语义关系，程序保留状态机、策略和执行权。

  • 固定流程：判断一封信应进入哪个队列，而不是生成一篇客服分析再解析。
  • 检索与工具：从已知候选中判断相关性、证据支持或下一步动作；原文与工具权限仍由程序控制。
  • 与 LLM 配合：大量局部判断交给可验证的轻量路径，开放式规划或表达仍交给生成模型；不是强制每轮先小模型、再大模型。

少生成、少搬运，但不能漏算返工

潜在收益不是“小模型必然便宜”，而是减少不必要的生成、重复上下文与人工筛查，并让判断成为可测试、可追踪的接口。收益取决于任务分布和能真正省掉多少工作。

  • 延迟/吞吐：省去长文本解码、合并独立问题，但预处理、排队、重复编码和网络仍要计算。
  • 工程可控性：有界输出便于组成流程、记录概率和复核原因；格式正确仍不等于语义正确。
  • 部署选择：可选托管或本地、通用或专项训练，换来不同的隐私、维护、数据与硬件成本。

采用条件：在质量要求相同、成本口径一致时，被省掉的工作成本应大于新增判别、运维与误判返工成本。若每轮仍让同一 LLM 处理同样材料，hybrid 可能只是多一道开销。

04A / 决策契约

用输出契约比较模型，分清概率、分数与置信度

以 Jev 为接口例子：请求由 model / state / questions 组成，响应包含 answers / usage。问题 ID 仅对应返回值，底层模型看不到它；把语义写进 instructions，不能只靠 is_urgent 这样的名字。[3]

三种原语的输入与返回值

原语是 API 的基本问题类型；这里以 Jev 的三种类型作对照。Choice 使用 criteria 映射，Score 使用有序等级列表；接口不生成任意 JSON、自由文本解释或思维链。[3] 本文建议审计保留输入证据与代码策略，事后解释不能视为 Jev 的真实推理。

原语定义与输出常见误用
Noul是非判断 → noul ∈ [0,1]，无独立 confidence0.5 表示是非不确定，不是中等严重度
Choice候选映射 → choice、probabilities、confidence候选不全却没有 other / none
Score有序等级 → score、legend、probabilities、confidence把概率加权等级当作精确金额或数量

共享状态并行，不等于问题之间有依赖顺序

所有问题看到同一个 state，分别求值；共享输入可减少重复传输和串行调用，但有依赖的判断仍需由代码安排。[10][11]

  1. 1
    可以合并

    同一工单的部门、急迫性与信息充足度，可在一个请求里分别询问。问题仍分别计入输入预算。[2][10]

  2. 2
    需要分阶段

    若第二个问题的候选必须由第一个答案决定，先返回结果、生成候选，再发第二个请求；或预先询问所有分支后由代码选择。

  3. 3
    不保证逻辑恒等式

    独立求值不表示统计独立，也不保证不同问题互补。不要直接相乘概率，或假设 P(A) + P(not A) = 1。[5]

类型正确、概率校准与事实正确是三件事

confidence 是概率分布形状的汇总值，不是本次判断正确的概率；校准则是预测概率与一组样本实际发生频率的对应关系。[4][19][22]

01
类型约束

合法返回 billing 仍可能误分本应 technical 的工单。官方「零幻觉」应限定在预定义输出空间，不能扩展为零语义错误。[1][5]

02
校准需要本地数据

预测约 0.8 的一组样本应约 80% 为真，是群体性质。版本、语言、候选与问法变化后，都需重测阈值。[4][22]

03
受约束 LLM 也是基线

传统 LLM 可用原生 structured outputs。公平比较应包含这种模式及其拒答、重试和语义错误，不能只比较未约束 JSON。[17]

05 / NanoJev 研究

NanoJev 实现了并行概率决策，尚不能视为 Jev 的等价替代

这里重点指仓库创建于 2026-09-17 的 TianyuCodings/NanoJev：Qwen3-0.6B 底座、决策头、训练流水线和可下载权重。本文核查代码提交 71a513bb0163、模型快照 4a19595eada0；Qwen 是该开源实现的选择，不是对 TypeSafe Jev 底座的披露。[37][41]

原理、训练与评测参考实现与接入本地 MLX 运行

候选路径与决策头

源码把每条 state + question + candidate 编成独立路径，一次底座 forward 批量处理，再从末尾 EOS 表示读取决策；没有逐 Token 生成循环。[38]

01

三个输出读法

Choice 用共享标量头，可选集合注意力；Boolean 用单路径 logit 的 sigmoid；Score 对等级路径归一化后取 Σi·pᵢ。当前范围是 Choice 2–255 项、Score 2–10 级。[38][40]

02

一次 forward 的边界

参考实现重复每条候选路径的 state 前缀，并未共享前缀计算；增加候选数与输入长度仍增加计算、填充和显存压力。一次函数调用不等于状态只算一次。[38][40]

03

可复现的是公开实现

代码可检查输入隔离、动态候选与分布读出。但官方 Jev 的结构和完整 RLCD 训练细节仍未在已核查资料中公开；不能从接口相似推出参数、训练或能力等价。[22][39]

RLCD-inspired：配对奖励与 Brier 目标

作者提出独立的 RLCD-inspired 候选方法，而非恢复官方配方。Brier 用预测概率向量与真实结果指示向量的平方距离评分；配对奖励从同一事件的多次预测与观察结果估计这一目标。[39]

  1. 1
    目标是恢复事件概率

    令 p 为预测分布、q 为事件真实条件分布。M≥2 个独立、有放回的预测样本，采用命中奖励减样本一致性惩罚，可得 E[R] = 2p·q − ||p||² = ||q||² − ||p−q||²，最优点是 p=q。[39]

  2. 2
    保留监督学习对照

    配对策略梯度（PG）在所列独立性条件下是预期 Brier 目标的无偏梯度估计；CE（交叉熵）和直接 Brier 也可学习 q。加入采样不自动更好，有限候选时直接计算可避免额外采样方差。[39]

  3. 3
    不要把事件与动作混同

    观察结果 Y 须在给定输入后独立于预测抽样；baseline 必须 stop-gradient 且不依赖当前样本。会改变世界结果的实际动作不满足这个简单前提。梯度结论也不等于有限样本或分布外校准保证。[39]

评测要分清控制器、检查点与统计口径

以下是项目作者的完整小地图对照，不是本报告重跑：4×4 test、6×6 OOD（分布外测试）各 20 张地图；每局最多 2×size² 步，只有一个训练检查点和一个采样种子。[42]

以上为上游 CUDA 服务契约。本文另实现了 Apple Silicon MLX 服务，并已接入 Playground；它采用更小的本地保护上限，不用游戏回放冒充推理。实现与验收见下一节。[49]

检索还发现 novvoo/nanojev；它与本文重点项目不是同一实现，不能把它的定义、设备支持或结果混用。[44]

对象关键事实
novvoo/nanojevREADME 的 Noul 是 K+1 拒答槽、Score 返回高斯均值 / 标准差，与官方 Noul=P(yes)、有序 Score 不同。核查提交 05acd4d5493d 未见 LICENSE。[44]

尚未验证标准库检查本身不涉及 GPU；随后已用现有权重运行真实 tokenizer、MLX 推理及 PyTorch 数值对照。仍未重训、验证业务准确率或校准泛化，也未调用付费推理。[49]

  2. 2
    保持输入与数值语义

07A / 业务流程

让语义判断进入固定流程，把政策与写入留在代码中

以客服工单为例，需求是识别部门和紧急程度，同时遵守退款政策、审批与审计。本文推荐固定流程承载执行，仅把难以穷举的语义判断交给 Jev；数字、计数和日期比较应由代码计算。[5]

从输入到动作的可重放流程

状态快照、模型判断、政策决策和业务动作分别记录，才能定位错误发生在哪一层。

  1. 1
    规范化与可信预检

    后端验证租户、身份、订单和重复扣费；生成最小 state，例如 request、account_status、verified_order_facts。客户自述不等于可信账务事实。

  2. 2
    并行语义判断

    一次请求评估 team、urgency、enough_info；Choice 中保留 other。不同字段回答同一状态的不同问题，而非互相授权。

  3. 3
    政策与持久化执行

    other、信息不足或阈值未通过转复核；其余仅生成队列建议。退款资格、批准记录和幂等执行由代码与持久化工作流决定。

取舍与失败走查：紧急不等于已获授权

相较让生成式 Agent 自行规划整条流程，固定代码便于测试和重放；代价是政策、问题与标签集需要显式维护。

07B / Agent 配合

让生成模型负责规划，让 Jev 负责局部分类

Jev 可以参与模型选择、技能候选筛选和工具风险判断，生成式 LLM 仍负责规划、写作和自由参数生成。LangChain 已提供分类器及实验中间件，但这些不消除权限与审批边界。[9][21]

模型与技能选择：只在有收益的决策点调用

多一次分类也多一次网络调用。本文建议先用固定规则排除明确情况，再评估 Jev 是否减少更昂贵的生成调用。

  1. 1
    入口选择

    ModelRouterMiddleware 根据最新用户消息选择模型，并在整次 run 的模型调用中沿用；它并非默认每一轮重新选型。[9]

  2. 2
    中途升级

    工具失败或新证据提高任务难度时，可用自定义 before_model hook 重新评估；设置调用预算，避免每轮无条件分类。[9]

  3. 3
    技能候选

    把技能描述与允许范围作为状态，Choice 选择候选，另设无需技能 / 不适用判断。候选过多时先检索或分层，不让 Jev 发明技能名。

工具安全：模型筛查在权限检查之后

AutoModeMiddleware 只筛查列出的工具；判定风险后拒绝调用，不会自动发起人工审批。需要批准流程时，应另接 human-in-the-loop 机制。[9]

顺序负责组件具体约束
1. 确定性验证执行器 / 权限系统参数 schema、租户、路径白名单、资源权限
2. 语义风险Jev 或其他筛查器检查意图与动作是否匹配；不把低风险概率当授权
3. 批准与执行人审 / 受限工具高风险或模型不可用时拒绝或复核；批准绑定具体参数

官方承认对抗性 state 能影响判断。[5] 因此，即使工具风险筛查返回「安全」，沙箱、最小权限和数据外发控制也不能省略。

规则、公平性与费用边界
      
推荐动作级模式 tank-v5-step：每条指令只尝试移动一格或开火一次，失败也消耗这条指令；不会反复撞墙或自动重试。动作完成后才请求下一次决策。实时模式两方独立取最新公开状态，快方不等慢方，因此快照时间可能不同；同步模式仍使用相同快照、等待双方再执行。相同本地服务用 FIFO 排队，独立模式在真正调用时才冻结输入。

      
决策次数不限。比赛可选 30 / 60 / 90 秒或无限制；无限制时持续到分出胜负或手动停止，页面离开及模型错误仍会安全停局。长局保留最近 1,800 帧、200 条决策；累计计数、用量和均值覆盖整局，p50/p95 使用每方最近 256 次的最近秩算法。省略的历史会明确标注，不冒充完整回放。原生阶段计时不是独立 GPU 内核时间。

      
强制行动 tank-v4-active：不提供 wait，模型必须选四向移动或向某个存活敌方目标开火。候选不会预先过滤撞墙方向或射界外目标，模型必须自己判断可行性。移动每 0.8 秒尝试一格；开火每 1.2 秒尝试一次，射界不符或目标消失也消耗一次机会并记为无效。指令持续到被替换，不自动绕路、追击或换目标。首条模型指令到达之前不会由程序代为行动，这段空档计入首令下达延迟。奖励踩到即拾取。

      
评分随每次模型返回更新，并标明所用快照时间，不按动画帧伪造变化。NanoJev 显示决策头的原生候选概率，不是判断正确的置信度。Copilot CLI 不提供同类概率，因此另请求模型自报 0–100 偏好分，分数不必合计为 100，不能与原生概率直接比较；未返回就标为缺失。请求自评分会增加 Copilot 输出 Token 和耗时，这部分计入实验记录。

      
tank-v2：排除已在撤退点、已在支援范围、已到达包抄点等冗余候选；hold 仍表示模型主动原地警戒，不强制改为进攻。同队争用空格时交替让行；远处坦克封路时允许沿地形路线接近，但下一格被占用仍禁止穿越。指令被接收不等于坦克发生位移，双方上方显示实际移动格数和停留原因。

      
地图按种子随机生成并旋转对称，出生点和奖励均检查连通。以下自动控制仅适用于战术模式：坦克每 0.8 秒移动一格，按同一 BFS 寻路；自动瞄准轴向 6 格内敌人，每 1.2 秒开火，墙体挡弹，无友伤。模型每轮为存活坦克选择追击、包抄、支援、撤退、奖励或警戒，不控制底层瞄准。先全歼获胜；到时先比较存活数，再比较总 HP，相同为平局。

09A / 坦克对战实践 · 2026-09-21

    
先把任务和协作建模清楚，再让模型参与决策

    
以下是本项目坦克对战迭代得到的工程实践，不是 Jev 厂商结论或通用最优策略。已完成的是输入、规划、调度与界面改进，没有重新训练模型权重；真实模型对局、纯搜索实验和模拟响应测试必须分开看。[50][51]

  

  

    

      
实践一：明确任务契约，而不是不断加强提示词

      

        

          
早期记录出现过有射击机会却持续移动、整局零开火的情况。开发集上，缩短文本和改成中性动作名仍未修复问题；这说明要检查任务表示与读出，而非只追加“积极进攻”。该旧局还受限流等待影响，不能把失败归因于单一因素。[50]

          
    
            
  1. 1
    先写执行契约
    写清目标、坐标、射程、装填、碰撞和时间单位；区分下达指令、实际开火与真实命中。一次动作尝试失败，也要反馈后重新决策。
    2. 
            
  2. 2
    精确事实由代码计算
    墙体遮挡、合法位置、BFS 距离和伤害计算交给程序；提供“接近有效射界”“若目标不动可造成伤害”等效果，同时保留预测假设。
    3. 
            
  3. 3
    披露辅助，不修饰失败
    合法性筛选发生在评分前，映射和候选集可审计；保留原始地图模式作对照。不能把程序代选的动作、受困退化或失败重试记成模型能力。
    4. 
          

        

        

          
接口返回了数值，不等于返回了可靠的胜率。当前模型参与候选排序；它的分数没有因此成为训练过的长期战斗价值。[50][51]

          
来源正确读法不要混淆

            
NanoJev 原生 Boolean独立 p_true，作为效果命题的相对效用不是动作集合的归一化概率，也不是校准胜率

            
在线模型自报分原样保留 0–100 偏好，严格检查所有问题 ID除以 100 只是算术缩放，不会变成原生概率

            
程序综合值公开的搜索价值与模型偏好组合，分别保存两项贡献权重属于控制器，不是模型训练参数

          

          
例如当前规划器采用“搜索值 + 12 ×（读出偏好 − 0.5）”；12 是本项目程序系数，不是最佳通用值。在线调用缺项、越界或失败时明确报错，不伪造 Boolean 分布，也不偷偷换回本地模型或另一种策略。[51]

        

      

    

    

      
实践二：评价团队动作的共同后果

      

        

          
当前按队伍请求，一次为本方所有存活坦克形成指令。但把两辆车放进同一请求，仍可能只是独立评分；共享位置、目标和资源约束必须进入联合计划。[51]

          
    
            
  1. 1
    组合候选，而非拼接各自最高分
    排除队友争用同一格的组合，比较集火、补刀与机动的整体后果。不能只把两个单车 argmax 拼在一起。
    2. 
            
  2. 2
    让预测中的对手也行动
    使用真实引擎预测 24 tick，对比进攻和躲弹两类对手，再把前 6 个计划交给模型评分。它是有限策略展开，不是穷尽搜索，也不读取敌方待执行订单。
    3. 
            
  3. 3
    优化获胜机会，而非机械保血
    短期少掉血不一定优于付出小代价击毁威胁。应共同考虑存活、敌方战力、交战距离和资源；装填时是否移动也应有战术收益，不能强制离开好射位。
    4. 
          

          
版本边界：上述早期规划只执行首步，后续仍是预测；后来的 v4 已加入有界目标与路线记忆及条件续走，不再把每次动作当成新目标。本方仍使用双车就绪屏障，复杂跨轮编队和按单车独立下令仍待验证，不能把接口验收当成战略最优证明。

        

        

          
v7 友伤规则下，子弹碰到第一辆存活坦克即停止，友军也会扣盾、扣血。仅检查当前枪口前有没有队友还不够：本次联合走位可能使队友进入已有弹丸或拟发射子弹的路径。[51]

          
    
            
  • 1评分前用同一个物理引擎检查装填、移动相位与弹丸到达时间；子弹飞过之后，仍允许安全穿越，不能永久封锁整条射线。
    • 
            
  • 2若有零预测友伤的根计划，优先只让这些计划进入评分；若全部有风险，显式记录 no_safe_plan，不捏造安全动作或隐藏等待。
    • 
            
  • 3分别统计对敌伤害、友伤 HP、护盾损失和失败尝试。敌方也可能死于其友伤，因此减员数不能自动当成己方击杀。
    • 
          

          
这项独立弹道检查假定敌人冻结、无新敌方订单，观察估计延迟加 12 tick；不是安全保证。基准保留过期指令的真实后果，不事后修补。迁移到不可逆业务写入时，应另加执行前状态与权限复核，失败时显式拒绝或转人工，而不是凭预测直接放行。

        

      

    

    

      
实践三：先证明系统改善，再证明模型有额外贡献

      

        

          
快规则方与慢模型方在实时模式里拥有不同的行动机会；输赢同时混合了策略、延迟和调度。建议先固定输入做局面检查，再同步对战，最后评估真实实时系统。[50]

          
    
            
  1. 1
    固定比较条件
    同地图交换出生侧，预先规定局数、时长与停止条件；保留失败、平局和超时。v6、v7 的碰撞规则不同，不能把旧胜局换个版本标签继续使用。
    2. 
            
  2. 2
    记录完整时间链
    分开看排队、限流、搜索、推理、执行等待和状态年龄。搜索放在独立线程，不能阻塞游戏时钟制造优势；限流公平暂停也不等于普通推理阶段的同步屏障。
    3. 
            
  3. 3
    留下不调用模型的对照
    至少比较规则基线、纯搜索、同一搜索器加模型评分。检查模型改变了哪些计划，以及改变后是否更好；请求次数、合法输出和命中数都不是模型准确率。
    4. 
          

        

        

          
v6 同步对照：3 张预先指定的新地图，各交换出生侧，共每种控制器 6 局，均自然歼灭结束。以下来自本项目记录，不是厂商或第三方基准。[50]

关键反证：模型在 114 次决策中仅有 2 次改变同快照的纯搜索选择；对应地图两侧的最终 HP 从纯搜索的 114 / 112 降至 102 / 106。本批次系统胜局更多，不等于模型评分优于纯搜索。旧、新控制器的装填约束等也不同，不能把整包改进归因于单个组件。[50]

          
另有 v6 真正实时的 4 局 FP32 规划对战全部获胜，94 次模型请求，各局平均完整决策耗时约 249–535 ms；不是纯 GPU 耗时。小样本与共享效果模板不能证明总体胜率。v7 友伤与在线兼容链路后来用物理／模拟响应测试验证，不能冒充 v7 或云端模型的新胜率。[50]

        

        

          
    
            
  1. 1
    先选问题，再选模型
    明确哪些内容可精确计算、哪些需要语义评分。固定快照、候选集和成功标准；一个请求可批量评分，但更多候选仍有编码与计算成本。
    2. 
            
  2. 2
    先同步复核，再实时试跑
    在对战设置中确认模型、策略和规则版本，再设置时长与截止。在线调用必须显式同意；换设置后重新确认，只有开始按钮触发运行。慢在线模型建议先用同步模式。
    3. 
            
  3. 3
    先做消融，再考虑训练与采用
    从诊断导出实际输入、原始分数、程序读出、时延和执行后果；不上传凭据或私有原始日志。若模型无增益，应报告这一结果，再考虑搜索／自博弈数据训练，不能继续堆提示词来掩盖。
    4. 
          

          
迁移原则：规则负责精确约束，模型提供有界判断，规划处理相互影响，执行器记录真实结果。业务场景仍需重测质量、时延、校准与权限，不能直接照搬本游戏的系数或胜局。公开材料只含汇总与方法，不含私有原始回执，尚不足以支持第三方独立复核。[50]

实践四：用闭环淘汰坏策略，而不是不断加规则

      

        

          
研究不能停在“固定局面通过”。本轮先固定种子、出生侧、预算、指标和源码哈希，再采集开发数据；书面复核后冻结策略，用未参与修改的种子复测，最后做有界模型影子调用。失败、预算耗尽和被否决的候选都保留。已看过的留出失败只能进入下一轮开发集，不能继续冒充新测试集。

          
一次具体优化：当前读出为搜索值＋12×（偏好−0.5）。若第一名领先超过 12，合法模型分数也不能改变第一名；只有一个候选时亦然。研究脚本在这种情况下可跳过模型，明确记为程序决定；其余情况照常调用，失败不重试。这是固定候选与读出的不变性证明，不是置信度猜测，也不证明搜索动作正确。

          
执行工具会拒绝覆盖旧轮次、检测源码变化、校验开发复核与预算；真实本地调用还需单独确认，用户正在进行的对局优先。它是研究人员监督的有限闭环，不是后台无限试跑或自动升级默认策略。

        

        

          
16 局纯搜索对战：每个数据划分两张地图、交换出生侧、比较 v2/v3，各局最多 180 tick；对手固定为规则进攻。表中歼灭胜局与达到预算上限分开，后者不按剩余 HP 冒充胜局。版本间是整包策略对照，不是单一规则的因果实验。

负面结果：v3 在留出地图上循环走位更多、搜索更慢，没有增加歼灭胜局。重复值是每次移动目标在最近 8 个位置中的出现次数之和，不等于 385 次错误动作。耗时是分版本顺序运行的本机 CPU 观察，不是独立 GPU 性能排名。不能因为功能更丰富就宣称策略更优。

          
效率证据：v3 开发集 30/115、留出集 22/115（19.1%）快照满足免调用证明。另按预定间隔抽取 6 个快照，两款 Laya 共真实调用 12 次；回放中 4 次可省，原始与门控动作无差异。这 4 次均来自开发快照，留出抽样未覆盖可省分支；其余回放复用同一响应，不能冒充独立验证或已测实时加速。Typed-decisions 改变过 1 个纯搜索动作，但未验证后续收益。

          
本轮结论：保留可证明的省调用研究策略，不自动改线上默认；否决“v3 已整体更优”的结论。下一轮先定位搜索热点与循环原因，把已看过的失败纳入回归，用全新留出地图验证，再测真实实时系统。最佳实践是能复测、能否决、能回退，而不是把最后一版叫作最佳。

          
预登记计划 · 首轮完整汇总与证据边界 · 研究方法、决策与复现步骤

        

        

          
后续针对 NanoJev FP32 与 Laya typed-decisions 执行了四轮候选筛选及一次固定确认批次：28 局纯 CPU 筛选、56 局已完成的模型对战，共 1,220 次本地请求、402 次有证明的实际免调用。另有一局被用户新对局打断，5 次已完成请求仍计成本；追加记录只补缺失局，没有重跑已完成的对照。这些是重复配对试验，不是 56 张独立地图。

          
全局加强反循环虽然更积极，却增加己方损失，不能通用推广；两个进一步方案在 CPU 筛选就被否决，没有浪费模型调用。最后的条件式修正仅在首选重复访问≥3、且两种预测中的伤害都≤12 时介入，其余保持原策略。单次搜索内的有界缓存还通过了评分与动作一致性测试，不跨变化后的战场复用。

逐轮结果与调用账本汇总 · 迭代、拒绝与中断续接方法 · 冻结的确认计划

        

        

          
外部研究提示要区分目标、计划和实际执行。Orkin 的 F.E.A.R. 架构使用工作记忆与变化的事实管理目标；MPC 资料也区分未来计划与当前实际执行的首步。本项目据此加入持续目标和路线承诺，但不把这些资料的结论当成坦克游戏的性能或稳定性证明。

          
v4 将目标、路线和动作分层：目标维持至完成或失效，路线保留路点，单步持续检查危险。批准路线后最多续走两步；一辆车可续走、另一辆需要评分时，前者作为公开固定动作进入联合请求。位置来回变化不算进展；必须缩短剩余路线，或实际造成敌方 HP／护盾损失。续走明确标为程序执行，不伪造模型评分。

          
真实短验收：NanoJev FP32 与 Laya typed-decisions 各返回一次评分，随后各执行一次双车路线续走，续走没有新搜索或模型调用。初版文字契约曾被 NanoJev 的 512-token 上限拒绝；改成明确的紧凑字段后，16 组纯分词检查最长为 386／381 tokens，没有截断或提高上限。这是执行链验收，不是新胜率。车身与履带也改为随实际移动方向共同旋转，炮塔独立瞄准；弹道和碰撞规则未改。

          
v4 验收与来源 · 实现边界、外部资料与复现检查 · 持续意图实现

        

        

          
自保不是永远不受伤。v5 用存活数、HP＋护盾的相对优势及绝对差值评价交换：同样损失 10 点，100:20 → 90:10 对己方更有利，20:100 → 10:90 则相反。歼灭、己方全灭和双方全灭单独处理。血量效用在同一结果交换双方时反号；完整搜索另有位置、时间和安全项，不能宣称已经求解整个博弈。

          
每个联合计划对进攻／躲避两种对手策略形成收益行，按 70% 最差＋30% 均值评估风险，而非只追求最高伤害或最少己方损失。血量关系或存活数明显变化时暂停路线续走重新评估。模型看到的是己方／敌方别名；NanoJev 的 Boolean、Laya 的 Noul、在线模型的 0–100 自报分各自正确转换到同一读出，原始来源仍分开。

          
验证覆盖旋转地图并交换阵营、不同 HP／护盾组合和三种适配接口；两款本地检查点共 8 次固定局面请求全部通过，涵盖左右两侧及血量领先／落后。领先案例选开火，落后案例选换位；但领先时程序筛选只留下一个计划，因此不能将其算作模型学会进攻。没有调用云模型，也没有据此宣称胜率、正确率或最优策略。

09 / 企业架构与采用


将结构化决策模型纳入企业架构
本章讨论整个模型类别的采用方法，适用于托管服务、本地模型或自训练分类器，不预设供应商。目标是在已有系统中增加可验证、可撤销的语义判断能力，而非替换规则引擎、权限、主数据或事务系统。以下是本文的架构建议与验收框架，不是产品功能清单、合规认证或已证明的收益。




价值与边界系统集成部署与治理责任与运维质量验证成本与上线决策交付物




先定义企业决策点，再决定是否需要模型


从现有流程登记决策点：谁发起、输入来自哪里、候选动作有哪些、动作能否撤销、错误由谁承担。适合候选有界但语义难穷举的分派、筛选和风险建议；金额、日期、资格与权限继续由可信记录和代码决定。开放式写作或规划仍需其他组件。


  • 价值基线：记录业务量、人工时、差错与申诉成本、处理时限；不要从低模型报价倒推需求。
  • 风险分层：分别估计误放行与误拦截损失，明确弃答、人审容量、用户纠错及不可逆动作的批准要求。
  • 不采用也是结论：规则、现有分类器或业务改造已能达标，就保留简单方案；关键少数类或复核路径未覆盖时暂缓。




嵌入现有业务链，判断不等于执行授权


建议边界：业务入口 → 身份与输入校验 → 最小状态快照 → 决策服务／适配器 → 政策引擎 → 工作流／人审 → 受权执行器 → 结果与审计。保留已有 CRM、ERP、工单系统和事件总线；模型输出先成为建议，再由现有控制平面授权行动。


  • 内部契约包含决策 ID、租户、证据版本、完整候选、输出语义、弃答／错误类型和审计关联 ID。适配器保留原始分数与来源，不把类别概率、标量判断、confidence 和 LLM 自评分混为一种概率。
  • 在线同步请求有截止与取消；批处理通过队列处理背压、优先级和隔离。传输重试受预算约束，业务写入另设幂等键，不能因模型重试重复退款或发货。
  • 执行前重验状态版本与权限；缓存按租户、模型、问题、政策和证据版本隔离并失效。多标签关联和上下游依赖由工作流建模，不能用一个最高分替代。




部署方式与数据治理必须一起选择


运行方式需要核实的条件与责任
托管 API外发许可、区域、留存／删除、分包方、鉴权、配额、SLA、价格和退役通知；能访问模型页面不等于有推理权限。
自托管／本地容量、冷启动、运行时与补丁、权重许可、供应链校验、访问控制、监控及灾难恢复；数据不出机器仍需要安全治理，下载权重不等于生产可用。
混合部署跨模型／区域升级须获得数据外发、输出语义和总时限批准；本地失败不能静默转云。供应商退出计划须可迁移契约、评测与审计，而不只是更换 SDK。


共同底线是数据最小化、租户隔离、密钥管理、日志访问与留存限制，以及注入和来源污染测试。模型说“低风险”不放宽沙箱或写入权限；法律和监管义务由对应负责人确认，本章不构成合规认证。




明确责任、故障策略与持续反馈闭环


  • 业务负责人定义收益和可接受损失；数据负责人负责标签、授权及留存；平台团队维护容量与 SLO；安全／风控审批高风险边界；人审团队必须有队列时限、处理能力和升级路径。不能让一枚模型分数承担组织责任。
  • 区分传输错误、输入超预算、语义不确定、状态过期和批准拒绝。按业务风险选择有界重试、弃答、规则降级、排队或转人工；不可逆动作默认不因错误放行。预先演练依赖故障、熔断、限流、背压与回滚，避免无限升级或重试。
  • 监控真实业务结果、漂移、分群错误、弃答／人审比例和尾延迟；审计关联输入证据、原始评分、政策版本与实际动作。人工纠错先经复核形成标签，不自动回灌训练。版本、候选、政策或分布变化触发回归；保留 champion/challenger 和明确退出条件。




数据与基线：避免只和昂贵大模型比较
500–1,000 条人工标注样本可作为试点起点，不是安全认证；稀有高风险样本和中文样本必须单独分析。


  1. 1
    分层并隔离测试集
    覆盖中英文、缺字段、歧义、注入、长输入和关键少数类；阈值调优集与最终测试集分离。
    

    2. 

  2. 2
    选择实际替代方案
    规则、现有分类器、专用 reranker 和优化后的结构化 LLM 都应按场景进入基线。保持输入、候选、质量目标及预算可比；另做相同工作流不加该模型的消融，不把相似 API 当作能力等价。
    

    3. 

  3. 3
    固定测量条件
    记录模型和 SDK 版本、输入信息、地区、并发、推理配置、超时及重试；不能给不同模型不同资料后把差异全归于模型。
    

    4. 



质量指标与阈值必须对应业务风险
概率校准应使用概率本身；对 confidence 可按区间统计实际正确率，但不能把它直接当作正确概率代入校准计算。[4][19]


指标组具体记录


分类质量准确率、宏 F1、关键风险漏判；不均衡任务不能只报总体准确率


概率与覆盖Brier 均方概率误差、分箱可靠性和期望校准误差 ECE；自动覆盖率及自动区错误率


运行质量完整请求的 p50 / p95 / p99 延迟、超时、重试率及每笔成功成本


示例业务目标可以是「自动区错误率 ≤1%、覆盖 ≥60%」，这是待验证的准入条件，不是任何模型或供应商承诺。独立同分布的 n 条自动样本零错误时，95% 错误率上界粗略约 3/n；300 条零错也只支持约 1% 上界，关键分层还需单独统计。独立留出集、置信区间和真实业务结果不能由合法 JSON 或模型自评分代替。




总成本、尾延迟与逐步发布
平均模型单价不能代表最终业务成本；升级路径还可能决定尾延迟。


  1. 1
    核算完整路径
    每次业务请求成本 = Cpre + Cdecision + r×CLLM + h×Chuman + Cretry + Cops。Cdecision 是所选决策实现成本；r 与 h 是升级和人审比例，可重叠。Cops 包含标注／校准、集成与维护的分摊，避免重复计费；另看每笔成功业务成本和人工节省，不将本地 token 等同云端账单。
    

    2. 

  2. 2
    从影子模式到低风险灰度
    先离线重放，再影子运行不执行；验证人审容量后对可撤销操作灰度。质量、覆盖率、总成本与尾延迟同时达标才扩大；高风险写入仍需独立批准，影子模式也须取得真实数据使用许可。
    

    3. 

  3. 3
    整体版本化与回滚
    model_id、问题配置、候选集和阈值一起发布；留旧版本及回退路径。模型、政策、语言或数据分布变化后重新验收。
    

    4.

    2. 

  2. 2
    交付设计

    3. 

  3. 3
    提交验证计划
    提交数据集划分、关键分群、基线／消融、质量与覆盖门槛、容量／故障演练、灰度规模、停止条件和复核日期。证据不达标就维持原流程；批准具体试点范围后才安装依赖、使用真实数据或调用计费 API。
    

    4.
