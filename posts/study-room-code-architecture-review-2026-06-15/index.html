01 / Executive Summary

1. 审查结论

项目在静态站约束、共享组件复用、文章脚本顺序、基础语法与页面结构方面表现稳定。下一阶段不应再把所有能力继续塞进少数几个巨型文件，而应建立“平台内核、内容数据、文章运行时、可选增强模块”的分层边界。

Strength

工程基础是稳的

  • 全量验证通过：知识树语法、文章 URL、脚本顺序、inline style、inline arrow function、CSS/JS 语法均通过。
  • 文章页面共享运行时已经统一：`article-common.js`、`article-presentation.js`、`scrollbar.js`、`article-lightbox.js`、`article-assistant.js` 顺序一致。
  • 知识树采用邻接表，数据模型简单，适合继续增长。
Concern

维护热点开始集中

  • article-presentation.js 已达 4,485 行，承担演示、样式、分享、导出、旁白、录屏等多种职责。
  • article.css 已达 4,918 行，组件、布局、演示模式、响应式和主题规则继续混杂。
  • 存在 3 个按设计暂不公开的文章页；建议把“私有/草稿”状态显式化，避免后续审查误判。
维度评分判断
架构一致性B核心模式稳定，但首页和文章演示运行时仍是大文件中心化结构。
代码重复度B+共享脚本显著降低重复；剩余重复主要是文章内 <style> 与局部组件样式。
可维护性C+三个 4k+ 行文件会持续拖慢审查、定位和安全修改。
可测试性B静态验证覆盖好，但缺少首页交互、演示模式、PPT 导出、旁白等行为回归测试。
数据治理B知识树注册完整性对公开文章有效；私有/草稿文章是有意不曝光，但目前缺少机器可读状态。
安全姿态B当前静态内容风险低；未来若 Markdown、AI 回复或远程内容进入 `innerHTML`，需要统一消毒层。
性能B静态页面可接受；Galaxy、Cards、Infographic 随节点增长需要持续观察。
设计系统B组件语言统一，但 CSS 文件规模已经越过拆分阈值。
文档健康度B历史复盘、标准、架构文档齐全；最新增长状态需要纳入常规报告。

02 / Architecture

2. 架构现状

当前系统由一个首页应用、一个知识树数据源、一组文章共享运行时和大量静态文章页组成。这个架构依然合理，但共享运行时已经从“工具脚本”升级成“前端平台内核”。

  1. Data
    assets/knowledge-data.js

    邻接表形式的唯一知识树数据源，当前 145 个节点、111 篇已注册文章。优点是简单透明；另有 3 篇页面按设计暂不公开，建议用 manifest 或 hidden 状态记录这类意图。

  2. Home
    index.html

    4,957 行，包含 Galaxy、Cards、Infographic、Cell/Game 入口、主题、字体、模型配置等逻辑。它已经是单页应用，而不只是静态首页。

  3. Article
    article.css + article-presentation.js

    承担文章视觉系统、演示模式、分享、导出、旁白、录制与移动演示体验。两个文件合计 9,403 行，是下一轮拆分的核心对象。

  4. QA
    tests/validate.js

    531 行验证脚本，已覆盖静态一致性。它是当前质量护栏的核心，应继续扩展成发布门禁。

HTML

posts 总行数 116,661

内容体量已经接近知识产品而非个人静态页，需要更强的内容注册、构建检查和回归测试。

CSS

article.css 4,918 行

已超过早期报告中的 3,500 行红线。建议拆分 core、components、presentation、themes 四层。

JS

article-presentation.js 4,485 行

功能边界过宽。建议优先拆出 share、export、narration bridge、presentation chrome。

Steps

527 个演示步骤标记

data-present-step 已成为内容结构契约，应被视为 schema，而不是普通 HTML 属性。

04 / Findings

4. 关键发现

以下按风险优先级排序。没有 D 级立即阻断项；最值得先修的是“共享运行时拆分”和“私有内容状态显式化”。

P1-1: article-presentation.js 职责过载

该文件 4,485 行，集中处理演示 UI、语言切换、样式面板、分享菜单、PPT/PDF、邮件、录屏、旁白、预加载和自动播放。任何修改都容易产生非局部回归。建议按功能拆成稳定内核 + 懒加载增强模块。

P1-2: article.css 已突破历史红线

当前 4,918 行，远超早期架构报告提到的 3,500 行红线。继续增长会让组件样式、演示样式、主题变量和响应式规则互相遮蔽。建议先拆 article-presentation.css 与 article-components.css。

P2-1: warning 预算缺失

验证脚本允许 21 个 warning 通过。warning 本身不是问题，但没有预算会导致告警逐步常态化。建议设定上限：新增 warning 阻断、存量 warning 分批清零。

P2-2: 行为回归测试不足

现有验证偏静态，尚未覆盖首页布局切换、Galaxy 交互、演示模式、PPT 导出、旁白 UI、AI 助手面板等关键行为。建议加入浏览器级 smoke test。

P2-3: 私有/草稿页面状态需要显式化

agentic-sales-mobile-proposal-review、mindray-crm-ai-proposal、mindray-crm-ai-proposal-design 暂不进入知识树是产品设计，不是缺陷。建议在 manifest、front matter 或约定文件中标记 private/draft，让验证脚本能区分“故意不公开”和“漏注册”。

P2-4: innerHTML 使用需要统一边界

当前多数 innerHTML 用于受控模板和静态内容，风险可接受。但 article-renderer.js 与 article-assistant.js 已具备渲染 Markdown/AI 文本的路径，未来接入远程或用户输入时必须有统一 sanitizer。

P3-1: 文章内 <style> 数量偏多

全站文章页中检测到 119 个 <style> 块。短期可接受，但长期会削弱设计系统一致性。建议只保留真正的文章专属可视化样式，通用组件回收到共享 CSS。

P3-2: 首页仍是单文件应用

index.html 4,957 行，包含数据派生、状态、布局渲染、设置面板、动画与本地存储。建议在下一次首页功能改动时顺手拆分，而不是单独大爆破。

05 / Remediation Roadmap

5. 整改路线图

推荐采用小步治理，先补验证盲区，再拆高风险大文件。这样可以避免为了“架构漂亮”而引入新的回归风险。

  1. 01
    显式标记私有/草稿文章

    保留 3 篇暂不公开页面的产品决策，但用 manifest、front matter 或目录级标记记录 private/draft 状态；验证脚本只报告既未注册又未标记的页面。

  2. 02
    清理 warning 预算

    先修 10 条摘要长度 warning；11 条 dark theme warning 要么补样式，要么把检查改成“共享暗色变量覆盖已满足”的更准规则。

  3. 03
    建立浏览器 smoke test

    覆盖首页加载、布局切换、打开一篇文章、进入演示模式、打开分享菜单。目标不是详测所有视觉，而是防止主流程断裂。

工作包目标完成判据
拆分 article-presentation.js把分享、导出、旁白、录屏从主演示控制器拆出。主文件降到 2,500 行以内；现有 114 篇脚本顺序验证仍通过。
拆分 article.css形成 core、components、presentation、narration、diagram 的清晰边界。article.css 降到 3,000 行以内；组件样式有归属说明。
首页模块化将 Galaxy、Cards、Infographic、Settings 分离为独立资产。index.html 降到 3,000 行以内；布局切换 smoke test 通过。
渲染安全边界为 Markdown、AI 回复和动态模板建立统一 sanitizer 策略。所有未来不可信输入只走一个渲染入口。
