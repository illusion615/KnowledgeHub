Service-Driven CRM：让现场服务少填表

现场服务人员的主要任务是解决客户问题，但当前工单与客户主数据要求他们在手机上处理数百字段。本方案基于 Microsoft Power Platform，把填表改造成贯穿工单全程的自然采集：系统根据工单类型只提出当前需要的问题，语音、照片和条码持续补齐信息；SLA 排程与访前简报则把数据立即回流为当天可执行的工作建议。

核心主张

让现场人员先解决客户问题，服务数据在工作过程中自然沉淀，并立即换回更清晰的下一步。

移动端不再以完整表单作为起点，而以今日任务、访前背景、现场采集和完成确认四个工作场景组织体验。AI 负责理解和起草，现场人员保留判断权，现有工单与客户系统继续承担最终记录责任。

01 / 业务挑战

现场服务与数据录入正在争夺同一段客户时间

现场人员必须同时解决故障、与客户沟通并维护完整记录。当前系统把这三项责任叠加到一张数百字段表单上，导致信息往往在服务结束后集中补录，也让 SLA 与历史数据未能及时帮助当天决策。

01

一张工单牵动两张数百字段表

现场人员既要完成工单字段，又要识别客户地址、联系人、资产等主数据变化；不同工单类型要求更新的内容并不相同。

02

有效信息分散在整个服务过程

客户陈述、现场测量、维修动作和结果确认发生在不同时间点。要求一次填完会迫使人员回忆、重复打开表单或在纸张与聊天工具中暂存。

03

SLA 存在于记录中，却没有转化为今日顺序

现场人员需要同时判断剩余时间、暂停状态、路程、计划工时与备件条件。缺少一屏汇总时，优先级判断依赖人工查询和经验。

04

历史工单很多，访前可用背景很少

客户、资产、投诉与未完成事项分散在多条记录中。现场人员到访前很难快速形成问题背景、沟通重点与检查策略。

业务判断 字段完整性仍然必要；需要改变的是信息采集时机和呈现方式。系统应在工作发生时逐步收集事实，并在出发、到场和关闭三个决策时点把数据回给现场人员。当前填写耗时、返工率与主数据错误率尚无实测基线，首期试点必须先测量再承诺收益。

02 / 设计哲学

Service-Driven CRM 让服务动作自然生成记录，并让记录立即回到下一步

本文将这种设计立场称为 Service-Driven CRM：移动端以服务任务为起点，系统在工作过程中收集必要事实，用户确认后写入业务系统，并立即返回 SLA 风险、背景信息或完成条件。四条原则共同约束后续界面与架构。

01

服务先行

首页先回答今天做什么、下一站在哪里、哪张工单有风险。完整表单保留为核对入口，不占据主流程。

02

持续采集

工单开始后到关闭前，语音、文字、照片和条码持续进入同一采集会话；人员可以随时暂停并恢复。

03

确认优先

系统主动给出字段草稿和主数据变化，用户只需确认、编辑或拒绝。任何 AI 结果都不能绕过确认直接写入。

04

记录即回报

每次信息补充后，系统立即更新完成度、缺失项和下一步；出发前则用同一数据形成 SLA 顺序与访前简报。

责任边界 AI 负责理解、整理与起草；现场人员负责业务判断；规则负责必填、范围、审批和关闭条件；现有工单、客户与资产系统继续持有权威记录。

03 / 移动界面蓝图

四个高频页面让现场人员看见方案如何工作

设计原则落在四个移动页面：今日任务决定先做什么，访前简报告诉到场前知道什么，现场采集承接持续输入，完成确认把工单答案与客户主数据变化分开处理。下列数字均为界面示意，不是客户实测结果。

页面 01 · 今日任务

6 张工单中，系统解释为什么先去第二站

首页把 SLA 剩余时间、暂停状态、预计工时、路程和备件准备度合并成当天顺序。用户看到排序依据，也可以按现场情况调整。

  • 12 张将在上午进入 SLA 预警
  • 21 张因客户暂停暂不执行
  • 3下一站路程 24 分钟，预计服务 90 分钟
页面 02 · 访前简报

三分钟看清客户、资产与未完成承诺

简报只保留影响本次服务的事实，并区分事实、推断与建议。每条事实可打开原工单、资产或客户记录。

  • 1近 90 天 3 张相关工单
  • 2同一资产有 1 项未关闭建议
  • 3建议先复测入口压力，再拆检阀门
页面 03 · 现场采集

说一句话，生成四项草稿，只追问三个关键缺口

语音、照片、条码与文字共享同一个工单会话。系统显示已识别内容、来源片段和完成度，人员可以随时暂停，稍后继续。

  • 1已生成：故障现象、位置、压力、处理动作
  • 2当前完成度 72%，仍缺 3 项关闭信息
  • 3确认 · 编辑 · 重录三种选择
页面 04 · 完成确认

关闭前分组确认工单内容与客户信息变化

工单答案可以在现场确认；服务地址、联系人等客户主数据变化则生成独立申请。页面明确显示哪些内容立即提交，哪些等待审批。

  • 1工单：18 项已确认，2 项待补充
  • 2主数据：服务地址与联系人各 1 项变化
  • 3关闭门禁：客户签字与序列号照片仍缺失

04 / 服务人员的一天

林工的一天：从 SLA 排程到工单关闭，信息在八个时点自然沉淀

上一章展示了四个移动页面；本章把它们放进现场工程师林工的一天，说明系统如何在不打断服务的前提下提供顺序、背景、采集和完成确认。

上午 · SLA 排程到首次现场采集
  1. 07:30 · 今日工单按 SLA 风险重新排序

    移动首页列出剩余时长、暂停状态、预计工时和路程。一个高优先级工单因客户暂停而不进入首位；另一个普通优先级工单将在 3 小时后预警，因此被提前。

  2. 08:10 · 访前简报呈现可引用事实

    林工看到该客户近 90 天的相关工单、同一资产的故障历史、未关闭行动项、现场联系人偏好与可用备件。每条事实都能回到原记录。

  3. 09:00 · 到场后冻结本次问卷版本

    系统依据工单类型加载问卷定义版本 12，并创建独立运行实例。之后管理员发布版本 13，不会改变林工正在执行的问卷。

  4. 10:15 · 第一段语音生成候选答案

    一句现场口述覆盖故障现象、设备位置、测量值与客户陈述。AI 只生成候选值并标记原文证据；类型、单位、范围和条件分支由规则引擎校验。

下午 · 渐进补齐、受控变更与关闭
  1. 11:40 · 系统只追问当前关键缺口

    条件规则触发 17 个相关问题，但当前只向林工展示三个会阻止下一步的缺失项。其余问题在测量完成或工单即将关闭时再出现。

  2. 14:00 · 客户主数据变化进入独立审批

    客户告知服务地址和现场联系人发生变化。系统生成两项主数据变更请求，附工单号、语音证据和目标记录版本；林工确认后仍需按字段策略进入数据管理员审批。

  3. 16:30 · 关闭门禁列出未满足项

    工单关闭前，确定性规则检查必填答案、客户签字、已用备件、实际工时和后续任务。缺少序列号照片时，系统阻止关闭并直接打开相机入口。

  4. 17:20 · 日终摘要只复用已确认事实

    系统汇总已完成工单、未关闭风险、待审批主数据变更和次日行动。未确认候选值不进入正式服务摘要，也不作为客户沟通依据。

05 / 系统架构

五层架构把移动体验、AI 理解与业务提交分开承担

林工的一天已经说明业务体验；本章把体验落到五层职责中。越接近工单、客户和资产等权威记录，允许的操作越少、规则越严格，生成式 AI 不持有通用写权限。

  1. 移动体验 · Field Service Mobile / Power Apps

    承载今日任务、访前简报、现场采集和完成确认，并复用相机、条码、签字与离线能力。

  2. 服务智能 · SLA、背景与采集进度

    把工单期限、历史记录和问卷完成度转化为当前排序、背景提示与下一步缺口。

  3. Agent 编排 · Microsoft Copilot Studio

    理解自然语言、调用所需读取能力、生成字段草稿与补问，并把多项结果整理成一段连贯回复。

  4. 业务规则 · Power Automate / Power Fx / Plug-in

    执行必填、范围、条件分支、关闭门禁、字段权限、审批与并发检查，保证相同输入得到相同判定。

  5. 数据与集成 · Dataverse + 现有业务系统

    Dataverse 保存采集过程、草稿与审批记录；现有工单、CRM、资产和 SLA 系统继续持有最终业务事实。

每张工单创建一个独立采集会话，锁定当时的问卷版本并保存进度；管理员之后更新模板，不会改变正在执行的工单。

  • 1工单开始：按类型加载对应问题与条件分支
  • 2服务进行：持续保存已确认、待确认和缺失信息
  • 3每次补充：重新计算相关问题和完成度
  • 4工单关闭：必填、签字、照片和后续任务全部通过门禁

离线保障服务继续执行，云端 Agent 提供增强理解；断网时系统回退到本地工单、缓存问卷、文字、照片和设备听写。

模式现场可用恢复方式
在线实时语音、自然补问、最新 SLA 与主数据核对持续同步已确认内容
弱网本地工单、缓存问卷、文字、照片、条码与设备听写按片段提交，失败项进入可见队列
离线离线范围内的工单、问卷、附件与本地草稿联网后解析，并在提交前重新核对服务器版本

现场事实影响当前服务，客户主数据影响未来派工、账单与合规，因此两类内容分组确认并采用不同审批。

工单内容

现场确认后提交当前工单

故障现象、测量值、维修动作、实际工时、备件与签字在规则校验后进入当前工单。

客户主数据

现场确认只创建变更申请

服务地址、联系人和资产归属等变化带证据进入数据管理员审批；高风险财务与法定字段只生成人工任务。

Agent 是增强能力，不能成为查看工单、执行安全步骤、采集必填信息和完成客户签字的单点依赖。

  • 1Copilot Studio 不可用：显示完整问卷与既有工单操作
  • 2Azure Speech 不可用：切换设备听写或文字输入
  • 3主数据系统不可用：保存为待提交，不显示成功
  • 4SLA 来源不可用：显示最后更新时间，不推算实时倒计时

06 / 数据策略

按数据责任分域：移动体验更快，现有系统仍是唯一权威来源

系统架构回答了各层如何协作；本章比较三条数据路径。方案选择按责任分域：采集会话、草稿和审批过程落在 Dataverse，工单、客户、资产与 SLA 的最终事实仍由现有业务系统持有。

方案 A

全量复制到 Dataverse

移动查询与离线体验最直接，但数百字段客户主数据需要持续双向同步，冲突、审计与数据驻留成本最高。

方案 B

所有数据实时调用现有系统

不产生数据副本，上线边界清晰；代价是每次交互都依赖网络和外部 API，离线采集、跨记录简报与多轮补齐难以连续。

方案 C · 采用

按责任分域，共享最小必要数据

Dataverse 保存移动运行状态、候选答案和审批过程；权威业务数据按需读取，确认后以最小变更集回写。该路径兼顾离线连续性与现有系统责任。

移动层只保存完成体验所需的运行状态，不成为工单、客户、资产或 SLA 的第二权威来源。

数据对象权威来源移动智能层保存
工单与服务任务Dynamics 365 Field Service 或现有工单系统采集进度、候选答案、证据与同步状态
客户与资产主数据现有 CRM、ERP 或主数据平台带证据的变更申请、审批状态与目标版本
SLA现有 SLA 或服务承诺引擎只读快照、最后更新时间与排序解释
Agent 运行记录Dataverse 与 Application Insights计划、工具调用、确认、拒绝、延迟与错误

审批按字段影响范围配置，使现场可确认信息快速进入工单，同时保护会影响后续派工、财务和合规的客户主数据。

类别示例处理方式
当前工单故障现象、测量值、维修动作、实际工时规则通过且现场人员确认后提交
中风险主数据服务地址、现场联系人、服务时间偏好现场确认后进入数据管理员审批
高风险主数据法定名称、税务、账单与受监管标识只创建人工核验任务，AI 不提交

系统使用实体标签（ETag）识别记录自上次读取后是否变化；不匹配时停止写入，并把现场值、后台值与来源交给数据管理员比较。

  1. 访前读取

    简报读取服务地址 A，并保留当时的记录版本。

  2. 现场发现

    客户告诉林工地址应为 B；与此同时，后台已把地址改为 C。

  3. 停止覆盖

    记录版本不一致，系统拒绝自动提交，不采用最后写入覆盖。

  4. 人工核对

    数据管理员同时看到 A、B、C、来源和时间，决定保留、修改或联系客户复核。

07 / Agent 地图

四个领域 Agent 覆盖现场人员一天中的四类稳定目标

数据策略明确了各系统责任；本章按用户目标划分 Agent，而不按每张表或每个 API 创建 Agent。四个领域能力分别负责当天顺序、访前背景、现场采集与客户数据变化。

01

Service Day Agent

每天开始时读取分配工单、SLA、路程、计划工时、备件和暂停状态，形成可解释的今日顺序。它不修改 SLA，只解释现有承诺。

02

Visit Brief Agent

在出发前汇总本次任务、客户背景、资产历史和未完成事项，并把事实、推断与建议分开呈现。

03

Capture Agent

在服务现场理解语音、照片、条码与文字，匹配当前工单问题，生成字段草稿并只追问阻止下一步的缺口。

04

Data Steward Agent

识别现场口述中可能涉及客户或资产主数据的变化，说明影响并起草带证据的变更申请；审批和提交仍由规则流程完成。

Agent 数量原则 首期保持四个职责清晰、描述不重叠的 Agent。只有当新能力对应稳定用户目标、独立数据权限和独立验收指标时，才增加新的领域 Agent；新增一张表或一个接口不构成新增 Agent 的理由。

08 / Agent 协同架构

读取可以自动完成，草稿必须确认，写入回到确定性流程

Agent 地图回答了谁帮助现场人员；本章回答它们如何安全协作。Copilot Studio 负责理解目标和编排步骤，但每种动作依据业务风险落在生成式、混合或确定性控制层。

01

生成式层 · 查找与整理

适用于读取工单、查找历史、理解自然语言、生成摘要和提出下一步问题。它受用户权限和可用数据约束，不产生最终写入。

02

混合层 · 起草与确认

适用于字段草稿、完成建议和主数据变化识别。AI 完成整理，用户在会话内确认、编辑或拒绝，确认点不能省略。

03

确定性层 · 校验与提交

适用于必填、范围、关闭、审批、并发检查和最终写入。规则按固定步骤执行，失败时返回明确原因和恢复动作。

  1. 理解目标

    林工说出现场事实；编排器识别其中同时包含工单补充、客户信息变化和后续动作。

  2. 读取上下文

    Capture Agent 读取当前问卷进度，Data Steward Agent 读取允许变更的客户字段，Service Day Agent 读取未完成任务。

  3. 合并草稿

    系统把工单答案、主数据变化和下一步分组展示，并为每一项附来源。

  4. 用户确认

    林工可以确认工单组、编辑主数据组并拒绝不相关建议；三组动作互不绑架。

  5. 规则提交

    工单内容经校验写入当前记录，主数据变化进入审批，后续动作创建为任务；每条结果返回成功、待审批或失败状态。

可信赖输出规则 访前简报和现场建议始终区分事实、推断与建议；事实必须链接原记录，推断必须列出依据，建议必须能够被接受、修改或忽略。用户无权访问的记录不得进入检索、提示词或摘要。

10 / 方案期望收益

收益从个人体验、服务质量与组织治理三层建立可测量闭环

实战演练说明了方案如何工作；本章定义如何判断它是否值得规模化。下列数值是建议的 PoC 验收目标，不是已实现结果，必须在试点开始前测量现状基线。

A1

主动填写耗时下降 ≥ 40%

以同类工单从开始输入到满足关闭条件的主动操作时间为口径，对比试点前后中位数；等待网络和维修时间单独记录。

A2

工单开放期间随时补充

语音、照片、条码和文字进入同一会话，人员无需等待服务结束后集中回忆；测量补录间隔与恢复成功率。

A3

访前准备从检索记录变成阅读简报

记录从多处查找转为一页带来源的背景；测量从打开工单到能够复述任务、资产风险和未完成事项所需时间。

B1

必填完整率 ≥ 95%

关闭时由规则直接计算，并要求不得低于现状；完整率与填写耗时同时评估，避免用增加负担换取数据完整。

B2

未经确认写入 = 0

审计记录必须能够把每次业务写入对应到候选、确认人与提交结果；任何无法对账的写入视为验收失败。

B3

访前事实 100% 可打开来源

事实项必须链接工单、资产或客户记录并显示更新时间；推断与建议采用不同标签，避免历史摘要被误读为当前事实。

C1

客户主数据直接写入 = 0

所有客户和资产变化都必须存在对应的变更申请、证据、字段策略与审批结果，高风险字段只创建人工任务。

C2

离线脚本零静默丢失

断网采集、后台并发修改、联网重放和冲突审阅全部进入可见状态；系统不得把待同步内容伪装成已提交。

C3

新工单类型复用同一采集与治理框架

扩展以问卷定义、字段映射和业务规则为主，不为每类工单重建移动应用；测量第二类工单相对首类的交付工作量。

度量原则 试点前先记录同类工单的时间、完整率、返工、SLA 和主数据变化基线；试点期间按同一口径比较。单独追求某项指标可能转移成本，因此效率、质量和治理必须同时通过。

产品配置说明了需要哪些能力；本章比较三条移动实现路径。选型依据是现有工单平台、离线能力、治理复用与定制自由度，而不是单纯追求界面自由。

维度扩展 Field Service Mobile独立 Power Apps 移动应用自研原生应用

13 / 投资回报

ROI 由节省时间、减少返工、降低 SLA 风险与主数据修正成本共同构成

方案路径已经确定；本章给出预算测算口径，不填入未经客户确认的金额。发现阶段应先收集同类工单量、填写耗时、返工、SLA 与主数据修正基线，再由财务团队代入。

01

现场时间释放

把补录与查找时间转化为可用于客户沟通、服务执行或新增工单的容量；只计算可兑现比例，不把全部节省时间直接视为现金收益。

02

返工与补录减少

字段完整、证据可追溯和关闭门禁减少管理人员退回、现场人员重新联系客户或再次打开工单的成本。

03

SLA 风险降低

更早识别不可执行与即将预警的工单，减少升级、赔付、加急调度或客户流失风险；只计入有财务口径的历史事件。

04

主数据修正成本降低

把现场变化转成带证据的审批申请，减少错误覆盖、跨系统修正和后续派工或账单异常。

价值项计算口径必须采集的基线
年度时间价值现场人数 × 人均月工单 × 单单节省分钟 ÷ 60 × 综合小时成本 × 12 × 收益兑现率同类工单主动填写时间分布与可兑现比例

年度 SLA 风险规避可避免的不合规事件 × 单次事件财务影响预警、失败、升级、赔付与加急调度历史

财务边界本文不提供许可单价、实施报价或三年净收益结论。首期试点只能建立基线与效果差异；正式 ROI 需由财务团队结合现有许可、内外部人力、Azure 用量和组织实际兑现能力计算。

14 / 交付方式

先建立证据，再共创高频场景，最后通过受控 ALM 推向生产

ROI 说明了需要测量什么；本章规定如何交付。方案采用三段式方式，把业务基线、现场共创与生产治理分别设置明确产出，避免在需求尚未稳定时同时扩展多类工单。

阶段 1 · Evidence First

先盘点两类工单与现状基线

确认字段、条件分支、客户主数据映射、现有耗时、返工、SLA、设备、离线和权限边界，输出锁定的试点范围与验收口径。

阶段 2 · Field Co-Design

围绕四个页面与真实一天共创

现场人员每周使用可运行版本，验证追问顺序、语音词汇、离线恢复、确认粒度和访前简报；一次只调整一个变量并保留对照。

阶段 3 · Governed Promote

通过 Solution、Pipeline 与审计进入生产

Dev、Test、UAT、Prod 环境分离；问卷、Agent、连接器、规则与权限纳入 Solution 和版本控制，发布前通过离线、角色、并发和回滚测试。

15 / 实施路线图

12 周用两类工单和一类主数据变化验证闭环，再决定是否规模化

交付方式确定了节奏；本章给出首期范围、四阶段计划和继续投资门槛。试点集中在一个区域与目标设备，不同时扩展更多工单类型。

    盘点字段、分支、主数据映射、现有耗时、返工、SLA、角色、设备与离线边界，确认试点门槛。

  2. 第 3–5 周 · 移动主路径

    完成四个页面、问卷版本、可恢复采集、完整表单、离线草稿和关闭门禁，先验证无 AI 时的业务正确性。

    接入语音、四个 Agent、草稿确认、主数据申请、审批、并发检查与审计，并完成角色和故障测试。

  4. 第 10–12 周 · 实地试点与决策

    真实执行并按同一口径比较耗时、完整率、采纳、SLA、主数据和离线恢复；所有门槛通过后再扩展区域与工单类型。
