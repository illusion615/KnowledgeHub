Obscura：为 AI Agent 与抓取而生的 Rust 无头浏览器

h4ckf0r0day/obscura 是一款用 Rust 编写、内嵌 V8、实现 Chrome DevTools Protocol 的无头浏览器，定位为 headless Chrome 的「替身」。仓库 3 周内积累 10.6k stars、688 forks、14 位贡献者，Apache-2.0 许可。本文基于其公开 README 与仓库结构整理设计要点、性能数据与适用边界。

核心命题

把浏览器从「桌面工具」剥离成「自动化引擎」。

  • 1Rust 核心，无 Node / 无 Chromium 二进制依赖

01 / 项目定位

不是再造 Chromium，而是为机器流量重写浏览器

Obscura 的 README 第一句即定义边界：The open-source headless browser for AI agents and web scraping. 项目刻意放弃桌面浏览体验所需的 UI 渲染、扩展系统、多媒体管线，把工程预算全部投入到「程序化访问」需要的 JS 执行、网络栈、协议兼容与反检测上。

当浏览器从「人类终端」变成「Agent 工具」时，需求函数发生反转：

  • A1启动延迟取代帧率成为关键指标——一次抓取常需冷启动几十次
  • A2常驻内存决定单机并发上限，30 MB vs 200 MB 直接转化为 6× 并发数
  • A3指纹一致性从隐私问题变成业务问题：webdriver 标记会让抓取直接被风控拦截
  • A4协议表面必须对齐 CDP，才能让现有 Puppeteer/Playwright 代码零改动迁移

headless Chrome 仍带着完整桌面包袱；Playwright 自带的 browsers 本质是同一份 Chromium；Browserless 是托管的 Chrome 集群。Obscura 选择重写引擎，把 Stealth 与轻量化做成「内核默认」而非「胶水补丁」。代价是协议覆盖目前限于 README 列出的 9 个 CDP Domain（Target / Page / Runtime / DOM / Network / Fetch / Storage / Input / LP），未达到 Chromium 全功能。

作者明确承诺开源引擎 Apache-2.0 永不功能阉割，付费部分是 Obscura Cloud——托管基础设施、住宅代理、专属支持。这是当下「Open-Core 但不掏空开源版」流派的典型实践（参考 Plausible、Posthog），把"运维负担"而非"功能"做成付费墙。

03 / 仓库架构

6 个 Rust crate 拆分浏览器关注点

仓库 crates/ 目录列出 6 个 crate，名字即职责：

obscura-cli

命令行入口。提供 fetch（单页抓取）、scrape（并行批量）、serve（CDP 服务器）三个子命令。

obscura-browser

浏览器顶层会话编排：Target / Page / BrowserContext 模型，对应 CDP 的 Target Domain。

obscura-cdp

Chrome DevTools Protocol 服务端实现，WebSocket 接入，使外部 Puppeteer / Playwright 客户端可直连。

obscura-dom

DOM 引擎与查询器，承载 Page / DOM Domain（getDocument、querySelector、resolveNode 等）。

obscura-js

V8 嵌入与 JS Runtime 桥接，处理 Runtime.evaluate、callFunctionOn、绑定，以及最近新增的 elementFromPoint stub。

obscura-net

HTTP / Cookie / Fetch 拦截栈，对接 Network 与 Fetch Domain，支持 setExtraHTTPHeaders、live request interception。

crates: 6 Languages: Rust 100% License: Apache-2.0 MSRV: 1.75+ First build: ~5 min（V8 源码编译，后续缓存）

04 / 隐身模式

Stealth：把反检测做进引擎而非外挂脚本

用 --features stealth 编译，或运行时加 --stealth。它是 Obscura 与传统方案最大的差异点——puppeteer-extra-stealth 之类项目用 JS patch 后注入，容易被新一代风控识别；Obscura 把这些行为内置到 V8 与协议层。

  • F1每会话随机化 GPU、屏幕、Canvas、Audio、Battery 指纹
  • F2真实的 navigator.userAgentData（Chrome 145，含 high-entropy 字段）
  • F3派发的 DOM 事件 event.isTrusted = true——这是 puppeteer 长期被识别的根因之一
  • F4隐藏内部对象，Object.keys(window) 不暴露注入痕迹
  • F5Function.prototype.toString() 对原生函数返回 [native code]（Native function masking）
  • F6navigator.webdriver 不存在，与真实 Chrome 一致

3,520 个域名的拦截列表覆盖广告、分析、遥测与指纹脚本。这是双重收益：① 减少被第三方收集的反向特征；② 抓取速度天然提升，因为不再下载 Google Analytics、Hotjar、各类 SDK。

CLI 提供 --obey-robots 选项默认 off。这是工具的中立姿态，但调用方必须自行判断目标站点的服务条款、robots.txt、法律辖区与速率约束。Stealth 让抓取"更像浏览器"，并不为绕过授权提供合法性。

05 / CDP 与生态兼容

Puppeteer / Playwright 直接连，存量代码零改动

启动 obscura serve --port 9222 后，外部客户端按标准方式连接 WebSocket 即可。这是 Obscura 的「生态借力」策略——不重造客户端 SDK，复用 npm 上数百万下载的 puppeteer-core / playwright-core。

// Puppeteer 直连
import puppeteer from 'puppeteer-core';
const browser = await puppeteer.connect({
  browserWSEndpoint: 'ws://127.0.0.1:9222/devtools/browser',
});
const page = await browser.newPage();
await page.goto('https://news.ycombinator.com');
const stories = await page.evaluate(() =>
  Array.from(document.querySelectorAll('.titleline > a'))
    .map(a => ({ title: a.textContent, url: a.href }))
);
await browser.disconnect();
// Playwright over CDP
import { chromium } from 'playwright-core';
const browser = await chromium.connectOverCDP({
  endpointURL: 'ws://127.0.0.1:9222',
});
const page = await browser.newContext().then(ctx => ctx.newPage());
await page.goto('https://en.wikipedia.org/wiki/Web_scraping');
console.log(await page.title());
await browser.close();
  • D1Target：createTarget / closeTarget / attachToTarget / createBrowserContext / disposeBrowserContext
  • D2Page：navigate / getFrameTree / addScriptToEvaluateOnNewDocument / lifecycleEvents
  • D3Runtime：evaluate / callFunctionOn / getProperties / addBinding
  • D4DOM：getDocument / querySelector / querySelectorAll / getOuterHTML / resolveNode
  • D5Network：enable / setCookies / getCookies / setExtraHTTPHeaders / setUserAgentOverride
  • D6Fetch：enable / continueRequest / fulfillRequest / failRequest（实时拦截）
  • D7Storage：getCookies / setCookies / deleteCookies
  • D8Input：dispatchMouseEvent / dispatchKeyEvent
  • D9LP（自定义）：getMarkdown——DOM 直转 Markdown，明显是给 LLM 上下文准备的

未列出的 Domain（Accessibility、Animation、CSS Coverage、Profiler、Tracing 等）目前不保证支持。如果你的 Puppeteer 代码用了高级特性，需要自己验证。

# 单页抓取 + 表达式求值
obscura fetch https://example.com --eval "document.title"

# 抓所有链接
obscura fetch https://example.com --dump links

# 等待动态内容
obscura fetch https://example.com --wait-until networkidle0

# 并行批量抓取（worker 进程模型）
obscura scrape url1 url2 url3 \
  --concurrency 25 \
  --eval "document.querySelector('h1').textContent" \
  --format json

Release 包含 obscura 与 obscura-worker 两个二进制，scrape 命令依赖 worker 进程并行调度——这暗示其并发模型是多进程而非单进程多 Tab，与 Chromium 设计一致，但更显式。

06 / 适用场景与局限

选 Obscura 的判断条件，与不该选它的场景

  • S1AI Agent 浏览器工具：LangChain / Agent SDK 里需要给 LLM 一个"看网页"的工具，LP.getMarkdown 直接给出 LLM-friendly 内容
  • S2大规模抓取集群：单机内存预算紧，需要把并发数推高 5–6 倍
  • S3反检测优先的数据采集：对手风控敏感，传统 puppeteer-stealth 已被识别
  • S4容器/Serverless 抓取：70 MB 二进制和无依赖让镜像体积大幅缩小，冷启动友好
  • N1需要 PDF 渲染、视频解码、WebRTC、扩展系统——Obscura 不提供
  • N2需要完整 CDP 表面（Tracing / Coverage / Heap Profiler）——目前覆盖有限
  • N3端到端 UI 测试 / 视觉回归——Playwright 自带 browsers 仍是更稳的选择
  • N4Windows 主机生产部署——Release 仅给 zip，没有官方 MSI / 服务封装

仓库时间轴：Initial Release 3 周前，最新版本 v0.1.2（3 天前），已发布 3 个 release。Issues 27、PR 22、贡献者 14 位。从信号判断处于早期采用期：核心功能可用，API 稳定性、边缘协议覆盖、跨平台分发仍在快速迭代。生产使用前应该 pin 具体版本，并持续观察 Cargo.lock / 二进制 ABI 变化。

07 / 实践探讨

用 Obscura 替代 Copilot 完成 Knowledge Hub 的拓取-生成闭环？

问题拆为三层：外部信息拓取、内容提炼与生成、HTML 文章落盘。Knowledge Hub 现有棈：浏览器端的 article-assistant.js + localStorage('llm-settings') 已具备调用 Ollama / Azure OpenAI / OpenAI-compatible 的能力；Copilot 现在承担的是“调用代理+文件写入+仓库上下文管理”三项。Obscura 只能裥上这里的“拓取”一项。

  • C1外部信息拓取 — 现在靠 Copilot 内置的 fetch_webpage，运行在服务端、绕过浏览器 CORS；仅返回静态 HTML 摘要，翻页/动态加载/反机器人页面会拿不全
  • C2内容提炼与生成 — 现在靠 Copilot 背后的大模型；Knowledge Hub 设置页已能接 Ollama/Azure/OpenAI，但这里只面向“读者在文章页聊天”，未应用于“作者写作”
  • C3HTML 文章落盘 — 现在靠 Copilot 的文件写入工具 + knowledge-data.js 手动注册；需要遵守 .github/instructions/article-pages.instructions.md 中的脚手架约束，以及 node tests/validate.js 十条检查
  • C4仓库上下文 — git 状态、列出已有文章、读取 user/repo memory；这部分是 Copilot Agent 运行时能力，Obscura 完全不覃

考虑到浏览器端不能 spawn 外部进程、也不能写本地文件，可行路径是在仓库里补一个小型 Node CLI（例如 scripts/research.js），它復用与浏览器端同一套 llm-settings（从 ~/.config/knowledge-hub/llm.json 或环境变量读取），拼出下面这条管道：

P1
启动 Obscura

obscura serve --port 9222 --stealth 常驻运行，CLI 连上 CDP

P2
拓取与清洗

Puppeteer-core 调用 LP.getMarkdown，直接拿 LLM-friendly 正文

P3
LLM 提炼

复用 llm-settings，POST 到 Ollama/Azure/OpenAI，输出结构化 JSON（标题/摘要/章节树）

P4
HTML 渲染

用本仓 article 骨架模板填入节点，生成 posts/{slug}/index.html

P5
注册与校验

向 knowledge-data.js append节点 → node tests/validate.js exit 0

// scripts/research.js 伪代码
const pup = require('puppeteer-core');
const llm = require('./llm-client');     // 复用与 article-assistant.js 同样的 settings 格式
const { renderArticle, registerNode, runValidate } = require('./hub-pipeline');

const browser = await pup.connect({ browserWSEndpoint: 'ws://127.0.0.1:9222/devtools/browser' });
const page = await browser.newPage();
await page.goto(targetUrl, { waitUntil: 'networkidle0', timeout: 30000 });
const markdown = await page.evaluate(() => /* CDP LP.getMarkdown 的 客户端调用 */ );

const plan = await llm.chat({
  messages: [
    { role: 'system', content: HUB_WRITING_RUBRIC },   // 提炼 Hero/01-08/References 结构
    { role: 'user', content: markdown }
  ],
  format: 'json'
});

const html = renderArticle(plan);                       // 填入 page-shell 骨架模板
await fs.writeFile(`posts/${plan.slug}/index.html`, html);
await registerNode(plan);                                // patch knowledge-data.js
await runValidate();                                     // node tests/validate.js
  • V1复现性：Copilot 的 fetch_webpage 黑盒，拿不动⓫动态页面；Obscura 能面对 SPA、需登录、需滚动加载场景调 --wait-until networkidle0
  • V2低检测率：--stealth 下反指纹与 3,520 域名拦截，避免被资料站拍“拒访”拦截，这是包含 GitHub 以外的重点资料源时的刚需
  • V3LLM-友好输出：LP.getMarkdown 是 Obscura 的自定义 CDP 方法，直接交付拼到 prompt 的正文，省了 readability/markdownify 步骤
  • V4本地闭环：与 Ollama 等本地模型串起后，一条“拓取 → 生成 → 落盘”全部走 localhost，资料不出机，适合内部知识库场景
  • L1“问题框定与结构设计”：Hub 的 Progressive Disclosure 纪律（hero/01-08/手风琴/insight grid）需要严格的 prompt rubric；小模型容易崩成传统博客，这是 LLM 质量问题不是拓取问题
  • L2事实与量化纠错：Copilot 会主动多轮抓取、互证、重读代码。本地管道需要显式编程实现“拼接多个资料源 + 要求模型标注不确定性”，不是架 Obscura 就有
  • L3脚手约束检查：tests/validate.js 中的 inline-style 禁用、脚本加载顺序、zh/en summary 长度需要主动迭代，Copilot 会读到错误后修复，本地管道需要“生成→校验→反馈重生”的 retry 逻辑
  • L4git 与 Memory：提交纪律、boss-guardrails、session memory 仍然由调用者（人或其他 agent）控制
  • E1scripts/research.js（约 200-300 LOC）：CDP 连接、getMarkdown 包装、LLM 客户端、retry、日志
  • E2scripts/render-article.js（约 300 LOC）：读取骨架模板、插入 hero/section/accordion/references、生成 inline <style> 补丁
  • E3HUB_WRITING_RUBRIC 提词（约 800 token）：明确优先级、禁使用修辞、证据纪律、脚手不变量
  • E4质量门槛：node tests/validate.js 作为硬报错、LLM 交叉检查作为软报错、人工评审作为发布门
结论

Obscura 能让 Knowledge Hub 的“拓取”环节从 Copilot 那里独立出来，配合已有的 llm-settings 可以实现“本地闭环生成”的 80%。剩下 20%（问题框定、多源交叉、结构纪律、脚手重生、git 纪律）仍需要一个「编排者」——可以是简易的本地 Node CLI + 严格 rubric，也可以是另一套 Agent。判断边界：如果资料源以 SPA / 需登录 / 反机器人为主，Obscura 是净增量；如果仅是静态页面与 GitHub README，Copilot 现有能力已足够。
