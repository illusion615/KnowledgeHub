Copilot Studio Agent 企业治理体系

企业治理不是某个 Agent 项目的交付流程。它由 IT、CoE、安全、合规和数据 Owner 预先定义环境、Zone、访问、数据策略、发布准入与运营规则，让后续项目在清晰边界内交付。

查看治理制度配置分区与环境

依据：Microsoft Learn Copilot Studio Guidance · Governance, Security, Testing, ALM, Monitoring

治理目标

治理要让团队知道：什么可以建、在哪里建、谁能访问、怎样发布、出了问题谁来处理。

  • 1将创新放入适当环境和数据边界
  • 2用预防性控制替代事后追查
  • 3将运行数据转成持续改进的决定
建立时点
Before在项目申请与规模化开发之前
治理责任
SharedCoE、IT、安全、合规与数据 Owner
首选控制
Built-in优先使用 Managed Environments 和平台原生策略

01 / Why Governance

没有治理时，风险不是抽象概念，而是会进入日常业务

Power Platform 的目标是让业务更快构建应用、流程和 Agent；治理的目标是让这种速度不以数据泄露、不可持续的个人资产或未经审查的发布为代价。微软将治理定义为管理和控制平台使用的政策、实践与工具组合。[1]

01

数据越界

Agent 可以连接组织数据、外部服务与 MCP 工具。没有数据策略，连接器、HTTP、知识源或发布渠道可能形成意外的数据外流路径。[3]

02

业务连续性中断

个人离职后遗留的 ownerless 资源，以及默认环境中高价值资源缺少 ALM，都会让关键业务能力失去可维护性。[5]

03

变更失控

数据策略既影响设计时能否保存，也影响运行时连接能否执行；策略更新会重新评估应用、流程和聊天机器人，违规资源可能被暂停或隔离。[4]

02 / Governance Relationship

Agent 治理建立在 Power Platform 治理底座之上，并增加 Agent 专属控制

两者不是互相替代的两套体系。Power Platform 治理为所有低代码资产建立通用的租户、环境、身份、连接、数据策略、容量与审计控制；Copilot Studio Agent 治理复用这些控制，再管理 Agent 的知识、工具、认证、渠道、运行时安全和对话质量。[1][8][10]

平台底座

Power Platform 治理

对象是 Apps、Flows、Dataverse、连接器和环境等所有平台资产。主要在 Power Platform admin center 设置环境类型、环境组、Environment routing、Microsoft Entra 组、角色、Data policy、容量和审计。

专项治理

Copilot Studio Agent 治理

对象是 Agent 及其 Knowledge、Topic、Action、Tool、HTTP、MCP、认证、发布渠道和对话记录。它在既有平台控制上，增加对知识接地、工具调用、渠道开放、运行时保护和回答质量的治理。

环境、身份和 Data policy 由平台治理预先设定；项目在这些边界内配置 Agent；一旦 Agent 需要新知识源、新工具或新渠道，就同时触发平台控制与 Agent 专项审查。因此，企业应由同一治理机制协调两层责任，而不是建立两套互不相干的审批流程。

02 / Enterprise Fit

企业应按 Agent 的影响范围启动治理，而不是按员工人数设门槛

微软的 Copilot Studio 指南没有以企业人数作为前提。它以用途、风险、技术复杂度、数据访问、受众和业务影响来划分治理强度。[9][10] 只要 Agent 从个人试验走向共享使用、接入组织数据或承担持续业务任务，无论企业规模，都应采用相应层级的治理。

个人试验

以安全默认值开始

面向个人或小团队、只读且在既有权限内使用的 Agent，适合 Zone 1。重点是隔离试验、限制共享，并让使用范围保持清楚。[10]

部门服务

共享使用即应启动治理

当 Agent 服务部门、跨团队共享、使用批准的数据源或连接器时，应进入 Zone 2：由业务作者和 IT 共同负责环境、访问、发布与支持。[10][11]

关键业务

高影响场景需要完整治理

当 Agent 写入业务系统、处理敏感数据、面向全组织或客户，或故障会影响服务承诺时，应采用 Zone 3 的专业开发、严格安全控制、测试和 ALM。[10][11][12]

出现跨团队共享、组织数据接入、业务系统写入、对外发布或持续运营责任中的任一项，就应先完成治理要求与 Zone 判断。这不是额外的审批步骤，而是确定环境、权限、数据策略、测试和运行责任的起点。[9][10][11]

03 / Governance Foundations

企业治理体系先建立四类规则，项目再在规则内运行

微软将租户、环境和 Agent 层的控制组合用于企业级治理。[8][10] 对企业而言，治理体系的交付物不是一个项目计划，而是一套可重复应用于后续项目的规则、配置、审批路径与监督机制。

01

制度与责任

明确谁可申请、谁可构建、谁审批数据和发布、何时必须升级审查，以及 CoE 如何提供培训、标准与支持。

02

分区与环境

按风险定义 Zone 1/2/3，并预置个人 Developer、专用开发、Sandbox 与 Production 环境，以及作者不进入 Default 的环境路由。

03

数据与访问控制

预先定义身份组、环境角色、允许的 Knowledge/连接器/端点、认证方式、共享限制和对外发布条件。

04

监督与持续治理

定义资产盘点、审计、保护状态、容量、例外和整改的监控方式；项目运行产生证据，治理团队据此调整规则。

04 / Governed Objects

用对象清单把官方治理动作落实到可审查资源

微软指南分别涵盖环境、角色、数据策略、Agent、解决方案、测试和运行信号。为方便实施，本文将这些内容整理为六类治理对象；这是一份实施清单，不是微软命名的官方“六类”模型。

01

环境与环境组

记录用途、地区、生命周期阶段、所属环境组、管理员和数据策略。环境组可将规则一致应用到关联的受管理环境。[2]

02

人员与权限

记录业务 owner、技术 owner、环境管理员、maker、审批人和运行支持人；按环境角色、资源权限和 Dataverse 角色实施最小权限。[1]

03

数据、知识与连接

清点知识源、连接器、HTTP 端点、自定义连接器、MCP 工具和保存的连接凭据。对每一项明确数据类别、允许范围和认证方式。[3][4]

04

Agent、Workflow 与 App

将业务场景、功能边界、人工接管、预期渠道和责任人绑定到每个可运行资产；解决方案中的组件应能随版本跨环境追溯。[6]

05

策略与发布记录

记录数据策略范围、连接器分组、例外批准、发布审批和回退方案。策略变更影响已运行资源，不能把保存策略等同于完成上线。[4]

06

运行证据

保存测试结果、评测记录、使用指标、异常与转人工记录、变更历史和复盘决定。Copilot Studio Monitor 提供采用、会话结果和满意度等运行信号。[7]

05 / Governance Roles

治理不是 IT 单独完成的工作，而是六类角色共同承担的责任

Copilot Studio 治理需要把业务目标、平台控制和租户运营分开负责。以下六类角色可以由不同团队承担，也可以在小型企业中由同一人兼任；关键是每项企业级规则都有具名 Owner，项目团队据此申请和交付。[9][10][11][13][17]

01

业务发起人与业务 Owner

提出场景、说明业务价值与用户范围，确认可接受的服务与风险，并在上线后对业务效果和人工接管负责。

02

业务作者与 Agent Owner

在获授权环境中配置 Knowledge、Topic、Action、Tool、认证和渠道；维护测试集，处理日常内容或行为变更。

03

CoE 与治理负责人

制定命名、分区、培训和申请流程，协调业务与平台团队，跟踪资产、采用情况和治理待办。CoE 是组织能力，不等同于某个工具包。[17]

04

平台与身份管理员

在 Power Platform admin center 创建环境、环境组与路由规则，分配环境和 Dataverse 角色，并用 Microsoft Entra 组管理成员资格。

05

安全、合规与数据 Owner

审查数据敏感度、保留、驻留、认证与对外发布要求；批准可用的知识源、连接器、端点和数据策略边界。

06

IT、专业开发与运营支持

负责关键系统集成、网络与密钥、解决方案和部署管道；处理生产事故、容量、性能和需要升级的技术变更。

06 / Governance Policy

由 CoE、IT 与控制 Owner 预先制定项目必须遵循的制度

治理制度把企业的业务目标、监管要求和平台能力转为可执行规则。它在项目开始前发布，至少覆盖项目申请、Zone 分类、数据与连接申请、发布准入和运行责任；业务 Owner 只能在这套制度内提出项目申请。[9][17]

发起与协调：企业负责人授权 CoE 或治理负责人建立制度；执行设计：平台、身份、安全、合规、法务与数据 Owner 共同形成规则。批准：相应控制 Owner 批准其负责的身份、数据、合规和技术边界；企业负责人批准整体治理章程。业务 Owner 和作者是制度使用者，不是规则制定者。
01

项目准入规则

规定谁可提交场景、申请材料需要哪些事实、哪些条件触发 Zone 2/3 或安全与数据审查，以及谁作出准入决定。

02

数据与访问规则

规定哪些 Knowledge 来源、连接器、HTTP 端点、MCP 工具、认证方式和渠道可直接使用，哪些必须申请，哪些一律禁止。

03

发布与运行规则

规定测试证据、审批角色、发布渠道、支持路径、审计与留存要求，以及何种运行信号触发整改、升级或停止。

一套可审查、可执行且能由项目团队直接引用的治理制度。

  • 1治理章程、角色 Owner 与项目准入、例外和升级路径
  • 2Zone 判定标准、环境类型、路由规则与访问模型
  • 3允许的数据与连接、发布条件、审计留存和治理复盘要求

06 / Zoned Governance

Zone 是环境与控制的治理分组，不是 Copilot Studio 中可单独创建的对象

Zone 是微软用来按风险分层管理 Agent 的治理模型。实际操作时，管理员在 Power Platform admin center 创建或选择 Power Platform 环境，把环境纳入相应的数据策略和安全组，并在其中创建或部署 Copilot Studio Agent；这些环境及其规则共同实现 Zone。环境决定 Agent 数据存放位置、谁能编辑、可用的连接器，以及开发、测试、生产如何隔离。[10]

发起：业务 Owner 或业务作者依据已确认的场景申请 Zone；协调：CoE 提供分区标准并记录决定。参与：平台管理员、IT、安全和数据 Owner。执行：平台管理员创建或选择环境、环境组和路由规则。批准：业务 Owner 接受使用范围；安全和数据 Owner 批准数据与连接边界；IT 对 Zone 2/3 的集成和生产路径确认可行。
Zone 1

公民开发区

对应每位作者自有的受管理 Developer 环境。个人或小团队可在既有权限内创建私有、只读的生产力 Agent；Environment routing 负责把作者带入这个环境，而不是 Default 环境。[10][16]

Zone 2

合作开发区

对应 IT 批准的受管理专用开发环境，并配套测试或生产环境。管理员在环境上配置安全组、Dataverse 角色、Data policy 和共享规则；经过培训的作者在该环境中创建 Agent，再经 ALM 发布。[10][14]

Zone 3

专业开发区

对应受管理的三环境组合：Development 和 Test 使用 Sandbox 类型环境，Production 使用 Production 类型环境。专业开发人员和 IT 以解决方案、环境变量、连接引用及自动化部署管理关键业务 Agent。[10][14][16]

  1. 01
    从用途和受众开始

    仅供个人或小团队使用、在既有权限内查询信息的场景，通常从 Zone 1 评估；面向部门或多人共享时，需要继续评估 Zone 2。

  2. 02
    检查数据与集成

    需要写入业务系统、调用高级连接器、连接敏感数据或开放更多渠道时，应采用 IT 管理的环境、策略和审批，至少进入 Zone 2。

  3. 03
    以业务影响作最终判断

    若故障、错误回答或数据误用会影响关键业务、服务承诺或全组织用户，就需要 Zone 3 的专业开发、强安全控制和完整 ALM。

使用 Environment routing，让 Copilot Studio 的作者门户按租户规则自动进入其自有的 Developer 环境。该功能默认关闭，需要 Power Platform 管理员启用。[16]

  1. 1在 Power Platform admin center 进入 Manage > Tenant settings > Environment routing，并选择对 Copilot Studio 启用。
  2. 2创建路由规则，指定适用范围为所有作者或某个 Microsoft Entra 安全组，并选择用于承载个人环境的 Environment group。
  3. 3为该 Environment group 发布受管理环境规则和租户级 Data policy，使新建的个人 Developer 环境继承统一的保留、AI 与共享控制。
  4. 4作者下次打开 Copilot Studio 时，系统会使用其已有的自有 Developer 环境，或自动创建一个新的环境并将其设为管理员；规则不匹配、路由未启用或创建失败时，才会回到 Default 环境。

07 / Secure Projects

把访问、数据和发布面分别纳入安全控制

第三阶段不是一项单独的安全设置。Copilot Studio 将作者权限、数据策略、Agent 认证、共享规则、数据驻留与关键场景网络控制放在不同层级管理；每层都要与所选 Zone 和业务场景相匹配。[11]

发起：业务作者提交所需 Knowledge、连接器、认证和发布渠道；审查：安全、合规和数据 Owner 审查其是否符合已批准边界。执行：平台管理员配置环境访问、角色、Data policy 与共享规则；身份管理员配置 Microsoft Entra 组与认证要求；IT 为关键系统实施网络和密钥控制。批准：安全或数据 Owner 批准高风险连接和对外发布。
A

访问与职责

在 Power Platform 环境的安全组和 Dataverse 安全角色中分配作者、管理员与转录查看权限；用 Microsoft Entra 组管理成员。Agent 的共享设置再决定哪些人可编辑或使用。

D

数据与连接

在 Power Platform admin center 的 Security > Data and privacy > Data policy 中，把 Copilot Studio 连接器归为 Business、Non-business 或 Blocked，并将策略应用到指定环境或整个租户。

P

发布与运行时

在 Agent 的 Settings 中配置终端用户认证，在 Channels 中配置发布渠道；租户级共享规则限制谁可授予 Editor 或 Viewer。发布后在 Agents 列表查看 Protection status 和威胁检测信号。[11][15]

09 / Governance Operations

用跨项目的运行证据审查并调整企业治理规则

治理运营关注的是整个租户，而非单个项目的日常待办。CoE、平台管理员、安全、合规与数据 Owner 汇总采用、审计、保护状态、容量、例外和整改信号，判断现有 Zone、Data policy、共享或发布规则是否仍合适。[5][13][15][17]

发起与协调：CoE 或治理负责人组织周期性治理复盘；执行：平台管理员汇总环境、容量和策略信号，安全、合规和数据 Owner 审查控制有效性。决定：各控制 Owner 提出规则调整，企业负责人或治理委员会批准涉及租户范围、风险边界或资金投入的变更。项目团队提供运行证据，并在新规则发布后调整其交付方式。
01

采用与资产清单

CoE 在 Copilot Studio Analytics 和 Power Platform admin center 汇总 Agent 使用、活跃资源和异常趋势，用于识别需要培训、支持或调整 Zone 的群体。[5][7][13]

02

审计与安全状态

在 Microsoft Purview 搜索和保留 Copilot Studio 审计记录；在 Copilot Studio 的 Agents 列表查看每个已发布 Agent 的 Protection status，进入详情检查认证、策略和内容审核问题。[13][15]

03

容量与政策演进

平台管理员在 Power Platform admin center 的 Copilot 区域汇总消息使用、容量和依赖项；当证据表明现有 Data policy、共享或发布规则不合适时，由相应控制 Owner 提出调整并按治理机制批准。[5][13]

已发布 Agent 的每一次实质变更，都应能追溯到运行信号、审批决定、测试结果和部署记录。Copilot Studio ALM 建议使用解决方案、环境变量、连接引用和自动化管道；部分设置不具备 solution-awareness，需要在下游环境完成部署后配置。[14]
