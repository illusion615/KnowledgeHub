Apple Silicon Local AI Stack

MacBook Pro M4 Max 64GB 本地模型部署选型：LLM、图像、视频、语音与音乐生成全景

对 M4 Max 64GB 这类 Apple Silicon 笔记本而言，本地部署的关键瓶颈不是“能不能跑模型”，而是“哪一类模型有成熟 Metal/MPS 路径、能在 64GB 统一内存内稳定迭代、并且延迟仍然适合日常工作”。本文把选型拆成六类任务：大语言模型、Function Calling、文生图、视频生成、语音生成和音乐生成，并按 内存占用、运行时成熟度、Apple 兼容性、交互体验 四个维度比较，给出适合 M4 Max 的推荐组合。

说明：文中“性能”优先指 资源级性能，即模型在 64GB 统一内存里的可放置性、是否需要频繁 swap、以及是否适合交互式使用。凡是出现具体时间或显存数字，都明确标注其来源条件；未在本文环境中实测的指标，不伪造本机速度。

核心结论

M4 Max 64GB 可以胜任高质量本地 LLM、图像与轻量音频生成，但视频仍然属于“可试验，不宜作为主力生产”。

01 / Baseline & Constraints

1. 先看机器边界：64GB 统一内存决定了什么能常用，什么只能偶尔跑

Apple Silicon 的优势是统一内存和 Metal 生态，弱点是大量开源生成模型默认以 CUDA 为第一目标。对本次选型，先定义三个判断条件：能否稳定装下、有没有成熟 Apple 运行栈、生成时长是否适合日常交互。其中第一条最重要，因为一旦进入 swap，Mac 的体感会从“可用”直接滑落到“不可持续”。

Criterion 01

内存占用先于峰值质量

64GB 并不意味着可以无成本常驻 70B。LLM 除权重外还要叠加 KV cache、上下文和采样缓冲；扩散模型则要叠加文本编码器、VAE、中间 latent 和 attention 工作区。

Criterion 02

优先选择 Apple 原生或 Metal 一等公民栈

LLM 首选 MLX-LM，其次是 GGUF + Metal 的 llama.cpp；多模态首选 Hugging Face Diffusers 的 MPS 路线。CUDA 专属优化越重，迁移到 Mac 的折损越大。

Criterion 03

把“能跑”与“适合工作”分开

能完成一次生成不等于适合常用。本文把结果分为三档：交互级、批处理级、实验级。交互级适合频繁往返调参；实验级只建议跑样片或验证可行性。

Weight Math

8B 级

4-bit 权重的理论下限约为 8B × 0.5 byte ≈ 4GB。考虑量化元数据、张量布局和运行时开销，日常工作集更接近 5GB 到 7GB。

Weight Math

14B 级

理论权重约 7GB，实际常见工作集更接近 9GB 到 12GB。这个区间是 M4 Max 64GB 最适合的高质量常驻档。

Weight Math

27B - 32B 级

4-bit 理论权重约 13.5GB 到 16GB，实际工作集容易进入 16GB 到 26GB。可以跑，但上下文一长、并发一多，交互感会明显变差。

Weight Math

70B 级

4-bit 理论权重约 35GB，算上缓存后非常容易挤压到系统可用内存边界。对于笔记本形态，不建议作为本地主力。

结论：在 M4 Max 64GB 上，模型选型不该围绕“最大的参数量”，而应围绕“14B 级是否已经满足任务质量”。对多数中文助手、工具调用、知识整理和原型生成场景，答案是肯定的。

02 / LLM & Tool Use

2. LLM 与 Function Calling：Qwen3 和 GLM-4 重新定义了本地选型格局

Apple 自家的 MLX-LM 已经覆盖 Qwen3 全系列[1]。llama.cpp 的 Metal 后端同样成熟[2]。在工具调用层，Ollama 已提供单/并行/agent loop 文档[3]。Qwen3 官方明确推荐 Ollama、LM Studio、MLX 和 llama.cpp 作为本地方式[4]；GLM-4-32B-0414 在 llama.cpp 中已有合并的模型实现[17]；Llama 4 Scout/Maverick 虽然发布了 MoE 架构，但 109B+ 总参对 64GB 笔记本仍然偏重[18]。

Qwen3 在 2025 年 4 月发布，相比 Qwen2.5 有三个关键升级：(1) thinking/non-thinking 混合模式，可按任务复杂度动态切换推理深度；(2) 预训练数据从 18T 扩至 36T tokens，覆盖 119 种语言；(3) 同级别模型质量大幅提升 — Qwen3-4B 匹敌 Qwen2.5-72B，Qwen3-30B-A3B（MoE，3B 激活）超越 QwQ-32B。官方明确推荐 Ollama、LM Studio、MLX 和 llama.cpp 作为本地运行方式[4]。

Gemma 4 是 Google 基于 Gemini 3 技术构建的最新开源模型，26B/31B 两档面向工作站和编码助手。原生支持 function calling、多模态（视觉 + 音频）和 140 语言[5]。在 AIME 2026 上达到 88.3%，τ2-bench agentic tool use 达到 85.5%，已上架 Ollama 和 LM Studio。26B 的内存占用与 Gemma 3 27B 接近但能力有代际提升。

若目标是开发速度，优先 Ollama，因为它已内置单工具、并行工具与 agent loop 样例[3]。若目标是协议控制和 JSON 约束，优先 llama.cpp 的 OpenAI 兼容 server 与 grammar。若目标是 Apple 原生吞吐，则用 MLX-LM 跑模型，把工具协议留给上层服务适配。

03 / Multimodal Matrix

3. 多模态模型对比：图像和音频已经实用，视频仍然明显偏向实验

Hugging Face Diffusers 已经把 Apple Silicon 的 MPS 作为正式优化路径，官方建议在内存紧张时打开 attention slicing，并提醒 batch 生成在 MPS 上可能不稳定[6]。这给图像和部分音频模型提供了可落地路径；但视频模型的主流优化仍围绕 CUDA、TorchAO、FSDP 或多卡展开，Mac 兼容层远不如图像成熟[8][9]。

Image

文生图已经进入“本地实用期”

SDXL 提供最稳兼容性，FLUX.1-schnell 提供更强提示遵循。如果你的目标是稳定工作流，先把 SDXL 跑顺；如果目标是更好的画质与语义对齐，再投入 FLUX 的工程化。

Video

视频生成仍是 Mac 上的高成本试验

Wan2.1 和 CogVideoX 都给了开源入口，但绝大多数速度优化、量化路径和社区经验仍围绕 NVIDIA。Mac 可做 demo，不适合做高频生产。

Audio

语音生成最适合走轻量模型

Kokoro 这类 82M 级模型和 Apple Silicon 的匹配度极高。对日常朗读、播客草稿、角色原型，它的收益远高于部署复杂的大模型 TTS。

04 / Model Engines

4. 模型运行引擎横评：oMLX、vMLX、Ollama、LM Studio、MLX-LM、llama.cpp、Jan 和 GPT4All

"模型"和"跑模型的引擎"是两回事。选平台时，先看它能否在本地完成你的任务，再比较交互方式、API 和模型管理。下表按文字、向量、图像、视频、音频列出八个平台的能力边界；支持某种模型不代表在 M4 Max 64GB 上有相同速度，也不代表所有任务能同时运行。

口径（2026-09-21）：仅计官方本地入口，含可选组件，不计外接云 API。图像 / 视频理解不等于生成；TTS 是语音生成，STT 是转写，均不代表音乐生成。“—”表示本轮官方资料未列该入口，“待核”表示证据不足。oMLX / vMLX 按稳定版 0.6.4 / 1.6.64，其余按当前官方文档，主线工具另行标明[22]。窄屏可横向滚动。

先按需求选：需要在同一平台管理聊天、生图和语音，先评估 vMLX；只需 LLM / API 服务，或已有独立生图工具、愿意分栈维护，再评估 oMLX。oMLX 当前没有已确认的生图入口，选它又要生图，就需要另外的工具。这是工作流建议，不是性能排名。

共同能力与差异：二者均提供文本 / VLM、向量、音频和兼容 API，也都有特定模型的投机解码 / MTP 路径。oMLX 的 Swift / SwiftUI 菜单栏 App 侧重缓存与多模型服务管理；vMLX 的 Electron 桌面端集成图像和模型工具，Gateway 统一路由会话。音频和 DFlash 不是独有卖点，加速也不等于提升模型能力[19][20][21]。

外部实测：没有全面赢家。第三方 OhYesMLX 在 2026-09-16 使用 M2 Max 64GiB、macOS 26.6.2，oMLX 0.6.4 / vMLX 1.6.59，逐行固定相同模型和量化，单并发、temperature 0、seed 0，预热后各测 9 次。以下采用其纠正预热问题后的吞吐表及输入长度测试；解码吞吐越高越好，首 token 延迟（TTFT，中位数）越低越好[24][25]。

边界：表中 TTFT 是模型已预热、未命中前缀缓存的请求，输出上限 64 token，不是加载模型的冷启动。测试关闭 vMLX 的 JIT / native MTP，不是双方最佳调优峰值；作者未公开入库原始逐请求结果。这些 M2 数据不能直接外推到本机 M4 Max、Qwen3-14B 或更新版本。

性能怎样影响选择：长篇输出看解码吞吐，多轮工具调用还要看实际缓存与首 token 延迟。另一组同机 Llama-3.1-8B-oQ4、约 4K 输入的重复请求，在缓存命中时 oMLX 为 0.529 秒、vMLX 为 0.419 秒，也说明缓存体验不是一方必胜[25]。目前没有足够证据给两者的并发、内存或功耗排总名次；不要为一句笼统的“oMLX 更快”放弃自己需要的一体化工作流。

可统一管理的任务：vMLX 通过 mflux 提供 Flux Schnell / Dev、Z-Image Turbo 等图像生成及部分编辑入口，通过 mlx-audio 提供 Kokoro TTS、Whisper STT 等语音任务。CLI 需相应可选依赖，桌面包则以其实际打包版本为准；不应把它概括为视频、音乐在内的“全部模态”平台[20]。

64GB 的边界：先分别验证 LLM、图像和语音任务，再考虑共驻留。模型权重之外还要留出 KV cache、图像中间张量和系统内存；官方 README 对全精度 Qwen Image Edit 给出约 54GB 的估计，这已非常接近本机容量，不能据模型文件大小承诺并发无压力。

与 Diffusers / ComfyUI 的区别：vMLX 减少手工集成，不等于不需要隔离环境或 PyTorch 依赖。mflux 自身已有部分 LoRA、ControlNet 和编辑能力，但上游支持不等于 vMLX 已提供相应 UI / API，也不等于兼容 SDXL 插件或 ComfyUI 节点工作流[23]。

MLX-LM 是底层库：Apple 官方团队维护的 Python 推理和量化框架，提供模型加载、生成、量化、提示缓存及基础 mlx_lm.server。它并非没有 API server，但官方提示该 server 只有基本安全检查，不建议直接用于生产[1]。

oMLX 是基于 mlx-lm 构建的服务化层：它在 mlx-lm 的推理核心之上加入了 continuous batching、block-based 分级 KV cache（RAM 热层 + SSD 冷层）、多模型并存 + LRU 自动管理、macOS 菜单栏原生 App、OpenAI/Anthropic 兼容 API、VLM/embedding/reranker 支持、tool calling 和 MCP 集成[19]。

选择逻辑：脚本推理或模型量化可直接用 MLX-LM；需要常驻 API、多客户端、管理界面和多模型内存调度时，再考虑 oMLX 这样的服务化层。二者不是互斥方案，也不能仅凭包装层名称推断吞吐或稳定性。

需要快速接入 API 和自动化，可先看 Ollama[3]；更重视可视化聊天、参数调节和模型管理，可先看 LM Studio，它也提供 headless 模式 (llmster)[14]。二者均有文字与向量接口，模型和 API 行为仍需分别验证。本轮官方文档未列其本地图像、视频或音频生成入口，不能因为下层引擎有相关工具，就认定桌面产品已经集成。

Jan 的定位是"个人 AI 客户端"，内置 web search、MCP 和多 provider 接入（OpenAI、Claude、Gemini、HuggingFace 等）[15]。如果你想要一个"类 ChatGPT 但完全本地"的体验，不想折腾命令行和 API，Jan 是最好的起点。但如果你要做 agent 或自动化管线，Ollama 和 llama.cpp 的工程控制力更强。

GPT4All 的最大卖点是全离线和 LocalDocs RAG[16]。但它不提供 tool calling API，推理后端不支持 MLX 原生加速，模型更新速度和社区活跃度也落后于 Ollama 和 LM Studio。在 M4 Max 上，它更适合当"不想碰命令行的备用聊天窗口"，不适合当开发栈。

Dev

开发者：oMLX 或 vMLX

需要统一管理聊天、生图与语音，先评估 vMLX；仅需 LLM / API，或愿意另配生图工具，再评估 oMLX。外部实测是部分解码场景 oMLX 领先、部分首 token 场景 vMLX 更快，不能按平台名称判定速度[24][25]。

Power User

高阶用户：vMLX 或 LM Studio

vMLX 桌面端集成聊天、服务、图像和模型工具；LM Studio 提供跨平台界面，并在 Mac 上支持 GGUF + MLX 双后端。按需要的本地任务和客户端接口选择，不以 GUI 功能数量代替实际验收。

Casual

轻度用户：Jan

界面最友好、开箱即用、内置搜索和多 provider。不需要折腾命令行就能用本地模型替代 ChatGPT 和 Perplexity。

05 / Runtime Stacks

5. 推荐运行栈：不要试图用一套框架统一所有任务

本地模型部署应按任务选择运行栈：LLM 可用 oMLX 或 Ollama；图像可用 Diffusers/MPS 或 vMLX 的 mflux 路线；语音可评估 oMLX / vMLX 的音频组件。视频生成和音乐生成仍需单独选型。统一界面或 API 端口可以简化管理，但不代表一个进程覆盖全部模态。

Stack A

MLX-LM

  • 最适合 Apple Silicon 上的 LLM 推理与量化。
  • 官方支持模型转换、量化、长上下文缓存和大模型 wired memory 调优[1]。
  • 适合作为“核心推理引擎”，但工具协议最好交给上层服务处理。
Stack B

llama.cpp / GGUF

  • Metal 是一等公民后端，OpenAI 兼容 server 与 grammar 支持完整[2]。
  • 适合追求模型兼容性、轻量 API 服务、JSON 约束和多模型切换。
  • 如果要跑很多社区量化模型，它往往比 MLX 更省心。
Stack C

Ollama

  • 最适合快速上手 agent loop、并行工具调用和 OpenAI 兼容接入[3]。
  • 适合把本地模型包装成统一 API，不适合承担所有底层优化。
  • 建议把它放在应用层，而不是当作唯一推理栈。
Stack D

Diffusers + MPS 或 vMLX

  • 图像、音频和部分视频任务的主通道。
  • Diffusers + MPS 官方明确支持 Apple Silicon，但需注意 attention slicing、batch 不稳定和大张量限制[6]。适合需要 LoRA、ControlNet 等高级管线的场景。
  • vMLX 的 mflux 路线可减少图像任务的手工集成，但需相应依赖，且不能将其入口与 SDXL / ComfyUI 的插件和节点工作流等同[20][23]。
1

日常助手栈

Qwen3-14B 4-bit + oMLX（常驻 API、多模型管理）或 Ollama（GGUF 生态优先）。先验证普通推理与工具调用，不默认 Qwen3-14B 有可用 DFlash 配对；需要集成图像和语音工作流时，再评估 vMLX。

2

图像创作栈

SDXL 插件与节点工作流 → Diffusers/MPS + ComfyUI；快速插图 → vMLX + Flux Schnell。CLI 路线在受支持的隔离环境中安装 pip install 'vmlx[image]'，先单独验证图像任务，再评估与 LLM 共用内存。

3

音频栈

Kokoro 做常规 TTS，MusicGen 做短音乐草稿，Stable Audio Open 做环境声和音效。F5-TTS 只在确实需要更强表现力时单独启用。

4

视频栈

单独隔离为实验环境。优先尝试 Wan2.1 1.3B 或 CogVideoX-2B，不把它们并入主工作流，也不把视频生成的成功率当作整机 AI 能力的判断依据。

06 / Recommendations

6. 最终建议：先把 Qwen3-14B、SDXL 和 Kokoro 跑顺，再决定是否投入 FLUX 与视频

如果目标是“在 M4 Max 64GB 上建立一套长期可维护的本地 AI 环境”，最优策略不是一次装满所有热门模型，而是分三层推进：先完成主力任务，再扩展高质量图像，最后才评估视频。下面给出三种面向不同目标的组合建议。

Default Build

默认工作组合

  • LLM：Qwen3-14B 4-bit
  • 引擎：oMLX（常驻 API + Homebrew 服务）
  • Function Calling：oMLX 内置 tool calling
  • 文生图：SDXL via Diffusers/MPS
  • 语音：Kokoro
  • 音乐：MusicGen-medium

先跑通文本推理与工具调用，再按需增加图像或音频；保持环境边界，避免一次叠加未经验证的加速与并发配置。

Unified Build

一体化组合（vMLX）

  • LLM：Qwen3-14B 4-bit
  • 引擎：vMLX（桌面管理 + Gateway 路由）
  • 文生图：Flux Schnell 4-bit（mflux 组件）
  • 语音：Kokoro TTS + Whisper STT（音频组件）
  • Function Calling：14 种自动解析器 + 26+ 内置工具

用 vMLX 统一管理已支持的聊天、图像和语音会话；Gateway 可提供统一端口，但后端仍有依赖与内存预算，视频和音乐生成不在这一组合的默认范围内。

Quality Build

质量优先组合

  • LLM：Qwen3-32B 或 GLM-4-32B 离线任务 + Qwen3-14B 常驻
  • 引擎：oMLX（多模型 LRU；加速按模型验证）
  • 文生图：FLUX.1-schnell
  • 语音：F5-TTS
  • 音乐：Stable Audio Open 1.0

适合愿意接受更长生成时间、并愿意为环境隔离投入更多工程成本的用户。

Research Build

研究实验组合

  • 视频：Wan2.1 T2V-1.3B 或 CogVideoX-2B
  • 图像：SDXL 作为对照基线
  • LLM：Gemma 4 26B 或 Qwen3-14B 负责 prompt 扩展

适合验证视频与多模态链路，不适合作为日常生产环境。

A

如果你主要做本地知识助手与 Agent

可从 Qwen3-14B 4-bit + oMLX 的普通推理开始，先验证响应延迟、工具调用与内存占用；不要默认该模型能用 DFlash。需要集成图像和语音操作时，可再比较 vMLX 的桌面工作流。若 function calling 是核心需求，额外测试 GLM-4-32B-0414。

B

如果你主要做图像创作

需要 SDXL 插件与节点编排：先验证 Diffusers/MPS、LoRA、ControlNet 和 ComfyUI。快速插图可试 vMLX + Flux Schnell：在隔离环境中安装 pip install 'vmlx[image]' 后使用 vmlx serve schnell。mflux 的部分高级能力与 vMLX 实际提供的入口应分开确认。

C

如果你想做视频

结论很直接：M4 Max 64GB 可以研究视频生成，但不应该被当作视频生成主机。若视频是高频生产任务，迁移到有大显存 NVIDIA 的桌面机或云端会更合理。
