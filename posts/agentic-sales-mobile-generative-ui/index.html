可行性评估 · 生成式界面与技能治理

让对话界面随技能演进自生：新增实体不再改前端控件代码

评估一个完整方案：当后端同步一张新的 Dataverse 表（例如服务工单）后，会话里的列表卡片与草稿表单能否由元数据在运行时自动生成；并进一步把「技能定义」也放进一张 Dataverse 表，让业务管理员维护与测试，而无需改前端代码。方案覆盖前端渲染、后端流程一致、元数据与技能治理三层。

直接看结论 先看现状盘点
一句话结论

条件可行：把「界面知识」与「技能定义」一并搬出代码——前端只读 Dataverse 元数据与一张技能表来渲染与路由。

关键支点已经具备——Power Apps SDK 运行时即可取到 Dataverse 表的完整元数据（类型、选项集、本地化标签、必填、主名称、图标）。再把技能定义也放进一张自建 Dataverse 表，业务管理员经模型驱动应用维护、前端运行时读取，新增技能无需改代码或发版。

  • 1前端：实体描述符驱动通用列表与表单
  • 2数据：DV 元数据 + 自建技能表双源
  • 3治理：业务管理员经 MDA 维护与测试
  • 4路径：分阶段、行为保持式改造

01 / The Ask and the Bar

把「加功能要改前端」变成「加元数据就够了」

当前应用覆盖客户、联系人、商机、活动四类业务对象。本评估要回答的是：若把覆盖面扩展到一个全新对象，前端要付出多少代价，以及这份代价能否压到趋近于零。本报告把范围扩展为一个完整方案——前端渲染、后端流程一致、技能与元数据的业务侧治理。读完本章，你将拿到一个可验证的成功判据，用来在后续章节逐条对账。

「同步一张服务工单的 Dataverse 表，补上工单相关技能；此后在会话里查询、创建、修改工单时所需的列表与草稿表单，应当自动出现，而不必再改 Copilot 面板的代码。」

01

术语：生成式数据界面

本文定义「生成式数据界面」为：会话内的数据控件由实体的结构化元数据在运行时推导生成，而非为每个实体手写一套组件分支。对应的已有概念是元数据驱动 UI（metadata-driven UI）。

02

范围：会话内的两类控件

主线聚焦两类控件：查询返回的列表卡片，与新建/修改触发的草稿确认表单。实体详情页与导航作为次要项讨论，后端技能的自动注册单列一节。

03

判据：零新增文件、纯元数据驱动

本评估采用最高判据——新增一个实体时，不新增、不修改任何 Copilot 面板/渲染/表单组件代码，控件完全由 Dataverse 元数据加技能描述驱动。后文精确界定该判据在工程上的可达边界。

02 / Verdict First

条件可行，且支点已经在代码里

结论可以一句话给出，再用三条判断展开。决策口径是：该方向值得投入，工程量中等，风险可控；它不是从零造系统，而是把已经「叶子层数据驱动、装配层按实体写死」的现状，改成「装配层也由描述符驱动」。

✓

结论：可行（条件式）

对标准增删改查实体的列表与草稿表单，「零前端控件改动」可达成。代价转移到：运行一次数据源代码生成、撰写一份技能描述——两者都不触碰面板、渲染器、表单组件。

!

判据精确化：零代码 ≠ 零产物

纯靠元数据、不写技能，只能得到统一的「通用样式」界面，足够做最小可用版。要达到与现有四类对象一致的精修体验，界面意图须由技能承载——而技能本就是要新增的产物，不构成额外文件。

◆

关键支点：运行时元数据可用

代码生成出的每个服务都带 getMetadata()，底层调用 Power Apps SDK 的 getEntityMetadata，返回字段类型、选项集、本地化显示名、必填级别、主名称字段、图标与配色——这正是生成式界面所需的全部输入。

⛁

延伸：技能即数据

把技能定义（描述、参数、提示词、启用开关）从代码搬进一张 Dataverse 表，业务管理员经模型驱动应用维护；可执行逻辑仍留代码、由 handlerKey 寻址。标准增删改查指向通用执行器，故新增标准实体可做到零前端代码。

一句话给决策者：投入一次「实体描述符 + 技能表」抽象改造（分阶段、行为保持），换来此后每加一个标准业务对象只需「同步 Dataverse + 配一行技能表」，且技能维护权可下放到业务管理员，前端不再是扩展瓶颈。

03 / The As-Built

今天加一个实体，要改动散落在约 7 处的实体知识

承接上一章的判据，本章定位「为什么现在做不到零改动」。渲染主路径其实已是数据驱动——智能体返回 JSON，渲染器通用解析。但每类实体的展示规则、字段标签、表单字段、导航目标，仍以 switch/if 形式写死。下表逐处列出这些耦合点，作为改造的拆除清单。

位置 写死了什么 加工单要改
copilot-agent.ts buildRecordList 按函数名 switch，逐类映射 title / subtitle / meta 新增一个 else-if 分支
dynamic-data-renderer.tsx 固定 EntityType 联合类型 + 图标/标签/列序/类型嗅探/导航/格式化/徽章配色 改 7 处常量与分支
form-card.tsx 固定 type 联合类型；约 8 段按实体的字段布局与保存；静态建档 Hook 加字段布局 + 建档 Hook + 图标分支

function-executor.ts 函数名到处理器的分派 + handlers 实现 新增分派项与 handler

读法：前五行是「应被拆除」的硬编码耦合，把界面知识锁在组件里。第六行（代码生成）与第七行的技能文件是「应保留」的声明式产物，本就随新实体一起产出。改造目标是把前五行的知识全部上移到这两类产物可表达的描述符里。

04 / Target Architecture

实体描述符注册表：元数据与技能的合并产物

拆除散落的开关后，需要一个统一的事实来源补位。本章给出目标形态：一个运行时解析器，把 Dataverse 元数据（机器可读、只懂类型不懂意图）与技能里的界面清单（人写的、表达展示意图）合并成一个实体描述符，供所有通用控件消费。先看四个责任层，再看描述符装什么。

数据/元数据层

Dataverse 元数据（机器可读事实）

经 service.getMetadata() 取回字段类型码、选项集、本地化标签、必填级别、主名称字段、配色与图标。提供「类型与合法值」，但不含「该不该在列表里露出」这类意图。

generated/services/*Service.ts · @microsoft/power-apps/data/metadata/dataverse

技能/意图层

技能里的界面清单（人写的意图）

技能描述补足元数据表达不了的部分：列表列与顺序、表单字段与分组、主/次显示字段、导航目标、模糊匹配键、写库前是否需草稿确认。意图寄存于本就要新增的技能，不构成额外文件。

copilot-studio/skills/*.SKILL.md · function-registry FunctionDefinition

描述符层

resolveEntityDescriptor 合并解析

一个解析器把两源合并为单一实体描述符：字段集合（类型、标签、必填、选项、格式化器）+ 展示规则（列表列、表单分组、主次字段、图标、导航）。带缓存，作为通用控件唯一消费的事实来源。

lib/entity-descriptor.ts（新增的唯一基础设施）

渲染层

通用列表卡片 + 通用草稿表单

GenericRecordList 取代渲染器的实体分支，GenericFormCard 取代表单的 8 段布局；二者只读描述符，不认识具体实体。已有的 EditableField 已是按类型渲染的通用字段组件，直接复用。

components/dynamic-data-renderer.tsx · components/form-card.tsx（改为描述符驱动）

为何两源合并而非纯元数据：元数据知道「金额是 Money 类型、阶段有 6 个选项」，但不知道「列表先露金额还是阶段、详情跳哪页」。这类展示意图属于产品决策，交给人写的技能最自然也最稳定，不会因某张表多一个内部字段就漂移。

▤

详情页：通用回退 + 按需精修

同一描述符可驱动一个只读通用详情页（字段分组 + 关联记录），新实体开箱即有详情视图；现有精修页作为按需覆盖保留。完全泛化的富详情页可达但收益递减，建议先通用回退、后按价值升级。

⚙

后端技能：模板化自动注册

前端 availableFunctions 可由描述符在构建期自动生成（query / draft / create / fuzzyMatch 四件套）。后端 Copilot Studio 是 design-as-code：参数化的通用增删改查技能模板加表名即可派生。两个「大脑」需各自知道新实体，自动注册要同时覆盖前端注册表与后端技能。

05 / Skills as Data

把技能定义从代码搬进一张 Dataverse 表

上一章把「界面意图」寄存在技能里。本章再进一步：把技能本身也变成 Dataverse 数据——一张自建技能表，业务管理员在模型驱动应用里维护，前端运行时读取。如此新增或调整一个技能不再需要改前端代码或发版。前提是先分清「契约」与「逻辑」：能进表的是声明式契约，不能进表的是可执行逻辑。

▤

声明式契约 → 进表

LLM 看到的、以及路由要用的部分：名称、双语显示名、description（路由信号）、参数 schema、必填、promptTemplate、responseFormat、示例触发语、技能边界、启用开关。全部可数据化，是业务侧能安全维护的部分。

⚙

可执行逻辑 → 留代码

调哪个服务、字段映射、业务规则、多步编排——不可能把可执行代码塞进表里安全运行。表里只放一个 handlerKey 指向代码侧 handler：标准增删改查指向通用执行器（零新增代码），特殊逻辑指向具名 handler。与现有「按函数名分派」执行器顺势对接。

字段 含义 归属
name · displayName_zh/en 技能唯一名与双语显示名 契约（表）
description 给 Frame/Orchestrator 的路由信号，最关键的一段 契约（表）
operation · targetTable 操作类型与目标 Dataverse 表 契约（表）
handlerKey 寻址代码侧 handler；标准 CRUD 指向通用执行器 契约引用代码
paramsJson · outputSchemaJson 参数 schema 与输出契约（加载时 Zod 校验） 契约（表）
promptTemplate · examples · boundaries LLM 提示词模板、示例触发语、技能边界 契约（表）
enabled · sort · version 启用开关、排序、版本，便于灰度与回滚 契约（表）

可选子表 crf5c_skillparameter：若想让管理员逐字段配参数而非直接编辑 JSON，体验更好、更防错。表名沿用 crf5c 发布者前缀，与现有自定义业务表一致。

运行时加载器取代写死的 availableFunctions 数组

前端启动时读技能表 → 每行用 Zod 校验 → 通过的进注册表喂给 Frame/Orchestrator → 坏行跳过并告警，绝不因一行错配置拖垮整个智能体 → 带缓存，管理员改了即失效重拉。这把第三章「手写 function-registry」那处耦合也一并拆除。

三层安全护栏（缺一不可）：① 表级 RBAC，只有管理员能编辑技能行并开启审计；② 执行器只认白名单，handlerKey 与 targetTable 必须在代码侧白名单内，绝不允许一行配置就调任意 handler 或碰不该碰的表；③ 平台数据裁剪兜底，Dataverse 安全角色 + owner 过滤照旧生效，哪怕配错技能也越不过用户本身的数据权限。

06 / Maintenance, Testing and the Two Brains

让业务侧维护技能，并把后端对齐

技能进表之后，维护权可以下放到业务管理员。本章给出维护与测试的落点，以及如何处理「前端流水线」与「后端 Copilot Studio」两个大脑的一致性，并界定与官方 Business skill 的关系。

✎

模型驱动应用维护

对技能表建一个模型驱动应用（MDA），管理员增删改行即可；RBAC 控制谁能编辑；表是 solution-aware 的，可随解决方案跨 dev/test/prod 搬运并版本化。这正是把「写技能」从开发者工作流移到业务工作流的落点。

▷

两档测试：轻量先行，端到端后补

轻量档（先做）：MDA 内嵌测试页输入一句话，调用已有 Power Automate Flow / AI Builder prompt 做一次 Frame 分类，回显「命中哪个技能、抽出什么参数」，不写库。端到端档（后做）：嵌入式 canvas/PCF 真正跑 draft→确认→落库，价值高但成本高，建议二期。

⇄

两个大脑要对齐

前端 Frame/Orchestrator 与后端 Copilot Studio agent 是两套技能来源。把技能表作为单一事实源，由它派生后端 Copilot Studio 技能（design-as-code），避免两侧各配一套、长期分叉。派生可放在构建期。

◈

与官方 Business skill 的关系

官方 Dataverse Business skills（Preview）是给运行时 agent 的自然语言流程定义，治理好但纯散文、不携带类型化契约、且尚未正式发布。本方案的自建表当下可生产、可控；将来其正式发布时，可把 description/promptTemplate 这类散文映射过去，二者并不冲突。

一句话定位：自建技能表是「技能意图」这一源的 Dataverse 实体化，让标准实体做到「同步 DV + 配表 = 零前端改动」；可执行逻辑仍由具名 handler 承载；安全靠 RBAC + 执行器白名单 + 平台数据裁剪三层兜底。

08 / Phased Rollout

分阶段、行为保持，工单作为验收试点

可行不等于一次性重写。本章把完整方案拆成若干「行为保持」的阶段——上线体验不变，只把知识从代码逐步搬进描述符与技能表。前几阶段用现有四类对象自证抽象够用，再接通运行时元数据与技能即数据，最后补 MDA 维护并以工单作为「零改动新增」的验收试点。

阶段 0 — 抽取描述符（行为保持）

把现有四类对象隐含的展示规则显式化为 EntityDescriptor 数据对象，组件暂照旧但改读描述符。零界面变化，验证描述符 schema 足以覆盖现状——整条路线的去风险起点。

阶段 1 — 列表走描述符

buildRecordList 与列表渲染改由描述符驱动，删除按函数名 switch 与 detectEntityType 嗅探，载荷显式带实体标签。列表行为不变，实体分支清零。

阶段 2 — 表单走描述符

form-card 的 8 段字段布局改为按描述符装配；静态建档 Hook 改为经服务注册表通用建档。复用 EditableField，草稿确认与保存语义保持。

阶段 3 — 技能即数据 + 运行时加载器

建 crf5c_skill 表；前端用运行时加载器读表、逐行 Zod 校验、带缓存，取代写死的 availableFunctions；handlerKey 接通用 CRUD 执行器。此后新增标准技能 = 配一行表，无需改前端。

阶段 4 — 元数据注水 + 后端对齐 + 通用详情页

描述符的字段类型、选项、标签、必填改由 getEntityMetadata 运行时注水；由技能表派生后端 Copilot Studio 技能，消除两脑分叉；补一个描述符驱动的只读通用详情页作为回退。

阶段 5 — MDA 维护与测试 + 工单验收

建技能表的模型驱动应用与轻量测试页（Frame dry-run）；以工单为试点，全程不改面板/渲染/表单，验证「同步 DV + 配表」即可上线，且维护权可下放给业务管理员。

09 / Risks and Residual Manual Work

工程附录：哪些地方仍需人，哪些地方会咬人

决策结论已在第二章给出，本章供工程评估：把「零改动」的边界说清，把可预见风险逐条标注，避免把条件可行误读为无条件可行。

01

代码生成是构建动作

新表需跑一次数据源代码生成（本项目用 npx power-apps，因 pac code add-data-source 对 Dataverse 失效）。不是手写文件，但是一步人工触发的构建。

02

界面意图需写进技能

列表列序、主次字段、导航目标、模糊匹配键属于产品决策，元数据给不出。寄存在本就要写的技能里，是声明式数据而非组件代码——这是「零新增文件」成立的精确含义。

03

富详情页与特殊校验

通用详情页开箱即用，但现有精修页与跨实体工作流仍需按需写代码；超出 Dataverse 必填级别的业务校验也需手写。这些是按价值的可选投入，不在「零改动」承诺内。

04

两个大脑要同步

前端函数注册表与后端 Copilot Studio 智能体是两套技能来源，新实体须让两者都知道。自动注册要覆盖两侧，否则出现「前端能渲染、后端不会路由」的错位。

风险 影响 缓解
类型安全弱化 从编译期联合类型转向运行期描述符，丢失部分静态检查 代码生成带类型描述符 + Zod 运行时校验补回
元数据获取延迟 运行时拉元数据可能拖慢首屏 按表缓存 + 构建期预取，元数据变更少可长缓存
多态/查找字段 活动族本就多态，工单查找字段也需解析目标实体 复用现有模糊匹配级联，描述符显式声明查找目标表
选项集本地化缺口 若某选项缺中文标签，下拉露出英文或键名 回退 UserLocalizedLabel，校验里标注缺口
函数调用准确率 自动生成的函数描述过泛，LLM 选错技能 技能里保留人写的一句话用途，喂给 Frame/Orchestrator
技能表配置错误 一行配错 description / 参数导致路由错乱 加载即 Zod 校验、坏行跳过并告警；MDA 测试页先验证再启用
技能表权限滥用 管理员误改技能行改变智能体行为 表级 RBAC 限管理员 + 审计；执行器白名单兜底；平台数据裁剪保证越不过用户权限

阶段 0 正是为这些风险兜底：不改变上线体验，先用现有四类对象把描述符 schema、缓存、校验、类型生成跑通，确认无回归，再接新实体。任一风险在阶段 0 暴露，都还来得及调 schema 而不影响用户。
