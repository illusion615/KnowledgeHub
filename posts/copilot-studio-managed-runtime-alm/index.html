01 / Managed Runtime Evolution

1. 托管运行时定位、产品演进与宿主边界

2026 年秋季起，打开门户首页顶部的 New experience 开关后，构建能力从传统的智能体、工作流与智能体流三类资产，正式扩展为包含全栈微应用（Apps）的四元矩阵 [1]。这一演进的核心底座是 Copilot Managed Runtime（托管运行时），它为自然语言生成或代码优先构建的交互式前端应用提供零基础设施运维的托管执行环境、平台内置版本仓库以及受控的数据连接代理 [1][2]。

01

原生代码仓与声明式配置驱动

每个托管应用默认关联一个平台托管的代码仓库（repoType: native），通过根目录下的 ms.config.json 声明连接引用、环境变量及共享连接策略，不再把前端源码塞入数据库解决方案二进制包 [2][5]。

02

初始无数据库的轻量个人沙盒

为降低试验门槛，系统为每位创作者自动分配的个人环境初始不包含底层关系型数据库，且在此纯托管应用状态下不受休眠自动清理策略影响 [2][3]。

03

严格沙盒化与高管级连接护栏

应用运行在 managedapps.cloud.microsoft 独立域名下，强制执行内容安全策略（禁止内联脚本与外部嵌套），默认环境组仅放行 19 个官方身份认证连接器并拦截任意外部接口请求 [3]。

在实际工程选型中，许多架构师容易将 Copilot Studio 中的托管运行时应用、基于新版编排框架的智能体以及传统画布或代码应用混为一谈 [1][7]。下表从物理宿主、构建期计费、运行期计量及源码持久化方式四个维度厘清三者的边界：

对比维度 Copilot Studio 托管应用 Copilot Studio 新版智能体 传统画布与模型驱动应用
核心产物与入口 首页开启新版体验后的 Apps 磁贴、协同画布或 ms 命令行 [1][5] 首页 Agents / Workflows 入口或 msagent 命令行 [1][6] 创作者门户画布应用、模型驱动应用与解决方案页 [4]

\text{Credits}_{\text{CMR-Run}} = N_{\text{API}} \times 0.1, \qquad \text{Credits}_{\text{Reasoning}} = \frac{T_{\text{input-uncached}} + T_{\text{cache-write}} + T_{\text{output}}}{1000} \times 10
构建期与运行期的计费池解耦 创作者在构建托管应用时，自然语言生成界面的对话消耗记入 Copilot Studio 环境的计费账单；而应用发布上线后，终端用户触发的连接器与数据读写则按托管运行时接口调用（每次 0.1 额度）独立计量 [1][2]。

02 / The Dual-Environment Illusion

2. 为什么创建后总落入个人环境，界面却显示在所选环境中

企业团队反馈最多的痛点是：开发人员在门户右上角的环境选择器里明确切换到了共享开发环境（例如 Team-Dev），随后点击创建应用或智能体，结果管理员在 Team-Dev 的解决方案里找不到该资产，或者发现它被静默写入了创作者的个人环境 [2][4]。这种“所见非所得”的双环境错觉，本质上是界面会话上下文、构建期地理令牌解析与强制环境路由规则三层控制面各自独立决策造成的 [2][3]。

表象层：门户顶栏环境选择器

仅约束当前会话列表与构建计费池

顶栏显示的 Team-Dev 仅用于过滤当前页面展示的智能体与工作流列表，并决定自然语言构建对话从哪个环境的计费池扣减额度；它对托管应用的物理落盘位置没有任何约束力 [1][2]。

控制层：托管运行时强制个人环境路由

租户级常开且默认忽略顶栏选择器

托管运行时的环境路由在所有租户中强制开启且无法关闭。只要通过界面磁贴、协同画布或不带环境参数的命令行创建应用，系统一律忽略顶栏选择器，强制将应用写入创作者的个人环境 [2][3]。

除了物理环境落盘的脱钩，构建期的数据驻留区域也会制造第二重错觉 [2]。即使顶栏选中的 Team-Dev 位于欧洲区，托管应用在自然语言构建阶段的会话数据驻留地也不由该环境决定，而是由创作者登录令牌（Entra ID Token）按以下三级优先级实时解析 [2]：

  1. 解析登录令牌首选数据位置 (PDL)

    系统首先读取创作者身份令牌中的 PDL 属性，将其映射为构建期对话与生成服务的物理区域，完全忽略顶栏所选环境的区域设置 [2]。

  2. 回退两字母国家代码与租户默认区

    若令牌未配置 PDL，则依次读取令牌中的两字母国家代码（c 声明）及租户主区域，若命中暂不支持托管运行时的区域则拒绝创建 [2]。

  3. 按序匹配托管运行时环境路由规则

    系统在 Microsoft 365 管理中心的路由表中自上而下匹配安全组规则；若无自定义规则，系统自动创建一条针对全员（Everyone）的兜底规则并指向默认环境组 [2][3]。

  4. 分配个人托管环境与平台代码仓库

    命中规则后自动创建或复用创作者专属个人环境（类型标记为托管环境），并在后台初始化平台托管代码仓库承载应用文件 [2][5]。

更隐蔽的治理陷阱发生在管理视图分裂与休眠清理连锁反应上 [2][3][4]。下面通过三组折叠抽屉拆解为什么管理员与创作者看到的资产状态经常对不上：

托管运行时应用与传统画布应用分属不同的资源提供方 [2][3]。应用创建后最长需要 15 分钟同步至 Microsoft 365 管理中心（MAC） 的 Apps -> All apps 页面；而在 Power Platform 管理中心（PPAC） 中，它根本不会出现在传统的 Power Apps 应用列表里，管理员必须进入 Manage -> Inventory 并将资产类型筛选为 Copilot Managed Runtime 才能检索到 [2][3]。终端用户的统一运行入口则是独立的 https://managedapps.cloud.microsoft 门户 [3]。

单独使用托管运行时创建应用时，系统分配的个人环境不包含关系型数据库（Dataverse），官方文档明确说明此类纯托管环境不会因休眠而被自动清理 [2][3]。然而，一旦管理员在 PPAC 中为 Copilot Studio 开启了产品级环境路由，或者创作者在顶栏停留在个人环境时顺手创建了一个智能体（Agent），系统就会自动为该个人环境注入数据库实例 [4]。数据库一旦挂载，整个个人环境（含其中的托管应用）立即被纳入开发者环境的休眠回收轨道：连续 60 天无活动即禁用环境，再过 15 天彻底删除全部资产 [4]。

当租户内第一位创作者构建托管应用时，平台会自动生成一条覆盖全员（Everyone）的默认路由规则 [2][3]。如果管理员随后在 Microsoft 365 管理中心新增了按安全组划分的路由规则，却删掉了末尾的 Everyone 兜底规则，那么任何不属于这些安全组的创作者在点击创建或运行 ms app create 时，都会因为无法命中路由条目而被直接拦截报错 [2][3]。

04 / Enterprise ALM Playbook

4. 打破个人环境孤岛：双轨企业级 ALM 全链路实战

要把落入个人环境的原型资产安全晋升至团队开发（Dev）、测试（Test）与生产（Prod）环境，首先必须区分资产属于代码级托管应用还是声明式新版智能体 [5][6]。微软为这两类构建物分别提供了 @microsoft/cmr-cli（命令名为 ms）与 Microsoft.Agents.Hosting.Cli（命令名为 msagent）两套专用工具链 [5][6]。

对于已经在个人环境中通过自然语言生成的应用，核心脱困思路是：将源码从个人环境的平台代码仓克隆到本地或企业代码仓，然后在目标团队环境中显式传入 --environment-id 参数注册应用，并通过阶段配置文件（Stage Overlays）解耦跨环境连接与数据库表 [5]。

  1. 克隆个人环境源码或直连企业代码仓

    运行 ms app clone --app <app-id> 将个人环境中的原型源码拉取至本地，或在创建时直接传入 --repo <github-url> 与 --environment-id <dev-env-id> 跳过个人环境 [5]。

  2. 编写多环境阶段覆盖配置 (ms.<stage>.config.json)

    保持基础 ms.config.json 稳定，新建 ms.test.config.json 与 ms.prod.config.json 覆盖目标环境的连接标识、环境变量与表名；数组按名称合并，设 "$remove": true 可剔除开发期调试项 [5]。

  3. 为共享连接配置动作白名单 (allowedActions)

    若使用管理员预建的共享连接（sharedConnectionId），必须在配置中显式绑定安全策略与动作白名单（如只读查询），否则服务端会在部署时拒绝执行该连接 [3][5]。

  4. 在无数据库托管环境通过平台接口授权服务主体

    不含数据库的托管环境无法通过传统数据库用户表赋权，需调用业务应用平台接口（BAP API）将企业应用对象标识（Enterprise App Object ID）授予环境管理员角色 [5]。

  5. 开启外部制品开关并执行自动化打包发布

    在目标测试与生产环境开启 AllowExternalArtifactDeployment 治理开关，随后由流水线执行 ms app pack 与 ms app deploy 完成零停机交付 [3][5]。

下面给出生产级 ms.config.json 与阶段覆盖文件 ms.prod.config.json 的配置范式，展示如何安全解耦个人连接（User Connection）、共享连接（Shared Connection）与数据库表引用 [5]：

针对运行在新版编排框架（Microsoft Copilot Harness）上的智能体，自 2026 年 10 月起可直接使用基于 .NET 10 的 Microsoft.Agents.Hosting.Cli（msagent）将云端智能体克隆为本地声明式文件（含 settings.mcs.yml、工作流定义、知识源及评测集），实现代码级多环境发布 [6]：

# 1. 从源环境克隆智能体定义至本地工程（切勿把 .mcs/ 与 .config/agent.config.json 提交到 Git）
msagent agent create --agent-type MCSAgent \
  --mcs-clone-agent-id 8a2f0000-1111-2222-3333-444455556666 \
  --mcs-clone-environment-id <source-env-id> \
  --project ./EnterpriseSupportAgent

# 2. 显式注册测试与生产部署目标槽位（仅切换 msagent env select 不会改变已有智能体的绑定环境）
msagent deployment create --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name test-slot --deployment-type test --environment-id <test-env-id>
msagent deployment create --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name prod-slot --deployment-type prod --environment-id <prod-env-id>

# 3. 推送草稿至测试槽位、换绑目标环境连接并执行云端评测门禁
msagent agent deploy --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name test-slot
msagent deployment connection update --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name test-slot --connection-reference shared_sales_crm --connection-id <test-conn-id> --non-interactive
msagent agent eval run --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name test-slot

# 4. 评测通过后一键推送并正式发布至生产环境槽位
msagent agent deploy --project ./EnterpriseSupportAgent --agent-name "Support Agent" --deployment-name prod-slot --publish

若团队沿用经典的 Power Platform Pipelines 或解决方案打包流程，则必须遵循自定义非托管解决方案（Unmanaged Solution）边界 [4][8]。下表汇总了工程团队在跨环境迁移与日常治理中最常踩中的六个真实故障点及修复动作：

高频踩坑场景 根因剖析 权威修复与规避动作
运行 msagent env select 后执行部署，智能体依然发回了旧环境 .mcs/conn.json 在克隆或创建时已静态锁定源环境标识，env select 仅影响新建命令 [6] 必须使用 msagent deployment create --environment-id <target> 显式注册目标环境槽位并按槽位名部署 [6]
为无数据库托管环境配置流水线服务主体时返回权限拒绝 传入了应用注册（App Registration）的客户端或对象标识，而非租户内的服务主体对象标识 [5] 在 Entra ID 的“企业应用（Enterprise Applications）”叶片复制对象标识，调用 BAP 接口赋权 [5]
流水线执行 ms app deploy 报外部制品禁止部署错误 目标环境默认关闭了外部构建包直传开关，仅允许从绑定的平台代码仓构建 [3][5] 管理员在目标环境配置中将 AllowExternalArtifactDeployment 设为 true 后重新触发流水线 [3][5]
员工离职后，团队无法拉取或更新其个人环境中的托管应用源码 平台托管代码仓（repoType: native）的读写权限严格绑定应用所有者列表 [3][5] 管理员执行 ms admin add owner new@contoso.com --app <id> 移交所有权并移除离职人员 [3][5]
导出包含智能体的解决方案到测试环境后，子组件或知识源丢失 直接在默认解决方案（Default Solution）散装修改，导出时未执行“添加必需对象” [4][8] 始终在自定义非托管解决方案中构建，导出前右键智能体执行 Add required objects [4][8]
开启单智能体月度额度上限后，关联的智能体流仍在后台持续扣费 单智能体配额仅阻断智能体主对话（满 125% 立即中断进行中会话），不拦截智能体流 [1][4] 为智能体流单独规划环境级容量池，并在 Microsoft Purview（审计记录类型 519）配置用量告警 [1][3]
企业级身份与审计底线 所有新建智能体均在全局蓝图（25664c89-cea5-4ab6-b924-a54fd8a19ae0）下强制自动分配独立的 Microsoft Entra Agent ID 且不支持环境级关闭；同时托管运行时的应用生命周期事件统一写入 Microsoft Purview 审计日志（RecordType = 519），架构师应将这两项标识纳入生产上线前的安全门禁核验清单 [3][4]。
